# HBOS 入库拍照识别服务

入库时对产品标签拍照，自动识别**产品名称 / 物料代码 / 批号 / 生产日期 / 有效期至**，
识别结果经**人工校对**后写入台账。

完整方案见 [`docs/milestones/M3_R6_入库拍照识别服务方案.md`](../../docs/milestones/M3_R6_入库拍照识别服务方案.md)。

## 两条硬边界（Owner 已定）

1. **照片不出内网。** 本服务**不开任何外网访问**，不调用任何云端 API。
2. **人工校对是强制的。** 识别结果**不直接入账**，必须经操作人确认。

## 架构位置

遵项目规范 `docs/team/05_开源代码二次开发与升级规范.md` 的**优先级 5：外部服务**——
独立服务、HTTP 交互、**不修改 Frappe 核心源码、不直连数据库**。

```
┌──────────────────────┐   HTTP (JSON)   ┌──────────────────────────┐
│  hb_inventory_app     │ ───────────────→ │  本服务（FastAPI）         │
│  (Frappe 容器)         │ ←─────────────── │  原生跑在宿主机上           │
└──────────────────────┘   结构化 JSON     └──────────────────────────┘
```

**为什么原生跑在宿主机、不塞进 Frappe 容器**：承载机是 Apple M4，MLX 能吃满
Metal；而容器是 Linux arm64，**拿不到 Metal**，模型只能跑 CPU。另，ML 依赖重，
塞进 backend 会拖慢 Frappe。

### 容器访问宿主机（已实测通过）

需两件事：

1. 本服务监听 `0.0.0.0`（或宿主机在 Docker 网络中的地址），而非仅 `127.0.0.1`；
2. Frappe 侧请求 `http://host.docker.internal:8100`。

M3-R6 已实测：容器内 `GET http://host.docker.internal:8100/health` 返回 200。

### 网络与安全

> ⚠ **监听 `0.0.0.0` 意味着同局域网内其他机器也能访问 8100 端口。**
>
> - 仅作本地验证时，风险窗口小（用完即停）；
> - **正式部署时应缩小暴露面**：改为只绑 Docker 网关地址，或在宿主机防火墙
>   限制 8100 仅允许本机 / Docker 网段访问。

服务本身**不主动发起任何外网请求**——照片不出内网这条边界由它保证。

## 快速开始

```bash
cd services/hbos_ocr

# 1) 建虚拟环境并安装 Web 骨架（**不含 ML 依赖**，几十秒即可）
uv venv && source .venv/bin/activate
uv pip install -r requirements.txt

# 2) 冒烟测试（stub 后端，不读图像，验证整条链路）
python tests/test_validate.py            # 约束校验层单测
python tests/test_c2_extract.py          # C2 抽取规则单测（不依赖 OCR）
python scripts/smoke_test.py             # 端到端链路（进程内，不启服务器）

# 3) 冒烟：只给自己看，绑本机就够
HBOS_OCR_BACKEND=stub uvicorn app.main:app --host 127.0.0.1 --port 8100

# 4) 真识别：先装后端（C2 更轻，建议先试它）
uv pip install paddleocr paddlepaddle

# 5) **要让 Frappe 页面用得上，必须绑 0.0.0.0**（容器走 host.docker.internal 进来，
#    只绑 127.0.0.1 容器连不上，页面会显示"识别服务不可用"）
HBOS_OCR_BACKEND=c2_ocr uv run uvicorn app.main:app --host 0.0.0.0 --port 8100

# 6) 拿真实样本测准确率（样本与结果都在仓库外）
python scripts/compare_accuracy.py --samples-dir ~/Documents/M3R6样本 --backend c2_ocr
```

> **PaddleOCR 版本**：本服务按 **3.x** 编写（实测 3.7.0 + PaddlePaddle 3.3.1）。
> 3.x 与 2.x 的 API 不兼容，`c2_ocr.py` 里已注明差异。
>
> **环境陷阱**：若启动服务时的**当前目录**里有个叫 `cv2.py` 的文件，它会把真正的
> OpenCV 顶掉，报 `AttributeError: module 'cv2' has no attribute 'IMREAD_COLOR'`。
> 从 `services/hbos_ocr` 启动不会有这个问题。

## 识别后端（可插拔）

服务不绑定某个模型。`POST /api/v1/recognize` 的后端可用 `backend` 参数切换：

| 后端 | 依赖 | 状态 | 用途 |
| --- | --- | --- | --- |
| `stub` | 无 | ✅ 可用 | **链路冒烟测试**——不读图像，返回值由 hints/默认值构造 |
| `c1_local_vlm` | `pip install mlx-vlm` | 需安装 | 本地量化视觉语言模型（MLX / Metal） |
| `c2_ocr` | `pip install paddleocr paddlepaddle` | ✅ 已装 | 本地 OCR + 结构化规则 |

**未安装的重型依赖不会让服务崩掉**——该后端在 `/health` 里标记为不可用，其余照常。

### C2 的模型档位（换档不用装依赖）

PaddleOCR 自带多档模型，`C2` 支持在**后端名后加档位**切换：

```bash
HBOS_OCR_BACKEND=c2_ocr         # 默认，等价于 c2_ocr:small
HBOS_OCR_BACKEND=c2_ocr:medium  # 更准但慢（35 s）
HBOS_OCR_BACKEND=c2_ocr:tiny    # 最快但掉太多
```

也可以只对**单次请求**切档（服务不用重启）：

```bash
# 请求里 backend 传 c2_ocr:tiny
```

或用环境变量固定默认档：`HBOS_OCR_C2_MODEL=small`。

档位只是模型名不同，**依赖完全一样**。实测（50 张真实标签、这台 M4）：

| 档位 | 单张耗时 | 品名 | 代码 | 批号 | 生产日期 | 有效期 | 全字段 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `medium` | 35 s | 92% | 98% | 100% | 94% | 96% | 84% |
| **`small`**（默认） | **8 s** | 90% | 98% | 100% | **94%** | 90% | 80% |
| `tiny` | 3 s | 88% | 94% | 96% | 84% | 80% | 72% |

选 `small` 是因为**它是唯一同时满足耗时标准（≤10 s）与准确率的档位**；
`tiny` 更快但有效期掉到 80%，不值得。

> 准确率一定要用**真实样本**量过再选，别凭直觉。轻量档更容易漏读**小字**——
> 实测 `small` 会把「2026年9月7日」只读成「2026年09月」，**把日整个漏掉**。

### 为什么要有 stub

M3-R6 方案第九节确认：**真实标签样本只能去仓库实地获取**。因此把工作分成两段：

| 工作 | 需要真实样本 |
| --- | --- |
| 服务骨架、校验层、Frappe 侧上传与校对界面、链路冒烟 | **不需要** |
| 测准确率、定 C1/C2 选型 | **必须** |

`stub` 后端让前半段**现在就能完整跑通**，不必等样本。

## 约束校验层（`app/validate.py`）

这是准确率的放大器。无论走 C1 还是 C2，识别结果都过这一层。

**核心**：物料代码是 **8 位、全数字**（Owner 确认）。OCR 最常见的错误是把数字
认成形近字母，因此可以**无条件把字母映射回形近数字**——

```
1300O215  →  13000215      l3000215  →  13000215
130002l5  →  13000215      13OOO215  →  13000215
```

**不需要知道"合法代码有哪些"**，纯字符映射即可纠错，不依赖任何主数据。

另含：批号三类结构提示、日期多格式解析、有效期早于生产日期的异常检测。

### 只到月的日期（实测约占三分之二）

真实标签上，**有效期常常只印到月**（如「2028年11月」），日根本没印——
实测 50 张里有 39 张的效期属于这种情况。这多是印刷惯例，但也可能是模型漏读了日。

ERPNext 的 `Batch.expiry_date` 是 Date 字段，存不下"只有年月"，所以校验层把它
**补成当月最后一天**，并在 `hints` 里明说一句：

```
识别只读到了年月（2028年11月），已按**月末**推定日；若标签上其实印了日，请按标签填写
```

取月末而不是月初，是为了不把效期提前一个月——否则还能用的批次会被预警先拦下。

> **措辞很重要**：说的是「**识别只读到**年月」，不是「**标签只印**到月」。
> 我们只知道模型读到了什么，不知道标签上印了什么——实测有标签印的是
> 「2026年9月7日」而模型只读出「2026年09月」，此时说"标签只印到月"就是
> **对着人撒谎**，会让人以为标签上真没有日。

> **Owner 已确认（2026-09-16）：按月末推定。**
> 并明确**不加「粒度」字段**：系统里存的就是月末那一天，与标签原印粒度不再区分。
> 因此打印件（待检证 / 货位卡）上会呈现 `2028-06-30` 这样的具体日，
> 而标签只印到月——**这是已知取舍，已记录在案**。
>
> 若要改口径，改 `app/validate.py::_month_end` 一处即可。

> 设计原则：**模型负责"读"，规则负责"筛"，人负责"定"。**
> 批号只提示不阻断——仓库不负责批号管理，批号由车间给出（M3-R0 确认）。

## 手动使用（仓库现场怎么操作）

### 一、启动识别服务（在跑 Frappe 的那台 Mac 上）

```bash
cd services/hbos_ocr
HBOS_OCR_BACKEND=c2_ocr uv run uvicorn app.main:app --host 0.0.0.0 --port 8100
```

**必须绑 `0.0.0.0`**，否则 Frappe 容器连不上（容器走 `host.docker.internal`），
页面会显示「识别服务当前不可用」。验证连通：

```bash
docker exec hbos-m0-r3a-backend-1 curl -s http://host.docker.internal:8100/health
```

### 二、在页面上操作

1. 浏览器打开 Frappe：`http://<这台Mac的地址>:8080`
2. 进「**仓储库存工作台**」→ 侧边栏点「**入库拍照识别**」
3. 四步：
   - **① 标签照片**：点「选择 / 拍摄照片」（手机浏览器会直接调相机）
   - **② 识别**：选「来源类型」→ 点「开始识别」（单张约 8 秒）
   - **③ 人工校对**：**橙色高亮的是需要核对的字段**，逐个对照实物标签改对
   - **④ 生成草稿**：选货位、填数量 → 点「生成草稿（不直接入账）」
4. 生成的是一张**草稿库存单**，点「打开草稿」在标准表单里复核，**确认无误后自行提交**

> **识别结果不直接入账。** 这是硬规则——AI 只负责"读"，人负责"定"。

### 三、提交后去哪取货位卡和待检证

**入库单提交时，系统会自动生成该批次的一套文件**（不区分是不是拍照识别建的，所有入库单都一样）：

- 内容：**「待检证（75×110mm 小标签）+ 货位卡（A4）」合并成的一个 PDF**
- 位置：挂在对应 **`Batch`（批次）的附件**里，文件名形如 `HBOS-<批号>-待检证+货位卡.pdf`
- 怎么拿：打开批次 → 附件区下载；或直接打印

**批次页面还有「重新生成货位卡 / 待检证」按钮**，用于两种情况：

- 自动生成失败（提交时会弹提示告诉你是哪几个批次）；
- 数据后来变了（如 QA 补了放行状态、产生了新的出入库流水），需要重出。

重新生成会**替换上一次自动生成的那份**，不会越堆越多；**不会动你手工上传的附件**。

### 四、常见情况

| 现象 | 原因 / 处理 |
| --- | --- |
| 页面提示「识别服务当前不可用」 | 服务没启动，或没绑 `0.0.0.0`；照第一节起服务 |
| 识别后某些字段是**空的** | 模型没读出来。**这不是 bug**，按标签手填即可 |
| 字段被**橙色高亮** | 有需要核对的地方（如"识别只读到年月"、形近字母纠正过）。**必须核对** |
| 「物料未建档」 | 该物料代码还没进 Item 主数据。**先建物料**，或核对代码是否取错 |
| 「是库位 / 层等分组节点」 | 货位选到了分组节点，要选具体的叶子货位 |

## 接口

### `GET /health`

返回各后端可用性，供 Frappe 侧判断"能不能用、能用哪个"。

### `POST /api/v1/recognize`

multipart 上传，字段：`image`（图片）、`backend`、`source_type`（自产/外购）、`request_id`（幂等键）。

响应（示例）：

```json
{
  "ok": true,
  "request_id": "…",
  "backend": "stub",
  "fields": {
    "product_name": "…", "item_code": "…", "batch_no": "…",
    "manufacturing_date": "…", "expiry_date": "…"
  },
  "raw_fields": { "…": "后端原始产出，便于追溯 AI 读到了什么" },
  "confidence": { "…": 0.99 },
  "hints": { "item_code": ["已按形近字符纠正：13OOO215 → 13000215"] },
  "needs_review": true,
  "elapsed_ms": 12
}
```

`hints` 按字段给出提示，供 Frappe 侧**高亮需要人工复核的字段**。

**本接口不写入任何业务数据**——落库由 Frappe 侧在人工确认后执行。

## 配置（环境变量）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `HBOS_OCR_BACKEND` | `stub` | 默认后端 |
| `HBOS_OCR_HOST` | `127.0.0.1` | 监听地址 |
| `HBOS_OCR_PORT` | `8100` | 端口 |
| `HBOS_OCR_TIMEOUT` | `60` | 单张识别超时（秒） |
| `HBOS_OCR_MAX_IMAGE_BYTES` | `5242880` | 图片大小上限 |
| `HBOS_OCR_C2_MODEL` | `small` | C2 模型档位（`medium` / `small` / `tiny`） |
| `HBOS_OCR_C1_MODEL` | `mlx-community/Qwen2.5-VL-3B-Instruct-4bit` | C1 模型 |
| `HBOS_OCR_LOG_LEVEL` | `INFO` | 日志级别 |

## 数据与安全

| 项目 | 做法 |
| --- | --- |
| 照片出网 | **否**。服务不开外网访问 |
| 照片落盘 | **否**。识别后即释放。对上游库只接受文件路径的限制，用临时文件并**用完立即删除**（已在主文档记录该让步） |
| 服务日志 | **不记照片内容、不记批号与产品名**；只记 `request_id` / 后端 / 耗时 / 成败 / 错误类型 |
| 照片归档 | 由 **Frappe 侧**存到 `Attach`，随批次或单据走 |
| 幂等 | 进程内短期缓存（默认 10 分钟）。**非持久**，重启即失效——防重复点击足够，不做严格去重 |
