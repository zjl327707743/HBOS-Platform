# 考勤提醒卡片化设计文档

- 日期：2026-09-11
- 项目：HBOS（新乡海滨智能运营管理平台）· `hb_attendance_app`
- 归属：M1-FIX-B5 后续追加（考勤通知出站推送的呈现层改版）
- 状态：DESIGNED（待 Owner 复核本 spec 后进入实施计划）
- 前置：[`2026-09-10-考勤通知出站推送设计.md`](2026-09-10-考勤通知出站推送设计.md)

## 1. 问题

现存考勤通知（每日 09:00 发到飞书群自定义机器人）为**纯文本 + 空格补位对齐**。
Owner 2026-09-11 反馈两点：

1. **找不到重点** —— 全部部门平铺，正常部门与问题部门混在一起，坏消息被好消息淹没。
2. **列对不齐** —— 飞书客户端使用比例字体，空格补位无法对齐；四列数字散成一团。

根因：`render_report` 用 `_width`/`_pad` 手算中文宽度来做表格对齐，这套办法只在等宽字体下成立。
飞书群消息不是等宽字体，故无论怎么调空格都不可能对齐。

## 2. 目标与范围

**目标**：把群里的考勤提醒从纯文本表格改为**飞书卡片（interactive message）**——
列由卡片组件负责对齐，重点由版式负责凸显。

**范围**

- 只改 `hbos_attendance/attendance_notify.py` 一个文件的**渲染与报文构造**。
- 新增「异常明细」的提取（部门 + 人名），数据来自既有 `get_data()["rows"]`，不新增取数逻辑。

**范围外（本轮不做）**

- 不改任何考勤判定规则、不改统计口径（`board_stats.py` 一行不动）。
- 不改调度（9 点 cron）、幂等位、干跑开关、失败处理策略。
- 不改部门看板页面（`hbos_department_board.js`）。
- 不做卡片交互（按钮、点击查询、入站通路）—— 群机器人 webhook 是单向的。
- 不做多群、不做按部门分群。

## 3. 方案选择

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A **列表式卡片** | 不依赖表格组件，异常部门一条一行，人名紧接部门行下一行（无缩进）；分层靠换行与间距 | **选定**（Owner 2026-09-11） |
| B 表格式卡片 | 用飞书卡片表格组件，列真正对齐 | 未选：卡片更长，且表格组件版本兼容性需额外验证 |
| C 数字块式卡片 | 全厂四个数字铺成并列色块 | 未选：卡片最宽，部门行仍要另起一段 |

选 A 的理由：卡片最矮、手机上最好读、版式最不容易出错，且**不依赖卡片表格组件的版本兼容性**——
只用到标题、正文、分隔线、彩色标题这几个最基础的能力。

**若卡片通路整体不可用**（见 §7 保底）：退回「纯文本加强版」——
仍用文本消息，但改为只列异常部门、去掉表格对齐、每部门一行，至少解决「找不到重点」，
并诚实接受「列对不齐无法根治」。这是保底，不是首选。

## 4. 卡片结构

### 4.1 有异常（橙色标题）

```
┌ 橙色标题 ─────────────────────────┐
│ 考勤到岗 · 2026-09-11 09:00        │
├───────────────────────────────────┤
│ 全厂  应出勤 696 · 已到岗 651       │
│       未打卡 12 · 迟到 3            │
│ ─────────────────────────────      │
│ ⚠ 需处理（5 个部门）                │
│                                    │
│ 六车间  未打卡 3                    │
│ 张三 · 李四 · 王五                  │
│ 仓储部  未打卡 2                    │
│ 赵六 · 孙七                         │
│ 质量控制部  迟到 2                   │
│ 周八 · 吴九                         │
│ ─────────────────────────────      │
│ 其余 8 个部门全部正常                │
│ 备注：晚班 20:00 / 夜班 0:00 上班，   │
│      未到班次时间不计入未打卡         │
└───────────────────────────────────┘
```

### 4.2 全厂无异常（绿色标题）

```
┌ 绿色标题 ─────────────────────────┐
│ 考勤到岗 · 2026-09-11 09:00        │
├───────────────────────────────────┤
│ 全厂  应出勤 696 · 已到岗 651       │
│ ✅ 各部门全部正常，无未打卡、无迟到  │
│ 备注：晚班 20:00 / 夜班 0:00 上班…  │
└───────────────────────────────────┘
```

注：绿卡不必「已到岗 == 应出勤」。09:00 时点本就有一部分人尚未到上班时间
（晚班 20:00、夜班 0:00，落 `before_start` 桶），这些人不计入未打卡，
故已到岗小于应出勤属正常，由备注行解释。这正是卡片的用武之地——
把「数字对不上」和「真有人没打卡」区分开。

### 4.3 今日无应出勤人员

绿色标题；正文一句「（今日暂无应出勤人员）」。不列部门、不列备注。

### 4.4 版式规则

| 元素 | 规则 |
| --- | --- |
| 标题色 | 有异常 → `orange`；无异常 → `green` |
| 标题文本 | `考勤到岗 · <YYYY-MM-DD> <HH:MM>` |
| 全厂汇总 | **只显示非零项**：应出勤恒显示；已到岗恒显示；未打卡 / 迟到为 0 时省略该字段 |
| 异常部门行 | **只显示有值的那一项**（未打卡 或 迟到）；两者都有则都显示。不出现「迟到 0」这类占位 |
| 人名行 | 紧接所属部门标题行的**下一行**，用 ` · ` 分隔；**不做缩进**（markdown 会吃掉行首空格，缩进做不出来，实测如此） |
| 部门排序 | 沿用 `dept_summary` 的既有排序（未打卡+迟到 降序，其次在册人数降序），不额外排序 |
| 正常部门汇总 | 「其余 N 个部门全部正常」；N = 应出勤 > 0 的部门数 − 异常部门数 |
| 口径备注 | 存在「未开始 / 仅下班卡 / 班次未定」人员时附带（沿用原设计的触发条件），文案沿用 `NO_CARD_HINT`；无应出勤人员时不附 |

## 5. 截断规则

防止极端情况把卡片撑爆。两条截断都必须在卡片上**显式说明被省略的数量**，不得静默截断。

| 位置 | 上限 | 超出时的呈现 |
| --- | --- | --- |
| 单个部门的人名 | 6 人 | `张三 · 李四 · 王五 · 赵六 · 孙七 · 周八 等 3 人` |
| 异常部门数 | 10 个 | 第 10 个之后加一行：`另有 N 个部门存在异常（详见部门看板）` |

人名口径：**只放姓名，不放工号**。部门已在行首，工号在群里无人阅读，只会加长行宽。
重名问题本轮不处理（真出现再加区分字段）。

## 6. 接口与数据流

```
send_daily_report()
  └─ get_data(department=None, date_str=...)      ← 不变
       ├─ stats      : 全厂汇总（既有）             ← 不变，本轮新消费
       ├─ dept_stats : 部门汇总（既有）             ← 不变
       └─ rows       : 人员明细（既有，本轮新消费）
            │
            ▼
  collect_exceptions(rows)        ← 新增，纯函数
       └─ [{dept, noCard: [{name, num}], late: [{name, num}]}]
            │
            ▼
  render_card(date_str, hhmm, stats, dept_stats, exceptions)   ← 新增，纯函数
       └─ 飞书卡片 JSON（dict，不涉及网络）

  build_feishu_payload(card)      ← 改：msg_type 由 text 改 interactive
  build_text_payload(text)        ← 新增：降级/留档用的纯文本报文

  render_report(...)              ← 保留不动：纯文本留档（Error Log / 干跑）
```

### 6.1 `collect_exceptions(rows) -> list`

按部门聚合明细行中的异常人员。**归桶判定不在此重写**——第四套口径正是本设计要避免的东西。

- 对每行调用 `board_stats.summarize_rows([r])` 取**单行结果**，`late` 与 `noCard` **都取它的计数**。
  这样归桶逻辑与统计口径**字面同源**，改口径时不会两处漂移；`board_stats.py` 本身**一行不改**。
  全厂约 600 行，逐行 O(1)，开销可忽略。

> 实现陷阱（必须守住）：**不能**改用 `board_stats.is_late(r)` 单独判迟到。`summarize_rows` 对
> 非应出勤行（`leave` / `rest` / `exempt` / `unknown` / `kind != "shift"`）直接跳过、不计任何桶，
> 而 `is_late` 只看 `state` 与 tags。一行「休假 + 迟到标签」会被 `is_late` 判为迟到、却被统计忽略，
> 于是卡片列出看板不认的人——正是验收标准 4 禁止的数字漂移。故必须以 `s["expected"]` 为前置门槛，
> 且迟到也取单行统计结果。测试用 state × kind × 标签 全枚举 + 聚合一致断言固化这一点。

`summarize_rows` 的单行结果自动覆盖了全部排除规则，无需另写分支：

| 行的情形 | 单行 `expected` | `noCard` | 归桶结果 |
| --- | --- | --- | --- |
| `anomaly_hidden`（如设备动力部） | — | — | 在调用前显式跳过 |
| `state` 为 `exempt` / `rest` / `leave` / `unknown` | 0 | 0 | 排除（即使带「迟到」标签） |
| `kind != "shift"`（非班次） | 0 | 0 | 排除（即使带「迟到」标签） |
| `before_start` / `out_only` / `absent_day` | 1 | 0 | 不进未打卡名单，也无迟到标签 |
| `fact_none`（班次未定） | 1 | 0 | 不进未打卡名单；**若带「迟到」标签则进迟到名单**（与统计一致） |
| `absent_expected` / `no_pair` / `pending` | 1 | 1 | 未打卡 |
| 未知 state（兜底） | 1 | 1 | 未打卡（与 `summarize_rows` 的兜底一致） |

> 边界说明：某人若同时满足 `is_late` 且归入未打卡，会在两个名单里各出现一次，
> 与 `summarize_rows` 的计数方式一致（它也是两边各加一）。这是刻意对齐，不是缺陷。

返回结构：

```python
[{"dept": "六车间",
  "noCard": [{"name": "张三", "num": "0001"}, ...],
  "late":   [{"name": "周八", "num": "0017"}, ...]},
 ...]
```

- 部门顺序与 `dept_summary(rows)` 一致（不另排序，保证卡片与看板同序）。
- 部门内按 `num` 升序，保证同一批数据每次渲染结果稳定。
- 仅返回至少有一项异常（`noCard` 或 `late` 非空）的部门。

### 6.2 `render_card(date_str, hhmm, stats, dept_stats, exceptions) -> dict`

纯函数，返回飞书卡片 JSON（`{"config":…, "header":…, "elements":[…]}`），**不含 `msg_type`**。

传入 `stats`（全厂汇总）是为了卡片头部的全厂那一行；`dept_stats` 用来数「其余 N 个部门全部正常」
的 N（应出勤 > 0 的部门数）。

### 6.3 报文构造

- `build_feishu_payload(card) -> {"msg_type": "interactive", "card": card}`

  > **字段名说明（终审修复，高置信度但未实测）**：**群自定义机器人 webhook** 的 interactive 消息
  > 把卡片对象放在顶层 `card` 键。`content` 是 `im/v1/messages` OpenAPI 的写法（那里卡片是
  > JSON **字符串**放在 `content` 里），两者不是同一个面。飞书文档通路被网络策略阻断，
  > 无法离线实测；实发时若飞书返回参数类错误码，改用 `content` 重发同一张最小卡片验证
  > （见 §7.1）。

- `build_text_payload(text) -> {"msg_type": "text", "content": {"text": text}}`（降级与留档用）

`render_report` 的纯文本输出**保留**：它仍用于干跑核对与失败留档——
出错时人是读文本日志的，不是读 JSON。

## 7. 兜底

| 场景 | 行为 |
| --- | --- |
| 卡片 JSON 构造抛异常 | **自动降级**：改用 `render_report` 的纯文本，仍以 `msg_type: text` 发出。宁可丑，不能不发 |
| 卡片发送被飞书拒绝（code 非 0） | 按既有链路记 Error Log，**不自动补发纯文本**——code 非 0 通常意味着 webhook 地址或鉴权有问题，纯文本同样发不出去；重试次日自然再算。幂等位行为不变（失败时不落，与现状一致） |
| 未配 webhook | 静默跳过（与现状一致） |
| 干跑 `HBOS_NOTIFY_DRY_RUN=1` | Error Log 中**同时**留卡片 JSON 与纯文本，便于先核对版式再配地址 |

### 7.1 卡片通路可行性验证（实施第一步）

飞书群机器人 webhook 对卡片组件版本的兼容性、以及 interactive 报文的**字段名**
**无法离线验证**（本次查文档的网络通路被策略阻断）。故实施计划的第一步是：
**发一张最小卡片到群里，确认能渲染**，通过后再往上堆版式。

- 该验证步骤**属飞书真实写入，须 Owner 明确授权后执行**。
- 验证是**程序化**的（spec §6.3 的字段名是「高置信度但未实测」，由本步骤裁决），不得临场发挥：

  1. 先按顶层 `card` 键发一张最小卡片（`{"msg_type": "interactive", "card": <最小卡片>}`）。
  2. **若飞书返回参数类错误码**（如 code 非 0，且错误信息指向参数 / 字段），**立刻改用
     `content` 键重发同一张最小卡片**（`{"msg_type": "interactive", "content": <同一张卡片>}`）。
  3. 哪一次渲染成功，就把 `build_feishu_payload` 的键名**定为那一个**；并把该次的**返回 `code`
     原样记下**（写入本轮报告与 `docs/HBOS考勤判定规则.md` 的待验证说明），供事后核对。
  4. 卡片**两种字段名都失败**时，再试把 `header.title.tag` 与文本元素 `tag` 降级为卡片 v1 结构重试。
  5. 仍不通则执行 §3 的「纯文本加强版」保底，并如实告知 Owner 卡片路线不可行、停止后续步骤。

> 「参数错误即换 `content` 重发」这一步是本 runbook 的核心：字段名判错时飞书只回一个非零
> `code`，而按 §7 卡片被拒**不会**自动补发纯文本——若临场不试第二遍，提醒会每天静默消失。

## 8. 测试

全部离线（无 frappe / 无网络），纳入既有 `tests/test_attendance_notify.py`。

`collect_exceptions`：

- 只挑未打卡 / 迟到的人；`exempt`/`rest`/`leave`/`unknown`/`anomaly_hidden` 的行不出现。
- **非应出勤行即使带「迟到」标签也不出现**（回归测试：`leave` / `rest` / `exempt` / `unknown` /
  非班次 + 「迟到」标签，都必须为空）。注意 `fact_none` 属**应出勤**，不在此列——它带「迟到」
  标签时按统计口径应进迟到名单。
- 判定结果与 `board_stats.summarize_rows` 逐项一致——用 state × kind × 标签**全枚举**断言，
  并对多部门样本断言「各部门名单之和 == 全厂统计」与逐部门一致。
- 部门顺序与 `dept_summary` 一致；部门内按工号升序、结果稳定。

`render_card`：

- 有异常 → 标题色 `orange`；无异常 → `green`；无应出勤 → `green` 且正文为「今日暂无应出勤人员」。
- 部门行只显示非零项，不含「迟到 0」。
- 全厂汇总：未打卡 / 迟到为 0 时该字段不出现。
- 人名超过 6 人 → 出现 `等 N 人`，且 N 正确。
- 异常部门超过 10 个 → 出现 `另有 N 个部门存在异常`，且 N 正确。
- 「其余 N 个部门全部正常」的 N 正确。
- 备注行的触发条件正确：存在「未开始 / 仅下班卡 / 班次未定」人员时出现，无应出勤人员时不出现。
- 卡片 JSON 结构可被 `json.dumps` 序列化。

`build_feishu_payload`：

- 返回 `msg_type == "interactive"`，`card` 即卡片对象（**顶层键集合恰为 `{"msg_type", "card"}`**——
  之前的测试从不约束这个外壳，字段名 bug 正住在这里）。
- **需同步修改既有断言**：当前 `FeishuPayloadTest` 断言 `msg_type == "text"`，改版后必须为 `interactive`。
  （契约测试 `ModuleContractTest` 中 `render_report` / `HBOS_NOTIFY_*` 相关断言保持不变。）

`send_daily_report` 降级路径：

- 打桩使 `render_card` 抛异常 → 断言最终 payload 为 `msg_type: text`，且发送仍被调用（不因渲染失败而漏发）。

运行态（**需 Owner 授权**）：

- `HBOS_NOTIFY_DRY_RUN=1` 跑一次，核对卡片版式与看板数字逐项一致。
- 按 §7.1 发最小卡片确认渲染，再实发一次完整卡片确认群里收到。

## 9. 验收标准

1. 群里收到的是一条**卡片**，列由组件对齐（不再依赖空格补位），无错列。
2. 只列异常部门，正常部门收成一行「其余 N 个部门全部正常」；一眼能看出今天要不要处理。
3. 异常部门行携带具体人名；超过 6 人 / 超过 10 个部门时**显式**标注省略数量。
4. 卡片上的数字与「部门看板」同日同范围**逐项一致**（口径未变，仅呈现层改动）。
5. 渲染失败时自动降级为纯文本且消息仍发出；未配 webhook 时静默跳过；发送失败不抛断调度器。
6. 全量离线测试通过，含降级路径与既有断言的更新。
