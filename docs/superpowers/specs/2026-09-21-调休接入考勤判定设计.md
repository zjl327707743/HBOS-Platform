# 调休接入考勤判定 设计文档

- 日期：2026-09-21
- 项目：HBOS（新乡海滨智能运营管理平台）· `hb_attendance_app`
- 归属：M1-FIX-B5 后续追加（加班/调休模块，本轮先做调休）
- 状态：DESIGNED（待 Owner 复核本 spec 后进入实施计划）

## 1. 目标

让**飞书调休审批**真正参与考勤判定：调休当天视同请假，不判缺勤；当天确实来上班的，照常按打卡判定。

调休走**与飞书请假完全相同的那条通道**（Owner 2026-09-21 确认「调休就做成跟飞书请假的那种一样的」），因此判定层、看板零改动。

### 本轮范围

- `sync_rest_leave.py` 改写：飞书调休表 → `HBOS Leave Record`，`leave_type = 调休`。
- 退休 `HBOS Rest Leave Record`（删除 DocType、入口、调度）。
- 摘掉换班同步的调度与 DocType（Owner 2026-09-21：换班等等再加）。
- 修同步健壮性问题（脏值中断、调度内 throw、静默 skip）。
- migrate 上线 + 校验。

### 范围外（明确不做）

- 不做加班模块（加班审批、加班余额、加班与调休的抵扣核对）。
- 不做换班判定接入。
- 不做额度校验：只要飞书审批通过就豁免，系统不核对加班余额（Owner 2026-09-21 确认）。
- 不做半天/小时级调休的时段判定：一律整天豁免（Owner 2026-09-21 确认）。
- 不改 `pairing.py`、`board_stats.py`、月报分类逻辑、考勤结果报表。
- 不写回飞书（只读同步）。

## 2. 决策变更说明（重要）

本设计**推翻** 2026-09-11 的一项决定，必须留痕，否则后续读代码的人会不解：

| | 2026-09-11（已被取代） | 2026-09-21（本设计） |
| --- | --- | --- |
| 出处 | `docs/superpowers/specs/2026-09-11-调休与换班记录界面设计.md` §1 | 本文档 |
| 决定 | 调休**另建** `HBOS Rest Leave Record`，与请假表「各记各的、互不影响」 | 调休**并入** `HBOS Leave Record`（`leave_type=调休`），与请假同一条判定通道 |
| 理由 | 当时定位为「只读登记展示」，不走判定 | 调休本质是请假的一个类型，`HBOS Leave Record.leave_type` 的 Select 里**本来就有「调休」**；另建通道会让判定/看板/报表都要各自再接一遍 |

**该决定的后果**：2026-09-11 那一轮交付的 `HBOS Rest Leave Record` 从未投入使用（见 §3.2），因此退休它不损失任何数据。

### 3.3 两张表的 SourceID 不相交

实测：调休表 115 个 SourceID、请假表 354 个 SourceID，**交集为 0**。

因此调休同步使用独立前缀 `feishu-bitable-restleave-` 不会与请假同步产生重复记录，也不存在「同一条审批被两个同步互相覆盖」的风险。

### 3.4 判定通道现状

请假走：`HBOS Leave Record 已通过` → `api.py` 建 `emp_leave_dates` → 传入 `pair_employee_checkins()`。

`pairing.py` 里 `leave_dates` 共 4 处使用（481/515/622/662），**全部只做一件事：抑制 Absent**。pairing 本身从不生成 On Leave 记录——记录只在 `api.py` 的零打卡分支生成。

## 4. 数据模型

**不改 DocType、不加字段、不建表。**

调休记录写入现有 `HBOS Leave Record`：

| 字段 | 取值 |
| --- | --- |
| `employee` | 按 `调休人员_工号` 匹配 → 退回按 `调休人员_姓名` 匹配 |
| `leave_type` | `调休`（该 Select 的既有选项之一） |
| `start_date` / `end_date` | `调休人员_开始时间` / `结束时间` 的日期部分 |
| `leave_days` | `调休人员_调休天数`（容错转换，见 §7；**仅供人工参考，判定不使用**；日期区间一律按 start/end 展开，与 `leave_days` 无关） |
| `approval_status` | 经 `STATUS_MAP` 映射（与请假同步一致） |

**状态写入范围**：与请假同步一致——**写入全部状态，不只写「已通过」**。判定只读「已通过」，但已撤回/已驳回的记录留档可查（当前实测 115 条中：已通过 104、已撤回 8、已拒绝 1、已删除 1、审批中 1）。

`STATUS_MAP`（`api.py:79-82`）覆盖 已通过/审批中/已拒绝/已撤回/已驳回/已撤销；实测出现的 **「已删除」不在其中**，按 **「已撤销」** 处理（已删除的审批等同于撤销，最接近的既有语义）。这是本设计唯一一处需要判断的映射，若 Owner 认为应另作处理可覆盖。该条不影响判定（非「已通过」即不参与豁免）。
| `feishu_approval_id` | `feishu-bitable-restleave-<record_id>`（唯一键） |
| `feishu_sync_time` | 同步时刻 |
| `remarks` | `说明` 原文（含「8 月 20 日的加班 3h，调休到 8 月 26 日」这类抵扣说明，供人工核对） |

`调休人员_联系电话` **不写入**——手机号与考勤无关，避免把 PII 再抄一份。

## 5. 判定接入：零改动

调休记录成为 `HBOS Leave Record` 后，`api.py` 的 `emp_leave_dates` 自然包含调休日期，
`pairing.py` 的 4 处抑制逻辑自动生效。

**`pairing.py`、`api.py` 判定段均不改。**

行为对齐：

| 场景 | 结果 |
| --- | --- |
| 调休日、无打卡 | 生成 `On Leave`（与年假/事假同级） |
| 调休日、有打卡 | 照常判 Present/迟到，不额外记录（与请假现状一致） |
| 调休日、孤立卡 | 不判 Absent |

## 6. 看板与报表：零改动

- **部门看板 / 9:00 飞书卡片**：`department_board_data._load_leave_records()` 读的就是 `HBOS Leave Record`，自动包含调休；标签显示「请假（调休）」。调休人员从 `absent_expected`/`fact_none` 桶转入 `leave` 桶，**不再被 9:00 卡片点名为「未打卡」**——这是本设计最直接的业务收益。
- **`board_stats.py`**：`leave` 桶本就存在，不改。
- **月度考勤汇总**：其 `is_leave` 判定依赖 `HBOS Leave Record`，调休记录天然命中，落入 leave 桶。**不新增「调休」列**（Owner 2026-09-21：调休与飞书请假做成一样的）。
- **考勤结果 / 导出异常考勤**：`On Leave` 本就被排除在异常之外，不改。

## 7. 同步健壮性修复

现有 `sync_rest_leave.py` 有三个上线即踩的问题：

| # | 问题 | 修法 |
| --- | --- | --- |
| 1 | `rest_leave_fields` 里 `float(调休天数)` 无保护——一个脏值即抛异常，**整次同步中断** | 容错转换，失败取 0，不中断 |
| 2 | 拉取失败用 `frappe.throw`——在调度任务里抛异常会打断调度链 | 改为记 Error Log + 返回错误摘要（对齐 `daily_feishu_sync` 的写法） |
| 3 | 匹配不到 Employee 的记录静默 skip——当前有 1 个工号匹配不到 | 计入返回摘要的 `unmatched` 计数并记日志，让问题可见 |

去重、状态映射、按天展开等保留现有实现。`STATUS_MAP` 复用 `api.py` 的（已拒绝→已驳回、已撤回→已撤销），使调休与请假的状态口径一致。

## 9. 上线步骤

```
bench --site frontend migrate
docker compose restart backend scheduler
```

- `migrate` 建出表结构、DocType 记录、以及 hooks 里的调度任务。
- 用 `restart` 而非 `up`：沿用飞书卡片那轮验证过的做法，保持容器 IP 不变，避免 nginx 连旧 IP 导致 502。
- 换班摘除后，migrate 只会注册调休同步任务。

**上线后校验**（逐项留证据）：

1. `tabHBOS Leave Record` 中 `leave_type=调休` 的行数 = 115（全状态写入），其中 `approval_status=已通过` 的 = 104。
2. `tabScheduled Job Type` 中只有 `sync_rest_leave_from_bitable`，无换班。
3. 触发一次同步，比对 `created/updated/unmatched` 与飞书实读一致。
4. 重算 8/15 起至今，抽查 2-3 名调休人员的调休日：确认由 `Absent` 变为 `On Leave`。
5. 看板取数：调休人员落 `leave` 桶，不计入 `expected` 分母。

## 10. 测试

**为什么必须改测试思路**：`test_rest_leave_swap_entry.py` 现有 4 个用例全是「读源码、断言字符串存在」，永远为真。它证明了模块「代码在」，却无法证明「运行态可用」——这正是该模块从未 migrate 却全绿通过的原因。新测试一律测真实行为。

| # | 用例 | 层次 |
| --- | --- | --- |
| 1 | 日期按**区间**展开：09-06→09-11（跨度 6、申报 1 天）必须展开成 **6 天** | 纯函数，CI |
| 2 | 脏值不炸：`调休天数` 为 `"abc"` / 空 / None / 非数值 → 不抛异常 | 纯函数，CI |
| 3 | 状态映射：已拒绝→已驳回、已撤回→已撤销、**已删除→已撤销**、未映射值→审批中 | 纯函数，CI |
| 4 | 豁免生效：调休日的孤立卡**不产生 Absent** | 纯函数（pairing），CI |
| 5 | 映射不泄漏 PII：`联系电话` 不出现在产出字段中 | 纯函数，CI |
| 6 | 调度契约：hooks 注册了调休同步、**未**注册换班同步 | 静态契约 |
| 7 | 无残留：`HBOS Rest Leave Record` / `HBOS Shift Swap Record` 的 DocType 目录与引用已清空 | 静态契约 |

日期展开逻辑放进 `swap_mapping.py`（本就是为离线纯测试准备的模块），使 1-5 在 CI 中可跑，不需要数据库。

## 11. 风险与回滚

| 风险 | 应对 |
| --- | --- |
| migrate 触发 `after_migrate`（B4 的工作台/侧栏/桌面图标同步） | 该逻辑设计为幂等，且本轮本就要改工作台 json，属预期内 |
