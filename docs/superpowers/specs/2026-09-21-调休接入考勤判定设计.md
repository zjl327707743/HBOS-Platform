## 1. 目标

让**飞书调休审批**真正参与考勤判定，且**与请假走不同的判定逻辑**：

- **请假** = 当天整天豁免。
- **调休** = 需要**先核实**「申报的加班确实发生过」，核实通过才豁免调休日；核实不通过则不豁免，转人工。

「模板一样」指 DocType 与同步写法照抄请假那套；「判定不一样」指上面的核实环节。两条通道分开，各自成表。

### 本轮范围

- 新建调休 DocType（模板同请假，另加 3 个自有字段）。
- 飞书调休表同步：日期字段 → 调休日；说明 → 交 LLM 提取加班日。
- **LLM 解析结果落库**；判定热路径不调用 LLM。
- 核实：加班日必须有完整的上下班打卡配对。
- 已核实的调休日接入判定（并入传给 pairing 的请假集合，`pairing.py` 零改动）。
- 退休从未生效的 `HBOS Rest Leave Record` 与换班相关代码。
- migrate 上线 + 校验。

### 范围外（明确不做）

- 不做加班模块（加班审批、加班余额、加班认定）。
- 不做按小时/半天的调休时段判定（见 §6）。
- 不做换班判定接入（换班代码本轮一并摘除，等其自己的轮次）。
- 不做额度校验（Owner 2026-09-21 确认）。
- 不改 `pairing.py`、`board_stats.py`、月度汇总分类逻辑、考勤结果报表。

## 4. 判定规则

```
请假：当天整天豁免（现状不变）。

调休：
  ① 调休日 = 日期字段「开始时间 ~ 结束时间」的区间         ← 结构化字段，说了算
  ② 加班日 = LLM 从「说明」提取（可多个，可能以他人名字列在同一单据内）
  ③ 核实   = 每个加班日当天是否存在【完整的一对上下班打卡】
  ④ 全部加班日都有完整配对 → 调休成立 → 调休日豁免
     任一加班日无完整配对 / 解析失败 / 无加班日 → 不成立
  ⑤ 不成立 → 不豁免调休日（按正常规则判，该缺勤即缺勤）
            → 标记「调休待核实」进异常名单，交人工
```

**关键设计**：只有确实发生过加班，才能换来调休。这防止「没加过班却拿调休换休」。

### 4.1 停用调休记录的处理（待确认项）

实操中会出现：调休已批准并已发生的加班被**后续撤销**（例：`9月14日 17:00-17:30 调休半小时`，以及说明中「4.11已调休完」这类历史核销记录）。

本设计采用：**不追溯、不二次撤销**。即一旦某条调休的加班核实通过并豁免，后续即便加班审批被撤销，已生成的考勤结果不回改（避免历史考勤被反复改写）。每月月底由人工核对。

> 这一条是本设计中最不确定的一处。若 Owner 认为应追溯（撤销后自动收回豁免并重判为缺勤），请在复核时指出，实施计划会相应调整。

## 5. 数据模型

新建 DocType `HBOS Rest Leave Record`（沿用该名称，因原同名 DocType 从未 migrate，无历史数据负担；亦可改名，见 §11 待确认）。

**模板同请假**（`HBOS Leave Record`）的字段：`employee`、`employee_name`、`employee_number`、`department`、`start_date`、`end_date`、`rest_days`、`feishu_approval_id`（唯一去重键）、`approval_status`、`feishu_sync_time`、`remarks`。

**自有字段（3 个）**：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `overtime_dates` | Small Text | LLM 提取的加班日，逗号分隔的 `YYYY-MM-DD` |
| `verify_status` | Select | `已核实` / `待核实` / `核实不通过` / `解析失败` |
| `verify_time` | Datetime | 最近一次核实时间 |

`verify_status` 默认 `待解析`（新记录先等 LLM 解析，再进入核实）。

> 实施细化（2026-09-21 实施计划）：设计原稿此处写「默认 `待核实`」，实施时为区分「LLM 调用失败（需重试）」与「尚未解析」，改为默认 `待解析`，并新增 `parsed_at` 字段记录最后一次解析时刻。详见 `docs/superpowers/plans/2026-09-21-调休模块第一阶段.md` Task 2。

`调休人员_联系电话` **不写入**（PII 与考勤无关）。

## 6. 与请假的关键差异（记录，避免日后被误改）

| | 请假 | 调休 |
| --- | --- | --- |
| 数据表 | `HBOS Leave Record` | `HBOS Rest Leave Record` |
| 判定前提 | 审批通过即豁免 | 审批通过 **+ 加班日核实通过** 才豁免 |
| 数据来源 | 飞书请假表 | 飞书调休表（说明需 LLM 解析） |
| 是否需要 LLM | 否 | **是**（仅解析加班日） |
| 记录生成 | `On Leave` | `On Leave`（复用相同状态与看板口径） |
| 按小时判定 | 不做 | **不做**（见下） |

**按小时/半天调休本轮不做**：实测说明里大量小时级描述（`9/3 上午休息半天，周六 9/6 上午上班`（含补班）、`9/14 调休 17:00-17:30`、`9/17 请 1.5h`），但**飞书表没有时段字段**，全在自由文本里。要做到按小时判，须先改飞书表单加结构化字段。本轮一律按**整天**处理，小时级信息留存于 `remarks` 供人工核对。

## 7. 执行时序（三段分离）

判定每 10 分钟重算一次，**绝不能在热路径调 LLM**。三段职责分开：

| 段 | 触发 | 职责 | 是否调 LLM |
| --- | --- | --- | --- |
| A. 同步 | 调度 `*/30` | 飞书表 → DocType；新增/说明变更的记录标记需解析 | 否 |
| B. LLM 解析 | 同步之后，仅对「需解析」的记录 | 说明 → `overtime_dates`，写回并标 `verify_status=待核实` | **是**（每条一次） |
| C. 核实 + 判定 | `regenerate_attendance`（`*/10`） | 对比 `overtime_dates` 当天的打卡配对 → 回写 `verify_status` → 已核实的调休日并入豁免集合 | 否 |

B 段必须落库的关键理由：判定每 10 分钟跑一次，若每次重算都调 LLM，成本与延迟不可接受，且同样输入未必同样输出——**判定必须基于稳定、可复查的落库结论**。

顺带补齐「AI 结论不落库、HR 无法复盘」（`ai_review.py:5-7` 现状）。

## 8. 判定接入：`pairing.py` 零改动

`api.py` 在 `regenerate_attendance` 内：

1. 读取 `verify_status=已核实` 的调休记录，把其调休日期展开成集合。
2. **并入**传给 `pair_employee_checkins()` 的请假集合。
3. 未通过核实的调休日**不并入**，因此自然不豁免。

由于 `pairing.py` 中 `leave_dates` 只用于抑制 Absent，合并后 4 处抑制分支自动生效，**`pairing.py` 一行不改**。

**「调休待核实」的呈现**：`verify_status != 已核实` 的调休日，若当天无打卡，按现有规则会判 `Absent`；在 `Attendance` 上标记，使其能进人工复核清单（实现方式见实施计划，优先不加新字段）。

## 9. 看板与报表

- **部门看板 / 9:00 飞书卡片**：已核实的调休日应落 `leave` 桶。`department_board_data._load_leave_records()` 目前只读 `HBOS Leave Record`，**需增加调休来源**（仅取 `verify_status=已核实`），否则调休人员会被算进「未打卡」预警。`board_stats.py` 不改。
- **月度考勤汇总**：现有 `is_leave` 依赖 `HBOS Leave Record`，调休记录不在其中。**不新增列**（Owner 2026-09-21：调休与请假做成一样的呈现），已核实的调休日按现有 leave 口径处理，具体实现见实施计划。
- **考勤结果 / 导出异常考勤**：`On Leave` 本就被排除在异常之外，不改。

## 12. 风险

| 风险 | 应对 |
| --- | --- |
| **LLM 解析不准** | 落库后逐条人工核对（校验步骤 4）；不通过即 `解析失败`；保守失败不豁免 |
| **LLM 成本** | 仅新增/变更记录调用；104 条一次性 + 日均个位数 |
| **LLM 不可用时** | 解析失败 → 不豁免 → 待核实清单；不影响其他考勤判定 |
| 说明中加班日与日期字段矛盾（实测 2 条） | 标记来交 HR 订正，不写特例 |
| migrate 触发 `after_migrate` | 该逻辑设计为幂等，且本轮本就要改工作台，属预期内 |
| 重算先删后插 `HBOS-ATT-%` | 与调休无关（属已知缺口，另行处理） |

**回滚**：migrate 前备份 `frontend` 站点（沿用 M2-STOCK-R1 备份方式）；LLM 解析可批量清空 `overtime_dates` 回到「全部待核实」；代码可从 git 整体恢复。
