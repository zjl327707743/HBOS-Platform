# 考勤通知（每日 9:00 出站推送）设计文档

- 日期：2026-09-10
- 项目：HBOS（新乡海滨智能运营管理平台）· `hb_attendance_app`
- 归属：M1-FIX-B5 后续追加（与部门看板同批）
- 状态：DESIGNED（待 Owner 复核本 spec 后进入实施计划）

## 1. 目标与范围

每天 09:00（北京时间）自动把**当日各部门到岗情况**推送到云端 OpenClaw，由它发到管理群。

**范围**

- HBOS 侧只做两件事：算当日部门统计、主动 POST 到 OpenClaw 的接收地址（出站）。
- 本机**不开任何入站端口**；HBOS **不存群 ID、不负责消息排版**、不做调度以外的编排。

**范围外（本轮不做）**

- 不做入站接口、不做群里对话查询（需入站通路；待 HBOS 上服务器或经隧道后再单开）。
- 不做多群 / 按部门群隔离、不做群 ID 管理。
- 不部署上云、不改任何考勤判定规则、不动既有报表与看板行为。

## 2. 架构

```
本机 HBOS(Docker)                                    云端 OpenClaw
└─ Frappe scheduler 每日 09:00(北京)
     ├─ 复用看板统计口径算「各部门当日到岗」
     ├─ 渲染成文本消息
     └─ HTTP POST(JSON) ─────────────────────────▶ 接收后发到群
```

职责边界：HBOS 保证**数字正确**；OpenClaw 负责**何时发、发给谁、怎么发**。

## 3. 统计口径收敛（本设计的必要前置）

现状：后端 `department_board_data._aggregate`（按 `state` 计迟到、无「缺勤」桶）与前端
`hbos_department_board.js` 的 `summarize`（按 `tags` 计迟到、单列缺勤）**已是两套口径**。
通知若再实现一遍将出现三处实现、三种数字。故本设计**把口径收敛到后端一处**：

新增纯模块 `hbos_attendance/board_stats.py`（无 frappe 依赖，可离线测试）：

- `summarize_rows(rows) -> {total, expected, present, late, noCard, absent, leave, rest, exempt}`
  规则（即当前前端口径，保持不变）：

  | 分组 | 归属 |
  | --- | --- |
  | 应出勤 expected | `kind == "shift"` 的行（含缺勤行） |
  | 已到岗 present | state ∈ {present, late, fact_present, present_offwindow, out_day, out_offwindow} |
  | 迟到 late | state == late **或** tags 含「迟到」（覆盖回顾模式的 HRMS 迟到标签） |
  | 缺勤 absent | state == absent_day（仅已定性的缺勤；计入 expected，**不计入** noCard） |
  | 无打卡记录 noCard | 期望上班、未到岗、且 state ∉ {before_start, absent_day} |
  | leave / rest / exempt | 各自 state |
  | unknown | 不计入任何桶（不参与出勤率分母） |

  恒等关系：`expected = present + noCard + absent`（逐部门、全厂均成立，可作为自检断言）。

- `group_by_dept(rows) -> {dept: [rows]}`
- `dept_stats(rows) -> [{dept, total, expected, present, noCard, late, absent}]`（按未打卡+迟到降序）

数据层 `department_board_data.get_data()` 改为**返回服务端统计**：

- 新增返回字段 `stats`（用 `summarize_rows`，替换原 `_aggregate`）
- 新增返回字段 `dept_stats`（用 `dept_stats`）
- 前端 `hbos_department_board.js` 删除本地 `summarize()`，改为直接渲染 `data.stats` /
  `data.dept_stats`；颜色与徽标逻辑不动。

这样看板、通知、以及未来任何消费方共用同一实现。

## 4. 通知内容

按部门一行，**不含全厂汇总行**（Owner 2026-09-10 确认）：

```
【考勤到岗】2026-09-10 09:00

部门              应出勤  已到岗  未打卡  迟到
无菌车间             60     58      2      0
六车间（非规）       57     52      5      0
厂外QC               55     53      2      0
环保部               50     47      3      0
…
```

- 部门排序：未打卡+迟到降序（便于先看问题部门）；部门间用全角空格/固定宽度对齐，群内以纯文本可读为准（不假设群支持 Markdown 表格）。
- 某部门当日无应出勤人员（如全员休息）时不出现该行。
- 消息末尾附一行说明口径：`（晚班 20:00 / 夜班 0:00 上班，9 点显示未开始，不计入未打卡）`——仅在有此类人员时附。

## 5. 9 点口径（关键）

09:00 这个时点，晚班（20:00 上班）与夜班（0:00 上班）人员本就未到上班时间。
`resolve_expected` 已把「班次未开始」判为 `before_start`，`summarize_rows` **不计入未打卡**
——因此这些人不会被误报为"未到"。早班（08:00 上班）已开始却无卡的，正常计入未打卡（这才是预警）。

## 6. 定时与幂等

- `hooks.py` 新增 scheduler cron 两条：`"0 1 * * *"` 与 `"0 9 * * *"`，均指向
  `hbos_attendance.attendance_notify.send_daily_report`。
- **时区**：Frappe cron 按容器系统时区触发，且我们无法假定容器时区。故**不靠 cron 定时刻**，
  而是在任务内加守卫：仅当**北京时间小时 == 9** 才发送（用既有 `TZ_PLUS8` 计算）。
  容器为 UTC 时北京 09:00 = UTC 01:00 → 由 `0 1` 那条触发并通过守卫；
  容器为北京时间时 `0 9` 那条触发并通过守卫。两条中只有一条会真正发送。
- **幂等**：以 `frappe.cache` 键 `hbos_notify_sent:<YYYY-MM-DD>` 去重，同日只发一次（防重复触发）。
- 运行态验证时须确认容器时区，并核对实际触发时间（此前已有 UTC 导致 8 小时错位的先例）。

## 7. 配置与鉴权

放本机 `.env`（`.gitignore` 已覆盖，**不进仓库**）：

| 变量 | 说明 |
| --- | --- |
| `HBOS_NOTIFY_WEBHOOK_URL` | OpenClaw 接收地址。**未配置 → 静默跳过发送**（记 info 级日志，不报错） |
| `HBOS_NOTIFY_TOKEN` | 可选。配置后作为 `Authorization: Bearer <token>` 请求头发送 |

请求体（JSON）：

```json
{
  "type": "attendance_daily",
  "date": "2026-09-10",
  "generated_at": "2026-09-10 09:00:03",
  "title": "【考勤到岗】2026-09-10 09:00",
  "text": "<完整多行文本，可直接发群>",
  "dept_stats": [{"dept": "无菌车间", "expected": 60, "present": 58, "no_card": 2, "late": 0}]
}
```

`text` 为可直接发送的纯文本；`dept_stats` 为结构化数据，供 OpenClaw 侧自定义排版。
若 OpenClaw 要求其它格式，仅调整渲染函数的输出映射，不动统计逻辑。

## 8. 失败处理

- 计算或发送异常：记 `frappe.log_error`，**不重试**（次日自然再算），不抛断调度器。
- 未配 webhook：静默跳过。
- 新增**试运行开关**：`HBOS_NOTIFY_DRY_RUN=1` 时只把消息写入 Error Log / 日志而不发送，
  供配地址前先核对内容。

## 9. 测试

离线（无 frappe，纳入 CI）：

- `board_stats.summarize_rows`：各 state 归属、迟到按标签计入、before_start 不进未打卡、
  unknown 不计分母、出勤率计算与 expected=0 时为 None。
- `dept_stats`：分组、排序（未打卡+迟到降序）、空部门不含行。
- 消息渲染：部门行对齐、无应出勤部门不出现、含「未开始」说明的触发条件。
- 契约：`department_board_data` 含 `stats`/`dept_stats` 返回；前端 JS 不再包含 `summarize(` 定义；
  `hooks.py` 含 9 点定时项。

运行态（需 Owner 授权）：

- `HBOS_NOTIFY_DRY_RUN=1` 下调一次任务，核对消息文本与看板数字逐项一致。
- 配好 webhook 后实发一次，确认群里收到。

## 10. 验收标准

1. 干跑输出的部门数字与「部门看板」同日同范围**逐项一致**。
2. 数值口径明确区分：应出勤 / 已到岗 / 未打卡 / 迟到；且满足恒等关系
   `应出勤 = 已到岗 + 未打卡 + 缺勤`（逐部门与全厂均成立）。
3. 09:00 时点下，晚班/夜班人员不被计入未打卡。
4. 未配 webhook 时任务静默跳过；发送失败只记日志不影响调度器。
5. 全量离线测试通过；前端行为与改版前一致（仅数据来源改为服务端）。
