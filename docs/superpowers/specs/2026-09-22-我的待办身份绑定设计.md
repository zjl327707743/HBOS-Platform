# 我的待办身份绑定设计

> 状态：Owner 已批准，已完成实施，待测试路径验收
>
> 日期：2026-09-22
>
> 范围：M2-LIMS 独立前端与 `hb_lims_app` 后端
>
> 修订：根据 2026-09-22 两轮审阅反馈，补充派生结果排除、项目粒度跨模块去重、深链契约、字段映射、`Administrator` 显式特判、缓存策略与验收项。

## 1. 目标与背景

当前侧栏「我的待办」角标把稳定性时间点的全局统计与待检任务入口混在一起：

- `pendingCount` 仍是前端占位值 `0`；
- 稳定性角标来自全量时间点状态统计；
- `/tasks` 加载的是未带过滤条件的全局「待检任务看板」；
- 用户点击「我的待办」后无法看到与当前身份绑定的统一任务清单。

本设计将「我的待办」改造成跨模块个人待办中心。用户点击后看到当前登录身份下所有需要完成的任务，任务来源可以是明确指派给当前用户的记录，也可以是当前用户所拥有角色能够处理的角色待处理记录；两类记录在列表中明确区分。

本轮不改变既有业务状态机、不绕过现有动作接口、不新建第二套独立业务任务状态。

## 2. 已确认的业务口径

### 2.1 身份来源

用户身份唯一以 Frappe 当前会话为准：

```python
current_user = frappe.session.user
roles = frappe.get_roles(current_user)
```

前端的 `auth.user` 只用于显示姓名、账号和角色，不作为权限判断依据；接口不接受可覆盖当前身份的 `user` 参数。

“身份”由两部分组成：

1. 当前登录用户账号；
2. 当前账号在 Frappe 中的有效 LIMS 角色。

当前阶段不新增 Employee、部门或组织树映射。若后续需要按部门、检验组或代理人分派，再单独增加身份组织映射设计。

### 2.2 待办归属类型

每条待办必须返回且展示 `owner_type`：

| 类型 | 业务含义 | 判定方式 | 展示文案 |
| --- | --- | --- | --- |
| `user` | 明确指派给当前用户 | 来源单据人员字段等于 `frappe.session.user` | 指派给我 |
| `role` | 当前用户角色可以处理，但未唯一指派给某人 | 当前状态对应动作的授权角色包含当前用户角色，且没有其他用户明确占用该动作 | 我的角色待处理 |

角色待处理允许同角色的多个用户看到同一条记录，但不应被渲染成“专属个人任务”。第一阶段不引入认领锁；如后续要求一条角色待办只能由一人处理，再增加认领/转派能力。

### 2.3 什么记录可以进入待办

只有“当前用户现在需要执行一个明确业务动作”的记录进入待办。以下记录不进入：

- 已完成、已批准、已关闭、已取消且没有后续动作的记录；
- 仅用于查看的台账、统计、主数据；
- 当前用户只是创建人，但当前阶段不需要创建人动作的记录；
- 当前用户无源单据权限或无动作权限的记录；
- 来源单据是其他模块自动同步产生的派生记录，且该动作必须回到来源模块执行。例如 `HBOS Stability Result.source_test_result` 非空时，稳定性结果的提交、复核、退回、批准、修订、作废动作全部不生成稳定性待办。

同一来源单据在同一时刻至多生成一条待办，`action` 取当前状态下的唯一可执行动作；动作推进后 `todo_key` 变化，视为新待办，而不是预先列出该单据的所有可能动作。如果同一用户同时因明确指派和角色权限命中同一动作，只保留一条，优先标记为 `user`。

### 2.4 跨模块同一工作的收敛

稳定性取样样品会同时关联 `HBOS Sample`/`HBOS Sample Task` 与 `HBOS Stability Timepoint`。去重必须以检验项目为粒度，不能因样品绑定了稳定性时间点就排除整张样品的所有任务：

- 当 `HBOS Sample.sample_source` 为稳定性来源且 `stability_timepoint` 已绑定时，先获取该时间点实际配置的稳定性项目；
- 对每条 `HBOS Sample Task`，以其 `test_item` 作为基础检验项目，解析 `HBOS Stability Test Item.base_test_item` 映射。只有映射后的稳定性项目确实存在于所绑时间点时，该业务任务才不进入「我的待办」，对应工作收敛到稳定性线；
- 未建立稳定性项目映射，或映射项目不在所绑时间点中的 `HBOS Sample Task`，仍按检验业务待办展示，不得因样品级排除而消失；
- 实现必须复用 `_business_stability_items_for_timepoint(timepoint_name)` 的项目映射口径，并与所绑时间点的 `test_items` 取交集，与 `record_result` 的项目粒度守卫保持一致，不再发明样品级判定；
- `/tasks` 全局待检任务看板仍保留全部原始业务任务，不改变既有事实记录和全局查询口径。

这样只去除两个模块中真正代表同一项工作的记录，同时保留样品推进所必需的未映射检验任务。

## 3. 方案选择

### 3.1 方案 A：前端聚合现有接口

前端分别请求检验、稳定性、留样和质量接口，再在浏览器中合并。

不采用。该方案会把身份过滤、角色判断、去重和计数逻辑放到前端，容易造成权限泄漏、不同页面口径不一致和角标与列表不一致。

### 3.2 方案 B：后端派生待办聚合层（采用）

新增统一待办服务，由后端基于当前会话调用各模块适配器，返回统一的待办项和汇总数。业务单据仍是事实来源，不复制一份状态。

优点：身份和权限在服务端闭环，角标和列表共享同一口径，适合当前 LIMS 已有多状态机、多模块的结构。

### 3.3 方案 C：新建持久化 `HBOS Todo` DocType

为每条业务待办创建一条新的待办单据，并同步业务状态。

暂不采用。当前会产生双写、同步失败和状态漂移；只有在未来需要认领锁、转派、提醒、通知、SLA 和人工备注时，再将方案 B 扩展为持久化任务分配层。

## 4. 后端设计

### 4.1 服务边界

新增跨模块服务文件：

```text
apps/hb_lims_app/hb_lims_app/hbos_lims/todo_service.py
```

服务包含三层：

1. `TodoProvider`：按业务模块发现候选待办；
2. `TodoPolicy`：统一执行当前用户、角色、来源权限、动作权限、状态和去重规则；
3. `TodoQuery`：统一筛选、排序、分页和汇总。

规则数据单独放置在：

```text
apps/hb_lims_app/hb_lims_app/hbos_lims/todo_contract.py
```

`todo_contract.py` 只保存纯数据规则（来源 DocType、状态、动作、人员字段、角色、截止日提取器名称、路由键），不依赖 Frappe；与现有 `workflow_contract.py` / `stability_contract.py` 一样配套离线契约测试。`todo_service.py` 负责读取规则并执行数据库查询、权限和聚合。

不让前端直接访问数据库，也不让待办服务通过低层写入改变业务状态。

### 4.2 API 契约

#### `get_my_todo_summary`

返回侧栏角标和页面顶部汇总。身份由服务端会话确定。

```json
{
  "user": {
    "name": "user@example.com",
    "full_name": "张三"
  },
  "summary": {
    "total": 8,
    "assigned_to_me": 5,
    "role_pending": 3,
    "overdue": 1,
    "by_module": {
      "testing": 3,
      "stability": 2,
      "retention": 2,
      "quality": 1,
      "compliance": 0
    }
  },
  "generated_at": "2026-09-22T10:30:00+08:00"
}
```

#### `get_my_todos`

请求参数仅允许筛选条件，不允许传入用户身份：

```json
{
  "module": "stability",
```

`get_my_todo_summary` 返回未过滤的个人全局摘要，供侧栏角标使用；`get_my_todos` 返回的统计字段命名为 `filtered_summary`，只反映本次筛选条件下的结果。两者不共用 `summary` 键名。服务端统一计算逾期，不由浏览器根据本地时区重复计算。

### 4.3 模块适配规则

| 模块 | 主要来源 | 明确指派匹配 | 角色待处理匹配 | 首期动作来源 |
| --- | --- | --- | --- | --- |
| 检验业务 | `HBOS Sample Task`、`HBOS Test Result` | `assignee`、结果相关人员 | 状态对应检验/复核/批准角色 | 现有 `start_task`、`submit_result`、`review_result`、`approve_result`；只排除 §2.4 定义的、已映射且存在于所绑稳定性时间点的项目任务 |
| 稳定性管理 | `HBOS Stability Timepoint`、`HBOS Stability Result` | `sample_by`、`test_by`、`evaluator` | 当前时间点/结果状态对应动作角色 | 现有取样、检测、结果提交/复核/批准动作；`source_test_result` 非空的结果全部排除 |
| 留样管理 | 观察、使用申请、处理申请及相关记录 | `observer`、`applicant`、`executed_by`、`disposal_by`、`monitor_by` 等 | QC、QA、QM 等审批状态 | 现有观察、库存确认、QC/QA/QM、执行/监督动作 |
| 质量与报告 | 有明确业务动作的报告或质量流程记录 | 来源单据人员字段 | 状态对应复核/批准角色 | 复用现有服务动作 |
| 合规审计 | 仅纳入未来明确配置为待处理的审计任务 | 显式责任人 | 显式角色动作 | 不把只读审计查询计入待办 |

具体状态到动作的映射必须在实现阶段形成单一规则表，不允许散落在 Vue 模板或多个服务函数中。

### 4.3.1 统一字段映射

统一待办字段必须由模块适配器明确提供，不能在聚合层猜测字段含义：

| 统一字段 | 检验业务 | 稳定性管理 | 留样管理 | 缺省口径 |
| --- | --- | --- | --- | --- |
| `priority` | `HBOS Sample Task.priority` | 当前 DocType 无优先级字段，返回 `null` | 当前申请/观察对象无统一优先级字段，返回 `null` | `null` 按普通优先级排序 |
| `due_at` | `HBOS Sample Task.due_date` | 取样动作使用服务层 `_effective_sample_due`；检测执行动作使用 `_effective_test_due`；稳定性结果的提交、复核、退回、批准、修订、作废动作返回 `null` | 观察使用 `HBOS Retention Sample.next_obs_due_date`；处理执行使用 `HBOS Retention Disposal Apply.deadline`；审批/使用申请暂无业务截止日时返回 `null` | 不使用创建日期代替截止日 |
| `is_overdue` | 服务端按 `due_date` 计算 | 取样/检测执行动作必须使用有效截止日：已批准延期顺延日，否则政策上限；不得直接查询不存在的 `effective_*_due` 数据库列。稳定性结果动作因 `due_at = null`，固定返回 `false` | 服务端按上述派生截止日计算 | `due_at` 为空时为 `false` |

稳定性适配器必须复用 `stability_service.py` 的 `_effective_sample_due` / `_effective_test_due` 及其延期政策，不在待办服务中复制计算逻辑，也不得把 `plan_sample_date` 或 `plan_test_date` 直接当作最终逾期日。

### 4.4 权限与安全

- 当前用户只从 `frappe.session.user` 读取；忽略或拒绝请求中的 `user` 参数。
- 动作权限是主闸门：必须按当前状态和作用域执行 `wf.action_allowed` / 现有 `_check_action` 规则；没有动作权限的记录不得进入待办，即使用户拥有来源单据读取权限。
- 来源单据读取权限是第二道边界：返回前仍需检查具体 DocType/记录的读取权限，不能把“有读权限”当成“可处理”。
- 待办接口只负责发现和展示，不替代现有业务动作接口。
- 用户点击操作后，仍由原业务 API 再次执行角色、状态、本人/角色和 SoD 校验。
- 查询优先使用受权限约束的 Frappe 读取方式；如必须使用 SQL，必须补齐来源权限和字段范围校验。
- 记录来源单据、动作、归属类型和候选角色，便于问题追溯；真正执行动作仍由现有审计机制记录。

`Administrator` 和 `System Manager` 不因为宽泛管理权限自动获得所有业务角色待办：

- 必须先按当前用户名显式特判 `Administrator`：其 `role_pending` 业务角色集合恒为空，只保留明确指派给 `Administrator` 的任务；
- 不得仅通过从角色集合中删除 `System Manager` 或同名管理角色来处理 `Administrator`，因为 `frappe.get_roles("Administrator")` 会返回全部 LIMS 业务角色；
- 对非 `Administrator` 账号，`System Manager` 等宽泛管理角色本身不参与 `role_pending` 展开；如果该账号另有明确的 LIMS 业务角色，则仅按这些业务角色匹配角色待办；
- 需要查看全局任务时使用 `/tasks` 或后续专门的管理视图，不通过“我的待办”隐式放大范围。

## 5. 前端设计

### 5.1 路由与现有页面关系

新增：

```text
/my-todos
```

保留：

```text
/tasks       待检任务看板，面向全局任务查询和管理
```

侧栏「我的待办」改为跳转 `/my-todos`。侧栏「待检任务看板」仍跳转 `/tasks`，两者不再共用语义。

### 5.2 页面结构

页面从上到下包含：

1. 页面标题「我的待办」；
2. 当前身份信息：姓名、账号、有效 LIMS 角色；
3. 汇总：全部待办、指派给我、我的角色待处理、已逾期；
4. 模块筛选：全部、检验业务、稳定性管理、留样管理、质量与报告、合规审计；
5. 条件筛选：归属类型、状态、优先级、逾期、关键词；
6. 统一待办列表；
7. 分页、刷新时间和手动刷新。

列表每行必须显示：

- 模块标签；
- 待办标题和来源单号；
- 当前状态；
- `指派给我` 或 `我的角色待处理` 标签；
- 责任人/候选角色；
- 优先级和截止时间；
- 一个明确的业务动作按钮。

角色待处理采用不同于个人指派的标签颜色和辅助说明，避免用户误以为该任务已独占。

### 5.3 交互规则

- 行点击进入来源业务页面，并带上 `route_params` 定位到具体记录；
- 业务操作按钮调用来源模块现有 API，不在待办页复制业务表单；
- 操作成功后刷新当前列表和侧栏摘要；
- 401/403 显示会话失效或无权限，不显示伪造的成功状态；
- 空列表显示“当前身份下暂无待办”，并保留模块筛选和刷新入口；
- 接口失败保留上一次成功结果，同时显示可重试提示；首次加载失败则显示错误空状态；
- 列表默认排序：逾期优先、截止日期升序、优先级降序、更新时间降序；
- 「我的待办」红色角标使用未过滤的 `get_my_todo_summary.summary.total`，为 0 时隐藏；不再叠加稳定性工作台全局 KPI；列表筛选使用 `filtered_summary`。
- 稳定性子项「取样与检测计划」「结果录入与趋势」保留模块级全局工作量角标，继续使用琥珀色并明确属于模块工作量，不计入“我的待办”；稳定性管理分组不再显示汇总全局角标，避免与个人角标混淆。

深链不是任意 query 参数透传，而是前后端共同维护的路由契约。第一阶段必须补齐待办来源对应视图的解析：

| 模块 | 目标页面 | 深链参数 | 前端处理要求 |
| --- | --- | --- | --- |
| 检验业务 | `/tasks` | `scope=mine`、`task` | `TaskBoardView` 解析 `scope=mine`，由后端按当前会话身份限制为“指派给我 + 我的角色待处理”，再定位任务并切换到对应状态列；不接受 query 中的用户值作为身份 |
| 稳定性 | `/stability/schedule` | `timepoint` | 定位时间点并打开详情 |
| 稳定性 | `/stability/results` | `timepoint`、`result` | 定位时间点/结果并打开结果区域 |
| 稳定性 | `/stability/samples` | `sample` | 定位稳定性样品并打开详情 |
| 稳定性 | `/stability/study`、`/stability/reports`、`/stability/ops` | 对应 `notice`/`protocol`/`report`/`change`/`fault`/`equipment` | 加载后定位对应记录或抽屉 |
| 留样 | `/retention/samples`、`/retention/observations`、`/retention/usage`、`/retention/disposal` | `sample`、`observation`、`usage`、`disposal` | 加载后定位台账行并打开详情/操作抽屉 |

适配器只能返回已经有解析实现的深链；没有解析能力时返回列表路由并显示来源单号，不得返回点击后无效果的伪深链。深链解析和回归测试属于第一阶段范围，不是后续补漏。

`scope=mine` 是「我的待办」进入 `/tasks` 时的保留语义，必须复用统一待办的检验业务身份谓词，不能等价为客户端传入 `assignee=<user>`。用户从常规侧栏直接进入不带 `scope` 的 `/tasks` 时，仍保持现有全局看板口径。

### 5.4 刷新策略

在以下时机刷新摘要或列表：

- 登录完成后；
- 进入 `/my-todos` 时；
- 待办动作成功后；
- 浏览器窗口重新获得焦点时；
- 仅当 `/my-todos` 页面可见且浏览器标签页处于前台时，才允许按 60 秒轮询一次；普通业务页面不启动待办轮询。

轮询失败不清空已有数据；注销或会话失效时清除个人待办状态。

服务端摘要使用 `(current_user, business_roles_hash)` 作为缓存键，短 TTL 目标为 30 秒；待办相关业务动作提交成功后调用统一失效钩子删除当前用户缓存。列表查询不使用全局缓存，避免筛选结果串用户。

## 7. 验收与测试标准

### 后端

- 用户 A 看不到用户 B 的明确指派任务；
- 请求伪造其他用户参数无效；
- 多角色用户能看到各角色待处理任务；
- 明确指派和角色命中同一动作时只返回一条；
- 已完成、取消、关闭任务不再返回；
- 状态变化后摘要与列表同步减少或增加；
- 无来源权限或无动作权限时不返回；
- 逾期、优先级、分页、关键词筛选口径稳定；
- 每个返回项都能定位到有效来源单据和动作；
- 已同步的稳定性结果（`source_test_result` 非空）不产生任何稳定性待办动作；
- 绑定稳定性时间点的业务样品中，已映射且存在于该时间点的项目任务不与稳定性线重复出现；未映射或不在该时间点的项目任务仍在检验业务待办中可见；
- `Administrator` 即使通过 `frappe.get_roles` 获得全部 LIMS 角色，也不产生任何 `role_pending` 待办，只返回明确指派给该账号的任务；
- 稳定性结果类动作返回 `due_at = null`、`is_overdue = false`；
- 在 1000 条来源单据规模下，摘要和分页列表满足约定响应时间，并有查询/缓存证据；
- 后台非 `/my-todos` 可见页面不启动待办轮询。

### 前端

- 「我的待办」进入 `/my-todos`，不再进入全局 `/tasks`；
- 角标与 `get_my_todo_summary.summary.total` 一致；
- `指派给我` 与 `我的角色待处理` 视觉和文本可区分；
- 模块筛选、归属筛选、空状态、错误重试、刷新状态可用；
- 点击列表项能进入正确业务页面；
- 从「我的待办」进入 `/tasks?scope=mine&task=...` 时，看板只加载当前会话下“指派给我 + 我的角色待处理”范围并定位目标任务；普通 `/tasks` 仍保持全局口径；
- 检验、稳定性和留样首期来源页面的深链参数均能定位记录或打开详情；不支持的深链降级到可用列表并显示来源单号；
- 操作完成后列表和角标刷新；
- 未认证、无权限和后端异常不显示虚假数量；
- 375px 宽度下列表可读且无页面级横向溢出。
