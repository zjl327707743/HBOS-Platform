# 我的待办身份绑定设计

> 状态：待 Owner 审阅
>
> 日期：2026-09-22
>
> 范围：M2-LIMS 独立前端与 `hb_lims_app` 后端

## 1. 目标与背景

当前侧栏「我的待办」角标把稳定性时间点的全局统计与待检任务入口混在一起：

- `pendingCount` 仍是前端占位值 `0`；
- 稳定性角标来自全量时间点状态统计；
- `/tasks` 加载的是未带过滤条件的全局「待检任务看板」；
- 用户点击「我的待办」后无法看到与当前身份绑定的统一任务清单。

本设计将「我的待办」改造成跨模块个人待办中心。用户点击后看到当前登录身份下所有需要完成的任务，任务来源可以是明确指派给当前用户的记录，也可以是当前用户所拥有角色能够处理的角色待处理记录；两类记录在列表中明确区分。

本轮不改变既有业务状态机、不绕过现有动作接口、不新建第二套独立业务任务状态。

## 2. 已确认的业务口径

### 2.1 身份来源

用户身份唯一以 Frappe 当前会话为准：

```python
current_user = frappe.session.user
roles = frappe.get_roles(current_user)
```

前端的 `auth.user` 只用于显示姓名、账号和角色，不作为权限判断依据；接口不接受可覆盖当前身份的 `user` 参数。

“身份”由两部分组成：

1. 当前登录用户账号；
2. 当前账号在 Frappe 中的有效 LIMS 角色。

当前阶段不新增 Employee、部门或组织树映射。若后续需要按部门、检验组或代理人分派，再单独增加身份组织映射设计。

### 2.2 待办归属类型

每条待办必须返回且展示 `owner_type`：

| 类型 | 业务含义 | 判定方式 | 展示文案 |
| --- | --- | --- | --- |
| `user` | 明确指派给当前用户 | 来源单据人员字段等于 `frappe.session.user` | 指派给我 |
| `role` | 当前用户角色可以处理，但未唯一指派给某人 | 当前状态对应动作的授权角色包含当前用户角色，且没有其他用户明确占用该动作 | 我的角色待处理 |

角色待处理允许同角色的多个用户看到同一条记录，但不应被渲染成“专属个人任务”。第一阶段不引入认领锁；如后续要求一条角色待办只能由一人处理，再增加认领/转派能力。

### 2.3 什么记录可以进入待办

只有“当前用户现在需要执行一个明确业务动作”的记录进入待办。以下记录不进入：

- 已完成、已批准、已关闭、已取消且没有后续动作的记录；
- 仅用于查看的台账、统计、主数据；
- 当前用户只是创建人，但当前阶段不需要创建人动作的记录；
- 当前用户无源单据权限或无动作权限的记录。

同一来源单据的不同动作分别用不同 `todo_key` 表示；如果同一用户同时因明确指派和角色权限命中同一动作，只保留一条，优先标记为 `user`。

## 3. 方案选择

### 3.1 方案 A：前端聚合现有接口

前端分别请求检验、稳定性、留样和质量接口，再在浏览器中合并。

不采用。该方案会把身份过滤、角色判断、去重和计数逻辑放到前端，容易造成权限泄漏、不同页面口径不一致和角标与列表不一致。

### 3.2 方案 B：后端派生待办聚合层（采用）

新增统一待办服务，由后端基于当前会话调用各模块适配器，返回统一的待办项和汇总数。业务单据仍是事实来源，不复制一份状态。

优点：身份和权限在服务端闭环，角标和列表共享同一口径，适合当前 LIMS 已有多状态机、多模块的结构。

### 3.3 方案 C：新建持久化 `HBOS Todo` DocType

为每条业务待办创建一条新的待办单据，并同步业务状态。

暂不采用。当前会产生双写、同步失败和状态漂移；只有在未来需要认领锁、转派、提醒、通知、SLA 和人工备注时，再将方案 B 扩展为持久化任务分配层。

## 4. 后端设计

### 4.1 服务边界

新增跨模块服务文件：

```text
apps/hb_lims_app/hb_lims_app/hbos_lims/todo_service.py
```

服务包含三层：

1. `TodoProvider`：按业务模块发现候选待办；
2. `TodoPolicy`：统一执行当前用户、角色、来源权限、动作权限、状态和去重规则；
3. `TodoQuery`：统一筛选、排序、分页和汇总。

不让前端直接访问数据库，也不让待办服务通过低层写入改变业务状态。

### 4.2 API 契约

#### `get_my_todo_summary`

返回侧栏角标和页面顶部汇总。身份由服务端会话确定。

```json
{
  "user": {
    "name": "user@example.com",
    "full_name": "张三"
  },
  "summary": {
    "total": 8,
    "assigned_to_me": 5,
    "role_pending": 3,
    "overdue": 1,
    "by_module": {
      "testing": 3,
      "stability": 2,
      "retention": 2,
      "quality": 1,
      "compliance": 0
    }
  },
  "generated_at": "2026-09-22T10:30:00+08:00"
}
```

#### `get_my_todos`

请求参数仅允许筛选条件，不允许传入用户身份：

```json
{
  "module": "stability",
  "owner_type": "role",
  "status": "",
  "priority": "",
  "overdue": false,
  "keyword": "",
  "limit": 20,
  "offset": 0
}
```

返回：

```json
{
  "items": [
    {
      "todo_key": "HBOS Sample Task:HBOS-TSK-2026-00001:start_task",
      "module": "testing",
      "module_label": "检验业务",
      "source_doctype": "HBOS Sample Task",
      "source_name": "HBOS-TSK-2026-00001",
      "title": "开始检验：阿莫西林批次 A01",
      "action": "start_task",
      "action_label": "开始检验",
      "status": "已分配",
      "status_label": "已分配",
      "owner_type": "user",
      "owner_label": "指派给我",
      "assignee": "user@example.com",
      "candidate_roles": ["LIMS Analyst"],
      "priority": "加急",
      "due_at": "2026-09-23",
      "is_overdue": false,
      "route": "/tasks",
      "route_params": {"task": "HBOS-TSK-2026-00001"},
      "modified_at": "2026-09-22T09:20:00+08:00"
    }
  ],
  "total": 8,
  "summary": {},
  "generated_at": "2026-09-22T10:30:00+08:00"
}
```

`summary` 可在列表接口中复用摘要，但其数字必须与同一次查询的过滤条件一致。服务端统一计算逾期，不由浏览器根据本地时区重复计算。

### 4.3 模块适配规则

| 模块 | 主要来源 | 明确指派匹配 | 角色待处理匹配 | 首期动作来源 |
| --- | --- | --- | --- | --- |
| 检验业务 | `HBOS Sample Task`、`HBOS Test Result` | `assignee`、结果相关人员 | 状态对应检验/复核/批准角色 | 现有 `start_task`、`submit_result`、`review_result`、`approve_result` |
| 稳定性管理 | `HBOS Stability Timepoint`、`HBOS Stability Result` | `sample_by`、`test_by`、`evaluator` | 当前时间点/结果状态对应动作角色 | 现有取样、检测、结果提交/复核/批准动作 |
| 留样管理 | 观察、使用申请、处理申请及相关记录 | `observer`、`applicant`、`executed_by`、`disposal_by`、`monitor_by` 等 | QC、QA、QM 等审批状态 | 现有观察、库存确认、QC/QA/QM、执行/监督动作 |
| 质量与报告 | 有明确业务动作的报告或质量流程记录 | 来源单据人员字段 | 状态对应复核/批准角色 | 复用现有服务动作 |
| 合规审计 | 仅纳入未来明确配置为待处理的审计任务 | 显式责任人 | 显式角色动作 | 不把只读审计查询计入待办 |

具体状态到动作的映射必须在实现阶段形成单一规则表，不允许散落在 Vue 模板或多个服务函数中。

### 4.4 权限与安全

- 当前用户只从 `frappe.session.user` 读取；忽略或拒绝请求中的 `user` 参数。
- 返回前同时检查来源单据读取权限和动作权限。
- 待办接口只负责发现和展示，不替代现有业务动作接口。
- 用户点击操作后，仍由原业务 API 再次执行角色、状态、本人/角色和 SoD 校验。
- 查询优先使用受权限约束的 Frappe 读取方式；如必须使用 SQL，必须补齐来源权限和字段范围校验。
- 记录来源单据、动作、归属类型和候选角色，便于问题追溯；真正执行动作仍由现有审计机制记录。

## 5. 前端设计

### 5.1 路由与现有页面关系

新增：

```text
/my-todos
```

保留：

```text
/tasks       待检任务看板，面向全局任务查询和管理
```

侧栏「我的待办」改为跳转 `/my-todos`。侧栏「待检任务看板」仍跳转 `/tasks`，两者不再共用语义。

### 5.2 页面结构

页面从上到下包含：

1. 页面标题「我的待办」；
2. 当前身份信息：姓名、账号、有效 LIMS 角色；
3. 汇总：全部待办、指派给我、我的角色待处理、已逾期；
4. 模块筛选：全部、检验业务、稳定性管理、留样管理、质量与报告、合规审计；
5. 条件筛选：归属类型、状态、优先级、逾期、关键词；
6. 统一待办列表；
7. 分页、刷新时间和手动刷新。

列表每行必须显示：

- 模块标签；
- 待办标题和来源单号；
- 当前状态；
- `指派给我` 或 `我的角色待处理` 标签；
- 责任人/候选角色；
- 优先级和截止时间；
- 一个明确的业务动作按钮。

角色待处理采用不同于个人指派的标签颜色和辅助说明，避免用户误以为该任务已独占。

### 5.3 交互规则

- 行点击进入来源业务页面，并带上 `route_params` 定位到具体记录；
- 业务操作按钮调用来源模块现有 API，不在待办页复制业务表单；
- 操作成功后刷新当前列表和侧栏摘要；
- 401/403 显示会话失效或无权限，不显示伪造的成功状态；
- 空列表显示“当前身份下暂无待办”，并保留模块筛选和刷新入口；
- 接口失败保留上一次成功结果，同时显示可重试提示；首次加载失败则显示错误空状态；
- 列表默认排序：逾期优先、截止日期升序、优先级降序、更新时间降序；
- 侧栏角标只显示 `summary.total`，为 0 时隐藏；不再叠加稳定性工作台全局 KPI。

### 5.4 刷新策略

在以下时机刷新摘要或列表：

- 登录完成后；
- 进入 `/my-todos` 时；
- 待办动作成功后；
- 浏览器窗口重新获得焦点时；
- 页面停留期间可按 60 秒轮询一次。

轮询失败不清空已有数据；注销或会话失效时清除个人待办状态。

## 6. 实施边界与阶段

### 第一阶段：统一查询与展示

- 新增后端待办聚合服务和接口；
- 完成检验、稳定性、留样模块的规则适配；
- 新增 `/my-todos` 页面；
- 侧栏角标改用统一摘要；
- 保留 `/tasks` 全局待检任务看板；
- 不新增持久化 Todo DocType；
- 不实现角色待办认领和转派。

### 第二阶段：任务认领与通知（后续单独立项）

仅在 Owner 确认存在“角色任务必须唯一归属”的业务需求后实施：

- 角色待办认领/释放；
- 代理人和转派；
- 待办备注和处理历史；
- 站内通知、邮件或飞书通知；
- SLA、提醒和升级。

## 7. 验收与测试标准

### 后端

- 用户 A 看不到用户 B 的明确指派任务；
- 请求伪造其他用户参数无效；
- 多角色用户能看到各角色待处理任务；
- 明确指派和角色命中同一动作时只返回一条；
- 已完成、取消、关闭任务不再返回；
- 状态变化后摘要与列表同步减少或增加；
- 无来源权限或无动作权限时不返回；
- 逾期、优先级、分页、关键词筛选口径稳定；
- 每个返回项都能定位到有效来源单据和动作。

### 前端

- 「我的待办」进入 `/my-todos`，不再进入全局 `/tasks`；
- 角标与 `get_my_todo_summary.summary.total` 一致；
- `指派给我` 与 `我的角色待处理` 视觉和文本可区分；
- 模块筛选、归属筛选、空状态、错误重试、刷新状态可用；
- 点击列表项能进入正确业务页面；
- 操作完成后列表和角标刷新；
- 未认证、无权限和后端异常不显示虚假数量；
- 375px 宽度下列表可读且无页面级横向溢出。

## 8. 依赖与待确认事项

实现前需要按现有状态机逐项完成“状态 → 动作 → 人员字段/角色 → 路由”的规则表，并为每个模块补充正向和越权测试。

本规格已确定的默认口径是：

> 「我的待办」合并显示“指派给我”和“我的角色待处理”，但在每条列表记录和汇总数字中清楚区分；角色待处理暂不独占、不自动认领。
