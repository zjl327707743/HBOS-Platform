### 2.4 为什么「复制 75 个 DocType」不可行（路线 C 的否决依据）

ERPNext 的库存 DocType 不是自包含的定义，其控制器深度依赖 ERPNext 全栈。以容器内 `erpnext/stock/doctype/stock_entry/stock_entry.py` 的头部 import 为证：

```
import erpnext
from erpnext.accounts.general_ledger import process_gl_map
from erpnext.accounts.utils import get_account_currency
from erpnext.buying.utils import check_on_hold_or_closed_status
from erpnext.manufacturing.doctype.bom.bom import (...)
from erpnext.setup.doctype.brand.brand import get_brand_defaults
from erpnext.stock.stock_ledger import NegativeStockError, get_previous_sle, get_valuation_rate
from erpnext.controllers.stock_controller import StockController
```

`item.py` 同样依赖 `erpnext.controllers.item_variant`、`erpnext.stock.doctype.item_default.item_default`、`erpnext.stock.utils`。

**后果**：把 75 个 DocType 的 JSON 定义复制到新 App，只能得到「能建表、能打开表单」的空壳——保存单据不会生成 `Stock Ledger Entry`，没有移动平均/先进先出估价，没有总账联动，`Bin` 不会更新。要让它真正能算库存，必须把控制器一并复制，那等于 fork ERPNext，与「不动原代码」直接冲突。

因此：**「独立库存数据」不应通过复制代码实现，而应通过 ERPNext 原生的隔离维度实现。**

### 2.5 站点路由机制（决定多站点可行性）

Frappe 站点解析顺序（容器内 `frappe/app.py:178`）：

```python
site = _site or request.headers.get("X-Frappe-Site-Name") or get_site_name(request.host)
```

即：**`X-Frappe-Site-Name` 请求头优先于主机名**。当前 nginx 为每个请求固定注入该头：

- `frontend` 容器生成的 `/etc/nginx/conf.d/frappe.conf` 内有两处 `proxy_set_header X-Frappe-Site-Name frontend;`
- `server_name frontend;`
- 来源：`docker-compose.yml` 中 `frontend` 服务的环境变量 `FRAPPE_SITE_NAME_HEADER: ${FRAPPE_SITE_NAME_HEADER}`，当前 `.env` 值为 `frontend`。

镜像自带的 `nginx-entrypoint.sh` 明确支持该变量为空时回退到 `$host`（第 24–28 行、第 47 行 evnsubst）：

```
if [[ -z "$FRAPPE_SITE_NAME_HEADER" ]]; then
  echo 'FRAPPE_SITE_NAME_HEADER defaulting to $host'
  export FRAPPE_SITE_NAME_HEADER='$host'
```

**含义**：一个前端容器通过 `FRAPPE_SITE_NAME_HEADER` 只能指向**一个**站点。要让第二个站点可被浏览器访问，必须新增一个注入不同该头值的前端入口。

另：本版本 Frappe 未发现 `serve_default_site` 相关实现（全仓库 `--include='*.py'` 检索无命中），`get_site_name()` 仅做「去掉端口号」。这意味着**一旦切到主机名路由，现有 `http://localhost:8080` 会因「无名为 `localhost` 的站点」而失效**。

## 4. 推荐方案 A2 详细设计

### 4.1 站点定义

| 项 | 取值 |
| --- | --- |
| 站点名 | `stock` |
| 安装 App | `frappe`、`erpnext`、`hb_stock_app`（**不装** hrms、hb_attendance_app） |
| 数据源 | 同一 MariaDB 实例（`db` 服务），**独立 schema** |
| 用户体系 | 独立（该站点的 Administrator + 自建用户） |
| 公司主体 | `HAIBIN`（同法人，CNY / China，语言 zh） |

不安装 hb_attendance_app 的理由：它是考勤专用 App，与库存无关；不装可避免把考勤的定时任务、飞书推送、考勤 DocType 带进库存站点。反之，hb_stock_app **不装到 `frontend` 站点**，考勤站点零污染。

**App 装载方式（沿用 `hb_attendance_app` 既有模式）**：

- 源码目录 `apps/hb_stock_app/`，与 `apps/hb_attendance_app/` 平级；
- 在每个 frappe 服务的 volumes 中增加挂载 `./apps/hb_stock_app:/home/frappe/frappe-bench/apps/hb_stock_app`；
- 在每个 frappe 服务的 `PYTHONPATH` 末尾追加 `:/home/frappe/frappe-bench/apps/hb_stock_app`；
- `sites/apps.txt` 由 `configurator` 的 `ls -1 apps` 自动生成，无需手工维护；
- `sites/apps.json` 当前只登记 `frappe`/`erpnext`（`hb_attendance_app` 也未登记），故新 App 同样无需登记。

涉及的服务：`backend`、`configurator`、`create-site`、`queue-long`、`queue-short`、`scheduler`、`websocket`、`frontend`、新增的 `frontend-stock`。

### 4.1.1 hb_stock_app 的职责边界

该 App **只承载配置层内容，不碰业务逻辑**：

- 一个 Workspace 定义：`海滨库存`，复制 ERPNext 原生 `Stock` 工作台的 72 条链接与 1 个图表；
- 一个 `after_migrate` 钩子：幂等同步该 Workspace（新建或更新），复用 M1-FIX-B4 已验证的模式；
- **不新建任何 DocType**，**不重写任何库存逻辑**，**不修改 ERPNext 源码**。

App 内文件结构（最小，层级对齐 `hb_attendance_app` 现有布局）：

```
apps/hb_stock_app/                     # 仓库内源码目录
  pyproject.toml
  README.md
  hb_stock_app/                        # Python 包（同名内层目录）
    __init__.py
    hooks.py                           # after_migrate 指向 setup.after_migrate
    modules.txt                        # HBOS Stock
    hbos_stock/                        # 模块目录（module folder）
      __init__.py
      setup.py                         # after_migrate 幂等同步工作台
      workspace/
        海滨库存/海滨库存.json
```

## 4.1.2 站点初始化（脚本程序化）

`bench new-site stock --install-app erpnext` 之后，通过一段一次性脚本在该站点内创建：

- `Company`：`HAIBIN`（CNY / China，与 `frontend` 站点口径一致）；
- 默认 `Warehouse` 树：与 `frontend` 现有 5 个仓库同名同口径（`All Warehouses - H`、`Finished Goods - H`、`Goods In Transit - H`、`Stores - H`、`Work In Progress - H`）；
- 保留 ERPNext 预置的 `Item Group`、`UOM`、`Price List`。

**注意**：新建站点默认无 `Item` 数据（`frontend` 站点也是 0 条），因此**不需要物料迁移**。若 Owner 后续要把 `frontend` 的物料档案搬过来，那是独立需求，不在本方案内。

## 4.2 浏览器访问路径（本方案最关键的一处改动）

**做法**：新增一个与现有 `frontend` 服务同构的 `frontend-stock` 服务，仅两处不同：

- 环境变量 `FRAPPE_SITE_NAME_HEADER: stock`
- 端口映射 `"${STOCK_HTTP_PORT}:8080"`（建议 `8082:8080`；已实测 8082、8083 当前均空闲，8080 被 frappe 前端占用）

**结果**：

| 地址 | 站点 | 影响 |
| --- | --- | --- |
| `http://localhost:8080` | `frontend`（现有考勤站点） | **完全不变，零回归** |
| `http://localhost:8082` | `stock`（新库存站点） | 新增 |

**为什么不选「切换为 `$host` 主机名路由」**：该做法只需清空 `FRAPPE_SITE_NAME_HEADER`，看起来更省事，但按 2.5 的核查结论，本版本无 `serve_default_site` 回退，切换后 `http://localhost:8080` 会因不存在名为 `localhost` 的站点而失效——等于拿现有考勤站点的可用性去换新站点，不可接受。**新增前端入口是纯增量改动，风险显著更低。**

### 4.3 真正的隔离边界（必须说清哪些隔离、哪些没有）

**真隔离**：

- 所有业务数据（Item、Warehouse、Stock Entry、Stock Ledger Entry、Bin、Serial No、Batch）完全独立，互不可见。
- 用户、角色、权限、会话独立。
- 备份/恢复可独立执行。
- 装什么 App 独立（库存站点不装考勤 App）。

**未隔离（同栈共享）**：

- 同一个 MariaDB 服务实例、同一个 `db-data` 卷（不同 schema）。
- 同一个 Redis 实例（cache/queue）。
- 同一个 `sites`、`logs`、`assets-data` 卷，队列 worker 与 scheduler 容器。
- 同一份 ERPNext 源码挂载。

**跨站点副作用（必须评估）**：

- `scheduler` 容器执行 `bench schedule`，会遍历 `sites/` 下**所有**站点调度任务。新站点会带入 ERPNext 自身的定时任务（如自动对账、订阅、清理类任务）。库存站点不装考勤 App，因此**不会**触发海滨考勤的 cron（`0 9 * * *` 等）——这一点已确认，因为该 cron 定义在 `hb_attendance_app/hooks.py`。
- 队列 worker 会同时消费两个站点的任务，属正常行为。

### 4.4 实施步骤（每步可独立回滚）

1. **备份**：对现有 `frontend` 站点做一次完整备份（`bench --site frontend backup --with-files`），留存恢复点。
2. **建 hb_stock_app 骨架**：在 `apps/hb_stock_app/` 落地最小 App（pyproject / hooks / modules / workspace JSON），先不装机。
3. **改 compose（App 挂载）**：为全部 frappe 服务补 `./apps/hb_stock_app` 卷挂载与 `PYTHONPATH` 追加。
4. **建站**：在 backend 容器内 `bench new-site stock --admin-password=<本地密码> --install-app erpnext`。**注意不要加 `--set-default` 参数**（该参数是布尔开关，不是键值对，写 `--set-default=false` 会报错），避免抢走 `frontend` 的默认站点身份。
5. **装 hb_stock_app**：`bench --site stock install-app hb_stock_app`，再 `bench --site stock migrate`，`after_migrate` 生成「海滨库存」工作台。
6. **站点初始化**：运行 4.1.2 的一次性脚本，创建 `HAIBIN` 公司与 5 个默认仓库。
7. **加前端入口**：按 4.2 在 compose 中新增 `frontend-stock` 服务与 `STOCK_HTTP_PORT`，追加 `8082:8080` 端口。
8. **验证**：`http://localhost:8082/app` 可登录并进入「海滨库存」工作台；`http://localhost:8080/app` 仍正常；`frontend` 站点 `list-apps` 不含 `hb_stock_app`。
9. **沉淀备份方式**：为 `stock` 站点补一条备份命令/脚本说明。

### 4.5 回滚

- 建站后未使用 → `bench drop-site stock`，移除 `frontend-stock` 服务与端口映射，回到当前状态。
- 已产生数据 → 从 4.4 第 1 步的备份恢复 `frontend`；`stock` 站点数据按需导出后 drop。

**禁止动作**（沿用 M1-FIX 全程禁令）：不执行 `docker compose down -v`，不删除 Docker volume，不重建 `frontend` site。

### 4.6 风险清单

| 风险 | 等级 | 说明 |
| --- | --- | --- |
| 新站点抢占默认站点身份 | 中 | 建站时误加 `--set-default` 会让 `frontend` 不再是默认站点。缓解：明确不加该参数，建站后核对 `common_site_config.json` 的 `default_site` 仍为 `frontend`。 |
| compose 改动引入现有站点回归 | 中 | 缓解：新前端入口为纯增量服务，不触碰现有 `frontend` 服务定义；App 挂载与 PYTHONPATH 追加为纯增量。 |
| PYTHONPATH 变更影响现有站点 | 低 | 缓解：只在末尾追加新 App 路径，不改动既有条目；改后先 `docker compose config` 校验，再滚动重启，最后回归验证 `http://localhost:8080/app`。 |
| 端口冲突 | 低 | 已实测 8082 空闲；若届时被占用，改 `STOCK_HTTP_PORT` 即可。 |
| 备份策略缺位 | 中 | 当前仓库只有 `frontend` 的备份习惯，新站点若无人备份会形成单点。缓解：4.4 第 9 步。 |
| 磁盘增长 | 低 | 第二套 schema + 文件。 |
| 权限/账号混乱 | 中 | 两个站点的 Administrator 密码不同，需登记保管方式（不得进 Git）。 |
| 新 App 被误装到考勤站点 | 低 | 缓解：只对 `stock` 站点执行 `install-app hb_stock_app`；4.4 第 8 步显式核验 `frontend` 的 `list-apps`。 |
