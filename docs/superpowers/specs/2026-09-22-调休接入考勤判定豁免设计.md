## 1. 目标

把**已核实的调休日**接入考勤判定：这些天不再判缺勤，并在看板 / 9 点飞书卡片上按「调休」而非「未打卡」呈现。

**这是调休第一次真正改变考勤结果。** 第一阶段只出结论、不动数据；本阶段起，核实通过的调休日会产生真实的豁免效果。

### 本轮范围

- 新建查询入口，统一「已通过 + 已核实」的过滤口径。
- 接入考勤判定（`api.py`）：已核实的调休日并入豁免集合。
- 接入看板 / 9 点卡片：调休人员落 `leave` 桶，不再被列为「未打卡」。
- 调休日本人生成的考勤记录**标记为「调休」**。
- 顺带修复 F3（重新解析失效键不含 `employee`）——本阶段起豁免是真的，该缺陷会变成「用甲的加班给乙换休」。

### 范围外（明确不做）

- 不做终态重新核实机制（Owner 2026-09-22 决定：暂不做，先观察）。
- 不做加班模块本体、不做额度校验。
- 不做按小时/半天的调休时段判定。
- 不改 `pairing.py`、`board_stats.py`、月度汇总报表、考勤结果报表。
- 不改第一阶段的三个调度任务。

## 2. 为什么现在才做（决策背景）

第一阶段刻意不接判定，理由是「先确认 LLM 解析准不准，再让它产生后果」。实测结果支撑进入本阶段：

| 验收项 | 结果 |
| --- | --- |
| 多行批量说明归属准确率 | 36 条中 **35 条 100% 正确**（97%） |
| 核实结论与考勤数据自洽性 | **违规 0 条**（40 条已核实全部加班日通过 / 53 条不通过全部有缺失） |
| 判据敞口（2026-07-28/29/30） | 实测**为零**——无任何真实主张的加班日落在该窗口 |

即：**结论本身是可信的**，可以开始产生后果。

## 3. 数据流

```
HBOS Rest Leave Record
  WHERE approval_status = '已通过'          ← 前提一（F2）
    AND verify_status  = '已核实'           ← 前提二
        ↓ 展开 start_date ~ end_date 日期区间
   已核实的调休日集合 {employee: {日期}}
        ↓
   ┌────┴────────────────┐
   ↓                     ↓
考勤判定（api.py）      看板 / 9 点卡片
并入豁免集合             _load_leave_records 增加来源
抑制 Absent             落 leave 桶，不再计「未打卡」
标记生成记录的班次为「调休」
```

## 4. 代码结构与职责

| 文件 | 职责 | 改动量 |
| --- | --- | --- |
| `rest_leave.py`（纯模块，已存在） | 新增 `expand_verified_records(rows)`：把记录列表展开成 `{employee: {日期}}` | 约 12 行 |
| **`rest_leave_apply.py`（新建）** | `verified_rest_dates()`：**唯一的查询入口**，返回同上结构 | 约 20 行 |
| `api.py` | 调用查询并把结果并入豁免集合；生成记录时标记调休 | 约 5 行 |
| `page/hbos_department_board/department_board_data.py` | `_load_leave_records()` 增加调休来源 | 约 6 行 |
| `sync_rest_leave.py` | 修 F3：重新解析的失效键由 `remarks` 改为 `(employee, remarks)` | 约 2 行 |

**为什么需要独立查询入口**：`已通过` 与 `已核实` 这两个过滤条件若有第二份副本，就会出现「改一处漏一处」——本项目已有先例（`daily_feishu_sync.py` 与 `rule_lists.py` 两份分叉的行政班名单）。两处调用方共用同一函数，口径无法漂移。

**为什么 `expand_verified_records` 放纯模块**：它是日期展开逻辑，与第一阶段 `expand_dates` 同族，可在无 frappe、无数据库的 CI 中单测。查询入口只负责取数并转交。

## 5. 关键设计取舍

### 5.1 用两个集合，不是一个

`emp_leave_dates` 用于**抑制缺勤**——合并进去即可生效。
但**标记「调休」**需要知道「这天为什么被豁免」，故另存 `emp_rest_leave_dates`。

### 5.2 命名必须避开 `emp_rest_dates`

`api.py` 中已存在 `emp_rest_dates`，语义是**排班休息日**（该天不生成任何记录，见 `api.py:367-375`）。本设计新增的是**调休日**（该天生成 `On Leave` 记录），二者完全不同。新集合命名为 **`emp_rest_leave_dates`**，不得与既有 `emp_rest_dates` 混用。

### 5.3 标记用「班次」列

调休日本人生成的 `On Leave` 记录，把「班次」列写为 `调休`。

该列本就是自由标签，**实测已在承载非 Shift Type 的值**（`无菌早` / `无菌晚` / `休息日加班` / `8:30班` / `行政班` / `夜班`），故不引入新问题、不需加字段。好处是报表里可一眼区分「这天是调休」与「这天是请假」——Owner 明确要求保留该区分（第一阶段已确认「调休是调休，请假是请假」）。

### 5.4 顺带修 F3

`sync_rest_leave.py:136` 判断「飞书记录是否需要重新解析」时只比较 `remarks`。若有人改了「调休人员_工号」，记录会重新匹配到**另一个人**，但 `remarks` 未变 → `verify_status` 不重置 → 结论仍属于原来那个人。

第一阶段仅出结论，后果是观感问题；**本阶段起豁免是真的，后果是「用甲的加班给乙换休」**。故必须同时覆盖。

## 6. 生效机制（重要）

工作副本通过 `docker-compose.yml` 直接挂载进容器，**代码落盘即生效，没有单独的发布步骤**。下一次 10 分钟考勤重算就会应用新逻辑。

因此：**「提交」与「上线」在本机是同一个动作。** 提交前必须确认改动正确。

## 7. 验收判据

接入前已做只读干跑，**预测值明确**：

| 项 | 预测条数 |
| --- | --- |
| 调休日当前为「无考勤记录」→ 新增 `On Leave` | **26** |
| 调休日当前为 `Absent` → 改为 `On Leave` | **3** |
| 调休日当前为 `Present` → 不变（本人当天确实来上班） | **11** |
| **合计受影响** | **29** |

（40 条已核实记录全部为单日调休，故展开后即为 40 天。）

**接入后实测必须与上述三个数字逐值吻合。** 任何偏差都说明代码行为与设计不符，必须查清后再继续。

## 9. 风险

| 风险 | 评估 |
| --- | --- |
| **3 条 `Absent` → `On Leave` 是真实数据变更** | 这是设计要修的误判（本人调休当天没打卡，被引擎判了缺勤）。但它是**真改数据**，Owner 已知情。 |
| 26 条新增 `On Leave` | 这些天原本无记录，新增后进入请假口径。影响月度汇总的请假天数统计。 |
| 已核实误判导致多给豁免 | 核实基于真实配对，且自洽性对账违规 0 条，风险低。 |
| 终态不可重核（F4） | Owner 决定暂不处理。若事后考勤数据变化导致旧结论失效，只能人工处理。**已记录为已知边界。** |

**回滚**：代码改动可从 git 恢复；考勤结果可由 `regenerate_attendance` 重算（每 10 分钟本就在跑），故回滚代码后下一轮重算即恢复原状。**但注意**：新生成的 `On Leave` 记录名字为 `HBOS-ATT-*`，会被重算的「先删后插」覆盖，故回滚是干净的。
