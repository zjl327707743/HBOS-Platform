## 1. 背景与目标

Owner 要求以 GitHub 仓库 `zjl327707743/HBOS-Platform` 的 `feature/hbos-portal-product` 分支（前端工作台分支）为基准，改造当前 HBOS。

**目标形态**：保留现有考勤后端不动，新增 portal 前端 + `hbos_portal` 平台 App 作为统一入口；门户内容区**同域 iframe 内嵌**现有 Frappe Desk 页面，实现「导航不出门户」；跑通考勤后再扩 Inventory / LIMS。

**Owner 已确认的决策**：

| 决策点 | 结论 |
|---|---|
| 目标形态 | 先做工作台外壳，不三 App 全平台一体 |
| 考勤入口形态 | 内嵌现有页面（hybrid），非跳转、非 Vue 重写 |
| 内嵌实现方式 | 同域 iframe 嵌入（明确推翻 portal 分支实施计划第 5 节「第一阶段不用 iframe」） |
| 运行环境 | 本地 Vite dev 直连现有 8080 生产栈 |
| `hbos_portal` 安装 | 授权在现有 `frontend` site 安装 |
| 集成方案 | A. 选择性移植（非全量 merge） |

## 2. 关键约束（探索实测结论）

### 2.1 两条分支严重分叉，不得全量合并

分叉点 `2675411`（2026-08-14）。此后 portal 分支 100 个提交、当前分支 164 个提交。

**两边都改过**：`pairing.py`、`api.py`、`rule_lists.py` —— 即承载 178 人行政班名单、调休豁免、配对判定的三个核心文件。

`apps/hb_attendance_app` 是 bind-mount 进运行中容器的（`docker-compose.yml:9`），合并冲突处理失误会直接污染真实考勤。**故禁止 merge，只做选择性移植。**

### 2.2 跨源 iframe 会被浏览器拒绝

实测现有 Frappe 响应头：

```
X-Frame-Options: SAMEORIGIN
```

来源：`hbos-m0-r3a-frontend-1` 容器内 `/etc/nginx/snippets/security_headers.conf:1`。

`http://127.0.0.1:5178`（Vite）与 `http://127.0.0.1:8080`（Frappe）**端口不同即不同源**。从 5178 页面 iframe 8080 会被浏览器直接拦截。

**结论：dev 与生产都必须收敛为单一来源**，iframe 的 `src` 使用相对路径。

### 2.3 `hbos_portal` 的设计天然支持解耦移植

`hbos_portal` 从不 import 业务 App（P1 架构基线明令禁止）。业务 App 通过 `hbos_portal_provider` hook **自注册**：

```python
hbos_portal_provider = [
    "hb_attendance_app.hbos_attendance.portal.provider.get_provider",
]
```

因此移植不需要碰考勤判定核心，只需新增一个 `portal/` 子包加一行 hook。

### 2.4 当前运行态基线

- 容器：`hbos-m0-r3a-*` 全套 Up（frontend 8 天、backend/scheduler/queue 3 天、db healthy）
- Frappe 端口：`8080`（`.env` 的 `HTTP_PORT=8080`）
- Node：v22.23.1 / npm 10.9.8
- `dashboard_data.get_data()` 已含 `anomaly_people` / `total_late` / `total_early` / `total_absent`，portal 的摘要投影可直接复用
- `Page hbos-attendance-dashboard` 与 `Workspace 海滨考勤工作台` 均已存在，portal 契约测试的两个前置断言可满足

## 4. 技术方案

### 4.1 同域机制（dev）

Vite dev server 把 Frappe 路径全部代理到 `127.0.0.1:8080`：

```
/hbos/*                  → Vite 自身（门户 SPA 路由）
/api /app /assets /files /login /socket.io /private → 127.0.0.1:8080
```

浏览器只看到 5178 单一源，iframe 用相对路径 `/app/hbos-attendance-dashboard`，同源放行。

**需验证的未知项**（不预设结论，实测后再定）：
- `/app` 返回 301 重定向的具体目标
- session cookie 是否随 iframe 导航携带
- `socket.io` 在 iframe 内的握手

### 4.2 同域机制（生产，R4 处理）

nginx 统一分发：`/hbos/*` → portal 构建产物，其余 → Frappe。**R4 需另行授权。**

### 4.3 集成边界

移植清单严格限定为新增，除以下两处外不改动既有文件：

| 文件 | 改动 |
|---|---|
| `apps/hb_attendance_app/hb_attendance_app/hooks.py` | 追加 `hbos_portal_provider` 一行 |
| `docker-compose.yml` | 追加 `./apps/hbos_portal` 挂载 + PYTHONPATH 条目 |

`docker-compose.yml` 因挂载变更需重建 backend / scheduler / queue-short / queue-long / websocket 五个容器。**不重建 frontend（nginx）、不碰 site、不碰数据。**

### 4.4 承载方式

`PortalLayout` 内容区在 portal 路由命中业务 App 时渲染 iframe；门户自身路由（`/hbos`、`/hbos/work`、`/hbos/apps`、`/hbos/profile`）仍由 Vue 渲染。

## 9. 未决事项

### 9.1 R2 浏览器实测结论（2026-09-28，已确认为事实）

原设计列为「未决」的三项，R2 实测后全部落定：

| 原未决项 | 实测结论 |
|---|---|
| session cookie 是否随 iframe 携带 | **携带，无需任何调整**。经 5178 登录后 cookie 正常建立并被 iframe 内的 Frappe 页面使用；门户内重复导航后仍保持登录态，未回落登录页 |
| `/app` 301 重定向目标是否超出代理范围 | **未超出**。`/app/*` → `/desk/*` 为**相对**路径 301，浏览器停留在 5178 单一源内 |
| socket.io 在 iframe 内的握手 | **握手成功（101）**，但存在一条**既有**的 `Invalid origin` 提示（见 9.2） |

补充实测事实：

- iframe 内 Frappe 运行时**完整启动**：`window.frappe`、`jQuery` 可用，11 个 script、4 个 stylesheet 全部加载。
- iframe 内加载的是**真实数据**：实测显示缺勤 2234、异常人员 388、出勤率 46.5%、总人数 696 及真实员工姓名。
- 同源性可由 `iframe.contentDocument` 可访问**直接证明**（跨源时该属性会抛错）。
- LIMS 走 SPA 分支（`/hbos/lims`，无 iframe），fallback 行为正确。

### 9.2 已识别但未处置的代理覆盖缺口

以下路径在 Frappe（8080）有真实响应，但未被 Vite 代理，在 5178 上会被 Vite 吞成 `200 text/html`（返回 SPA 的 index.html）：

| 路径 | 8080 真实响应 | 影响 |
|---|---|---|
| `/website_script.js` | 200，25 字节 JS | Frappe 页面的网站脚本钩子。经代理后浏览器把 index.html 当 JS 解析并报错；因该文件实际为空，**无功能影响**，仅有控制台报错 |
| `/robots.txt` | 200 text/plain | SEO，与门户无关 |
| `/sitemap.xml` | 200 application/xml | SEO，与门户无关 |
| `/backups` | 403 | 管理员工具 |

四者均**不阻断** iframe 内嵌考勤仪表盘。如需覆盖，应在后续轮次统一评估，而非零散补条目。

### 9.3 既有环境问题（非本轮引入）

`socket.io` 的 `Invalid origin` 提示**在本轮之前就存在**：`docs/PROJECT_STATUS.md:439` 与 `docs/deployment/M0-R3C_FIX_HRMS前端资源与Roster白屏修复记录.md:178` 均已记载，当时即判定「非 HRMS 白屏根因，留待后续环境治理」。

R2 实测补充了一个反证：对同一升级请求分别发送 `Origin: http://localhost:8080`、`http://localhost:5178`、`http://127.0.0.1:8080`，**三者均返回 101**。即该提示并非由 5178 这个新来源触发，而是既有的环境配置问题。本轮不动它。

### 9.4 安装 hbos_portal 时的 migrate 副作用（已记录，Owner 裁定暂不处理）

**现象**：Task 9 的 `bench --site frontend migrate` 移除了 DocType
`HBOS Attendance Policy Assignment` 在 `tabDocType` 中的**记录**。

**数据完好**。表 `tabHBOS Attendance Policy Assignment` 与其中 **422 行**业务数据
（含 `employee` / `employee_number` / `employee_name` / `policy_type`）**无损**。
仅元数据记录消失，导致该 422 行经 app 暂时不可达。

**根因**（已读源码确认）：`frappe/migrate.py:188-189`

```python
print("Removing orphan doctypes...")
frappe.model.sync.remove_orphan_doctypes()
```

该函数以 `get_controller(doctype)` 是否抛 `ImportError` 判定孤儿。本分支没有
`hbos_attendance_policy_assignment.py`，故被判为孤儿并删除记录。Frappe 自己的
docstring 明确说明：

> Note: Deleting the entry doesn't delete any data.
> So this is supposed to be non-destrictive operation.

**归属**：该 DocType 属**另一条工作线**（LIMS / 平台集成线）——源文件存在于 `main`
（3 个文件，`creation` 2026-09-24），本分支从未拥有。表建于 2026-09-25 08:12:23，
422 行于 2026-09-25 08:13:27~28 批量写入。

**复现性**：只要在本分支（缺这些文件）上再跑 `migrate`，该记录会再次被移除。

**恢复方式**：从 `main` 取回那 3 个文件 → `migrate` → 记录重建并指向现有表 → 422 行恢复可达。

**误伤面排查（实测）**——本分支自身功能零附带损伤：

| 对象 | 结果 |
|---|---|
| 4 个 Report（打卡流水 / 考勤结果 / 月度考勤汇总 / HBOS 月度汇总暂存（对账）） | 全在 ✓ |
| 6 个 Page（dashboard / import / department-board / employee-management / monthly-upload / shift-management） | 全在 ✓ |
| Workspace 海滨考勤工作台 | 在 ✓ |
| 全库孤儿表复扫 | 仅此 1 张真实孤儿表 |

**Owner 裁定（2026-09-28）**：**暂不处理**。数据完好、可恢复，待两条线合并时该
DocType 自然回归。本文档即为记录在案。
