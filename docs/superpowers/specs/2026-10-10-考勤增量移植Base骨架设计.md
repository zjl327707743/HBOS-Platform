## 一、目标与背景

把本团队考勤线（head）的业务增量，**以 base 为骨架选择性移植**（非 merge）到一条新分支，开一个干净、可审查、无冲突的 PR，交 Owner 审核。

**为什么不用 merge**：base 与 head 自 `2675411` 分叉后各自演进——base +108 提交（安全/治理加固较新），head +207 提交（考勤业务逻辑较新）。两边对同一模块的安全政策相反，109 个文件冲突无可行解。base 自带的 15 项治理测试对 head 当前文件实测失败 14 项，即 **head 无法通过 base 的验收**。按 head 解冲突会退回 base 的全部加固；按 base 解会丢失 head 的考勤业务修复。

### 前提修正（实测）

裁定单与 PR #34 描述中的「新增 5 个 DocType / 3 个页面」是相对更早的 base 而言。**当前 base `ddbe9bf` 已经全部具备**：

- 7 个 DocType（含 `hbos_attendance_policy_assignment`——即「名单进业务数据」那套）；6 个页面（含 `hbos_department_board` / `hbos_employee_management` / `hbos_shift_management`）；`board_stats.py`、`roster_export.py`。
- 4 个旧引擎（`daily_feishu_sync` / `generate_attendance` / `pair_checkins` / `shift_matcher`）base **已删除**。

因此真正的移植增量比 PR #34 描述的更小、更聚焦。

## 三、67 个双方改动文件的收敛政策

**总原则**：先取 base，再判断 head 的差异是「业务增量」（重落）还是「加固回退」（丢弃）。

### 三.0 head 独有的 12 个考勤 App 文件的处置

| 文件 | 处置 |
| --- | --- |
| `list_data.py`、`report_data.py`、`file_api.py`、`bump_page_cache.py` | **并入**（base 没有，是门户取数/上传所需） |
| `public/css/hbos_attendance.bundle.css`、`public/js/hbos_attendance.bundle.js` | **并入**（Desk 视觉层产物） |

| `tests/test_regenerate_window.py` | **丢弃/改造**（依赖被弃用的 35 天回溯） |

## 四、验证策略

分三层，逐层不越权：

| 层 | 能跑什么 | 不能跑什么 | 依据 |
| --- | --- | --- | --- |
| **L1 静态** | 全部改动 `.py` 语法解析、`git diff --check`、base 的 5 个治理测试（`test_merge_governance.py` / `test_admin_nums_single_source.py` / `test_monthly_upload_authz.py` / `test_shift_governance.py`）**源码级静态比对** | 需要 site 的 Frappe 套件 | 本机容器承载约 700 人真实数据，禁止 `migrate`/写库 |
| **L2 前端** | `frontend/hbos-portal-web` 的 `npm ci && npm run build`（`vue-tsc -b && vite build`） | 门户真实后端联调 | 纯构建，无副作用 |
| **L3 真闸门** | **PR CI**：`platform-integration-gate.yml` / `hbos-portal-backend.yml` / `hbos-portal-frontend.yml` / `portal-unified-account-release.yml` | —— | 冲突清零后 GitHub 才触发；唯一可复现的验收证据 |

### 验收判据（必须同时满足）

1. `git merge-tree` 相对 base **0 冲突**；
2. 新分支**不含** `apps/hb_stock_app/**`、2 份 PII 名单、`tools/repro_chen_yuxin_0819.py`；
3. 新分支**不含**任何硬编码 `APP_TOKEN` 字面量（`grep` 为 0）；
4. base 治理测试静态比对 **15/15 通过**；
5. 本地 `npm run build` **PASS**；
6. PR 的 CI **全部 SUCCESS 或明确 Pending**（Pending 报 `PR_CREATED_PENDING_CI`，不宣称 PASS）。

### 已知的诚实边界

- Frappe 套件本地跑不了 → 只报 L1/L2 实跑 + CI 结果，**不引用仓库旧记录当 PASS**；
- 阶段 4 预期零改动；若发现 `file_api.get_csrf_token` 与 base `api/csrf.py` 重复，只做「消除双通路」的最小改动并单列报告；
- 新 DocType 需 `bench migrate`——**不在本机执行**，写入 PR 描述交由 CI/部署侧。
