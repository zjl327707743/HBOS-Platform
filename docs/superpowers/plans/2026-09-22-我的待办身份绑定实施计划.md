# 我的待办身份绑定 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan. Use superpowers:test-driven-development for every behavior change, superpowers:systematic-debugging for unexpected failures, superpowers:verification-before-completion before any completion claim, and superpowers:requesting-code-review before closeout.

**Goal:** 将侧栏「我的待办」改造成基于 Frappe 当前会话身份的跨模块个人待办中心，合并展示“指派给我”和“我的角色待处理”，同时保持原业务状态机、权限校验与全局业务看板口径不变。

**Architecture:** 后端以无 Frappe 依赖的 `todo_contract.py` 保存动作规则、归属判定、去重和排序契约，以 `todo_service.py` 读取当前会话并聚合检验、稳定性、留样三个既有事实源。前端新增 Pinia 待办 store 与 `/my-todos` 页面，所有直接动作继续调用原模块 API；无法安全直接执行的动作跳转到支持定位的原业务页面。侧栏仅使用独立摘要接口，列表筛选计数与侧栏全局个人计数分离。

**Tech Stack:** Frappe Framework、Python、pytest、Vue 3、TypeScript、Pinia、Vue Router、Ant Design Vue、Node 内置测试能力、Vite。

**Spec:** [`docs/superpowers/specs/2026-09-22-我的待办身份绑定设计.md`](../specs/2026-09-22-我的待办身份绑定设计.md)

## Global Constraints

- 身份只能来自 `frappe.session.user` 与 `frappe.get_roles(current_user)`；两个白名单接口均不得接受 `user`、`roles` 或等价身份覆盖参数。
- `Administrator` 必须按用户名显式特判：其 `role_pending` 业务角色集合为空，只能看到明确指派给该账号的待办；不能依赖从角色列表剔除 `System Manager`。
- 不新建持久化待办 DocType；业务单据继续作为唯一事实来源。
- 同一来源单据在同一时刻至多产生一个当前动作；同时命中用户与角色归属时只保留一条并优先 `owner_type=user`。
- 稳定性派生结果 `source_test_result` 非空时，不产生提交、复核、退回、批准、修订或作废待办。
- 稳定性样品与检验任务的跨模块收敛必须按项目粒度判定：只排除映射到该时间点实际项目的 `HBOS Sample Task`，未映射项目继续保留。
- 动作权限是主闸门，源单据读权限是第二道边界；待办页不得成为绕过既有服务校验的旁路。
- 稳定性截止日必须复用服务层有效截止日派生逻辑，不得把 `effective_sample_due` 或 `effective_test_due` 当数据库列查询。
- 结果类稳定性待办统一返回 `due_at=null`、`is_overdue=false`。
- `/tasks` 无 `scope` 时保持全局原始口径；只有 `scope=mine` 时由后端按当前会话收敛，前端不得传用户账号。
- 列表接口返回 `filtered_summary`；侧栏角标只读取独立的 `get_my_todo_summary`，不叠加稳定性模块全局 KPI。
- API 字段名严格沿用批准规格：筛选键使用 `overdue`，来源类型使用 `source_doctype`，个人数量使用 `assigned_to_me`；不得另造近义字段导致前后端双口径。
- 列表查询不做跨请求结果缓存；摘要缓存键包含 `(user, roles_hash)`，TTL 为 30 秒，原业务动作提交成功后统一失效。
- 轮询只在 `/my-todos` 已挂载且 `document.visibilityState === 'visible'` 时运行，周期 60 秒；后台标签页不空转。
- 第一阶段不实现认领、转派、通知、飞书集成和持久化任务中心。
- 本计划只包含本地实现、测试和浏览器验收；生产提交或部署必须另获明确授权。
- 所有文件修改使用小步提交；每个行为先看到指定测试失败，再写最小实现使其通过。

## Review Focus

1. `Administrator` 即使从 `frappe.get_roles` 获得全部 LIMS 角色，也不能看到任一角色待处理记录。
2. 同一稳定性样品同时包含已映射和未映射检验项目时，只抑制已映射项目，未映射任务不能消失。
3. `source_test_result` 非空的稳定性结果不能泄漏任何人工待办动作。
4. 查询后源单据状态或权限发生变化时，原业务 API 必须再次拒绝无效动作，前端刷新待办且不伪造成功状态。
5. 1000 条候选记录下聚合性能有可复现证据，摘要缓存与页面轮询不会在普通页面或后台标签页持续扫描。

### Step 2.2：实现服务公共契约和内部聚合管线

公开 API 固定为：

- `@frappe.whitelist() get_my_todo_summary() -> dict`

内部接口固定为：

- `_current_identity() -> Identity`
- `_collect_testing_todos(identity: Identity) -> list[dict]`
- `_collect_stability_todos(identity: Identity) -> list[dict]`

### Step 2.3：实现检验业务 provider 和项目粒度收敛

- 批量读取候选 `HBOS Sample Task` 与关联 `HBOS Sample`，避免逐行数据库查询。
- 普通任务按 `assignee` 判定 `user`；未被他人明确占用且当前业务角色允许当前动作时判定 `role`。
- 稳定性来源样品按时间点分组；每个时间点复用 `stability_service._business_stability_items_for_timepoint(timepoint_name)` 获取已映射项目，再与时间点真实 `test_items` 取交集。
- 只抑制 `testing_task_is_covered(...)` 返回真的任务。
- `HBOS Test Result` 的提交、复核、批准动作通过其既有人员字段与工作流角色判定；职责分离不满足时不生成当前用户待办。
- 各来源候选使用 `frappe.get_list` 的 permission-aware 查询获得，读权限在批量入口收敛；不得逐行 `frappe.get_doc` 或 `frappe.has_permission` 形成 N+1。动作权限仍以 `workflow_contract.action_allowed` 为主。

### Step 7.4：实现动作调度器

export interface TodoActionContext {
  navigate(item: TodoItem): Promise<void>
  refresh(): Promise<void>
  notifySuccess(message: string): void
  notifyError(message: string): void
}

export async function runTodoAction(item: TodoItem, context: TodoActionContext): Promise<void> {
  if (item.execute_mode === 'route') return context.navigate(item)
  return executeMappedBusinessAction(item, context)
}
