# P4 Inventory 剩余 6 项前端化 — 可行性与优先级评估

> Date: 2026-09-25
>
> 用途：**回答「剩下这些怎么排」**。不是设计文档，是决策依据。
>
> 已完成（本分支）：概览 / 入库拍照识别 / 草稿复核 / 批次 / 四张报表 / 物料 / 货位。
> 剩余 6 项：采购入库、待检与放行、销售出库、拣货单、库存对账、库存余额。

## 0. 一句话结论

**只有两项适合现在单独做：**

1. **库存余额** —— 报表类，与已做的四张同一种做法；
2. **待检与放行** —— 但**不是表单，是只读看板**（放行由 LIMS 投影，本 App 无权写）。

**另外四项（采购入库 / 销售出库 / 拣货单 / 库存对账）应当合成一轮做**，
不该一个个来 —— 理由见 §3。

## 1. 库存余额：可做，但有一个必须先说的前提

**它和另外四张报表不是一回事。**

| | 已做的四张 | 库存余额 |
|---|---|---|
| 类型 | 自建 Script Report | **ERPNext 标准报表** |
| 数据源 | 本 App 的 `report/*.py` | `Stock Ledger Entry`（V16 起改走 `Serial and Batch Bundle`） |
| 运行方式 | **即查即得** | **默认是「预处理报表」（prepared report）** |

**实测**：直接调 `query_report.run(report_name="Stock Balance")` 返回的是

```json
{"prepared_report": true, "doc": null, "add_total_row": true}
```

——**它不给数据**，而是要你先建一个「预处理报表」文档、由后台任务生成快照。

**绕过办法（已实测可用）**：加 `ignore_prepared_report=1`，即时返回真实数据
（返回了 `opening_qty` / `in_qty` / `out_qty` 等完整列）。

**这个绕法有代价，必须让你知道**：

- **性能**：ERPNext 之所以默认预处理，是因为这张报表在流水量大时很慢。
  当前库很小（实测即查即回），但**流水积累后会变慢**；
- **口径**：预处理是**生成那一刻的快照**，即时查是**当前值**。
  两者在跨日结账时可能不同，报表页必须写清「这是实时查询，不是期末快照」。

**我的建议**：做，用 `ignore_prepared_report=1`，并在页面上如实标注
「实时查询」+ 提供一个「生成快照」的次要入口留给将来的大数据量场景。
**但这条要你同意**——因为它等于替使用者选了「宁可慢也要实时」。

## 2. 待检与放行：**不能做成表单**（这条是硬边界）

界面上写着「到货检验结论与 QA 放行」，容易让人以为要在这儿做放行。
**做不了，而且不该做**——`quality_projection.py` 里已经钉死了：

```python
def guard_batch_projection(doc, method=None):
    """Reject direct/user mutation of LIMS-owned release projection fields."""
    # 挂在 Batch.validate 上，任何直接改放行字段的操作都会被 throw
    frappe.throw(_("质量放行字段由 LIMS 投影维护，不能在 Batch 中直接修改：{0}"))
```

而写入口 `apply_release_projection` **刻意不加 `@frappe.whitelist()`**——只有 LIMS 侧内部能调。

**所以本 App 能拥有的是「看板」，不是「表单」**：

```text
待检与放行  →  只读工作台
  ├─ 待检批次清单（hbos_release_status = 待检）
  ├─ 按效期紧迫度排序（谁先到期谁先催）
  ├─ 按货位 / 物料筛
  └─ 每行给一条「去 LIMS 处理」的路径，而不是「在此放行」的按钮
```

**为什么这反而值得做**：它是**出库的前置门禁**。出库被
`release_gate.validate_release` 拦下时，操作员最需要的正是「这批卡在谁那里、还剩几批」。
现在这个信息在 Portal 里完全没有。

**实测**：`Batch` 按 `hbos_release_status = 待检` 查得到，**当前 15 批**，
字段（物料、效期、来源类型）都取得到。

**一个要定的措辞问题**：页面叫什么？

- 叫「待检与放行」会让人以为能放行（与 LIMS 边界冲突）；
- 建议改叫 **「待检批次」** 或 **「待放行」**，并在页面上明确写
  「放行由 LIMS 完成，本页只显示进度」。

## 3. 另外四项：**建议合成一轮**，不要逐个做

采购入库 / 销售出库 / 拣货单 / 库存对账 的共同点：

| | 采购入库 | 销售出库 | 拣货单 | 库存对账 |
|---|---|---|---|---|
| 类型 | ERPNext 标准单据 | 同左 | 同左 | 同左 |
| 可提交 | 是 | 是 | 是 | 是 |
| 带明细子表 | 是 | 是 | 是 | 是 |
| **HBOS 自定义字段** | **0** | **0** | **0** | **0** |
| 特殊门禁 | 无 | **放行门禁** | 无 | 无 |

**四个都是「纯 ERPNext 单据，没有一行是本 App 的业务字段」**（实测：`setup.py` 里
自定义字段只加在 `Item` / `Batch` / `Stock Entry` 上，这四个一个都没有）。

这意味着两件事：

**一、逐个做得把同一套骨架写四遍。** 单据编辑器需要的东西是一样的：
明细子表增删行、客户/供应商选择、日期、提交前校验、提交/取消、错误呈现。
写四遍就是四份要同步维护的代码。

**二、这正是「通用 Stock Entry 该不该前端化」那个悬而未决的问题。**
你之前定的是「通用 Stock Entry 另起一轮」。现在这四项（+ 通用 Stock Entry）
是**同一类东西**——要么一起做，要么一起不做。**不该先做两个、剩下的再说。**

**一个额外的价值点，值得放进那一轮**：销售出库的**放行门禁在 `before_submit`**。
若照搬表单，操作员会填完一整张单、点提交、**才发现某批次没放行**。
Portal 版可以**提前**把批次的放行状态查出来、在提交前就标红——
这是 Desk 做不到的（Desk 只在提交时才知道）。这条属于「Portal 化带来的真实改进」，
不是换皮。

## 4. 建议顺序

```text
第 1 步  库存余额          —— 与已做的四张同构，最快；需你同意 §1 的实时查询取舍
第 2 步  待检批次（只读看板）—— 补上出库门禁的可视化，无写操作、无边界风险
         ↓
         到这里，Inventory 的**只读面**全部完成
         ↓
第 3 步  通用单据一轮      —— 通用 Stock Entry + 采购入库 + 销售出库 + 拣货单 + 库存对账
                             一起做，共用一套单据骨架；销售出库顺带做放行预检
```

**为什么不建议先挑一项单据试水**：会立刻撞上「通用 Stock Entry 怎么算」这个
未决问题。先把它定下来（哪怕只是定「这五个用一套骨架」），再动手，才不会白做。

## 5. 需要你定的三件事

   若不接受，就得走「生成快照」那条路——那是另一套交互（建任务、等结果、下载）。
2. **「待检与放行」改名吗？** 建议改叫「待检批次」或「待放行」，避免与 LIMS 边界冲突。
3. **第 3 步的「通用单据一轮」现在立项，还是先把只读面做完再议？**
