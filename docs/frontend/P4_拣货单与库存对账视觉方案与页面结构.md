### 2.1 拣货单

### 2.2 库存对账

| 能力 | 结果 |
|---|---|
| 建草稿 | ✅ 实测成功。**但一开始失败过**，见下 |
| **批次物料必须给批次** | ⚠️ 第一次 insert 报 `ValidationError: 行号1：请为物料13000894添加序列号和批次包`。补上 `use_serial_batch_fields: 1` + `batch_no` 后成功 |

| 账面为 0 时 | 实测新建单据时 `current_qty = 0`——**要等填完物料+批次+货位后重新查**才有真值 |

## 4. 页面 A：拣货单

```text
┌──────────────────────────────────────────────────────────────┐
│ 拣货单                              STO-PICK-2026-00001      │
│ 填要拣的物料与数量，系统告诉你它们在哪些货位。  [草稿 · 未拣] │
│ ⓘ 拣货单本身不动账面。它告诉你货在哪；把货挪走要再开一张移库单 │
│ ┌─── ① 范围 ─────────────────────────────────────────────┐  │
│ │ 拣货用途[内部移货]  查找范围[3904 六车间中间库]  日期__  │  │
│ └────────────────────────────────────────────────────────┘  │
│ ┌─── ② 要拣什么 ─────────────────────────────────────────┐  │
│ │ 物料代码 | 要拣数量 | 单位 | 货位 | 该货位库存 | ×      │  │
│ │ 13000901 |  50.000 | Kg  |[16-03-206]|   3.000   | ×   │  │
│ │ [+ 添加一行]  [定位货位]                                │  │
│ └────────────────────────────────────────────────────────┘  │
│ ┌─── ③ 定位结果 ─────────────────────────────────────────┐  │
│ │ ⚠ 有 1 项凑不够。硝酸钠要 100，全部货位只有 3——差 97。  │  │
│ │ 物料 | 货位 | 可拣 | 要拣 | 够不够                      │  │
│ │ 13000894|16-03-212|6.000|6.000|[刚好]                  │  │
│ └────────────────────────────────────────────────────────┘  │
│ 先保存，再定位。      [放弃] [保存草稿] [提交]               │
└──────────────────────────────────────────────────────────────┘
```

### 4.1 最关键的一条：**明确说「拣货单不动账面」**

这是本页最容易让人误解的地方。ERPNext 的拣货单**只是分配指示**——
它记录「该从哪个货位拣多少」，**库存不会因为它改变**。真正移货要再开一张移库单
（或领用出库）。

不写这一句，仓管会以为提交拣货单货就出去了，然后对不上账。

### 4.2 「先保存再定位」是 ERPNext 的硬约束，必须写在界面上

`set_item_locations` 是**单据方法**——它需要单据已存在（有单号）才能计算。
新建时若直接点「定位货位」会失败。

所以原型里把这句话**直白写在按钮下方**，而不是让用户点了才知道。
（这也是 `FRONTEND_IMPLEMENTATION_GUIDE` 的精神：把框架的约束讲清楚，而不是藏起来。）

### 4.3 「凑不够」要显式提示，并给出下一步

定位结果是「每个货位能拣多少」。当合计凑不够要拣的数量时，必须：
- 说清**差多少**（「要 100，全部货位只有 3——差 97」）；
- 给出**两条出路**（改小数量，或先入库）。

只显示「不足」而不说差多少，用户还得自己减。

## 5. 页面 B：库存对账

```text
┌──────────────────────────────────────────────────────────────┐
│ 库存对账                            MAT-RECO-2026-00002      │
│ 按实盘数调账。填之前先看到账面是多少——差异自己就出来了。      │
│ ⓘ 只填「实盘数」，差额由系统算。提交后记入差异科目。           │
│ ┌─── ① 基本信息 ─────────────────────────────────────────┐  │
│ │ 对账用途[库存对账]  过账日期[2026-09-25]*  默认货位__   │  │
│ └────────────────────────────────────────────────────────┘  │
│ ┌─── ② 盘点明细 ─────────────────────────────────────────┐  │
│ │ 物料|批次|货位|单位|账面数|实盘数|差异|×               │  │
│ │ 13000894|B2507343|16-03-212|Kg|6.000|[5.000]|-1.000   │  │
│ │ 13000912|BMT2609001|16-03-211|Kg|160.000|[160.000]| 0  │  │
│ │ 13000900|BMT2407502|16-03-206|Kg|3.000|[8.000]|+5.000  │  │
│ └────────────────────────────────────────────────────────┘  │
│ ┌─── ③ 差异合计 ─────────────────────────────────────────┐  │
│ │ ⚠ 3 行里有 2 行对不上。盘亏 1.000、盘盈 5.000。          │  │
│ │ 差异会记入差异科目——这是财务口径的调整。                │  │
│ └────────────────────────────────────────────────────────┘  │
│ 提交后按差额调账。        [放弃] [保存草稿] [提交]           │
└──────────────────────────────────────────────────────────────┘
```

### 5.1 只填「实盘数」，账面数与差异**由系统算**

这是对账页的核心。用户只需要填**现场数出来的那个数**；
账面数由 `get_stock_balance_for` 查出，差异列随之变化。

**不让用户填账面数**——那是系统的事实，填了就成了自己骗自己。

### 5.2 差异要区分方向、且 0 要安静

- 盘盈（正）：绿
- 盘亏（负）：红
- **0：灰 + 常规字重**（与库存概览页「值为 0 就安静下来」同一条口径）

三行里两行对不上，说明差异有方向性——颜色让这件事一眼可见。

### 5.3 必须说清「这是财务口径的调整」

对账不是「改个数字」。它按差额**调账并记入差异科目**。
不写这一句，仓管会随手填个数就当改了个显示值。

原型在差异合计里点明：**「这是财务口径的调整，不只是改个数字。提交前请确认实盘数没错。」**

### 5.4 批次物料的坑要写在界面上

实测：不填批次时服务端报

```text
ValidationError: 行号1：请为物料13000894添加序列号和批次包
```

所以明细底部注明**「批号管理的物料必须填批次」**——这是实测踩到的，
不是推测。

## 7. 状态设计

| 状态 | 拣货单 | 库存对账 |
|---|---|---|
| 加载中 | 骨架 | 骨架 |
| 正常 | 三段表单 | 三段表单 |
| 已提交 | 「已提交拣货单」+ 去建移库单 + **取消**（2026-09-28 追加） | 「已调账」+ 看库存余额 |
| **已取消** | 灰调说明块 + 新建一张 / 回列表 | 灰调说明块 + 新建一张 / 回列表 |
| 取不到 | 「单号可能已被删除」 | 「单号可能已被删除…**草稿还没调账**」 |

「已提交」态的下一步刻意不同：拣货单指向**移库单**（因为拣货不动账），
对账指向**库存余额**（因为已经调账，该去复核）。

> **「已取消」是独立状态**：`docstatus` 三态（0/1/2），早先
> `docstatus === 1 ? 'submitted' : 'draft'` 会把已取消的单据染成琥珀色的「草稿」
> 并放开编辑。见库存单据设计文档 §11.7。

### 11.1 复刻时发现：「定位货位」还有一个前提

原方案只写了「先保存再定位」。**实测发现还缺一条**：

`set_item_locations` 的搜索范围来自 **`parent_warehouse` 或 `work_order`**。
**两个都不给时它无处可搜**——实测把未拣的行清掉、且一行也不填。

更糟的是**报错信息会误导**：界面当时显示「要拣 1.000，全部货位加起来只有 0.000——差 1.000」，
看起来像「库存不够」，实际原因是**没设查找范围**。两件事的下一步完全不同
（一个去设范围，一个去入库）。

**修法**：
1. 「定位货位」按钮**要求先选查找范围**，未选时禁用；
2. 提示按前提分三档：未保存 → 说「先保存」；已保存但未选范围 → 说「先选范围」；
   两者都满足才展示「它调 ERPNext 的 set_item_locations」那段说明；
3. 定位回来**一行都没有**时，走**单独的黄条**说明（`explainEmptyLocate`），
   与「凑不够」的红条分开。

这条也印证了本项目反复出现的那个形状：**把「不知道」显示成「是零」**。
缺范围导致的「找不到」和真的「没库存」，在屏幕上都是 0。

### 11.2 另一处实测出来的必要开关

**`pick_manually: 1` 是必需的**。不设它时 ERPNext 的 `before_save` 会调用
`set_item_locations()`，把用户手填的货位**整个重算掉**——手工填的行保不住。
要重算由用户显式点「定位」触发。已写进 `inventoryPick.toWireLocations` 的注释。

### 11.3 端到端实测（拣货单）

| 步骤 | 结果 |
|---|---|
| 填一行（物料 + 数量 + 批号 + 货位）→ 保存 | ✅ 建出 `STO-PICK-2026-00001`，单号回落 |
| 保存后「定位货位」按钮 | ✅ 由禁用变可用 |
| 点定位（未设范围） | ✅ 黄条「定位没找到任何货位。还没选…」——**不是**「库存不够」 |
| 提交 | 走 `submitDocument`（与已修的那条路一致） |
