### 2.2 一个已修的缺陷：**页面做完了但入口被挡住**

2026-09-25 用户问「是不是只剩采购入库和销售出库」时才发现：
**「批次」与「库存余额」两页早就做好了**，但 `inventoryNav.ts` 里仍是
`implemented: false`——点侧边栏直接落到「这个功能的前端页还没有做出来」。

**根因**：同一件事写在两处（后端路由表 + 前端导航数据），每做一页要改两处。
此前几轮都改对了，唯独这两处漏了。

**修法**：
1. 两项改 `implemented: true` 并补 `stablePath`；
2. **「批次」原来根本进不去**——它只有 `batch/:batchName`（详情路由），
   没有不带参数的入口。补了一个**批次选择器** `/hbos/inventory/batch`
   （与物料/货位同构：进来给列表，选中后地址变成 `/batch/<批号>`）；
3. 加测试 `test_every_registered_native_route_has_a_portal_page`——
   **从 `router/index.ts` 读路由**（不手写，否则「路由改了测试没改」会假通过），
   逐个交给后端 `resolve_stable_route`，断言它们都不被解析去 Desk。

**反向验证过**：临时把 `/pick` 从后端路由表拿掉，那条测试立刻变红——
说明它真能抓到这类漂移，不是摆设。

### 2.3 「真正没做的」现在是 0 项 —— 采购入库 / 销售出库**不属于本前端**

> 「真正没做」，并花了 §7 两个待决项讨论客户档案从哪来、采购入库要不要做。
> 那两个前提都不成立——**这两张单不由仓管开**，所以它们从来不是缺口。

仓库确认的口径：**仓管执行的是仓库的入库、出库、移库，没有采购入库、销售出库操作。**

**库存单据**里的 `Material Receipt` / `Material Issue` / `Material Transfer`

### 2.6 2026-09-28：仓管可自行取消，并修掉四个实测出来的缺陷

**规格变更（不在过审版本里）**：Owner 要求「让仓管能自己取消」。此前三个页面的
提交确认框都写着「提交后如需撤销，要走红字冲销」——仓管填错只能找后台。
现已在**库存单据 / 拣货单 / 拍照识别复核页**的「已提交」态各加一个危险色
「取消」按钮（二次确认 + 服务端错误原样呈现）。权证、传参语义与副作用见
`P4_库存单据通用表单视觉方案与页面结构.md` §11.7。

**同一轮把「全量验证」提到运行态，因此实测出四个缺陷**（前三个是同一类：
**假设了不存在的结构**）：

| # | 缺陷 | 形态 | 后果 |
|---|---|---|---|
| 1 | `Pick List` 查了 `posting_date` | 该 doctype **没有任何日期字段** | 查询 417，**拣货单列表整页打不开** |
| 2 | 批次页读 `Batch.hbos_storage_condition` 等三项 | 这三项**是 `Item` 的字段**，`Batch` 上没有 | `frappe.client.get` 不校验字段 → 静默 `undefined` → 「本批信息」永远空白，而打印件却有值 |
| 3 | 拣货单行不带 `uom` / `stock_qty` | 服务端不会替你补 | 单位列存成 NULL；**「定位货位」把未拣行全删光、一行不填**（`set_item_locations` 用 `stock_qty` 算剩余量） |
| 4 | 三处 `docstatus === 1 ? … : '草稿'` | `docstatus` 是**三态** | 已取消的单据显示成琥珀色「草稿」且**可编辑** |

**为什么会漏**：此前几轮的「验证」跑的全是**读源码文件 + 正则断言**的静态测试，
**看不到运行态到底有没有那个字段/报表**。现已补上「对活库核对
doctype/字段/子表/报表/筛选键/whitelisted 方法」这一层，并把可静态守的部分
固化成四个契约测试（每个都**故意改回错版本跑过、确认会红**）：

- `test_batch_master_field_contract.py` — 别从 `Batch` 读 `Item` 的字段
- `test_pick_payload_contract.py` — 拣货行必须带 `uom` / `stock_qty`
- `test_doc_state_contract.py` — 已取消 ≠ 草稿；`readonly` 必须走三态
- `test_cancel_contract.py` — `cancel` 与 `submit` 的传参形状不许互相抄

## 4. 「点入库拍照识别跳到后端仓库工作台」——**已解决**

## 6. 草稿复核页 + 批次页的关键判断（实现时做了两处修正）

原型审查通过后，实现时对着真实数据发现两个**原型没说准**的地方，都改掉了：

### 6.1 「有 3 项没填」必须看来源类型，不能一律说「可以不填」

原型里那句「本次来源是自产，可以不填」是**写死的**。实现时接上真实字段
（`Batch.hbos_source_type`）后分成三种情形：

| 来源类型 | 文案 |
|---|---|
| 自产 | ⓘ 可以不填（原文案） |
| **外购** | ⚠ **必须填**——待检证要印这三项，现在提交会缺栏，收货方可能不认 |
| **未记录** | ⚠ 平台无法判断，**不替用户下结论**，请自行确认 |

第三种是刻意的：不知道就说不知道，不猜。这与 `api._enrich_from_master`「多命中不猜、
只列候选」是同一条纪律。

### 6.2 批次页「卡片为何不在」有三种原因，不能共用一句文案

原型只有一个「生成失败」态。实现时发现还有两种同样常见的情形，且**下一步动作完全不同**：

| 情形 | 判定 | 文案与动作 |
|---|---|---|
| 入库单**还没提交** | 该批次无已提交的入库单 | ⓘ 提交后就自动出，**不需要**在这里手动生成 |
| 提交了但**生成失败** | 有已提交入库单、无附件 | ⚠ 提供「重新生成」+ 说明「不影响入库本身」 |
| **外部已有批次** | 无放行状态字段（非本流程建） | ⓘ 本工作台的入库流程不涉及它 |

三态合并会让「还没提交」的用户误以为出错了、去点「重新生成」——而那时
`StockEntry.on_submit` 钩子还没跑过，生成了也是多余的。

### 6.3 附件地址是跨源绝对地址

实测确认：`HBOS-B2607519-待检证+货位卡.pdf` 的下载链接必须是
`http://localhost:8080/private/files/...`（Frappe 源），不能是相对路径。
直连该地址返回 `200 / application/pdf / 72638 bytes` ✅。
