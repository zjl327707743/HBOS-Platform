## 1. 范围：**刻意只读**

侧边栏「主数据」组三项：批次（已前端化）、货位、物料。

这两页**不新建、不修改、不删除任何主数据**。理由不是「做不了」，是**不该由这个前端做**：

| 主数据 | 谁维护 | 为什么前端不该改 |
|---|---|---|
| **物料** | **SAP 分配代码** | 平台不能自造物料代码。这是既定口径——识别到未知物料时只提示去建档，从不自动创建 |
| 物料的 HBOS 专属字段 | 入库拍照识别页**仅补空**、受权角色 | 已有的写入路径有明确的「只补空、不覆盖人工修正」语义，不该在这个浏览页开第二个入口 |
| **货位** | ERPNext 主数据 | 货位树的层级直接决定「哪些节点能存货」，改错会破坏入库/出库的落点 |

所以本轮的产出是：**查得到、看得懂、能跳到相关页面、能打印二维码** —— 仅此而已。

改动入口在页面顶部写成一条明确的说明条，不在按钮上做「禁用态」——
禁用态会让人反复点击试图弄明白为什么不能点，说明条一次讲清。

### 4.1 主从两栏，左侧列表粘住

物料 129 条，列表必须能滚；而右侧详情字段多（11 项）。用**左侧固定高、内部滚动**的做法，
列表与详情各自滚，不互相带着跑。

搜索放列表顶部而不是页面顶部——它只作用于列表，放页面顶部会让人以为过滤的是整页。

### 4.2 空字段不藏，但要说清「为什么空」

「效期期限」「生产车间」为空时**照常显示，值写「未设置」**，并给一条说明：

> 有 2 项主数据为空。入库拍照识别时若在标签上读到，会**仅补空**写回这里；已填的值不会被覆盖。

不说这一句，仓管看到空字段会以为数据坏了；说了，就变成「这是正常的，将来入库时会补上」——
正好把入库流程的「仅补空」语义也传达给了使用者。

### 4.3 「相关」是跳转，不是重复查询

详情底部三个按钮都跳到**已带好过滤条件**的既有页面（货位明细表 / 按批号查货位 / 批次列表）。
这一块存在的理由是：仓管在物料页的高频下一步就是「这批料放在哪」，让他手动复制代码去报表里搜是浪费。

### 5.1 树：原定懒加载，实现时改为一次取全

原计划用 `get_children` 懒加载（也是 ERPNext Desk 的做法）。**实现时改了**，
因为 Owner 选定的第 4 条（分组节点显示下级汇总）让懒加载变得别扭——
`get_children` 只给直接子节点，算整棵子树的汇总要递归请求。

**§9.1 记录了完整理由与代价。** 这里保留原方案，是为了让偏离有据可查。

展开状态记在组件内，切走再回来会重新加载——**不做「记住展开到哪」**（这一条实现了）。

### 5.2 「可存货 / 分组」是这一页最重要的区分

`api.py` 里那条规则是硬的：

> 「『{0}』是库位 / 层等分组节点，不能直接存货。请选择具体货位。」

所以：

- **树里**每个节点右侧标注 `分组` 或 `货位`，形状也不同（文件夹 vs 叶子图标）；
- **详情**顶部一个明确的 `✓ 可存货` 徽标，字段区再写一行「货位（叶子）· 可存货」；
- 分组节点被选中时，徽标改为警示态并写明**「此节点不能存货，请选具体货位」**。

**原型里演示的是可存货的叶子节点。** 分组态的样子需要你确认——我没在这一版里画出来，
因为它牵涉一个判断：**分组节点要不要显示「当前库存」**。
分组本身不存货，但它的**下级**可能有库存。我倾向**显示下级汇总并标明是汇总**，
不做则整块隐藏。**这一条想听你的**（§8）。

### 5.3 二维码放详情里，不放列表

打印二维码是**针对某一个货位**的动作。放列表行里会让人误点错行；放详情里，
「选中 → 打印」是清晰的因果。实测该 Print Format 渲染正常（60×40mm 标签纸）。

### 5.4 库存表只读、且不合计

来自 `Bin`，按批号逐行列出。**不做数量合计**——同页面其它地方已经确立过这个口径
（概览页的「不显示库存合计：不同物料的计量单位不同，相加没有意义」）：
货位下可能是 Kg 与「个」混放，加一起没有意义。

## 6. 状态设计

| 状态 | 物料页 | 货位页 |
|---|---|---|
| 加载中 | 列表骨架 + 详情骨架 | 树骨架 + 详情骨架 |
| 有数据 | 列表 + 详情 | 树 + 详情 |
| **无结果** | 「没搜到这个物料」+ 说明代码由 SAP 分配、平台不能自造 | 「没有货位」+ 指向 ERPNext |
| 出错 | 「取不到这个物料」+ 建议核对 | 「取不到这个货位」 |
| 空列表（无搜索） | 同上但文案不同 | 同上 |

**「没搜到」与「出错」分开**，与报表页同一条纪律。物料页的「没搜到」文案特意点明
「代码由 SAP 分配，平台不能自造」——因为仓管第一反应会是「那我建一个」。

## 9. 实现记录与一处**与审查意见的偏离**

**已完成**：`InventoryItemView.vue` / `InventoryWarehouseView.vue` / `services/inventoryMaster.ts`，
路由 `/hbos/inventory/item/:itemCode?`、`/hbos/inventory/warehouse/:warehouseName?`。

### 9.1 偏离：货位树由「懒加载」改为「一次取全」

第 5 条审查的是「货位树用懒加载」，实现时改成了一次取全部节点、在前端建树。
**这是一处主动偏离，理由如下**（当时应更早说明）：

1. **分组节点的下级汇总成了硬需求**（第 4 条 Owner 选定）。ERPNext 的
   `get_children` 只给**直接**子节点，要算「这个库位下共有多少库存」得递归 N 次请求；
   全量在手时用 `lft`/`rgt` 一次筛出整棵子树即可。
2. **面包屑同理**——有全量就能一路向上找父节点，不必逐级请求。
3. 实测规模：**224 个节点 × 7 字段**，响应体很小；且这是「查主数据」不是高频操作。

**偏离的代价（如实记录）**：货位数量再涨一个量级（数千）时，首屏会变慢，
届时需要改回懒加载 + 服务端聚合。**当前规模下不构成问题，但这是个会随规模恶化的地方。**

### 9.2 复刻时发现并修掉的两个缺陷

**(a) 批次页「当前库存」恒为空（上一轮已交付的缺陷）**

`getBatchStock` 用 `Bin` 按 `batch_no` 过滤 → 服务端 417
（`DataError: 查询过滤条件字段无效…batch_no`）→ 被 `catch` 吞掉 → 界面显示
**「当前没有库存」**。

**根因**：ERPNext v16 起 **`Bin` 上没有 `batch_no`**，批次级库存在
`Serial and Batch Entry`。

**这正是本项目反复在防的「把故障读成空」——而写的时候自己犯了。**
上一轮还专门检查过「空态与错误态必须分开」，却在一个 `try/catch` 里把错误静默转成了空。

**(b) 货位页「下级库存汇总」取不到数** —— 同一个根因、同一处写法。

**统一修法**：两处都改走**本 App 已有的报表**，不另写一套 SQL：

| 页面 | 改用 | 为什么 |
|---|---|---|
| 货位页库存 | `货位明细表` + `{warehouse, include_children:1}` | 它的 `_warehouse_scope` **已经**按 `lft/rgt` 展开整棵子树 |
| 批次页库存 | `按批号查货位` + `{batch_no}`，再按精确批号筛 | 报表 SQL 已审计，与报表页口径天然一致 |

理由与「`lft/rgt` 只写一处」相同：**同一个问题不要有两个算法**。
（报表的 `batch_no` 是 LIKE 模糊匹配，故客户端再按精确批号筛一遍。）

**错误不再被吞**：两处都改成把异常抛出去，界面分成
`取不到库存` 与 `当前没有库存` **两个状态**，错误态带重试并写明「**不代表这里没库存**」。
