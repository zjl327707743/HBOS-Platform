# 生产看板 — 取数架构方案对比

> Status: **待 Owner 决策**
>
> Date: 2026-10-02
>
> 背景：看板原型与口径已定稿（见 `P4_生产看板视觉方案与页面结构.md` REV 7）。
> 本文解决**下一个卡点** —— 数据怎么从飞书进到页面。
>
> 关联：`P4_生产看板_AI分析服务规格.md`（AI 分析节点）、`P4_生产看板_会议纪要与既有项目口径对照.md`

## 1. 要解决的问题

看板需要读 **9 张飞书表**：

```text
Base 3  NGSdbumUGa8oWQsT5E9cwviWn0c
  产量明细数据-二车间 / 三车间 / 四车间 / 五车间 / 六车间 / 粗品 / 无菌   ← 完成、收率（按收料日期）
  月度生产计划明细                                                    ← 目标（1–31 日求和）
  月度目标产能                                                       ← 目标收率

Base 新 Dl45bIEEya78fWsL4DXcwuJtn8c
  AI工艺分析结果                                                     ← AI 分析结论摘要
```

**难点**：飞书 OpenAPI 要 `app_id` / `app_secret`，而**浏览器里不能放密钥** —— 放进去等于公开
（任何人打开 DevTools 就能拿到，进而读写你们全部多维表格）。

所以**必须有个服务端来持有凭据**。问题只是这个服务端长什么样。

## 2. 三个方案

### 方案 A —— 前端直连飞书 OpenAPI

```
浏览器 ──(app_id/app_secret)──> 飞书 OpenAPI
```

| | |
|---|---|
| 工作量 | **最小** —— 前端加几个 axios 调用即可 |
| 安全性 | ❌ **不可接受** |
| 否决理由 | 密钥进前端产物 = **对所有人公开**。且必须开 `Access-Control-Allow-Origin`，任何网站都能借你们的凭据读表 |

**结论：不做。** 列在这里是为了把选项说完。

### 方案 B —— 独立取数服务（**推荐**）

```
浏览器 ──HTTP──> HBOS 取数服务 ──(app_secret 在服务端)──> 飞书 OpenAPI
                      ↑
                 services/hbos_production
```

**本仓库已有先例**：`services/hbos_ocr` 就是这么做的（独立 FastAPI 服务，密钥在 `.env`，
README 明确「照片不出内网」「独立服务，通过 HTTP 交互，不修改 Frappe 核心源码、不直连数据库」）。

| | |
|---|---|
| 工作量 | 中 —— 起一个 FastAPI 服务 + 3~4 个接口 |
| 安全性 | ✅ 密钥只在服务端 `.env`，前端拿不到 |
| 与既有架构 | ✅ 照 `hbos_ocr` 的模式，同一套规范 |
| 依赖 | 需要能跑服务的机器（本机 / 内网服务器 / Docker） |

**服务要暴露的接口**（建议）：

```text
GET /production/monthly          → 当月在产产品行（完成/目标/完成率/收率/目标收率）
GET /production/yesterday        → 昨日入库量（按收料日期）
GET /production/ai-analysis      → AI 分析结论摘要（读 AI工艺分析结果表）
GET /health                      → 健康检查
```

**响应直接就是看板要的结构**（服务端把 7 张明细表聚合完再返回），前端**不做计算** —— 口径逻辑集中一处，不会前后端两套算法对不上。

### 方案 C —— 走 `hbos_portal` 的 provider 模式

```
浏览器 ──> hbos_portal（Frappe）──> 各 App 的 provider ──> 飞书 OpenAPI
```

复用 Portal 已有的 `get_summary` / `get_tasks` 那套。

| | |
|---|---|
| 工作量 | 中（要建 Frappe App + 注册 provider） |
| 安全性 | ✅ 密钥在 Frappe 服务端 |
| 与既定口径 | ❌ **冲突** —— Owner 2026-09-29 定过「生产看板与 Frappe 没有任何关联」「不建 Frappe App、不注册 provider」 |

**结论：与既定口径矛盾。** 若 Owner 改口径，这条路技术上也成立（有先例：LIMS/Inventory 的 provider），
但会带来「生产看板必须依赖 Frappe 运行」的耦合。

## 3. 三方案对照

| | A 前端直连 | **B 独立服务**（推荐） | C hbos_portal |
|---|---|---|---|
| 密钥安全 | ❌ 公开 | ✅ 服务端 | ✅ 服务端 |
| 工作量 | 最小 | 中 | 中 |
| 与既有先例 | — | **`services/hbos_ocr`** ✅ | LIMS/Inventory provider ✅ |
| 与「与 Frappe 无关」口径 | ✅ 不冲突 | ✅ 不冲突 | ❌ **冲突** |
| 谁能维护 | 前端 | 前端/运维 | **必须懂 Frappe** |
| 部署 | 无 | 需跑服务 | 随 Frappe |

## 4. 推荐与理由

**推荐方案 B**，四条理由：

1. **安全上唯一没有妥协的可行选项**（A 直接排除，C 虽安全但违背既定架构口径）；
2. **有现成模板** —— 照 `services/hbos_ocr` 抄结构（`app/config.py` 环境变量 / `.env` / FastAPI / 独立端口），
   连「密钥在 `.env` 不进仓库」这条都不用重新想；
3. **口径集中一处** —— 7 张表明细的聚合、收料日期落月、合并规则、排除规则全在服务端，
   前端只渲染。日后口径变了改一处；
4. **不引入 Frappe 依赖** —— 与 Owner 既定口径一致。

## 5. 建议的服务边界

```text
放服务端的          读飞书（密钥）· 按口径聚合 · 结果缓存 · 供前端查询
不放服务端的        不写飞书（除 AI 分析结果的写入，见 AI 规格）· 不做权限/用户体系
```

**只读为主**。唯一写入是 AI 分析服务往 `AI工艺分析结果` 写（那是独立职责，见另一份文档）。

**端口建议**：`8101`（`hbos_ocr` 占了 `8100`）。
**绑定**：`127.0.0.1`（同 `hbos_ocr` 的做法，不开外网）。

## 7. 本方案明确不做的

- 不写业务规则（口径已在前述文档定稿，本文只说「放哪算」）
- 不做权限体系（看板当前无登录态要求，如日后要，另议）
- 不做实时推送（按需拉取即可；如要实时刷新，另议）
- **不写任何飞书表**（取数服务只读；写入职责归 AI 分析服务）
