## 1. 范围：我最初的两条理由**都不成立**，已更正

> **本节经过一次更正。** 初稿里我写了两条理由，Owner 追问后我逐条核实，
> **两条都是错的**。原文保留在 §1.3，作为「不要把推断当事实」的记录。

### 1.1 更正一：说「提交会被拒」——**错**

初稿写：

> 一旦前端省略它们，**提交时 ERPNext 的服务端校验可能直接拒绝**。

**核实结果**：实测这几个子表的 `reqd` 标记：

```text
Delivery Note      items                 reqd=1   ← 唯一必填
Delivery Note      taxes                 reqd=0
Delivery Note      sales_team            reqd=0
Delivery Note      packed_items          reqd=0
Purchase Receipt   items                 reqd=1   ← 唯一必填
Purchase Receipt   taxes                 reqd=0
Purchase Receipt   supplied_items        reqd=0
```

**只有 `items` 是必填。** 缺税行不会被服务端拦下——**会照常提交**。

这比「被拦下」更危险：被拦下至少会报错，而「能提交但账做错了」是**静默的**。
不过这是**推论，我没有实测建单**（那三项零记录，没有可对照的真实单据）。

### 1.2 更正二：说「6 个子表都要建」——**夸大**

实测这几个子表在 ERPNext 里**本来就不可编辑或已隐藏**：

```text
pricing_rules          read_only=1   ← 系统算出来的，人根本不填
item_wise_tax_details  hidden=1      ← Desk 里自己就藏着
```

所以 Delivery Note 的 6 个子表里，**真正要人填的只有 4 个**（items / taxes /
sales_team / packed_items），其中**必填只有 items**。我按「子表个数」下的判断
是把「系统自动算的」和「人要填的」混在了一起。

### 1.3 更正后的真实picture

| 单据 | 记录数 | 人要填的子表 | 其中必填 | 属谁的流程 |
|---|---|---|---|---|
| **Stock Entry** | **29** | items（+ 附加费用，仓库不用） | items | **仓库**（入库/领用/移库） |
| Stock Reconciliation | 0 | items | items | 仓库（盘点调账） |
| Pick List | 0 | Item Locations | — | 仓库（拣货） |
| **Purchase Receipt** | 0 | items + taxes | items | **采购** |
| **Delivery Note** | 0 | items + taxes + sales_team + packed_items | items | **销售** |

**所以真正的问题不是「子表多」，而是「这单该由谁开」：**

- **Purchase Receipt / Delivery Note 是采购单与销售单**，货物流只是它们的副作用。
  `taxes` 里是增值税，`sales_team` 是业绩归属，`packed_items` 是装箱。
  **这些归采购部与销售部，不归仓管。**
- 值得注意：中国的公司 **VAT 是实的**（Company `country = China`，币种 CNY）——
  一张没有税行的出库单，账面收入就不含税。所以这两张单要么完整做（含税模板选择器），
  要么别做。**半做比不做更糟。**

### 1.4 结论（不变，但理由换了）

```text
本轮做      Stock Entry —— 仓库真正在用的（29 条记录），且 2 张子表里仓库只用 items
下一轮议    Stock Reconciliation、Pick List —— 字段少、属仓库，但没有记录
先不做      Purchase Receipt、Delivery Note —— 属采购/销售流程，且需要完整的税处理
```

**但这条结论现在依赖一个我不知道的事实**：这两张单**实际由谁开**。

- 若仓管确实要开销售出库（很多公司发货归仓库）→ 它们**是**仓库流程，该做；
- 若由销售/采购在 Desk 开 → 不该搬，`FRONTEND_IMPLEMENTATION_GUIDE` 的
  「不为好看重做 Desk」正好适用。

**这一条我不该替你判断。** 见 §10 第 1 项。

## 5. 四条关键判断

### 5.1 单据类型决定表单形态，不是一个表单打三个补丁

三种 purpose 的差别是**结构性的**：

| 类型 | 源货位 | 目标货位 | 放行预检 |
|---|---|---|---|
| Material Receipt（入库） | — | 必填 | — |
| Material Issue（领用出库） | 必填 | — | **有** |
| Material Transfer（移库） | 必填 | 必填 | — |

所以**列本身就是按类型显示/隐藏的**，不是「都显示但灰掉」。灰掉会让人以为能填。

### 5.2 出库放行预检 —— **本页存在的主要理由**

这是 Portal 化**真正能做而 Desk 做不到**的一件事。

`release_gate.validate_release` 挂在 `Stock Entry.before_submit`，它要求每个出库批次：

```python
status == "已放行" and release_date and cert and cert_file and lims_ref and source == "LIMS"
```

**六项齐全**才放行（缺任一项都拦）。Desk 里仓管要填完一整张单、点提交，
**才知道某一批的手续不全**——然后回去翻批次页、翻 LIMS，再重来。

Portal 版把这件事**提到填写阶段**：明细里每填一个批号，就查出它的放行手续，
在下方逐条列出「缺什么」。**这不是换皮，是流程改进。**

文案上刻意写清**责任边界**：

> 放行状态由 **LIMS** 写入，仓库侧改不了。缺手续请走 LIMS 完成检验与 COA 发布；
> 本页只负责在提交前把话说清楚。

不写这一句，仓管会以为能在这儿补。

### 5.3 「提交被拦」是一个**独立状态**，且表单继续显示

提交真被拦下时，**不能只弹一个错误**——用户需要同时看到「我填了什么」和「为什么失败」。
所以拦住之后表单照常显示，只是上方多一条错误块，并给一条「去看待检批次」的路径。

（**原型里这里踩了个坑**：错误块一度嵌在 `data-view="ready"` 内部，切到 `blocked`
状态时父级被隐藏、错误块一起消失（实测高度 0）。已改成外层在 `ready blocked` 都显示。）

### 5.4 「其它信息」只留三个，其余**明确说不提供**

ERPNext 的 Stock Entry 还有附加费用、序列号明细等。原型底部一句话交代：

> 附加费用、序列号明细等 ERPNext 字段**本页不提供**——仓库日常用不到，
> 需要时到 ERPNext 原表单里改。

**为什么不是「都收进来」**：收进来就要跟着上游版本维护，而仓库流程用不到。
**写明「不提供」比留一堆没人懂的字段干净**——用户知道该去哪儿找。

## 6. 明细表的编辑方式

EA-5.4 §23 要求关键业务表单有 Save State / Validation Summary / Dirty State。
原型演示的是**最低限度**：

- 每行一个「物料 + 批次」，行可增删（删行用 `×` 图标 + `aria-label`）；
- **单位只读**——它取自物料主数据，不该在这儿改（改了会和主数据不一致）；
- 批号管理的物料必须填批次（底部说明里点明，**没有批次就没有货位卡、出库也追不到源头**）。

## 11. 实现记录（2026-09-25）

**已实现**：`InventoryEntryView.vue` / `services/inventoryEntry.ts`，
路由 `/hbos/inventory/entry`（列表 + 新建）与 `/hbos/inventory/entry/:entryName`（编辑）。

### 11.1 实现前验掉的两个前提

**(a) 空 items 的 insert 会失败** —— 实测：

```text
MandatoryError: [Stock Entry, MAT-STE-2026-00030]: items
```

第一次 0.03 秒就失败，**没留下残留记录**（总数仍是 29）。所以**「空草稿」不存在**——
界面必须先填一行才让保存（§6 的校验因此不是可选项）。这也让「未保存离开提醒」
变得更不重要：用户本来就存不下空东西。

**(b) 服务端会自动带出 company / purpose / 命名系列** —— 实测 insert 成功那次：

```text
created: MAT-STE-2026-00030 | docstatus: 0 | company: hb | purpose: Material Receipt
```

前端**不需要传** company、purpose、naming_series。少传少错。

### 11.2 实测放行预检（用真实批次）

| 批次 | 状态 | 预检结果 |
|---|---|---|
| `B2507343`（待检） | 待检 | 缺 **6 项全部**：状态、日期、证号、**附件**、LIMS 引用、来源 |
| `TEST-M3R1-B001`（已放行） | 已放行 | 缺 **3 项**：合格证附件、LIMS 引用、来源 |

第二条特别值得看——**它的状态是「已放行」，但手续并不齐**。这正说明预检的价值：
只看状态是看不出来的，六项缺一不可。同时提交按钮被禁用，文案逐条列出缺什么。

### 11.3 实测的错误呈现

| 场景 | 表现 |
|---|---|
| 明细为空就保存 | 弹「至少填一行明细（物料代码 + 数量大于 0）才能保存。」 |
| 出库没选源货位 | 弹「明细「…」还没选源货位。」 |
| 批号填了不存在的批次 | 服务端抛**中文业务错误**「找不到行 #1: 批号: E2E-TEST-BATCH」——没有变成英文状态码 |
| 保存成功 | 跳到 `/hbos/inventory/entry/MAT-STE-2026-00030`，单号回落 |
| 放弃草稿 | 二次确认 → 删除 → 跳回列表；**总数回到 29** |

### 11.4 一处刻意的取舍

**改类型会清掉已选的货位**（保留物料/数量/批号）。因为三种类型的源/目标组合不同，
留着「入库单里带源货位」这种组合，提交时会被服务端拒——**与其留着让它出错，
不如当场清掉**。

### 11.5 范围遗留

Owner 说销售出库 / 采购入库也属仓库，但实测有两个硬前提：

```text
Customer（客户）   0 条   ← Delivery Note 的「客户」是必填
Supplier（供应商） 1 条
Sales Order        0 条
Purchase Order     0 条
```

**没有客户档案，销售出库连单都开不出来。** 客户从哪来（SAP？手工建？）需要 Owner 定，
在此之前这两张单无法推进。

### 11.6 一个已交付的缺陷：**提交单据必然失败**

做拣货单时实测发现，**此前两处提交都是坏的**：

- `inventoryDocs.submitIntakeDraft`（草稿复核页「提交入库」）
- `inventoryEntry.submitStockEntry`（库存单据页「提交」）

两处都只传 `{doctype, name}`。而 `frappe.client.submit(doc)` 内部是
`frappe.get_doc(dict)` —— 它**不按名字去库里加载**，而是**拿传进来的 dict 当文档**。
于是必失败，两种错实测都复现了：

```text
TimestampMismatchError: ... has been modified after you have opened it
（因为 dict 里没有 modified，check_if_latest 判定「你打开后别人改过」）

ValidationError: 目的必须是一个'Material Issue', ...
（就算过了上一关，dict 里也没有 purpose）
```

**实测对照**：先 `frappe.client.get` 取全文、再把那份 dict 传去提交
→ `docstatus = 1` ✅

**修法**：`frappeClient` 新增 `getDocument` / `submitDocument` / `saveDocument`，
**先读全文再改/提交**；三处全部改走它。`inventoryEntry.updateStockEntry`
原先手拼字段，同样是 `get_doc(dict)` 语义，一并改掉。

**排查时留下的痕迹**（用户已确认「系统里的单据先不管，等正式部署前再处理」）：

```text
MAT-STE-2026-00030   草稿（创建者不明，备注是拍照识别草稿）
MAT-STE-2026-00031   已取消（我 A/B 测试提交的，有库存流水故删不掉）
MAT-STE-2026-00032   已取消（同上，浏览器端到端验证那次）
```
