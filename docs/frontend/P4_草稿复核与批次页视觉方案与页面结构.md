## 1. 为什么做这两页

入库流程走完前两步后，仓管原本还有两次跳后台：

```text
① 拍照识别              ✅ 已前端化
② 打开草稿复核 + 提交    ❌ 跳 /app/stock-entry/<name>   ← 本页之一
③ 取待检证/货位卡去贴货位 ❌ 跳 /app/batch/<name>          ← 本页之二
```

只做 ② 的话，提交完仍卡在 ③——同一个问题往后挪一格。所以两页一起做，把入库流程**整条打通**。

## 2. 范围边界（刻意收窄）

**只做「拍照识别建的草稿」这一类**，即 `Stock Entry` 上 `hbos_intake_batch` 非空的
Material Receipt。判据那个字段是现成的——`setup.py` 里写得很明确：

> 「非空即代表来源是拍照识别——提交后据此提示去批次取货位卡 / 待检证。」

**不重造通用 Stock Entry 表单。** 通用表单动辄几十个字段 + 子表 + 税 + 序列批次明细，
重造一遍等于把 ERPNext 抄一份，还会跟着上游版本漂。而这类草稿的形状是固定的：
单物料、Material Receipt、带一张照片、带批次信息。

**通用 Stock Entry 要不要也前端化，单独议**，不在本轮顺手决定。

## 3. 视觉强度：V1

按 EA-5.4 §2.2。无 aurora、无模糊、实底卡片、布局稳定。域色只用于侧边栏当前项。

```text

│ HBOS  H  HBOS/仓储库存工作台          [] 🔔 ? AD              │
├────────────┬─────────────────────────────────────────────────┤
│ 侧边栏      │  仓储库存 / 入库拍照识别 / 草稿复核              │

│            │ │  供货单位 未填          │ ⓘ 提交后才生成…   │ │

│            │ │ 包装构成 / 件数         │                    │ │
│            │ │ 标签原文（可检索）      │                    │ │
│            │ └───────────────────────┴────────────────────┘ │
│            │ ┌────────────────────────────────────────────┐ │
│            │ │ 提交会立刻入账…  [放弃草稿] [提交入库]      │ │ ← 常驻
│            │ └────────────────────────────────────────────┘ │
└────────────┴─────────────────────────────────────────────────┘
```

### 4.1 为什么用「键值行」而不是可编辑表单

这是**复核**场景，不是录入场景。操作员要的是「跟照片对一遍，没问题就提交」，不是重新填一遍表单。所以：

- 主区用 `dl / dt / dd` 键值行，左标签右值，**读起来像单据，不像表单**；
- 数量与货位是唯一两个**常改**的字段，但它们已经在动作条里可编辑（见下），不必在主区再放一遍输入框；
- 不做「每行都可编辑」的假象——那会让人以为处处可改，实际后端只接受部分字段。

### 4.2 「有 3 项没填」的告警带条件

批次信息里「供货单位 / 生产单位 / 原厂批号」为空时给橙告警，但**文案写清了为什么可以不填**：

> 主要是**外购料的待检证**要用——本次来源是**自产**，可以不填。若这张标签其实是外购的，
> 请回上一步改来源并补填。

不说这一句，操作员会以为漏填了、卡在这里不敢提交。

### 4.3 提交是唯一 Primary，且明确告知后果

动作条文案：**「提交后会立刻入账，并生成货位卡与待检证。提交前请对着照片核对数量与货位。」**

「提交」这个词本身没说清是「存一下」还是「真入账」——对仓库单据必须讲明白，因为**提交后要冲销就得走红字**。

「放弃这张草稿」放在次级位置、用普通按钮——它是破坏性动作，但不该比提交更显眼。
**它需要二次确认**，且确认文案要说清后果（照片与批次信息一起丢弃、不可恢复），
不是一句「确定吗？」。

### 4.4 四个状态

| 状态 | 呈现 |
|---|---|
| 正常 | 键值行 + 照片 + 动作条 |
| 加载中 | 骨架，与最终布局同尺寸 |
| 找不到 | 「单号可能已被删除…**草稿还没入账**——如果它曾经存在，账面不会有任何记录」+ 回上一步 |
| 已提交 | 「账面已入账，货位卡与待检证已生成」+ **直接带去批次页**的两个按钮 |

「找不到」那句刻意点明「草稿没入账」，因为操作员最担心的是「我是不是漏了一笔」。

## 5. 页面 B：批次页

```text
┌──────────────────────────────────────────────────────────────┐
│ HBOS  H  HBOS/仓储库存工作台          [] 🔔 ? AD              │
├────────────┬─────────────────────────────────────────────────┤
│ 侧边栏      │  仓储库存 / 批次 / B2609503                      │
│            │  批次 B2609503              [已放行] 放行来源:LIMS│
│ 主数据 ◀    │  硝酸钠 · 13000901 · 自产                        │
│  批次       │ ┌───────────────────────┬────────────────────┐ │
│            │ │ 货位卡 / 待检证 ★      │ 库存                │ │
│            │ │ ┌───────────────────┐ │  所在货位 A-01-03   │ │
│            │ │ │📄 HBOS-…pdf       │ │  现有数量 100.000kg │ │
│            │ │ │ [打印][下载][重生成]│ │  入库单 MAT-STE-…  │ │
│            │ │ └───────────────────┘ ├────────────────────┤ │
│            │ │ 批次信息（只读）       │ 质量放行（LIMS 只读）│ │
│            │ │ 包装构成 / 件数        │  放行状态 已放行     │ │
│            │ │ 标签原文              │  🔒 未放行的批次出不去│ │
│            │ └───────────────────────┴────────────────────┘ │
│            │ ┌────────────────────────────────────────────┐ │
│            │ │ 打印货位卡贴到货架…      [打印货位卡/待检证]│ │
│            │ └────────────────────────────────────────────┘ │
└────────────┴─────────────────────────────────────────────────┘
```

### 5.1 为什么把「货位卡 / 待检证」放在最前面

**这是仓管来批次页的唯一理由。** 他们在入库提交后要做的事就是「把这个 PDF 打出来贴到货架上」。所以它是页面第一块、视觉最重（绿色成功态边 + PDF 图标 + 三个动作），而不是埋在「附件」这种通用区域里。

### 5.2 「重新生成」为什么放在这里

现有 Desk 版在 `Batch` 表单上有「重新生成货位卡 / 待检证」按钮（`public/js/batch.js`），后端有对应的 whitelisted 方法 `doc_gen.regenerate_for_batch`。前端化时这个能力必须一起搬——否则 PDF 生成失败（`doc_gen` 的 `on_submit` **刻意吞掉异常**、只记 Error Log）之后，仓管就没路可走了。

原型里专门有一个 **「附件生成失败」** 状态演示这条路径，文案如实告知：

> 入库本身已完成，账面不受影响。点「重新生成」重试；若反复失败，请联系管理员查看错误日志。

并说明安全边界：**「重新生成」会替换上一次生成的那份，人工上传到本批次的其他附件不受影响**（对应 `doc_gen._purge_previous` 的既定行为——它只删自己那份）。

### 5.3 质量放行区是只读的，且明确说了为什么

批次上有 LIMS 写入的放行投影字段（`hbos_release_status` / `hbos_release_date` / `hbos_certificate_no` / `hbos_lims_reference` / `hbos_release_source`），由 `quality_projection.py` 守成仓库侧只读。前端**必须保持只读**，并用一个 ⓘ 说明：

> 放行状态由 **LIMS** 写入，仓库侧只读。出库时系统会校验它——未放行的批次出不去。

这句不只是解释，还是在告诉仓管**为什么它不能改**——否则会有人反复点击期待它能改。

### 5.4 「批次信息」为何只读

生产日期、储存条件、供货单位这些在提交入库时定下，且**已经印在发出去的货位卡上**。允许前端改会造成「纸上和系统不一致」。原型底部说明：

> 这几项在提交入库时定下，之后不再改动。要改请找管理员——它们印在已发出的货位卡上。

## 6. Typography

严格走 EA-5.4 §44 **v2.0**。脚本核对：无 13/15/17/18/19/21/22/26/28/32，无半像素；只用 30/20/16/14/12；字重只有 400/500/600。全部走 token，无裸字号。

## 7. 状态语义映射

按 EA-5.4 §24，**色 + 文字 + 图标三通道并存**：

| 本页状态 | 语义 | 呈现 |
|---|---|---|
| 草稿 · 未入账 | warning | 橙 + 文字 + ⓘ |
| 已提交 | success | 绿 + 文字 + ✓ |
| 待检 / 未放行 | processing | 蓝 + 文字 |
| 已放行 | success | 绿 + 文字 + ✓ |
| 生成失败 | warning | 橙 + 文字 + ⚠ |
| 找不到 | critical | 红图标 + 文字 |

## 8. 响应式

| 断点 | 行为 |
|---|---|
| ≥1600 | 居中，max-width 1600 |
| 1200–1599 | 标准桌面，双栏 |
| 768–1199 | 侧边栏折叠 76px；**双栏改单栏**；键值行由「左右」改「上下」（`dl` 在窄屏挤成两列会折断中文） |
| <768 | 侧边栏隐藏；页头 64px；动作条按钮撑满 |

已在 1440 / 1100 / 390 下实测，无横向溢出。

## 9. 实现缺口（原型是目标态）

| 能力 | 现状 |
|---|---|
| 读草稿 `frappe.client.get` | ✅ whitelisted，GET 可用 |
| **提交** `frappe.client.submit` | ✅ whitelisted（POST/PUT），已确认 |
| 提交会不会被门禁拦 | ✅ **不会**。`release_gate.py` 只拦出库；Material Receipt 注释写明「待检物料本就该能入库」 |
| 待检证/货位卡 PDF | ✅ 提交时由 `doc_gen.generate_for_stock_entry`（`Stock Entry.on_submit`）自动生成 |
| 重新生成 | ✅ `doc_gen.regenerate_for_batch` whitelisted |
| 批次读 | ✅ `frappe.client.get` |
| **删除草稿** | ✅ **已查证可行**。`frappe.client.delete` → `delete_doc` → `check_permission_and_not_submitted`：走 `doc.check_permission("delete")`，且**已提交的单据会被拒**（`Submitted Record cannot be deleted`）——正合本页需要（只能删草稿） |
| CSRF | ✅ 上轮已解决 |

**删除草稿的一处细节**：`frappe.client.delete` 同时接受 POST 和 **DELETE** 方法。
Portal 的 `frappeClient` 目前只有 GET/POST/multipart 三个封装。实现时用 **POST**
（避免为它单独开路，也不需要 DELETE 的额外跨源预检）。

**「放弃这张草稿」要做二次确认**——它是破坏性动作。确认文案要说清「照片与批次信息
会一起丢弃，不可恢复」，而不是一句「确定吗？」。
