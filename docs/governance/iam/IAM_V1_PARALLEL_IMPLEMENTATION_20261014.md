## 2. 已确认的 V1 规则，覆盖旧候选中的冲突条款

Owner 于 2026-10-13 明确要求首版简单可用，并确认普通部门权限自动迁移、高风险单独授予；2026-10-14 要求与项目合并并行继续权限开发。10月12日文档是复用依据，不是要整包实现的强制模型清单。

1. 保留唯一 Frappe User、原生 HRMS Employee、Company/Department。飞书和密码共用同一 User、Employee 关联及有效授权，不新建第二套人员/密码体系。
2. 企业确认员工后，在管理员触发或已核准名册同步中受控自动建户。未核准人员不能通过公开注册或任意 OAuth 回调自行开户；不按姓名、手机号或邮箱猜测绑定。
3. 每人独立随机临时初始密码，安全一次性交付；管理员可以重置临时密码，但不能读取员工现用密码。首次使用临时密码须改密；不生成全员通用默认密码，不将明文密码存入日志、Git、审计正文或批量名单。复用 Frappe 密码及既有 MFA/CSRF/state/企业核验/会话撤销。
4. 飞书身份按 provider + tenant_key + app_id + 已核验 id_type/open_id 绑定。导出表的“用户 ID”不能未经确认就当作 open_id。部门按稳定外部 ID 映射原 Department；无法对账的条目进入待核对，不自动合并或删除。真实数据缺失不阻塞合成测试。
5. 部门权限是可选默认模板，不是唯一授权依据。管理员可对个人增、删、改 APP 进入资格、具体操作点、完整数据范围；支持明确允许与明确禁止，匹配范围内的个人禁止优先于部门/岗位允许。
6. HR 修改已核准主部门后，旧部门来源的普通权限失效，新部门已配置的普通权限自动生效，不另建逐次审批流。没有模板即没有新增授权；离职/停用/撤权必须及时失效，不能等重新登录。个人授予要标明是否绑定某个部门/岗位来源；来源失效的授权撤销，明确独立的个人授权只在自身范围及有效期内保留。
7. LIMS 质量签署、重要库存调账、平台管理等高风险动作不随部门模板自动授予，必须由具备对应管理资格的管理员明确配置并留审计；不绕过本人自审禁止、质量放行等领域硬约束。不得把 System Manager 默认视为所有业务签署人。
8. Portal、受限管理中心、原生 Desk 共用账号但入口权限分离。关联 Employee、赋予基础员工角色时，不得意外开通 Desk 或重新激活停用账号。
9. V1 不做通用多级审批、复杂委派中心或全套角色版本平台。复用 #37 已有合适代码和页面；不要仅为与旧候选一致而一次创建全部拟议 DocType。最少保留必要持久化、管理员操作审计、授权来源和失效/缓存版本。
10. 页面隐藏不算鉴权。Frappe 原生 Role/DocPerm/User Permission 与 HBOS 动作/范围约束必须共同在服务端执行；不能向原生 Role 无限制投影以获得 UI 效果。API、Desk、列表、统计、导出、附件、后台任务应遵循相同限制。未知动作/缺 scope/不完整身份默认拒绝，不把空范围当 ALL。

## 3. 开发包与本窗口第一交付

### A1：账号建户、双登录与安全生命周期（先做）

读取现有 `auth/feishu.py`、`onboarding.py`、`accounts.py`、`operations.py`、Identity/Security DocType 与测试，复用现有实现。解耦“登录配置完整/已有账号可登录”和“允许受控建户”，不要粗暴关闭 auto_provision_internal 后连旧绑定都锁死。

交付受控建户/精确 Employee 关联、随机临时密码/首次改密/管理员重置、已绑定飞书和密码同账号、无归属身份拒绝、重复/并发幂等及冲突提示。优先使用现有账号安全操作模型；真实名单导入、正式 Feishu secret/站点设置不在本轮权限内。管理员重置或换绑要复用已有重新验证和会话撤销，不以“简化审批”为由取消身份验证。

先补回归失败用例，再写最小实现。本窗口首个输出必须是**真实代码 Draft PR + 可复跑测试**，不是又一份仅供继续讨论的总设计。开工时提交一张短的字段/文件差异清单；未决事项保守关闭，仅把确实需要 Owner 决策的内容列出，不阻塞不相关能力。

### B1：部门默认 + 个人覆盖（A1 后或独立无共享冲突时并行）

实现一个可复用的服务端决策入口，输入采用受信 User、app/action 和完整 scope，不接受浏览器声称的 roles/department。保留“动作与范围绑定”的授权单元，不能将角色集合和范围集合交叉组合。高风险类别来自服务端注册表，不由前端自报。

管理员页面必须能看到有效权限及来源，并做到单人 APP 可见性/操作点/数据范围的新增、取消、禁止、恢复继承。撤销个人额外授权与明确禁止部门继承是两个不同操作。修改原部门必须原子撤旧/生新，后端缓存及时失效。操作需有授权人、时间、前后值与理由；初版不强制额外多级审批。

### A2/管理闭环：组织对照与四页最小可用管理

从 #37 精确复用组织/岗位/任职的必要模块及 peopleAccess 组件，用真实 Frappe API 替换 demo store。保持 User/Employee/Department 权威，组织多部门关系与业务数据范围分开。首次交付一个员工在“人员→账号→部门→权限→有效权限预览”的完整闭环，而不是只做可点击原型。

## 4. 必须跑的合成正反例

- 已核准员工建户两次仍一个 User；双登录同账户；同名不同人不能合并。
- 未核准飞书用户/冲突身份拒绝；已有绑定在建户关闭时仍正常登录。
- 每人初始密码不同；改密后管理员不能读原密码；旧临时密码/已撤销会话失效；重置流程有重新验证/限流/MFA兼容。
- 普通部门模板自动生效；调岗后旧部门拒绝、新部门普通权限允许；高风险不自动出现。
- 个人额外 APP/动作授权有效；个人明确禁止覆盖模板；撤销额外授权不会伪装成取消所有继承；跨部门个人权限不泄漏到别的 scope。
- A组复核+B组录入不能变成B组复核；平台管理员没有QA签署资格；本人自审与未放行出库始终拒绝。
- Employee 关联不意外授予 Desk；Portal 禁止动作不能被直接 REST/Desk/导出绕过。
- 全部对象/缓存对停用、撤权、过期及时失效；数据迁移在新隔离 Site 双次执行/回滚可核验。

真实飞书 OAuth、公司名单对账、历史数据迁移、正式角色发放和 Owner 浏览器 UAT 分开标注 NOT_RUN。合成测试通过不等于生产可用。
