# 09 安全密钥与敏感数据规范

> **受众**：HBOS 项目全体开发者
> **目的**：确保敏感数据（密码、密钥、Token、员工数据）不会被泄露到 Git 仓库或公开渠道
> **前置阅读**：项目 README.md 中的环境搭建章节

---

## 1. 哪些东西绝对不能提交到 Git

### 1.1 禁止提交清单

| 类别 | 具体内容 | 原因 |
|------|----------|------|
| 环境变量 | `.env` 文件（含真实密码） | 包含数据库密码、管理员密码等 |
| 数据库密码 | `DB_ROOT_PASSWORD`、`MYSQL_ROOT_PASSWORD` | 拿到密码就能直接操作数据库 |
| 管理员密码 | `ADMIN_PASSWORD`、Frappe 后台管理员密码 | 获得系统的完全控制权 |
| API 密钥 | 飞书 App Secret、OAuth Secret、第三方 API Key | 冒充你的服务进行 API 调用 |
| Token | GitHub Token、CI/CD Token、个人访问令牌 | 读取你的代码仓库、触发 CI 流程 |
| 证书文件 | SSL 证书私钥、`.pem`、`.key` 文件 | 私钥泄露 = 加密通信被破解 |
| 员工数据 | 真实姓名、工号、考勤记录、打卡时间 | 隐私数据受法律保护，泄露即违法 |
| 备份文件 | 数据库备份 `.sql`、Docker 卷备份 | 包含完整数据库内容和用户数据 |
| Excel 数据 | `docs/data/` 下的真实员工数据 | 考勤和薪资数据属于高度敏感信息 |
| Session 数据 | Cookie、Session Token、`frapid_session` | 会话劫持风险 |

### 1.2 为什么不能提交

用通俗的方式解释：

> 假设你把家里的钥匙（密码）放在 GitHub 公开仓库里。任何一个能上网的人，只要 clone 你的仓库，就能拿到这把钥匙，打开你的"家门"（数据库、服务器）。

更具体地说：

- **数据库密码泄露**：攻击者可以直接连接你的数据库，读取或删除所有数据
- **Admin 密码泄露**：攻击者登录你的系统后台，创建账号、导出数据、修改配置
- **API Key 泄露**：攻击者用你的飞书身份发送消息、拉取通讯录，所有费用由你承担
- **员工数据泄露**：根据《个人信息保护法》，企业可能面临高额罚款和法律责任

## 2. .env 文件管理

### 2.1 .env.example 和 .env 的区别

HBOS 项目中有两个环境变量文件：

| 文件 | 内容 | 是否提交 Git | 作用 |
|------|------|-------------|------|
| `.env.example` | 密钥的**占位符模板** | **是** | 新成员知道需要填哪些变量 |
| `.env` | 密钥的**真实值** | **否** | 本地开发和部署使用 |

`.env.example` 中的占位符示例：

```bash
# .env.example（可以提交 Git）
DB_ROOT_PASSWORD=<LOCAL_DB_ROOT_PASSWORD>        # 替换为你的数据库 root 密码
MYSQL_ROOT_PASSWORD=<LOCAL_DB_ROOT_PASSWORD>     # 同上
ADMIN_PASSWORD=<LOCAL_ADMIN_PASSWORD>            # 替换为你的管理员密码
```

`.env` 中的真实值（绝不提交）：

```bash
# .env（绝对不能提交 Git）
DB_ROOT_PASSWORD=MyActualSecretP@ssw0rd123       # 真实密码
ADMIN_PASSWORD=AnotherStrongP@ssw0rd456          # 真实密码
```

### 2.2 如何安全地传递给新成员

**原则：密码不通过聊天工具、邮件或文件共享明文传输**

推荐方式（按安全性排序）：

1. **最推荐：面对面或语音电话口述** — 逐字读出来，新成员本地输入
2. **次推荐：密码管理器分享链接** — 如 1Password、Bitwarden，设置一次性查看和过期时间
3. **可接受：自毁式便签** — 如 privatebin.net，设置阅后即焚和过期时间
4. **不推荐：飞书私聊发送** — 聊天记录可能被截屏或在设备同步时泄露
5. **绝对禁止：把 `.env` 文件发到群里** — 群里有离职同事、外包人员、或误加入的外部人员

### 2.3 .env 泄露后怎么办

如果你怀疑 `.env` 已经泄露（例如不小心提交到 Git）：

1. **立即停止使用，不要 panic** — 但需要立刻行动
2. **轮换所有密码** — 修改 `.env` 中出现的每一个密码和密钥
3. **检查泄露范围** — 确认密码是否已出现在公开仓库、聊天记录或其他地方
4. **清理 Git 历史** — 参见第 9 节
5. **通知团队** — 让所有成员知道需要更新本地密码

## 3. Frappe 站点配置

### 3.1 两种配置文件

HBOS 项目使用 Frappe/ERPNext 框架，运行时会产生两类站点配置：

| 文件 | 位置 | 包含内容 | 安全级别 |
|------|------|----------|----------|
| `common_site_config.json` | Docker 卷内 | `db_host`、`db_port`、Redis 地址 | 低敏感（无密码） |
| `site_config.json` | Docker 卷内 | `db_name`、`db_password`、`db_user`、加密密钥 | **高敏感** |

### 3.2 site_config.json 包含什么

`site_config.json` 是 Frappe 在创建站点时自动生成的，包含：

- `db_name`：数据库名称（自动生成的唯一标识，格式如 `_` 前缀的随机字符串）
- `db_password`：数据库用户密码（自动生成的随机字符串）
- `db_user`：数据库用户名
- `encryption_key`：站点数据加密密钥（如果启用）

这些信息存储在 Docker 卷中，**不在宿主机文件系统上**。因此：

- 正常流程下不会误提交到 Git
- 不要手动把这些内容复制到项目目录
- 备份 Docker 卷时，确保备份文件也被 gitignore 保护

### 3.3 volumes/ 目录保护

当前 `.gitignore` 已经包含：

```gitignore
volumes/
```

这意味着所有 Docker 卷数据都不会被 Git 跟踪。不要移除这一行。

## 4. 飞书和外部服务密钥

### 4.1 飞书 App ID 和 App Secret

HBOS 项目后续会集成飞书开放平台能力（消息推送、通讯录同步、考勤数据拉取等）。

**飞书开放平台的关键凭证：**

| 凭证 | 作用 | 敏感度 |
|------|------|--------|
| App ID | 应用的唯一标识 | 低（公开信息） |
| App Secret | 应用的密钥，用于获取 access_token | **极高** |

**管理规范：**

- App Secret 存放在 `.env` 中，示例变量名 `FEISHU_APP_ID`、`FEISHU_APP_SECRET`
- 在 `.env.example` 中提供占位符
- 飞书开放平台后台可以随时重置 App Secret
- 如果怀疑泄露，**立即在飞书后台重置**

### 4.2 OAuth Secret

如果项目使用 OAuth 2.0 实现第三方登录或 API 授权：

- OAuth Client Secret 与 App Secret 同等敏感
- 存储在 `.env` 中，绝对不提交 Git
- 各 OAuth 提供商（GitHub、Google、飞书）均提供后台重置功能

### 4.3 API Key 管理原则

无论对接哪个外部服务，统一遵循：

1. **一个 Key 一个用途** — 不要多个服务共用一个 Key
2. **最小权限原则** — 只申请当前功能需要的权限，不要申请"全部权限"
3. **定期轮换** — 建议每 90 天更换一次 API Key
4. **测试用 Key 和正式 Key 分开** — 参见第 12 节

### 4.4 测试密钥 vs 生产密钥

| 环境 | 密钥来源 | 特点 |
|------|----------|------|
| 本地开发 | 飞书开发者后台创建测试应用 | 仅影响测试企业，泄露影响可控 |
| 生产环境 | 飞书企业应用正式上线 | 影响真实企业数据，泄露后果严重 |

**绝对禁止用生产 App Secret 做本地开发测试。**

## 5. GitHub Token 和 CI Secret

### 5.1 Personal Access Token 的权限范围

如果你需要 GitHub Token（例如自动化脚本、CI/CD 配置），创建 Token 时务必：

- **选择最小权限**：只勾选当前任务需要的权限
- **设置过期时间**：推荐 30 天或 90 天，不要选"永不过期"
- **经典 Token vs 细粒度 Token**：优先使用 Fine-grained Token，可以精确控制到单个仓库

不需要的权限绝对不勾选（尤其是 `repo` 全量权限和 `admin` 权限）。

### 5.2 CI/CD Secret

如果项目配置了 GitHub Actions 或其他 CI 流程：

- 使用 GitHub 的 **Settings > Secrets and variables > Actions** 功能
- CI 中需要的密钥通过 `${{ secrets.MY_SECRET }}` 引用
- 绝对不要把 Secret 明文写在 workflow YAML 文件里
- 给 CI Secret 起清晰的名字，如 `HBOS_DB_PASSWORD`、`FEISHU_APP_SECRET`

### 5.3 不共享个人 Token

- 每个人的 GitHub Token 是**个人身份凭证**，不要共享给团队成员
- 项目级别的 Token 应使用 **机器账号** 或 **GitHub App** 创建
- 离职成员的 Token 必须及时吊销

## 6. 数据库安全

### 6.1 数据库密码管理

HBOS 项目使用 MariaDB（MySQL 兼容），涉及的密码：

| 密码 | 环境变量 | 用途 |
|------|----------|------|
| Root 密码 | `DB_ROOT_PASSWORD` / `MYSQL_ROOT_PASSWORD` | 数据库超级管理员 |
| 站点密码 | 自动生成在 `site_config.json` 中 | 单个站点连接数据库 |

**要求：**

- Root 密码和 Admin 密码**不能相同**
- 密码长度至少 16 位，包含大小写字母、数字和特殊字符
- 不要使用常见密码（如 `admin123`、`password`、`123456`）

### 6.2 Administrator 密码

`ADMIN_PASSWORD` 是 Frappe/ERPNext 系统管理员的登录密码。

- 这是系统最高权限账号，能访问所有模块和数据
- 不要与数据库密码相同
- 不要使用默认密码（某些系统默认是 `admin`/`admin`）

### 6.3 数据库备份的安全存储

数据库备份文件（`.sql` 或 `.sql.gz`）包含：

- 所有数据库表结构和数据
- 包括用户表、员工表、考勤记录等所有敏感信息

**安全要求：**

- 备份文件存放在 `backups/` 目录（已在 `.gitignore` 中）
- 不要用 U 盘或聊天工具传输备份文件
- 备份文件应加密存储
- 传输备份文件时使用加密通道（SCP、SFTP，而非 FTP）

### 6.4 数据库备份中的敏感数据

即使备份文件不在 Git 中，也要注意：

- 备份文件如果被放在桌面或共享文件夹中，任何有权限的人都能访问
- 本地开发用的备份文件可以在完成测试后删除
- 生产环境备份具有最高安全级别，访问需要明确授权

## 7. 数据脱敏

### 7.1 哪些数据算敏感

在 HBOS 项目的业务场景中，以下数据属于敏感数据：

| 数据类别 | 具体内容 | 敏感原因 |
|----------|----------|----------|
| 个人身份信息 | 员工姓名、工号、身份证号 | 可直接定位到具体个人 |
| 考勤数据 | 打卡时间、迟到早退记录、加班时长 | 员工隐私，可能涉及薪资计算 |
| 组织架构 | 部门、汇报关系、人员编制 | 企业商业信息 |
| 薪资数据 | 工资、奖金、社保、个税 | 高度敏感，受法律严格保护 |
| 联系方式 | 手机号、邮箱、家庭住址 | 个人隐私 |

### 7.2 Demo 数据规范

如果需要展示系统功能（截图、演示、培训），**必须使用虚构数据**：

- 姓名使用"张三"、"李四"、"王五"等通用化名，或"测试员工A"、"测试员工B"
- 工号使用 `DEMO001`、`T00001` 等明显带有测试标识的格式
- 打卡时间随机生成，不与真实考勤记录重合
- 部门名称使用"测试部门A"、"Demo Department"等

### 7.3 测试数据前缀规范

所有测试数据的前缀约定：

| 字段 | 前缀 | 示例 |
|------|------|------|
| 员工姓名 | `测试_` 或 `Demo_` | `测试_张三`、`Demo_Alice` |
| 工号 | `T` 或 `DEMO` | `T00001`、`DEMO001` |
| 部门 | `测试_` 或 `Demo_` | `测试_技术部` |
| 公司 | `测试_` 或 `Demo_` | `测试_科技有限公司` |

### 7.4 禁止行为

- 禁止把真实员工数据推到 GitHub
- 禁止用真实数据做截图或录屏
- 禁止在 Issue 或 PR 描述中贴出真实数据
- 禁止在代码注释中硬编码真实姓名、工号或密码
- 禁止把 `docs/data/` 下的 Excel 文件推送到 Git（已在 `.gitignore` 中）

### 8.3 如何检查是否误提交了敏感文件

**方法一：检查 Git 历史中是否存在敏感文件**

```bash
# 检查是否曾经提交过 .env 文件
git log --all --full-history -- .env

# 搜索所有历史中是否出现过特定敏感字符串
git grep -i "password" $(git rev-list --all)
git grep -i "secret" $(git rev-list --all)

# 检查是否有证书文件被提交
git log --all --full-history -- "*.pem"
git log --all --full-history -- "*.key"
```

**方法二：使用 git-secrets 工具**

```bash
# 安装 git-secrets（AWS 开源的工具）
brew install git-secrets

# 在仓库中注册敏感模式
cd /path/to/HBOS
git secrets --install
git secrets --register-aws

# 添加自定义模式
git secrets --add 'password\s*=\s*.+'
git secrets --add 'DB_ROOT_PASSWORD\s*=\s*.+'
git secrets --add 'ADMIN_PASSWORD\s*=\s*.+'
git secrets --add 'FEISHU_APP_SECRET\s*=\s*.+'

# 扫描历史
git secrets --scan-history
```

**方法三：使用 truffleHog 进行深度扫描**

```bash
# 安装 truffleHog
brew install trufflesecurity/trufflehog/trufflehog

# 扫描整个 Git 历史
trufflehog git file:///path/to/HBOS --only-verified
```

## 9. Secret 泄露处理 SOP

当发现敏感数据被提交到 Git 仓库时，按以下流程处理：

### 9.1 第一步：立即止损

1. **立即轮换泄露的密钥** — 在对应平台修改密码或重置密钥
   - 数据库密码：在 `.env` 中修改，然后重建容器
   - 飞书 App Secret：在飞书开放平台后台重置
   - GitHub Token：在 GitHub Settings 中吊销并重新生成
2. **评估影响范围** — 确认泄露发生的时间、是否已被他人访问
3. **如果仓库是公开的** — 立即将仓库设为私有（临时措施）

### 9.2 第二步：清理 Git 历史

**注意：以下操作会改写 Git 历史，如果仓库有其他协作者，需要提前通知。**

```bash
# 方法一：使用 git filter-branch（传统方式）
# 从所有历史中删除 .env 文件
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env" \
  --prune-empty --tag-name-filter cat -- --all

# 方法二：使用 BFG Repo-Cleaner（推荐，更快）
# 安装：brew install bfg
# 删除所有历史中的 .env
bfg --delete-files .env

# 方法三：使用 git filter-repo（最推荐）
# 安装：pip install git-filter-repo
git filter-repo --path .env --invert-paths

# 清理后强制推送
git push origin --force --all
git push origin --force --tags
```

**重要提醒：强制推送后，所有协作者需要重新 clone 仓库，不能使用 `git pull`。**

### 9.3 第三步：通知相关人员

- 通知团队成员发生了什么、影响了什么
- 告知需要更新本地密码的原因
- 如果是客户数据泄露，需要按照合同和法律要求通知客户

### 9.4 第四步：事后复盘

- 为什么泄露会发生？（忘加 `.gitignore`？不小心 `git add -A`？）
- 当前的安全措施是否足够？
- 需要增加什么检查或工具来防止再次发生？

## 10. 日志安全

### 10.1 日志中可能包含敏感信息

运行时日志可能意外记录敏感数据：

- 包含密码的请求参数
- 包含 Token 的 HTTP Header
- 包含用户数据的调试日志
- 错误堆栈中暴露的数据库连接字符串

### 10.2 日志文件已被 gitignored

当前 `.gitignore` 已包含 `logs/`，日志文件不会被提交到 Git。

但还需要注意：

- 不要在日志中打印完整请求体（可能包含密码）
- 不要在日志中打印数据库查询结果（可能包含用户数据）
- 使用结构化日志时，对敏感字段做脱敏处理

### 10.3 查看日志时注意脱敏

- 分享日志片段给他人排查问题时，先检查是否包含敏感信息
- 截图日志时，遮挡密码和 Token 部分
- 不要把日志文件上传到公开的 Issue 或论坛

## 11. 安全检查清单

### 11.1 提交前检查

每次 `git commit` 之前，逐项确认：

- [ ] `.env` 不在暂存区中（`git status` 确认）
- [ ] 代码中没有硬编码的密码、Token 或 Key
- [ ] 新增的依赖文件不包含敏感数据
- [ ] 截图或文档中不包含真实员工数据
- [ ] 配置文件中的密码使用环境变量引用，而非明文

### 11.2 定期检查（建议每月一次）

- [ ] 运行 `git grep -i "password\|secret\|token\|key" $(git rev-list --all)` 扫描历史
- [ ] 检查 `.env.example` 和 `.env` 中的变量列表是否一致
- [ ] 轮换超过 90 天未更换的 API Key
- [ ] 检查 GitHub 仓库的协作者列表，移除已离职人员
- [ ] 检查 CI/CD 中配置的 Secret 是否仍然有效

### 11.3 PR 审查时的安全检查点

审查 Pull Request 时，特别关注：

- [ ] 新增文件是否包含硬编码密码？
- [ ] `.env.example` 的修改是否合理？

## 12. 本地 Secret vs 测试 Secret vs 生产 Secret

### 12.1 不同环境的管理原则

| 环境 | 密码来源 | 安全级别 | 管理方式 |
|------|----------|----------|----------|
| 本地开发 | 开发者自行生成 | 低 | `.env` 文件 |
| 测试环境 | 团队统一分配 | 中 | `.env.test` 或 CI Secret |
| 生产环境 | 运维/安全团队生成 | **极高** | 密钥管理服务 + 加密存储 |

### 12.2 禁止复用密码

**不同环境绝对不能使用相同的密码：**

- 不要用本地开发密码作为测试环境密码
- 不要用测试环境密码作为生产环境密码
- 不要用 HBOS 的密码作为其他项目的密码

**为什么？** 一旦某个环境的密码泄露，如果所有环境用同一个密码，攻击者就能横向渗透到所有环境。

### 12.3 环境隔离

环境的隔离不仅仅是密码：

- 飞书：本地用测试企业 + 测试应用，生产用正式企业 + 正式应用
- 数据库：本地用 Docker 容器内的 MariaDB，生产用独立的数据库实例
- 第三方 API：本地用 Sandbox/Staging 的 Key，生产用 Live Key

### 12.4 密码生成建议

```bash
# 生成随机密码（macOS/Linux）
# 16 位随机密码
openssl rand -base64 16

# 32 位随机密码
openssl rand -base64 32

# 生成随机密钥（64 位十六进制）
openssl rand -hex 32
```
