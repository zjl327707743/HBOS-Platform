# 05 开源代码二次开发与升级规范

> **面向读者**：本文件面向没有开源项目二次开发经验的团队成员编写。每个规则都附带「为什么」的解释——理解原因比记住规则更重要。
> **前置知识**：了解项目基本结构（参阅 `01_项目真实结构与代码归属审计.md`），知道 Frappe/ERPNext/HRMS 是什么。

## 1. 开源代码能不能修改

新成员最常见的疑问：「我看 HRMS 的某个功能不满足需求，能不能直接改它的源码？」

这个问题需要从三个层面回答：法律、技术、工程。三个层面指向同一个答案，但理由不同。

### 1.1 法律层面：可以改

| 组件 | 许可证 | 是否允许修改 | 是否允许商用 | 修改后是否必须开源 |
|------|--------|-------------|-------------|-------------------|
| Frappe Framework | MIT | 是 | 是 | 否 |
| ERPNext | GPLv3 | 是 | 是（内部使用） | 分发时需要 |
| HRMS | GPLv3 | 是 | 是（内部使用） | 分发时需要 |
| MariaDB | GPLv2 | 是 | 是 | 分发时需要 |
| Redis | BSD 3-Clause | 是 | 是 | 否 |

**结论**：法律上，所有组件都允许修改。MIT 和 BSD 几乎没有任何限制；GPL 系列许可证允许修改源码，只是在你「对外分发」修改后的软件时需要同时提供源码。

**为什么 MIT 和 GPLv3 的差异很重要**：

- **MIT（Frappe）**：你可以修改、商用、闭源，基本没有限制。只需要保留原始版权声明。
- **GPLv3（ERPNext、HRMS）**：你可以修改，也可以内部使用不公开。但如果你把修改后的 ERPNext/HRMS「分发」给第三方（如打包成产品卖给客户），你必须同时提供修改后的完整源码。
- **关键区分**：HBOS 目前是内部管理系统，不对外分发，所以 GPLv3 的「传染性」条款目前不触发。如果未来 HBOS 作为 SaaS 产品对外提供，GPLv3 的 AGPL 变体差异需要重新评估（见第 8 节）。

### 1.2 技术层面：可以改，但代价很大

技术上，修改开源代码本身没有障碍——源码就在那里，改一行就能生效。

但真正的代价不在「改」这一步，而在「改完之后」：

```
修改一行代码 → 功能正常 → 三个月后上游发布新版本 → 你的修改与新版本冲突
→ 要么放弃升级（安全漏洞不修），要么手动合并冲突（每次升级都重复）
```

**为什么 Docker 镜像里的代码更难改**：Frappe 和 ERPNext 的源码在 Docker 镜像 `frappe/erpnext:v16.26.2` 内部，不在宿主机上。要修改它们，需要：

1. 进入容器内部修改文件
2. 容器重启后修改可能丢失（除非你定制了镜像）
3. 每次拉取新镜像都会覆盖你的修改

HRMS 通过 bind mount 挂载到宿主机，物理上可以改，但下一节会说明为什么不应该改。

### 1.3 工程层面：不应该改

这是三个层面中最关键的。「能改」不等于「应该改」。

HBOS 项目的架构决策 ADR-0004 明确规定：**禁止直接修改 Frappe/ERPNext/HRMS 核心源码**。

这不是技术限制，而是工程纪律。下面第 2 节详细解释为什么。

## 2. 为什么默认不直接修改核心

### 2.1 原因一：升级冲突——每次升级都是一场噩梦

**场景**：你在 HRMS 的 `attendance.py` 里改了 5 行代码，实现了一个特殊考勤规则。三个月后，HRMS 官方发布了 v16.13.0，修复了 3 个安全漏洞，但同时也修改了 `attendance.py` 的同一个函数。

**结果**：

```
你的修改        官方新版本
   │                │
   └──────┬─────────┘
          ▼
    手动合并冲突
```

这不是一次性的麻烦。HRMS 大约每 1-2 个月发布一个版本，**每次升级你都要手动处理这个冲突**。如果改了 10 个文件，每次升级就要处理 10 个潜在冲突点。

**为什么**：开源项目持续演进，你的修改和上游的修改是两条平行线。一旦你修改了核心代码，你就「分叉」了这条线，每次上游更新，你都需要手动把两条线合并。这不是技术问题，而是维护成本问题。

### 2.2 原因二：调试困难——别人看不懂你的「魔改版」

**场景**：新同事入职，遇到一个 HRMS 的 Bug。他按照 HRMS 官方文档排查，发现代码行为与文档描述不一致。

**为什么**：因为你修改了核心代码。官方文档、社区问答、Stack Overflow 上的所有答案，都基于「未修改」的 HRMS。你的修改让项目变成了一个「魔改版」，只有你自己知道改了哪里。

**后果**：
- 新成员无法用官方文档解决问题
- 社区求助时，别人无法复现你的问题
- 团队依赖「谁知道改了哪里」的口头知识，而不是文档

### 2.3 原因三：License 合规风险——边界模糊

**场景**：你在 ERPNext 的 `sales_invoice.py` 里插入了一段自定义逻辑。这段代码与 ERPNext 的 GPLv3 代码混在一起。

**为什么**：GPLv3 许可证有"copyleft"条款。如果你的自定义代码与 GPLv3 代码紧密耦合，是否构成「组合作品」或「衍生作品」是一个需要结合具体集成方式、链接方式和分发模式判断的法律问题。虽然 HBOS 目前是内部使用，但一旦未来需要对外分发或商业化，这种边界模糊会带来合规风险。**本文档只做工程与许可证风险提示，不替代正式法律意见。**

**正确做法**：自定义代码放在独立的 `hb_attendance_app` 中，通过 Frappe 的 Hook 机制与 HRMS 交互，而不是修改 HRMS 的源文件。代码隔离 = 许可证隔离。

### 2.4 原因四：Docker 镜像的不可变性

**场景**：你 `docker exec` 进入容器，修改了 Frappe 的某个文件。功能正常了。一个月后，你 `docker compose pull` 拉取了新镜像，修改消失了。

**为什么**：Docker 镜像是不可变的。容器的文件系统是临时的——容器重启、镜像更新、甚至 Docker 守护进程重启，都可能导致你的修改丢失。Frappe 和 ERPNext 的代码在镜像内，不在宿主机上，任何容器内的修改都是「临时的」。

**HRMS 的特殊情况**：HRMS 通过 bind mount 挂载到宿主机（`runtime/apps/hrms`），物理上修改不会丢失。但这只是「技术上可行」，工程上仍然不推荐（原因一、二、三仍然适用）。

### 2.5 总结：不是「不能改」，是「有更好的方式」

```
直接修改核心                     HBOS 推荐方式
─────────────                   ──────────────
改 HRMS 源码                   用 Custom Field + Property Setter
改 ERPNext 源码                 用 Hook + Event 扩展
改 Frappe 框架源码              用自定义 App 独立实现
在核心文件里插代码              用外部服务 + API 调用
```

下面第 3 节详细说明这 7 层优先级。

## 3. HBOS 修改优先级

当你需要实现一个功能，而现有系统不满足时，按以下优先级从高到低选择实现方式。**优先级越高，长期维护成本越低。**

```
优先级 1：原生配置　　　　　　　　← 最推荐，零维护成本
优先级 2：Custom Field / Workflow / Workspace　← 低代码，自动迁移
优先级 3：自定义 App　　　　　　　← 代码隔离，独立升级
优先级 4：Hook / Event　　　　　　← 无侵入扩展
优先级 5：外部服务　　　　　　　　← 完全独立
优先级 6：Fork　　　　　　　　　　← 必须经过审批
优先级 7：直接修改核心源码　　　　← 禁止
```

### 3.1 优先级 1：原生配置

**含义**：Frappe/ERPNext/HRMS 本身已经提供了配置项，直接使用即可。

**举例**：
- 系统设置（System Settings）中的时区、货币、默认公司
- HRMS 的 Holiday List、Shift Type 配置
- 用户权限通过 Role Permissions Manager 配置

**为什么优先**：原生配置不需要写代码，升级时完全不受影响。配置被 Frappe 框架自动管理，migrate 不会丢失。

**怎么判断**：先去官方文档搜一下你需要的功能，看看是不是已经有配置项了。不要默认「没有」。

### 3.2 优先级 2：Custom Field / Workflow / Workspace

**含义**：通过 Frappe 的「自定义」机制，在不写代码或写少量代码的情况下扩展系统。

**可用的自定义机制**：

| 机制 | 能做什么 | 举例 |
|------|---------|------|
| Custom Field | 给已有 DocType 加字段 | 给 Employee 增加「紧急联系人」字段 |
| Property Setter | 修改已有字段的属性 | 把「Employee Name」标签改成「员工姓名」 |
| Workspace | 自定义导航页面 | 创建「海滨考勤工作台」 |
| Workflow | 自定义审批流程 | 请假申请的三级审批 |
| Custom Button | 在表单上增加按钮 | 在 Employee 表单上增加「导出考勤」按钮 |
| Print Format | 自定义打印模板 | 定制工牌打印格式 |

**为什么比直接改源码好**：
- 这些自定义内容通过 Fixture 导出为 JSON 文件，提交到 Git
- `bench migrate` 时自动加载，不依赖手动操作
- 升级 HRMS 后，自定义内容仍然生效（因为没改 HRMS 的源码）
- 详见 `06_Frappe自定义内容与数据库迁移规范.md`

**举例**：你想要在 Employee 上增加一个「考勤组」字段。

```bash
# 正确做法（优先级 2）
# 1. 在 Frappe UI 中为 Employee DocType 创建 Custom Field "attendance_group"
# 2. 导出 Fixture
bench --site 你的站点名 export-fixtures --app hb_attendance_app
# 3. 提交到 Git
git add fixtures/custom_field.json
git commit -m "feat: 给 Employee 增加考勤组自定义字段"
```

```python
# 错误做法（优先级 7，禁止）
# 直接修改 runtime/apps/hrms/hrms/hr/doctype/employee/employee.json
# 在 fields 数组中手动添加字段定义
```

### 3.3 优先级 3：自定义 App

**含义**：创建独立的 Frappe App（如 `hb_attendance_app`），在 App 中实现自定义功能。

**当前项目已有**：`apps/hb_attendance_app/`，包含自定义 DocType、Report、Page、Workspace。

**App 能做但 Custom Field 做不到的事**：
- 创建全新的 DocType（如 `HBOS Attendance Import Log`）
- 编写复杂的 Python 业务逻辑
- 自定义 Report 的数据查询和计算
- 自定义 Page（完整的 Web 页面）
- 与其他系统（如飞书）集成

**为什么 App 是最佳平衡点**：
- App 代码完全独立，不碰任何核心源码
- App 有自己的版本号，独立升级和回滚
- App 通过 Frappe 的标准 Hook 机制与系统交互
- 升级 Frappe/ERPNext/HRMS 时，App 不受影响（只要 API 兼容）

**当前 `hb_attendance_app` 已经演示了正确做法**：
- 通过 `hooks.py` 注册 DocType、Report、Page
- 使用 Custom Field 和 Property Setter 扩展 HRMS 的 DocType
- 创建自定义 Workspace 而不修改 HRMS 的 Workspace
- 完全不修改 `runtime/apps/hrms/` 中的任何文件

### 3.4 优先级 4：Hook / Event

**含义**：利用 Frappe 的 Hook 和 Event 系统，在特定时机插入自定义逻辑，而不修改触发这些逻辑的核心代码。

**Frappe 的 Hook 机制**（在 `hooks.py` 中配置）：

| Hook 类型 | 触发时机 | 用途 |
|-----------|---------|------|
| `doc_events` | DocType 的增删改查发生时 | 在 Employee 保存后自动更新考勤配置 |
| `scheduler_events` | 定时任务触发 | 每天凌晨自动同步考勤数据 |
| `override_doctype_class` | DocType 加载时 | 用自定义 Controller 替换默认 Controller |
| `jenv` | Jinja 模板渲染时 | 添加自定义模板方法和过滤器 |

**举例**：当 Employee 被创建时，自动为其分配默认的考勤组。

```python
# apps/hb_attendance_app/hb_attendance_app/hooks.py

doc_events = {
    "Employee": {
        "after_insert": "hb_attendance_app.hb_attendance_app.events.employee.after_employee_insert"
    }
}
```

```python
# apps/hb_attendance_app/hb_attendance_app/events/employee.py

import frappe

def after_employee_insert(doc, method):
    """Employee 创建后，自动设置默认考勤组"""
    # 这里的逻辑在 Employee 保存后自动触发
    # 不需要修改 HRMS 的 employee.py
    if not doc.get("custom_attendance_group"):
        doc.db_set("custom_attendance_group", "默认考勤组")
```

**为什么 Hook 优于直接修改**：
- 你的代码在 `hb_attendance_app` 中，不在 HRMS 中
- 升级 HRMS 不会影响你的 Hook 逻辑
- 如果一个 Hook 不够用，可以在 `hooks.py` 中注册多个

### 3.5 优先级 5：外部服务

**含义**：将复杂功能放在独立的服务中，通过 API 与 Frappe 交互。

**适用场景**：
- AI 视频分析、算法计算等重型任务
- 用 Python 以外的语言（Go、Rust）实现性能敏感的功能
- 与第三方系统（如飞书）的深度集成

**举例**：假设需要 AI 分析考勤视频，识别迟到早退。这个功能不适合放在 Frappe App 中（Python 性能瓶颈、依赖复杂）。

```
┌──────────────┐     REST API      ┌──────────────────┐
│  Frappe App  │ ────────────────→  │  AI 视频分析服务   │
│  (调用方)     │ ←──────────────── │  (FastAPI / Go)   │
└──────────────┘    返回结果        └──────────────────┘
```

**为什么外部服务是好的选择**：
- 完全独立的技术栈，不依赖 Frappe 版本
- 可以独立部署、独立扩展、独立升级
- 不增加 Frappe 容器的复杂度和资源消耗

### 3.6 优先级 6：Fork

**含义**：将上游开源仓库完整复制一份到自己的控制下，在 Fork 上修改。

**注意**：Fork 不是「随便 fork 一个玩玩」。见第 5 节的详细说明。

**什么时候可以考虑 Fork**：只有当优先级 1-5 都无法满足需求，且修改量足够大（不是改几行代码），且团队有长期维护的意愿和能力时，才考虑 Fork。

**Fork 的代价**：你需要持续追踪上游的更新，手动合并到你的 Fork。这是一个「永久性的维护承诺」。

### 3.7 优先级 7：直接修改核心源码

**禁止。** 除非你经过 Fork（优先级 6）的完整评估和审批流程。直接在核心源码上改 = 给自己埋雷。

### 3.8 优先级选择决策树

```
你要实现一个功能
    │
    ▼
现有系统的配置项能满足吗？ ──是──→ 用原生配置（优先级 1）✅
    │否
    ▼
能用 Custom Field / Property Setter 实现吗？ ──是──→ 用自定义机制（优先级 2）✅
    │否
    ▼
能放在自定义 App 中实现吗？ ──是──→ 在 hb_attendance_app 中实现（优先级 3）✅
    │否
    ▼
能用 Hook / Event 扩展吗？ ──是──→ 在 hooks.py 中注册（优先级 4）✅
    │否
    ▼
适合独立服务吗？ ──是──→ 建外部服务（优先级 5）✅
    │否
    ▼
需要 Fork 吗？ ──是──→ 走 Fork 评估流程（优先级 6）⚠️
    │否
    ▼
直接改核心（优先级 7）❌ 禁止
```

## 4. 自定义 App 的正确做法

`hb_attendance_app` 已经演示了正确的扩展方式。本节汇总所有可用的技术手段。

### 4.1 hooks.py —— App 的入口

`hooks.py` 是 Frappe App 的「配置中心」，所有扩展都在这里注册：

```python
# apps/hb_attendance_app/hb_attendance_app/hooks.py

app_name = "hb_attendance_app"
app_title = "HBOS Attendance"

# 注册自定义 DocType（优先级 3）
doctype_js = {"Employee": "public/js/employee.js"}
doctype_list_js = {"Employee": "public/js/employee_list.js"}

# 注册事件 Hook（优先级 4）
doc_events = {
    "Employee": {
        "after_insert": "hb_attendance_app.events.employee.after_employee_insert",
    }
}

# 注册定时任务（优先级 4）
scheduler_events = {
    "daily": [
        "hb_attendance_app.tasks.sync_attendance_data",
    ]
}

# 注册 Fixture（优先级 2）
fixtures = [
    "custom_field.json",
    "property_setter.json",
    "workspace.json",
]

# 注册自定义页面
website_route_rules = [
    {"from_route": "/attendance-import", "to_route": "attendance-import"},
]
```

### 4.2 Custom Field —— 给别人的 DocType 加字段

```bash
# 1. 在 Frappe UI 中创建 Custom Field
# 2. 导出到 App 的 fixtures 目录
bench --site 你的站点名 export-fixtures --app hb_attendance_app
# 3. 确认 hooks.py 中已注册 fixtures
# 4. 提交 Git
```

Custom Field 是扩展 HRMS 的核心手段。详见 `06_Frappe自定义内容与数据库迁移规范.md` 第 3 节。

### 4.3 Property Setter —— 修改别人的字段属性

```bash
# 1. 在 Frappe UI 中修改字段属性（如标签、必填、隐藏）
# 2. 导出到 fixtures 目录
bench --site 你的站点名 export-fixtures --app hb_attendance_app
# 3. 提交 Git
```

详见 `06_Frappe自定义内容与数据库迁移规范.md` 第 4 节。

### 4.4 Workflow —— 自定义审批流程

如果需要审批流程（如请假审批），创建自定义 Workflow 并导出。详见 `06_Frappe自定义内容与数据库迁移规范.md` 第 6 节。

### 4.5 Fixture —— 让配置随代码迁移

Fixture 是配置的「快照」，以 JSON 文件存在，在 `bench migrate` 时自动加载到数据库。

```bash
# 导出所有 Fixture
bench --site 你的站点名 export-fixtures --app hb_attendance_app
# 文件位置
apps/hb_attendance_app/hb_attendance_app/fixtures/
```

详见 `06_Frappe自定义内容与数据库迁移规范.md` 第 9 节。

### 4.6 Patch —— 一次性数据操作

当需要修改已有数据（而不是结构）时，写 Patch：

```python
# patches/v1_0_0/set_default_attendance_group.py

import frappe

def execute():
    """给所有现有 Employee 设置默认考勤组"""
    employees = frappe.get_all("Employee", fields=["name"])
    for emp in employees:
        frappe.db.set_value("Employee", emp.name, "custom_attendance_group", "默认考勤组")
    frappe.db.commit()
```

```txt
# patches.txt
hb_attendance_app.patches.v1_0_0.set_default_attendance_group
```

详见 `06_Frappe自定义内容与数据库迁移规范.md` 第 10 节。

### 4.7 API / Event —— 外部服务集成

```python
# 在 Frappe App 中调用外部服务
import requests

def call_ai_service(video_url):
    response = requests.post(
        "http://ai-service:8080/analyze",
        json={"video_url": video_url}
    )
    return response.json()
```


## 5. 什么时候可以 Fork

### 5.1 Fork 的代价清单

Fork 不是「免费」的。在你决定 Fork 一个开源项目之前，先确认你能承担以下代价：

| 代价 | 说明 | 工作量估计 |
|------|------|-----------|
| 跟踪上游 | 持续关注上游的每次 Release，阅读 Changelog | 每周 1-2 小时 |
| 合并更新 | 将上游的修改合并到你的 Fork（可能有冲突） | 每次大版本 1-3 天 |
| 解决冲突 | 你的修改与上游修改冲突时，手动合并 | 不可预估 |
| 安全补丁 | 上游修复安全漏洞后，你需要手动应用到 Fork | 紧急情况下可能数小时 |
| 文档维护 | 写清楚你改了什么、为什么改、怎么升级 | 持续的文档工作 |
| 团队培训 | 新成员需要理解 Fork 与上游的差异 | 每人 1-2 天 |

### 5.2 Fork 的条件——请逐条确认

在决定 Fork 之前，必须满足以下所有条件：

- [ ] 优先级 1-5 的方案全部尝试过，确实无法满足需求
- [ ] 修改量足够大——不是改 5 行代码，而是需要系统性改动
- [ ] 团队至少有 1 人愿意长期负责跟踪上游更新
- [ ] 已明确 Fork 后的维护计划（谁来跟踪、多久合并一次）
- [ ] 已评估 Fork 的长期成本（人力 vs 自研）
- [ ] 已获得 Owner 书面批准

### 5.3 Fork 后必须做的事

如果 Owner 批准了 Fork，以下事必须做：

1. **明确记录 Fork 点**：记录 Fork 时的上游 commit hash 和版本号
   ```
   Fork 来源：https://github.com/frappe/hrms.git
   Fork 点：v16.12.0，commit 666bf10
   Fork 日期：2026-07-14
   Fork 原因：需要修改考勤引擎的底层算法，Custom App 无法实现
   ```

2. **建立上游跟踪机制**：
   ```bash
   # 添加 upstream 远程仓库
   git remote add upstream https://github.com/frappe/hrms.git
   # 定期拉取上游更新
   git fetch upstream
   # 查看上游新增了哪些 commit
   git log upstream/version-16 --oneline --since="2 weeks ago"
   ```

3. **维护修改清单**：在 Fork 的仓库中维护一个 `HBOS_CHANGES.md` 文件，记录每一项修改：
   ```markdown
   # HBOS 自定义修改清单

   ## 修改 1：考勤引擎支持弹性工作制
   - 文件：hrms/hr/doctype/attendance/attendance.py
   - 函数：mark_attendance()
   - 修改内容：增加了弹性工作制的打卡时间计算逻辑
   - 修改原因：HRMS 原生只支持固定班次，海滨需要弹性工作制
   - 上游冲突风险：高（attendance.py 是核心文件，每版都有改动）
   - 修改日期：2026-07-14
   - 修改人：张三
   ```

4. **定期合并上游**：建议频率：
   - 安全补丁：收到通知后 24 小时内评估和合并
   - Bug 修复版本：1 周内评估和合并
   - 功能版本：1-2 周内评估和合并
   - 大版本：提前规划，预留 1 周合并时间

5. **考虑向上游贡献**：如果你 Fork 的修改对其他人也有用，考虑向上游提交 PR。如果被接受，你的 Fork 差异会减少，合并成本降低。

### 5.4 Fork 的替代方案

在决定 Fork 之前，考虑以下替代方案：

| 替代方案 | 说明 |
|---------|------|
| 向上游提 Feature Request | 描述你的需求，等上游实现 |
| 向上游贡献代码 | 把修改提交到上游，所有人都受益 |
| 用 Monkey Patch | 运行时替换函数，不修改源码（风险高，不建议） |
| 用继承/包装 | 包装上游的类，在子类中覆盖方法 |

## 6. 如果已经修改了核心怎么办

如果你发现项目中已经有人修改了核心源码（或者不小心自己改了），按以下步骤处理。

### 6.1 第一步：识别修改

```bash
# 检查 HRMS 是否有未提交的修改
cd runtime/apps/hrms
git status
git diff

# 如果有修改，列出所有被修改的文件
git diff --name-only
```

### 6.2 第二步：建立补丁清单

把每一项修改记录下来，判断每项修改的「必要性」：

| 修改 | 文件 | 行数 | 目的 | 必要性 | 替代方案 |
|------|------|------|------|--------|---------|
| 修改了 attendance.py 的打卡逻辑 | hrms/hr/.../attendance.py | 15 行 | 支持弹性工作制 | 高 | 用 Hook 替代？ |
| 修改了 Employee 表单的字段标签 | hrms/hr/.../employee.json | 3 行 | 中文化 | 低 | 用 Property Setter |

### 6.3 第三步：逐项判断迁移

对每一项修改，问自己：

```
这项修改能用优先级 1-5 的方式替代吗？
    │
    ├── 是 → 撤销修改，用正确方式重新实现
    │
    └── 否 → 这项修改真的无法用任何其他方式实现吗？
              │
              ├── 是 → 纳入 Fork 评估（见第 5 节）
              │
              └── 不确定 → 找技术负责人讨论
```

### 6.4 第四步：Fork 策略

如果确认需要 Fork，有两种策略：

**策略 A：从干净的上游开始（推荐）**

```bash
# 1. 备份你当前的修改
cd runtime/apps/hrms
git diff > ~/hrms-hbos-changes.patch

# 2. 重新 clone 上游到一个新目录
git clone https://github.com/frappe/hrms.git runtime/apps/hrms-fork
cd runtime/apps/hrms-fork
git checkout version-16

# 3. 谨慎地应用你的修改
git apply ~/hrms-hbos-changes.patch

# 4. 解决冲突，逐项审查每项修改

# 5. 提交到你的 Fork 仓库
```

**策略 B：基于当前状态建立 Fork**

```bash
# 1. 提交当前所有修改
cd runtime/apps/hrms
git add -A
git commit -m "HBOS: 记录所有自定义修改"

# 2. 标记 Fork 点
git tag hbos-fork-v16.12.0

# 3. 推送到你的 Fork 仓库
git remote add hbos-fork <你的 Fork 仓库地址>
git push hbos-fork version-16
```

**策略 A 更安全**——它迫使你重新审视每一项修改，避免把调试代码、临时修改也带进 Fork。

## 7. 上游升级操作指南

### 7.1 升级前：检查

```bash
# 1. 查看当前版本
docker exec -it <容器名> bench version
# 输出示例：
# Frappe Framework: v16.25.0
# ERPNext: v16.26.2

# 2. 查看 HRMS 当前版本
cd runtime/apps/hrms
git describe --tags
# 输出：v16.12.0

# 3. 查看上游最新版本
git fetch origin
git tag -l "v16.*" | sort -V | tail -5

# 4. 阅读 Changelog
# 访问 https://github.com/frappe/hrms/releases
# 或 https://github.com/frappe/erpnext/releases
```

**升级前必须确认**：

- [ ] 阅读了新版本的 Release Notes / Changelog
- [ ] 确认了新版本与当前版本的兼容性（特别是主版本号不变）
- [ ] 没有看到 Breaking Changes（破坏性变更）会影响现有功能
- [ ] 新版本与 HBOS 自定义 App 的兼容性（Frappe API 有没有变化）

### 7.2 升级前：备份

```bash
# 1. 备份数据库（最重要！）
bench --site 你的站点名 backup

# 2. 确认备份成功
bench --site 你的站点名 list-backups

# 3. 备份 HRMS 当前状态（如果是 bind mount 的）
cd runtime/apps/hrms
git stash  # 如果有未提交的修改
git tag backup-before-upgrade-$(date +%Y%m%d)
```

**铁律：不备份不升级。** 升级失败后，备份是你唯一的救命稻草。

### 7.3 执行升级

#### 升级 HRMS（bind mount 方式）

```bash
# 1. 进入 HRMS 目录
cd runtime/apps/hrms

# 2. 查看当前分支和状态
git status
git branch

# 3. 确保工作区干净
# 如果有未提交的修改，先 stash 或 commit

# 4. 拉取最新版本
git fetch origin
git checkout version-16
git pull origin version-16

# 5. 如果要切换到特定版本（推荐）
git checkout v16.13.0

# 6. 在容器内执行 migrate
docker exec -it <容器名> bench --site 你的站点名 migrate
```

#### 升级 Frappe/ERPNext（Docker 镜像方式）

```bash
# 1. 修改 docker-compose.yml 中的镜像标签
# 将 frappe/erpnext:v16.26.2 改为新版本

# 2. 拉取新镜像
docker compose pull

# 3. 重启容器
docker compose up -d

# 4. 在容器内执行 migrate
docker exec -it <容器名> bench --site 你的站点名 migrate
```

### 7.4 升级后：验证

```bash
# 1. 检查版本
docker exec -it <容器名> bench version

# 2. 检查 HRMS 版本
cd runtime/apps/hrms && git describe --tags

# 3. 验证关键功能
# 在浏览器中访问站点，逐一检查：
# - 登录是否正常
# - 自定义 DocType 是否正常显示
# - 自定义 Report 能否正常运行
# - 自定义 Page 能否正常访问
# - Workspace 布局是否正常
# - 考勤导入功能是否正常

docker logs <容器名> | grep -i migrate
```

**验证清单**：

- [ ] 登录正常
- [ ] 自定义 DocType 正常显示
- [ ] 自定义 Report 能正常运行
- [ ] 自定义 Page 能正常访问
- [ ] Workspace 布局正常
- [ ] 考勤导入功能正常
- [ ] 无新增 Error 日志
- [ ] 数据库迁移无报错

### 7.5 升级失败：回滚

```bash
# 方案 A：数据库回滚
bench --site 你的站点名 restore 备份文件名

# 方案 B：HRMS 版本回滚
cd runtime/apps/hrms
git checkout v16.12.0  # 回到升级前的版本

# 方案 C：Docker 镜像回滚
# 修改 docker-compose.yml 回到旧镜像标签

```

**回滚后必须做的事**：
1. 记录升级失败的原因
2. 在团队中分享失败信息，避免其他人踩同样的坑
3. 评估是否需要等待下一个补丁版本再升级

### 7.6 升级频率建议

| 组件 | 建议频率 | 理由 |
|------|---------|------|
| Frappe/ERPNext 安全补丁 | 尽快（1-3 天内） | 安全漏洞不能等 |
| Frappe/ERPNext 小版本 | 1-2 周内 | Bug 修复有益，风险低 |
| Frappe/ERPNext 大版本 | 谨慎评估，可能数月 | 主版本升级可能有不兼容变更 |
| HRMS 小版本 | 1-2 周内 | 考勤相关修复及时跟进 |
| MariaDB/Redis | 跟随 Docker Compose | 基础设施升级频率低，按需 |

## 附录 B：常见问题

**问：我在 HRMS 里改了一行代码，功能正常了，这有什么问题？**

答：这行代码现在只存在于你的电脑上。其他同事 clone 代码后看不到这行修改。三个月后 HRMS 升级，你忘了这行代码在哪，升级后功能又坏了。这不是「改一行代码」的问题，而是「这行代码不属于任何版本控制」的问题。如果确实需要这行修改，应该用优先级 1-5 的方式实现。

**问：我能不能在容器里临时改一下，测试完就还原？**

答：可以。临时测试修改是正常开发行为。但测试完成后必须还原，不能在容器里留下「永久修改」。如果是需要长期保留的修改，必须用正确方式实现。

**问：如果社区有人已经 Fork 了 HRMS 并维护得很好，我能不能直接用他的 Fork？**

答：可以，但需要评估：
- 这个 Fork 的维护者是谁？是否可靠？
- Fork 的更新频率如何？是否跟上上游？
- Fork 的修改是否与 HBOS 的需求匹配？
- 建议优先使用官方版本，Fork 作为最后手段。

**问：我们的 hb_attendance_app 需要声明什么许可证？**

答：当前建议添加一个 `LICENSE` 文件，声明为 "All Rights Reserved"（版权保留，内部项目暂不开源）。如果未来确定要开源，可以在那时选择 MIT 或 GPLv3。详见第 8.3 节。

**问：GPLv3 的「传染性」是什么意思？**

答：如果你修改了 GPLv3 的代码，并且对外分发，你的修改也必须以 GPLv3 开源。但如果你不修改 GPLv3 的代码，或者不对外分发（内部使用），传染性不触发。HBOS 当前是内部使用，不触发传染性条款。
