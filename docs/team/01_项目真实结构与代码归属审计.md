## 2. 项目真实形态判定

**结论：这是一个"文档 + Docker 部署编排 + 自定义 Frappe App"的混合仓库，不是完整项目仓库。**

### 判定依据

1. **仓库中仅包含一个自定义 App**：`apps/hb_attendance_app/`，这是海滨自研的考勤管理模块，总计约 20 个源文件，是整个仓库中唯一的业务代码。

2. **核心框架和平台代码不在仓库中**：Frappe Framework（16.25.0）和 ERPNext（16.26.2）的源代码不存在于宿主机文件系统的任何位置。它们仅存在于 Docker 镜像 `frappe/erpnext:v16.26.2` 内部的容器文件系统中。

3. **HRMS 以嵌套 Git 仓库形式存在**：`runtime/apps/hrms` 是 frappe/hrms 官方仓库的克隆，有自己的 `.git` 目录和独立版本历史。它在主仓库中不被跟踪（被 `.gitignore` 忽略），属于"本地开发依赖"而非"仓库资产"。

4. **仓库的核心价值在于**：
   - 自研考勤模块的源代码
   - Docker Compose 部署编排
   - 项目文档、里程碑、ADR（架构决策记录）

### 仓库形态示意

```
HBOS Git 仓库（已跟踪）
```

## 5. 高风险情况检查结果

### 5.1 HIGH - 容器内代码（Frappe + ERPNext）

**问题：** Frappe Framework 和 ERPNext 的源代码仅存在于 Docker 镜像 `frappe/erpnext:v16.26.2` 内部，不在宿主机文件系统的任何位置。

**影响：** 如果 Docker 镜像被删除，且 `frappe/erpnext:v16.26.2` 从 Docker Hub 下架或更新，当前使用的精确版本源代码将无法恢复。

**缓解措施：**
- 记录精确镜像标签（`frappe/erpnext:v16.26.2`）和内部版本号（Frappe 16.25.0, ERPNext 16.26.2）
- 考虑将镜像推送到私有镜像仓库
- 如需长期保留，可在宿主机上 `docker save` 导出镜像 tar 包

### 5.2 HIGH - Site 配置在 Docker 卷中

**问题：** `sites/` 目录（包含 `site_config.json`、数据库配置、上传文件等）仅存储在 Docker 命名卷 `hbos-m0-r3a_sites` 中，未在 Git 中备份。

**影响：** 如果该卷被删除，site 配置将丢失。重建 site 需要重新执行 `bench new-site` 并重新配置所有设置。

**缓解措施：**
- 定期执行 `docker cp` 从容器中导出 site 配置
- 将 `site_config.json`（脱敏后）纳入版本控制
- 建立 site 配置备份流程

### 5.3 HIGH - 数据库在 Docker 卷中

**问题：** 全部数据库数据存储在 Docker 命名卷 `hbos-m0-r3a_db-data` 中。Git 仓库中无可见的数据备份策略。

**影响：** 如果该卷被删除或损坏，所有业务数据将丢失。

**缓解措施：**
- 建立定期数据库备份流程（`mariadb-dump` 导出到宿主机）
- 将备份文件纳入 Git LFS 或独立存储
- 制定灾难恢复方案

### 5.4 MEDIUM - HRMS 嵌套 Git 仓库

**问题：** `runtime/apps/hrms` 目录内存在独立的 `.git` 目录。虽然 `runtime/` 被主仓库的 `.gitignore` 忽略，但嵌套 Git 仓库在本地操作时容易引发混淆（如 `git add` 时误将 HRMS 作为 submodule 添加）。

**影响：** 团队成员可能误操作导致仓库状态异常。环境重建时需要手动执行 `git clone` 来获取 HRMS。

**缓解措施：**
- 明确文档化 HRMS 的获取方式：`git clone https://github.com/frappe/hrms.git runtime/apps/hrms -b version-16`
- 考虑使用 `git submodule` 正式管理 HRMS 依赖
- 或在 `docker-compose.yml` 的启动脚本中自动 clone HRMS

### 5.5 MEDIUM - 未导出的 UI 自定义配置

**问题：** 通过 Frappe UI 进行的任何自定义配置（Workspace、Custom Field、Property Setter、Workflow、Role、Report 等）仅存储在数据库中，未通过 Fixture 导出到 Git 仓库。

**影响：** 数据库重建后，所有 UI 层面的自定义配置将丢失，需要手动重新配置。

**缓解措施：**
- 在 Frappe Desk 中使用 "Export Fixtures" 功能导出所有自定义配置
- 将导出的 JSON 文件纳入 Git 版本控制
- 在部署流程中加入 Fixture 导入步骤

### 5.6 MEDIUM - `.env` 含真实密钥

**问题：** 宿主机上存在 `.env` 文件，包含真实数据库密码和管理员密码。虽然已确认该文件被 gitignore 排除，但文件本身存在且未加密。

**影响：** 如果宿主机被未授权访问，或 `.env` 文件被意外复制/分享，密钥将泄露。

**缓解措施：**
- 确认 `.env` 在 `.gitignore` 中（已确认）
- 考虑使用 Docker Secrets 或密钥管理工具
- 限制 `.env` 文件权限（`chmod 600`）

### 5.7 LOW - 单一贡献者

**问题：** 仓库 72 个 commit 全部来自单一贡献者 "Carlo"。无可见的代码审查记录。

**影响：** 缺少代码审查带来的质量保障，知识集中在单一人员。

**缓解措施：** 不构成即时风险，但建议在团队扩展后引入代码审查流程。
