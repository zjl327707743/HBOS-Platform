### 5.1 redis-cache 和 redis-queue —— 退出时间线

**关键时间：2026-07-14 08:08:10 UTC**

```
redis-cache:

  User requested shutdown...
  Saving the final RDB snapshot before exiting.
  DB saved on disk
  Redis is now ready to exit, bye bye...

  signal-handler (1784016490) Received SIGTERM scheduling shutdown...
  User requested shutdown...
  Saving the final RDB snapshot before exiting.
  DB saved on disk
  Redis is now ready to exit, bye bye...
```

**关键发现：**
- 两个 Redis 容器在**同一秒**（08:08:10-08:08:11）收到 SIGTERM
- **相同的 signal-handler 值**（1784016490），说明来自同一信号源
- 均正常保存 RDB 快照后退出（Exit code 0）
- 日志中无任何错误、无 OOM、无 crash 迹象
- 错误类别：**外部信号（非 crash）**

### 5.2 queue-long 和 queue-short —— 退出时间线

**关键时间：2026-07-14 08:08:11 UTC**

- 两个 worker 在 Redis 退出后**同一秒**退出
- Exit code 0（正常退出）
- 退出前日志显示 worker 正常运行 scheduled jobs，无异常
- 行为模式：Worker 失去 Redis 连接后，收到 SIGTERM，正常退出
- 错误类别：**上游依赖（Redis）**

### 5.3 websocket —— 重启循环

**错误签名（重复出现，136 次）：**

```
Linking fresh assets to volume...
Realtime service listening on: ws://0.0.0.0:9000
node:events:486
      throw er; // Unhandled 'error' event
      ^
SocketClosedUnexpectedlyError: Socket closed unexpectedly
    at Socket.<anonymous> (...socket.js:194:118)
    ...
Emitted 'error' event on RedisClient instance at:
    at RedisSocket._RedisSocket_onSocketError (...socket.js:218:10)
```

**模式分析：**
- websocket 启动成功（绑定 9000 端口）
- 尝试连接 Redis Queue（通过 `FRAPPE_REDIS_QUEUE` 环境变量 → `redis://redis-queue:6379`）
- Redis 连接被拒绝或关闭（redis-queue 容器已退出）
- Node.js 进程未捕获此错误 → crash（Exit code 1）
- Docker `on-failure` 策略触发重启
- 重启后 redis-queue 仍然不可用 → 再次 crash → 无限循环
- 错误类别：**Redis（上游依赖不可用）**

## 12. 端口口径

### 12.1 事实

| 来源 | 端口值 | 说明 |
|------|--------|------|
| `.env.example` | `HTTP_PORT=8080` | 模板默认值 |
| 实际 `.env` | `HTTP_PORT=8081` | Owner 本地覆盖值 |
| `docker-compose.yml` | `"${HTTP_PORT}:8080"` | 变量引用 |
| 文档 `04_Docker开发环境复现手册.md` | `http://localhost:8081` | 多处使用 8081 |
| 文档 `08_版本发布回滚备份与环境管理.md` | `http://localhost:8081` | 多处使用 8081 |
| 历史原因 | 8080 被占用 | M0-R3A 记录：首次启动时 8080 端口被占用，修改为 8081 |

### 12.2 结论

1. **`.env.example` 默认 8080 是有意设计**——这是 Frappe 标准端口，也是模板的合理默认值。
2. **Owner 当前 8081 只是本机覆盖**——因为首次启动时 8080 被占用。
3. **新成员应默认使用 8080**——除非他们的 8080 端口也被占用。
4. **存在文档与模板冲突**——团队文档中多处硬编码 8081，但 `.env.example` 写的是 8080。新成员按照 `.env.example` 配置会得到 8080，但文档告诉他们访问 8081，会造成困惑。
5. **G1B-B 建议**：
   - 文档中应将端口说明改为「默认为 `.env.example` 中配置的 `${HTTP_PORT}` 值，通常为 8080；如端口被占用可改为 8081」
   - 不需要修改 `.env.example` 的默认值

## 13. 已确认根因

### 13.1 websocket Restarting

```
症状：websocket 容器持续 Restarting，136 次重启
→ 直接错误：SocketClosedUnexpectedlyError — Redis 连接被意外关闭
→ 故障组件：websocket 容器中的 Node.js socketio.js（@redis/client）
→ 上游依赖：redis-queue 容器
→ 根因假设：redis-queue 容器已退出，websocket 启动后无法连接 Redis Queue，Node.js 进程未捕获该错误导致 crash（exit 1），Docker on-failure 策略触发重启形成无限循环
→ 支持证据：
  1. 日志中每次 crash 前都显示 "Realtime service listening on: ws://0.0.0.0:9000" 然后立即 SocketClosedUnexpectedlyError
  2. redis-queue 容器状态为 Exited（2026-07-14 08:08:10 退出）
  3. websocket 的 FRAPPE_REDIS_QUEUE 环境变量指向 redis://redis-queue:6379
  4. backend 中 DNS 解析 redis-queue 返回 198.18.1.80（不在 frappe_network 子网）
  5. docker inspect 确认 ExitCode=1（crash），RestartCount=136
→ 反证：无。websocket 没有其他错误模式
→ 置信度：HIGH（95%）
→ 最小修复方向：启动 redis-queue 容器，websocket 将自动恢复（当前 restart policy 为 on-failure，redis-queue 恢复后下次重启会成功）
```

### 13.2 queue-long Exited

```
症状：queue-long 容器 Exited (0)，不再运行
→ 直接错误：无可视错误。容器正常退出（exit 0）
→ 故障组件：queue-long（bench worker --queue long,default,short）
→ 上游依赖：redis-queue 容器
→ 根因假设：redis-queue 收到 SIGTERM 退出后，queue-long worker 失去 Redis 连接，随后收到 SIGTERM 并正常退出（exit 0）。由于 exit code 为 0，Docker 的 on-failure 策略不会触发重启
→ 支持证据：
  1. exit code = 0（正常退出，非 crash）
  2. 退出时间（08:08:11）与 redis-queue 退出时间（08:08:10）相差 1 秒
  3. 退出前日志显示 worker 正常运行 scheduled jobs
  4. queue-long 依赖 FRAPPE_REDIS_QUEUE=redis://redis-queue:6379
  5. RestartCount=0，说明 Docker 从未尝试重启它
→ 反证：无
→ 置信度：HIGH（90%）
→ 最小修复方向：启动 redis-queue 容器，然后启动 queue-long 容器
```

```
→ 根因假设：与 queue-long 相同——Redis 退出导致级联退出
→ 支持证据：与 queue-long 完全一致的时间线（08:08:11 退出，与 redis-queue 08:08:10 相差 1 秒）
```

### 13.4 redis-cache Exited

```
症状：redis-cache 容器 Exited (0)，不再运行
→ 直接错误：无。Redis 正常保存 RDB 后退出
→ 故障组件：redis-cache 本身
→ 上游依赖：无（Redis 是底层服务）
→ 根因假设：redis-cache 收到外部 SIGTERM 信号（signal-handler 1784016490），执行正常关闭流程。Exit code 0 表示正常退出，Docker 的 on-failure 策略不会触发重启。信号来源为 Docker 编排层（docker compose stop/restart 或 Docker Desktop 生命周期事件）
→ 支持证据：
  1. 日志明确显示 "Received SIGTERM scheduling shutdown" 和 "User requested shutdown"
  2. 与 redis-queue 在同一秒收到相同 signal-handler 值的信号
  3. 正常保存 RDB 后退出，无任何错误
  4. Exit code = 0
  5. RestartCount = 0
→ 反证：无 crash 日志、无 OOM、无错误
→ 置信度：HIGH（90%）
→ 未确认：SIGTERM 的确切来源（可能是手动 docker compose stop、Docker Desktop 重启、或系统事件）
```

### 13.6 级联故障链总结

```
外部 SIGTERM（来源未最终确认，推测为 Docker 编排操作）
  ├── 2026-07-14 08:08:10 → redis-cache 正常退出 (exit 0)
  ├── 2026-07-14 08:08:10 → redis-queue 正常退出 (exit 0)
  │     ├── on-failure 策略：exit 0 不触发重启 → redis-cache 和 redis-queue 保持 Exited
  │     │
  │     ├── 2026-07-14 08:08:11 → queue-long 失去 Redis 连接 → 退出 (exit 0)
  │     ├── 2026-07-14 08:08:11 → queue-short 失去 Redis 连接 → 退出 (exit 0)
  │     │     └── on-failure 策略：exit 0 不触发重启 → workers 保持 Exited
  │     │
  │     └── websocket 失去 Redis 连接 → crash (exit 1)
  │           └── on-failure 策略：exit 1 触发重启 → 重启后 Redis 仍不可用 → 无限循环
  │
  └── db 也收到 SIGTERM，正常关闭后于 2026-07-15 08:59 被重新启动
```
