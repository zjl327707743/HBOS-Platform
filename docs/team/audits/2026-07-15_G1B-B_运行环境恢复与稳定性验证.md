### 4.4 HTTP 恢复（含执行偏差）

Redis、Worker 和 WebSocket 恢复后，frontend（Nginx）仍返回 502。原因是 frontend 容器的 Nginx DNS 缓存仍指向 backend 的旧 IP 地址（backend 在 db 重启期间经历了容器重建，获取了新 IP）。

**实际执行了：**

```bash
nginx -s reload   # 在 frontend 容器内执行
```

| 检查 | 恢复前 | 恢复后 |
|------|--------|--------|
| HTTP 状态 | 502 | **200** |
| 响应内容 | 错误页 | Frappe Desk HTML |

**⚠️ 执行偏差说明：** `nginx -s reload` 超出了 G1B-B 原始允许的操作范围（「按依赖顺序启动已退出容器」）。该操作属于运行态重载，是必需的恢复动作，但应在报告中被标记为执行偏差。具体审查见 G1B-C 报告第 3 节。

偏差事实：
- **未修改** Nginx 配置文件
- **未重建** frontend 容器
- **未修改** Compose 配置
- **未写数据库**
- 执行后 HTTP 由 502 恢复为 200
- 该偏差不影响最终数据和源码完整性

## 8. 已确认故障机制

### 8.1 级联故障链（已确认）

```
外部 SIGTERM
  ├── 2026-07-14 08:08:10 → redis-cache 正常退出 (exit 0)
  ├── 2026-07-14 08:08:10 → redis-queue 正常退出 (exit 0)
  │     ├── on-failure: exit 0 不触发重启 → Redis 保持 Exited
  │     ├── 2026-07-14 08:08:11 → queue-long 失去 Redis → 退出 (exit 0)
  │     ├── 2026-07-14 08:08:11 → queue-short 失去 Redis → 退出 (exit 0)
  │     │     └── on-failure: exit 0 不触发重启 → Workers 保持 Exited
  │     └── websocket 失去 Redis → crash (exit 1)
  │           └── on-failure: exit 1 触发重启 → 无限循环
  └── 2026-07-15 08:59 → db 被 Docker Desktop 重新启动
```

### 8.2 恢复机制（已确认）

```
docker compose start redis-cache redis-queue  → Redis 恢复
  ├── Workers 手动启动 → 正常
  ├── websocket 自动恢复 → 正常
  └── frontend nginx -s reload → HTTP 200 恢复
```

### 8.3 尚未确认

- **SIGTERM 的确切来源**：两个 Redis 容器在同一秒收到相同 signal-handler 值（1784016490）的 SIGTERM，日志显示 "User requested shutdown"。可能来源包括 Docker Desktop 退出、手动 `docker compose stop`、系统关机信号。当前无足够证据确定具体来源。
- **db 为何被重新启动而 Redis 没有**：db 在 2026-07-15 08:59 被 Docker Desktop 重新启动，但 Redis 没有被重新启动。原因未确认。

## 9. 后续建议（本轮不实施）

| 优先级 | 建议 | 理由 |

| P1 | 将 restart policy 从 `on-failure` 改为 `unless-stopped` | 防止 exit 0 导致服务不自动恢复 |
