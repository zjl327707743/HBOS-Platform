## 1. 环境划分

### 1.1 开发环境（当前）

当前 HBOS 只有一个环境：Owner 的 macOS 本地 Docker Compose 开发环境。

| 项目 | 当前状态 |
|------|----------|
| 用途 | 日常开发与调试 |
| 运行方式 | `docker compose up -d` |
| 数据库 | MariaDB 11.8，数据存储在 Docker volume `hbos-m0-r3a_db-data` |
| 站点 | `frontend`，文件存储在 Docker volume `hbos-m0-r3a_sites` |
| 数据持久性 | 数据在 Docker volume 中，`docker compose down` 不会丢失 |
| 代码热加载 | 支持（通过 volume 挂载 `apps/hb_attendance_app`） |
| 访问地址 | `http://localhost:${HTTP_PORT:-8080}`（实际端口以项目 `.env` 中的 `HTTP_PORT` 和 `docker compose ps` 映射结果为准） |

### 1.2 测试环境（未来）

当团队扩大到 2 人以上时，建议配置独立的测试环境。

**推荐配置：**

| 项目 | 建议值 |
|------|--------|
| 用途 | 集成测试、PR 验证、UAT |
| 运行方式 | 独立服务器或同一机器不同端口/项目名 |
| 数据库 | 独立 MariaDB 实例，数据与开发环境完全隔离 |
| 数据来源 | 从生产备份恢复的脱敏数据，或专用测试数据集 |
| 访问控制 | 仅团队内部可访问，不暴露公网 |
| 部署方式 | CI/CD 自动部署（GitHub Actions 推送到测试服务器） |

**建议的环境变量差异：**

```bash
# 测试环境 .env.test
COMPOSE_PROJECT_NAME=hbos-test
HTTP_PORT=8081              # 与开发环境 8080 错开
SITE_NAME=frontend-test     # 站点名区分
DB_ROOT_PASSWORD=<测试环境独立密码>
```

### 1.3 生产环境（未来）

当系统需要对外提供服务时，建议以下配置最小集：

| 项目 | 建议值 |
|------|--------|
| 服务器 | 至少 4C8G，建议 8C16G |
| 操作系统 | Ubuntu 22.04 LTS 或更高 |
| 数据库 | 独立 MariaDB 11.8 实例（不用 Docker volume，用宿主机目录挂载） |
| HTTPS | 必须启用，使用 Let's Encrypt 或企业证书 |
| 备份 | 每日自动备份 + 异地存储 |
| 监控 | Prometheus + Grafana，或至少 Uptime Kuma |
| 日志 | 集中收集（推荐 Loki + Grafana） |
| 访问控制 | VPN 或 IP 白名单 + 强密码 + 2FA |

### 1.4 环境差异对比表

| 维度 | 开发环境 | 测试环境（建议） | 生产环境（建议） |
|------|----------|-----------------|-----------------|
| 用途 | 日常开发 | 集成测试与 UAT | 真实业务运行 |
| 数据 | 开发假数据 | 脱敏测试数据 | 真实业务数据 |
| 代码热加载 | 是 | 否 | 否 |
| 备份频率 | 按需手动 | 每周 | 每天 |
| HTTPS | 不需要 | 建议启用 | 必须启用 |
| 监控告警 | 不需要 | 基础监控 | 完整监控 + 告警 |
| 访问权限 | 仅本地 | 团队内网 | 授权用户 |
| 密码强度 | 弱密码可接受 | 中等强度 | 强密码 + 2FA |
| 重启策略 | `on-failure` | `unless-stopped` | `always` |

## 2. 版本号规范

### 2.1 语义化版本（SemVer）

HBOS 项目遵循语义化版本 2.0.0：

```
MAJOR.MINOR.PATCH
  │     │     │
  │     │     └─ 修订号：bug 修复，不改变功能
  │     └─────── 次版本号：新增功能，向后兼容
  └───────────── 主版本号：不兼容的 API 变更
```

**示例：**

| 版本变化 | 含义 | 示例 |
|----------|------|------|
| `0.0.1 → 0.0.2` | 修了一个 bug | 修复考勤记录重复保存 |
| `0.0.1 → 0.1.0` | 加了新功能，不影响旧功能 | 新增加班审批流程 |
| `0.0.1 → 1.0.0` | 重大变更，可能不兼容 | 考勤数据结构重构 |

### 2.2 App 版本号规则

HBOS 自研 App 的版本号写在 `apps/<app_name>/<app_name>/__init__.py` 中。

**当前 hb_attendance_app：**

```python
# apps/hb_attendance_app/hb_attendance_app/__init__.py
__version__ = "0.0.1"
```

**规则：**

- 每次 Release 前，手动更新 `__init__.py` 中的版本号
- 版本号必须与 Git tag 一致
- `0.x.y` 阶段表示"开发中，API 不稳定"
- 当 App 首次用于生产时，升到 `1.0.0`

### 2.3 平台集成版本

HBOS 依赖的上游平台组件不使用自研版本号，而是直接引用上游版本：

| 组件 | 版本来源 | 固定方式 |
|------|----------|----------|
| Frappe Framework | Docker 镜像内置 | `docker-compose.yml` 中 `ERPNEXT_VERSION` |
| ERPNext | Docker 镜像内置 | `docker-compose.yml` 中 `ERPNEXT_VERSION` |
| HRMS | `runtime/apps/hrms` 的 Git tag | `git checkout v16.12.0` |
| MariaDB | Docker 镜像 tag | `docker-compose.yml` 中 `mariadb:11.8` |
| Redis | Docker 镜像 tag | `docker-compose.yml` 中 `redis:6.2-alpine` |

### 2.4 Docker 镜像版本固定

> **关键规则：永远不要使用 `latest` 标签。**

所有 Docker 镜像必须固定到具体版本号，写在 `.env` 文件中：

```bash
# .env（示例，不要提交到 Git）
ERPNEXT_VERSION=v16.26.2    # 固定版本，不用 latest
```

**为什么不能使用 `latest`：**

- `latest` 指向的版本会随时间变化
- 今天 `docker compose up` 和明天 `docker compose up` 可能拉取不同镜像
- 排查问题时，没人知道到底跑了哪个版本
- 回滚时无据可依

**升级镜像的正确流程：**

1. 在开发环境先测试新版本镜像
2. 确认所有功能正常
3. 更新 `.env`（和 `.env.example`）中的版本号
4. 提交 `.env.example` 到 Git
5. 记录到版本矩阵

## 4. Release 流程

### 4.1 Release 前检查清单

每次正式 Release 前，必须逐项确认以下清单：

- [ ] 所有代码已合并到目标分支
- [ ] 所有单元测试通过（如已配置）
- [ ] 在本地 Docker 环境完整启动并验证核心功能
- [ ] `apps/hb_attendance_app/hb_attendance_app/__init__.py` 版本号已更新
- [ ] CHANGELOG 已更新
- [ ] 版本矩阵（本文档第 3.1 节）已同步
- [ ] `.env.example` 已同步（如有环境变量变更）
- [ ] 数据库备份已创建（如有破坏性变更）
- [ ] 所有调试代码和 `console.log` 已清理
- [ ] 敏感信息未硬编码（检查 `.env` 和 `site_config.json` 未被提交）

### 4.2 Tag 命名规范

Git tag 用于标记 Release 节点。格式：

```
v<semver>
```

**示例：**

| Tag | 含义 |
|-----|------|
| `v0.1.0` | hb_attendance_app 首个功能版本 |
| `v0.1.1` | 修了一个 bug |
| `v0.2.0` | 新增模块功能 |
| `v1.0.0` | 首个生产可用版本 |

**Tag 注释：**

Tag 必须附带简要注释，说明本版本的关键变更：

```bash
git tag -a v0.1.0 -m "v0.1.0: 完成考勤打卡基础功能，支持签到/签退记录"
```

### 4.3 Release 创建步骤

```bash
# === 步骤 1：确保在正确的分支上 ===
git checkout main
git pull origin main

# === 步骤 2：确认工作区干净 ===
git status
# 输出应显示：nothing to commit, working tree clean

# === 步骤 3：更新版本号 ===
# 编辑 apps/hb_attendance_app/hb_attendance_app/__init__.py
# 将 __version__ = "0.0.1" 改为新版本号

# === 步骤 4：更新 CHANGELOG ===
# 编辑 docs/CHANGELOG.md（如果有）或在 Release Notes 中描述变更

# === 步骤 5：提交版本号变更 ===
git add apps/hb_attendance_app/hb_attendance_app/__init__.py
git commit -m "release: hb_attendance_app v0.1.0"

# === 步骤 6：打 Tag ===
git tag -a v0.1.0 -m "v0.1.0: 完成考勤打卡基础功能"

# === 步骤 7：推送代码和 Tag ===
git push origin main
git push origin v0.1.0

# === 步骤 8：在 GitHub 上创建 Release ===
# 进入 GitHub 仓库 → Releases → Draft a new release
# 选择 Tag v0.1.0
# 填写 Release Notes
# 如果是预发布版本，勾选 "This is a pre-release"
```

## 5. 数据库备份

### 5.1 bench backup 命令详解

HBOS 使用 Frappe 内置的 bench backup 命令创建数据库备份。该命令需要在运行中的 `backend` 容器内执行。

```bash
# 进入 backend 容器执行备份
docker compose exec backend bench --site frontend backup

# 也可以添加额外选项
docker compose exec backend bench --site frontend backup --with-files
```

**参数说明：**

| 参数 | 作用 |
|------|------|
| `--site frontend` | 指定要备份的站点名 |
| `--with-files` | 同时备份站点文件（上传附件、配置等） |
| `--backup-path` | 指定备份输出路径（默认输出到 `sites/frontend/private/backups/`） |

### 5.2 备份内容包括什么

bench backup 创建的文件包括：

**数据库备份（SQL 文件）：**

- 完整的 MySQL/MariaDB 数据库 dump（通过 `mariadb-dump` 生成）
- 包含所有表结构、数据和存储过程
- 文件名示例：`20260714_150000-frontend-database.sql.gz`

**站点文件备份（site_config_backup.json）：**

- `sites/frontend/site_config.json` 的副本
- 包含站点配置参数

**文件备份（仅当使用 `--with-files`）：**

- 上传的附件（`sites/frontend/private/files/`）
- 站点备份配置

### 5.3 备份存储位置

| 存储位置 | 说明 |
|----------|------|
| `sites/frontend/private/backups/` | bench backup 默认输出目录，在 Docker volume `hbos-m0-r3a_sites` 中 |
| 容器内路径 | `/home/frappe/frappe-bench/sites/frontend/private/backups/` |

**重要：备份文件存储在 Docker volume 中，不是宿主机目录。** 如果 Docker volume 被删除（`docker compose down -v`），备份也会丢失。因此必须将备份文件复制到宿主机安全位置。

### 5.4 备份频率建议

| 场景 | 建议频率 | 保留策略 |
|------|----------|----------|
| 日常开发 | 每天结束前 | 保留最近 7 天 |
| 大改动前 | 改动前立即备份 | 永久保留（标记原因） |
| Release 前 | Release 前立即备份 | 永久保留（标记版本号） |
| 数据库迁移前 | 迁移前立即备份 | 永久保留 |
| 生产环境（未来） | 每天自动 | 最近 30 天 + 每月永久保留一份 |

### 5.5 自动备份脚本

当前没有配置自动备份。以下是一个手动备份脚本，可放在项目根目录：

```bash
#!/bin/bash
# 文件路径：scripts/backup.sh
# 用法：bash scripts/backup.sh
# 作用：备份 HBOS 数据库到宿主机

set -euo pipefail

# 配置
PROJECT_NAME="hbos-m0-r3a"
BACKUP_DIR="./backups"
SITE_NAME="frontend"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)

# 创建备份目录
mkdir -p "$BACKUP_DIR"

echo "=== 开始备份 HBOS 数据库 ==="
echo "时间：$(date)"
echo "项目：$PROJECT_NAME"
echo "站点：$SITE_NAME"
echo ""

# 步骤 1：在容器内执行 bench backup
echo "[1/3] 正在执行 bench backup..."
docker compose exec -T backend bench --site "$SITE_NAME" backup --with-files

# 步骤 2：找到最新的备份文件
echo "[2/3] 正在定位备份文件..."
LATEST_BACKUP=$(docker compose exec -T backend bash -c \
  "ls -t /home/frappe/frappe-bench/sites/$SITE_NAME/private/backups/*.sql.gz 2>/dev/null | head -1" | tr -d '\r')

if [ -z "$LATEST_BACKUP" ]; then
  echo "ERROR: 未找到备份文件"
  exit 1
fi

echo "  最新备份文件：$LATEST_BACKUP"

# 步骤 3：复制到宿主机
echo "[3/3] 正在复制备份到宿主机..."
HOST_BACKUP_NAME="${TIMESTAMP}_${SITE_NAME}_backup.sql.gz"
docker compose cp "backend:$LATEST_BACKUP" "$BACKUP_DIR/$HOST_BACKUP_NAME"

echo ""
echo "=== 备份完成 ==="
echo "备份文件：$BACKUP_DIR/$HOST_BACKUP_NAME"
echo "文件大小：$(du -h "$BACKUP_DIR/$HOST_BACKUP_NAME" | cut -f1)"
```

**创建并赋予执行权限：**

```bash
mkdir -p scripts
# 将上述脚本写入 scripts/backup.sh
chmod +x scripts/backup.sh
```

### 5.6 备份文件命名规范

| 命名格式 | 示例 |
|----------|------|
| 数据库备份：`<YYYYMMDD>_<HHMMSS>_<站点名>_database.sql.gz` | `20260714_150000_frontend_database.sql.gz` |
| 完整备份：`<YYYYMMDD>_<HHMMSS>_<站点名>_full_backup.sql.gz` | `20260714_150000_frontend_full_backup.sql.gz` |
| Release 前备份：`<YYYYMMDD>_pre_release_<版本号>.sql.gz` | `20260714_pre_release_v0.1.0.sql.gz` |
| 大改动前备份：`<YYYYMMDD>_<改动描述>_backup.sql.gz` | `20260714_migrate_attendance_schema_backup.sql.gz` |

## 6. 数据库恢复

> **警告：恢复操作会覆盖当前数据库的全部数据。操作前必须确认已创建最新备份。**

### 6.1 bench restore 命令详解

```bash
# 基本恢复命令
docker compose exec backend bench --site frontend restore <备份文件路径>

# 示例：恢复指定备份文件
docker compose exec backend bench --site frontend restore \
  /home/frappe/frappe-bench/sites/frontend/private/backups/20260714_150000-frontend-database.sql.gz

# 恢复后自动执行 migrate
docker compose exec backend bench --site frontend restore \
  /home/frappe/frappe-bench/sites/frontend/private/backups/20260714_150000-frontend-database.sql.gz \
  --mariadb-root-password=<DB_ROOT_PASSWORD>
```

**参数说明：**

| 参数 | 作用 |
|------|------|
| `--site frontend` | 指定要恢复到的站点 |
| `--mariadb-root-password` | MariaDB root 密码（如果配置文件里没有则需要手动提供） |
| `--with-private-files` | 同时恢复私有文件（需备份时包含） |
| `--with-public-files` | 同时恢复公共文件（需备份时包含） |

### 6.2 恢复前检查

恢复操作前必须逐项确认：

- [ ] 已创建当前数据库的最新备份（以防恢复出问题还能回退）
- [ ] 确认恢复的备份文件是正确的（检查文件名中的时间戳）
- [ ] 确认备份文件完整（未损坏，文件大小合理）
- [ ] 通知所有使用者当前正在进行恢复操作，系统将短暂不可用
- [ ] 确认 `DB_ROOT_PASSWORD` 与创建数据库时的密码一致

### 6.3 恢复步骤

```bash
# === 步骤 0：创建"恢复前安全备份" ===
# 这是恢复操作的安全网。如果恢复出问题，还能回到当前状态。
bash scripts/backup.sh

# === 步骤 1：将备份文件复制到容器内 ===
# 如果备份在宿主机上，先复制进容器
docker compose cp ./backups/20260714_150000_frontend_database.sql.gz \
  backend:/home/frappe/frappe-bench/sites/frontend/private/backups/

# === 步骤 2：执行恢复 ===
docker compose exec backend bench --site frontend restore \
  /home/frappe/frappe-bench/sites/frontend/private/backups/20260714_150000_frontend_database.sql.gz

# === 步骤 3：恢复后迁移（确保数据库 schema 与当前代码一致）===
docker compose exec backend bench --site frontend migrate

# === 步骤 4：清除缓存 ===
docker compose exec backend bench --site frontend clear-cache

# === 步骤 5：如果使用了 --with-files，还需恢复文件 ===
docker compose exec backend bench --site frontend restore \
  /path/to/backup.tar --with-private-files --with-public-files
```

### 6.4 恢复后验证

恢复完成后，必须执行以下验证：

```bash
# 1. 检查站点是否能正常访问
curl -s -o /dev/null -w "%{http_code}" "http://localhost:${HTTP_PORT:-8080}"
# 应返回 200

# 2. 登录系统，检查关键页面
# 浏览器打开 http://localhost:${HTTP_PORT:-8080}
# 用 Administrator 账号登录
# 检查：考勤模块 → 验证数据是否与预期一致

# 3. 检查核心表记录数
docker compose exec db mariadb -u root -p"$DB_ROOT_PASSWORD" -e "
  SELECT COUNT(*) AS employee_count FROM \`frontend\`.tabEmployee;
  SELECT COUNT(*) AS attendance_count FROM \`frontend\`.tabAttendance;
"
```

**验证清单：**

- [ ] 站点能正常打开（HTTP 200）
- [ ] 能正常登录
- [ ] 核心业务数据完整（记录数大致匹配预期）
- [ ] 没有明显的页面报错或 500 错误

### 6.5 部分恢复（只恢复特定表）

如果只需要恢复某几张表的数据，不能直接用 bench restore（它会覆盖整个数据库）。需要手动操作：

```bash
# === 步骤 1：解压备份文件 ===
gunzip -k 20260714_150000_frontend_database.sql.gz
# 得到 .sql 文件

# === 步骤 2：从 SQL dump 中提取目标表的 INSERT 语句 ===
# 例如只恢复 tabAttendance 表
grep -A 100000 "Table structure for table \`tabAttendance\`" \
  20260714_150000_frontend_database.sql | \
  grep "^INSERT INTO" > attendance_recovery.sql

# === 步骤 3：将提取的 SQL 复制到容器内 ===
docker compose cp attendance_recovery.sql db:/tmp/

# === 步骤 4：执行恢复 ===
# ⚠️ 危险操作：先备份目标表
docker compose exec db mariadb-dump -u root -p"$DB_ROOT_PASSWORD" \
  frontend tabAttendance > tabAttendance_backup.sql

# 执行恢复
docker compose exec db mariadb -u root -p"$DB_ROOT_PASSWORD" frontend \
  < /tmp/attendance_recovery.sql
```

> **警告：部分恢复操作风险极高。** 如果表之间有外键关联，部分恢复可能导致数据不一致。仅在没有其他选择时才使用，并且必须在操作前完整备份。

## 8. 回滚操作

> **核心原则：回滚的目的是恢复系统到上一个已知正常的版本。回滚不是"撤销"按钮，而是"恢复"操作。**

### 8.1 代码回滚（git revert）

当新提交的代码引入问题，需要回退代码。

```bash
# === 方式 1：创建 revert 提交（推荐，不改变历史）===

# 回滚最近一个 commit
git revert HEAD

# 回滚指定的 commit
git revert <commit-hash>

# 推送到远程
git push origin main


# === 方式 2：硬回退（⚠️ 危险，改变历史，仅限个人分支）===

# 回退到指定 commit，丢弃之后的所有更改
# ⚠️ 不要在共享分支上使用
git reset --hard <commit-hash>

# 强制推送（⚠️ 非常危险，会覆盖远程历史）
# git push --force origin main  # 禁止在 main 上执行
```

**规则：**
- 共享分支（`main`）必须使用 `git revert`，不得使用 `git reset --hard`
- 个人功能分支可以使用 `git reset`，但推送后也要发 PR 让其他人审查
- revert 后再提交时，commit message 要注明为什么回滚

### 8.2 数据库回滚（restore backup）

当数据库变更引入问题，需要恢复到变更前的数据。

```bash
# === 步骤 1：创建当前状态的紧急备份 ===
bash scripts/backup.sh
# 备份文件会被标记为"回滚前紧急备份"

# === 步骤 2：找到目标备份文件 ===
# 选择问题出现之前的备份文件

# === 步骤 3：执行恢复 ===
docker compose exec backend bench --site frontend restore \
  /home/frappe/frappe-bench/sites/frontend/private/backups/<目标备份文件>.sql.gz

# === 步骤 4：执行迁移 ===
docker compose exec backend bench --site frontend migrate

# === 步骤 5：清除缓存 ===
docker compose exec backend bench --site frontend clear-cache

# === 步骤 6：验证恢复结果 ===
# 按照 6.4 节中的验证步骤操作
```

### 8.3 App 版本回滚

回滚自研 App（如 hb_attendance_app）到上一个版本。

```bash
# === 方式 1：通过 Git tag 回滚 ===

# 1. 查看所有 tag
git tag -l

# 2. 检出目标 tag 的 App 目录
#    如果 App 代码在仓库中被跟踪：
git checkout v0.0.1 -- apps/hb_attendance_app/

# 3. 确认版本号已回退
cat apps/hb_attendance_app/hb_attendance_app/__init__.py

# 4. 提交回滚
git add apps/hb_attendance_app/
git commit -m "revert: hb_attendance_app 回滚至 v0.0.1"

# 5. 重启容器使更改生效
docker compose restart backend

# 6. 执行迁移（确保数据库 schema 与回滚后的代码一致）
docker compose exec backend bench --site frontend migrate


# === 方式 2：如果 App 版本变更包含数据库迁移，需要同时恢复数据库 ===

# 1. 代码回滚（同方式 1）
# 2. 数据库恢复到回滚版本对应的备份
# 3. 详见 8.2 节
```

### 8.4 回滚决策树

当发现问题时，按以下决策树选择回滚方案：

```
发现生产/测试问题
│
├─ 问题类型是？
│  │
│  ├─ 代码 bug（功能异常但数据完好）
│  │  └─ 操作：git revert → 重启容器 → 验证
│  │
│  ├─ 数据问题（数据库数据损坏或错误）
│  │  └─ 操作：紧急备份 → restore backup → migrate → 验证
│  │     注意：回滚会丢失恢复点之后产生的所有新数据
│  │
│  ├─ 配置问题（环境变量或 site_config 错误）
│  │  └─ 操作：修复配置 → 重启相关容器 → 验证
│  │
│  └─ 上游组件问题（ERPNext/HRMS/Docker 镜像 bug）
│     └─ 操作：回退镜像版本 → 重新部署 → 验证
│        如果上游有数据库迁移，需评估是否需要同时回滚数据库
```

### 8.5 回滚后验证

回滚操作完成后，必须执行以下验证：

```bash
# 1. 检查所有容器状态
docker compose ps
# 所有服务应显示 "Up" 或 "running"

# 2. 检查站点可访问性
curl -s -o /dev/null -w "HTTP Status: %{http_code}\n" "http://localhost:${HTTP_PORT:-8080}"
# 应返回 200

# 3. 检查后端健康
docker compose exec backend bench --site frontend doctor
# 应无错误

# 4. 手动验证核心功能
# - 登录系统
# - 检查受影响的模块
# - 确认关键数据完整

# 5. 检查日志无异常
docker compose logs --tail=50 backend | grep -i error
```

## 9. 紧急修复流程（Hotfix）

### 9.1 什么是紧急问题

以下情况适用 Hotfix 流程：

| 严重级别 | 描述 | 响应时间 |
|----------|------|----------|
| **P0 - 阻断** | 系统完全不可用、数据丢失、安全漏洞 | 立即处理 |
| **P1 - 严重** | 核心功能不可用，无替代方案 | 2 小时内 |
| **P2 - 一般** | 功能受影响但有替代方案 | 下一个工作日 |
| **P3 - 轻微** | 显示问题、文案错误 | 下一个版本 |

> **当前阶段（本地开发）：** 所有问题都可以直接在 main 分支上修复，不需要独立 Hotfix 分支。

### 9.2 Hotfix 分支创建（多人协作时）

当有测试/生产环境且多人协作时，使用以下 Hotfix 分支策略：

```bash
# 1. 从 main 创建 hotfix 分支
git checkout main
git pull origin main
git checkout -b hotfix/<简短描述>

# 示例
git checkout -b hotfix/fix-attendance-duplicate
```

**分支命名规范：** `hotfix/<问题简述>`，使用小写英文和连字符。

### 9.3 Hotfix 修复步骤

```bash
# === 步骤 1：创建备份（安全第一）===
bash scripts/backup.sh

# === 步骤 2：定位问题 ===
# 查看日志
docker compose logs --tail=200 backend | grep -i error

# 进入容器调试
docker compose exec backend bench --site frontend console

# === 步骤 3：修复代码 ===
# 在本地编辑器中修改代码

# === 步骤 4：本地验证 ===
# 重启相关服务
docker compose restart backend
# 验证修复效果

# === 步骤 5：更新版本号 ===
# 编辑 __init__.py，升级 PATCH 版本号
# 例如：0.1.0 → 0.1.1

# === 步骤 6：提交修复 ===
git add .
git commit -m "hotfix: <问题描述>"

# === 步骤 7：打 Tag ===
git tag -a v0.1.1 -m "v0.1.1: Hotfix - <问题描述>"

# === 步骤 8：推送 ===
git push origin main
git push origin v0.1.1
```

### 9.4 合并回 main（多人协作时）

当 Hotfix 在独立分支上完成时：

```bash
# 1. 切换到 main
git checkout main
git pull origin main

# 2. 合并 hotfix 分支
git merge hotfix/fix-attendance-duplicate

# 3. 推送
git push origin main

# 4. 删除 hotfix 分支（本地和远程）
git branch -d hotfix/fix-attendance-duplicate
git push origin --delete hotfix/fix-attendance-duplicate
```

### 9.5 Hotfix 部署步骤

```bash
# === 部署到开发环境 ===

# 1. 拉取最新代码
git pull origin main

# 2. 重启受影响的容器
docker compose up -d --force-recreate backend

# 3. 执行迁移
docker compose exec backend bench --site frontend migrate

# 4. 清除缓存
docker compose exec backend bench --site frontend clear-cache

# 5. 验证
curl -s -o /dev/null -w "%{http_code}" "http://localhost:${HTTP_PORT:-8080}"
```

### 10.3 灾难恢复方案

当出现以下情况时，采用灾难恢复：

- Docker volume 被意外删除（`docker compose down -v`）
- 宿主机硬盘故障
- 数据被不可逆地损坏

**灾难恢复的前提条件：**

> **没有备份 = 没有恢复。** 这是所有灾难恢复讨论的唯一基础。

**恢复优先级从高到低：**

| 优先级 | 数据 | 恢复方式 |
|--------|------|----------|
| 1 | 数据库 | 从宿主机备份的 `.sql.gz` 恢复 |
| 2 | 上传附件 | 从宿主机备份的 `files_*` 目录恢复 |
| 3 | 站点配置 | 从 Git 仓库中的 `.env.example` 重建 `.env` |
| 4 | 自研代码 | 从 Git 仓库恢复（`git clone`） |
| 5 | HRMS 源码 | 从 GitHub `frappe/hrms` 重新克隆 |
| 6 | Docker 镜像 | 从 Docker Hub 重新拉取 |

**灾难恢复检查清单：**

- [ ] 宿主机上有最近的完整备份
- [ ] 备份文件已确认可读（未损坏）
- [ ] Git 仓库可访问（GitHub 上有最新代码）
- [ ] Docker Hub 可访问（能拉取镜像）
- [ ] `.env` 中的密码已知（或从密码管理器获取）
- [ ] 恢复后的系统经过完整验证（6.4 节）

## 11. 环境监控

### 11.1 健康检查

**当前可用的基础检查：**

```bash
# 1. 检查所有容器状态
docker compose ps
# 确保所有服务状态为 "Up" 或 "running"

# 2. 检查站点响应
curl -s -o /dev/null -w "HTTP %{http_code} | Time: %{time_total}s\n" "http://localhost:${HTTP_PORT:-8080}"

# 3. 检查数据库连接
docker compose exec db mariadb -u root -p"$DB_ROOT_PASSWORD" -e "SELECT 1;"
# 应返回 1

# 4. 检查 Redis 连接
docker compose exec redis-cache redis-cli ping
# 应返回 PONG

# 5. 检查 Frappe 后端
docker compose exec backend bench --site frontend doctor
# 应无错误

# 6. 检查磁盘空间
df -h .
```

**建议的健康检查脚本：**

```bash
#!/bin/bash
# 文件路径：scripts/healthcheck.sh
# 用法：bash scripts/healthcheck.sh

set -euo pipefail

RED='\033[0;31m'
GREEN='\033[0;32m'
NC='\033[0m' # No Color

check() {
  local name="$1"
  local cmd="$2"
  if eval "$cmd" &>/dev/null; then
    echo -e "  ${GREEN}[PASS]${NC} $name"
  else
    echo -e "  ${RED}[FAIL]${NC} $name"
  fi
}

echo "=== HBOS 健康检查 ==="
echo "时间：$(date)"
echo ""

echo "容器状态："
docker compose ps --format "table {{.Name}}\t{{.Status}}"
echo ""

echo "服务检查："
check "站点可访问"      "curl -s -o /dev/null -w '%{http_code}' http://localhost:\${HTTP_PORT:-8080} | grep -q 200"
check "数据库连接"       "docker compose exec -T db mariadb -u root -p\"\$DB_ROOT_PASSWORD\" -e 'SELECT 1'"
check "Redis 缓存"       "docker compose exec -T redis-cache redis-cli ping | grep -q PONG"
check "Redis 队列"       "docker compose exec -T redis-queue redis-cli ping | grep -q PONG"
echo ""

echo "资源使用："
docker stats --no-stream --format "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}"
```

### 11.2 日志监控

```bash
# 查看所有容器日志（最近 100 行）
docker compose logs --tail=100

# 持续监控 backend 日志
docker compose logs -f backend

# 只看错误和警告
docker compose logs backend 2>&1 | grep -iE "error|warning|exception|traceback"

# 查看特定时间范围的日志
docker compose logs --since 2026-07-14T10:00:00 --until 2026-07-14T12:00:00 backend

# 查看 scheduler 日志（定时任务）

# 查看 worker 日志（后台任务）
docker compose logs --tail=50 queue-short queue-long

# 导出日志到文件供分析
docker compose logs --tail=500 backend > logs_backend_$(date +%Y%m%d).txt
```

**Frappe 内部日志路径：**

| 日志 | 容器内路径 | 备注 |

## 附录 B：危险操作标记

以下操作带有数据丢失风险，执行前必须确认已备份：

| 操作 | 风险等级 | 前置条件 |
|------|----------|----------|
| `docker compose down -v` | **极高** | 删除所有 volume，数据永久丢失。必须先在宿主机备份 |
| `bench restore` | **高** | 覆盖当前数据库。必须先执行完整备份 |
| `git reset --hard` | **高** | 丢弃代码变更。确认不需要保留当前更改 |
| `git push --force` | **极高** | 覆盖远程历史。绝不在 main 分支使用 |
| `mariadb DROP DATABASE` | **极高** | 数据库完全删除。必须确认备份可用 |
| `docker system prune -a` | **高** | 清理所有未使用的镜像和 volume。确认不需要的才删 |
| 手动 SQL DELETE/UPDATE | **高** | 批量数据操作。先 SELECT 确认范围，先备份表 |

> **规则：看到红色（风险极高）操作时，停下，确认备份，然后再执行。**
