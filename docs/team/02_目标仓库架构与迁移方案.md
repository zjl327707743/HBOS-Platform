## 2. 方案 A：单仓库 / Monorepo

### 2.1 结构示意

```
HBOS/
├── docs/                    # 所有文档
├── docker-compose.yml
├── .env.example
├── apps/
│   ├── hb_attendance_app/   # 自定义 App（Git 子目录）
│   ├── hb_core_app/         # 自定义 App
│   └── hb_feishu_app/       # 自定义 App
├── services/                # 外部服务
│   ├── ai-service/
│   └── video-service/
└── scripts/                 # 部署/运维脚本
```

### 2.2 优点

- **零迁移成本**：无需拆分，直接在当前仓库上继续开发。
- **单一事实来源**：所有内容在一个仓库，开发者 clone 一次即可。
- **原子提交**：跨 App 的改动可以在一个 commit 中完成，CI 联动简单。
- **适合当前团队规模**：1-3 人团队，Monorepo 管理成本极低。

### 2.3 缺点

- **无法独立版本管理**：每个 App 无法独立打 tag、独立发布（Frappe App 的本质是独立可安装模块，Monorepo 违背了这种模块化设计）。
- **权限无法细分**：未来团队扩大后，无法按 App 设置不同人的读写权限。
- **CI/CD 耦合**：任何一个 App 的 CI 失败可能阻塞其他 App 的部署。
- **历史膨胀**：所有 App 的提交历史混在一起，回看单个 App 的演进路径困难。
- **与 Frappe 生态惯例不符**：Frappe 社区中每个 App 都是独立仓库，Monorepo 会让未来的社区协作和上游依赖管理变得困难。

### 2.4 适用场景

当前（1 人开发）勉强可用，但团队扩展到 2 人以上后，权限管理、版本管理的缺陷会迅速暴露。

## 3. 方案 B：多仓库 / Multi-Repo

### 3.1 结构示意

```
hbos-infra/                 # 部署编排仓库
hb_attendance_app/          # 考勤 App 仓库
hb_core_app/                # 核心 App 仓库
hb_feishu_app/              # 飞书 App 仓库
hbos-docs/                  # 文档仓库（or 合并到 infra）
hbos-ai-service/            # AI 服务仓库
```

### 3.2 优点

- **完全独立版本管理**：每个 App 独立打 tag、独立发布、独立 CHANGELOG。
- **权限细粒度**：按仓库分配开发者权限。
- **CI/CD 解耦**：每个 App 独立构建、独立测试、独立部署。
- **符合 Frappe 生态惯例**：`bench get-app https://github.com/...` 安装独立 App。
- **历史清晰**：每个 App 的提交历史干净、聚焦。

### 3.3 缺点

- **跨仓库协调成本高**：改动涉及多个 App 时，需要跨多个仓库提 PR、协调合并顺序。
- **环境搭建复杂**：新开发者需要 clone 多个仓库，并配置正确的目录结构。
- **版本一致性难保证**：`docker-compose.yml` 中引用的 App 版本需要手动同步。
- **文档分散**：项目整体文档放在哪个仓库难以抉择，容易多份拷贝或无人维护。
- **CI 联动复杂**：跨 App 的集成测试需要额外的编排脚本。
- **当前团队规模过高配**：2-3 人团队管理 5+ 个仓库，管理成本显著高于收益。

## 4. 方案 C：混合模式（推荐）

### 4.1 核心思路

**一个主仓库做"骨架"，每个自定义 App 独立仓库做"模块"，上游从官方获取不 fork。**

```
hbos-infra/                  # 主仓库：部署编排 + 文档 + 环境模板
├── docs/                    # 全部项目文档
├── docker-compose.yml       # 容器编排（引用各 App 的具体版本）
├── .env.example
├── apps.txt                 # 声明各 App 的仓库地址和版本
├── scripts/
│   ├── clone-all.sh         # 一键 clone 所有 App 仓库
│   └── dev-setup.sh         # 新开发者环境搭建
└── fixtures/                # 跨 App 的共享 fixture

hb_attendance_app/           # 独立仓库：考勤 App
hb_core_app/                 # 独立仓库：核心 App
hb_feishu_app/               # 独立仓库：飞书 App
hbos-ai-service/             # 独立仓库：AI 服务（未来）

# 上游直接引用，不 fork
# Frappe: frappe/frappe (docker.io/frappe/erpnext:v16.26.2)
# ERPNext: frappe/erpnext (同上镜像)
# HRMS: 上游仓库（gitignored 到 runtime/apps/hrms，不纳入主仓库管理）
```

### 4.2 主仓库（hbos-infra）职责

| 内容 | 说明 |
|------|------|
| docker-compose.yml | 声明所有服务的编排，App 通过 `build` 或 `volume mount` 引用 |
| apps.txt | 记录每个 App 的仓库 URL、期望版本/分支 |
| docs/ | 架构文档、团队文档、API 文档 |
| .env.example | 环境变量模板 |
| scripts/ | 开发环境搭建脚本、部署脚本 |
| fixtures/ | 跨 App 共享的 fixture 数据 |

### 4.3 各 App 仓库职责

| 内容 | 说明 |
|------|------|
| App 源码 | 遵循 Frappe App 标准目录结构 |
| App 专属 fixture | 每个 App 自己的 fixture |
| App 专属 migration | 数据库迁移 patch |
| App 专属 CI 配置 | 独立测试、lint |
| App 专属 README | 该 App 的安装和使用说明 |

### 4.4 上游处理策略

| 组件 | 策略 | 说明 |
|------|------|------|
| Frappe Framework | 不 fork，直接引用 Docker 镜像 | `frappe/erpnext:v16.26.2` |
| ERPNext | 不 fork，直接引用 Docker 镜像 | 同上 |
| 第三方 App（如 HRMS） | 不 fork，gitignored 安装 | 通过 `bench get-app` 从上游安装 |

### 4.5 优点

1. **权限细粒度**：按 App 仓库分配开发者权限，核心基础设施只有 Owner 和骨干成员可改。
2. **独立版本管理**：每个 App 独立 tag、独立 CHANGELOG、独立发布。
3. **新人友好**：`clone hbos-infra && ./scripts/dev-setup.sh` 一键完成环境搭建。
4. **CI/CD 解耦又联动**：每个 App 独立 CI，主仓库的 CI 负责集成测试和部署。
5. **符合 Frappe 生态惯例**：每个 App 独立仓库，`bench get-app` 安装。
6. **仓库数量可控**：不把文档、部署、脚本拆成独立仓库，集中在主仓库，避免过度拆分。
7. **跨 App 改动可追溯**：在 apps.txt 中记录每个 App 的当前版本，版本变更一目了然。
8. **上游不 fork 降低维护成本**：不维护 Frappe/ERPNext 的 fork，直接跟踪官方镜像版本。

### 4.6 缺点

- 需要在主仓库中维护 `apps.txt` 的版本一致性（但可以通过脚本自动化）。
- 跨 App 的原子性改动仍需要协调（但频次远低于单仓库方案的缺点）。

## 5. 推荐方案

### 明确推荐：方案 C（混合模式）

**推荐理由：**

1. **匹配 Frappe 生态的模块化设计**

   Frappe 框架的核心理念是"App 即模块"——每个 App 是独立可安装的单元。混合模式尊重这一设计，每个自定义 App 独立仓库，通过 `bench get-app` 安装，与上游生态无缝对接。

2. **平衡当前团队规模与未来扩展**

   当前 1-3 人团队，Monorepo 过度便利但缺乏约束；全部拆散又管理成本过高。混合模式把"不变的"（infra、docs、deploy）集中在主仓库，把"变化的"（各 App 业务代码）拆分出去，仓库数量控制在 4-5 个，维护成本可控。

3. **新开发者加入零摩擦**

   一个 `clone hbos-infra` + `./scripts/dev-setup.sh` 即可完成环境搭建，不需要新人理解"哪个仓库放哪里"、"哪个版本对应哪个版本"。避免多仓库方案中常见的"少 clone 了一个仓库导致报错找半天"的问题。

4. **权限控制天然适配团队分工**

   未来 Owner 可以这样分配：骨干开发者有 hbos-infra 写权限，实习生只有 hb_attendance_app 读权限，飞书集成负责人只有 hb_feishu_app 写权限。Monorepo 做不到这一点。

5. **版本管理和发布清晰**

   每个 App 独立打 tag（如 `hb_attendance_app@v1.2.0`），独立编写 CHANGELOG，独立判断是否准备好发布。主仓库的 `apps.txt` 记录当前部署的各 App 版本，生产环境的配置一目了然。

6. **不 fork 上游 = 极低维护成本**

   Frappe/ERPNext 通过官方 Docker 镜像引入，第三方 App 通过 `bench get-app` 从上游安装，不维护任何 fork。官方更新时，只需升级 Docker 镜像 tag 和重新 `bench get-app`，没有合并冲突，没有代码差异积累。

7. **迁移路径清晰，可分阶段执行**

   不需要一次性完成拆分，可以按 App 逐个抽离，每阶段有明确的回滚方案（详见第 6 节）。

## 6. 分阶段迁移步骤

### 阶段 0：当前不动（M1-FIX 期间）

**目标：** 不拆仓，继续在当前 Monorepo 交付 M1-FIX。

**操作：** 无。

**状态：** 当前即为阶段 0。

**回滚：** 不需要（还未开始迁移）。

---

### 阶段 1：创建主仓库 + 基础设施就绪

**前置条件：** M1-FIX 完成并稳定。

**操作：**

1. 在 GitHub 创建 `hbos-infra` 仓库（私有）。
2. 将当前 HBOS 仓库中的以下内容迁移到 `hbos-infra`：
   - `docs/` 目录（全部文档）
   - `docker-compose.yml`
   - `.env.example`
   - `scripts/`（新建：clone-all.sh、dev-setup.sh）
   - `apps.txt`（新建：声明各 App 仓库地址和当前版本）
3. 编写 `scripts/dev-setup.sh`：
   ```bash
   #!/bin/bash
   # 一键搭建开发环境
   git clone git@github.com:zjl327707743/hbos-infra.git
   cd hbos-infra
   # 读取 apps.txt 并 clone 每个 App 到 apps/ 目录
   while IFS= read -r line; do
     repo=$(echo "$line" | awk '{print $1}')
     branch=$(echo "$line" | awk '{print $2}')
     git clone "$repo" "apps/$(basename "$repo" .git)" -b "$branch"
   done < apps.txt
   # 启动 Docker Compose
   docker compose up -d
   ```
4. 在 `hbos-infra` 中配置 GitHub Actions 用于集成测试。
5. 原 HBOS 仓库添加 README 迁移说明，指向 `hbos-infra`。

**验证：** 在另一台机器上执行 `dev-setup.sh`，确认可以成功搭建完整环境。

**回滚：** 原 HBOS 仓库未删除，`hbos-infra` 只是新增仓库。如果出问题，继续使用原 HBOS 仓库即可。

---

### 阶段 2：抽离 hb_attendance_app 为独立仓库

**前置条件：** 阶段 1 完成并验证。

**操作：**

1. 创建 `hb_attendance_app` 仓库（私有）。
2. 使用 `git filter-repo` 从原 HBOS 仓库中提取 `apps/hb_attendance_app/` 的提交历史：
   ```bash
   git clone https://github.com/zjl327707743/HBOS.git temp-attendance
   cd temp-attendance
   git filter-repo --subdirectory-filter apps/hb_attendance_app --force
   git remote add origin git@github.com:zjl327707743/hb_attendance_app.git
   git push -u origin main
   ```
3. 在 `hb_attendance_app` 仓库中：
   - 添加独立 CI 配置（GitHub Actions：lint + test）
   - 编写独立 README（安装说明、使用文档）
   - 打第一个 tag `v1.0.0`
4. 在 `hbos-infra` 的 `apps.txt` 中添加：
   ```
   git@github.com:zjl327707743/hb_attendance_app.git main
   ```
5. 更新 `hbos-infra` 的 `docker-compose.yml`，将 `hb_attendance_app` 的安装方式从本地目录改为 git clone + volume mount。
6. 从原 HBOS 仓库中删除 `apps/hb_attendance_app/`，提交并推送。

**验证：** 执行 `hbos-infra` 的 `dev-setup.sh`，确认 `hb_attendance_app` 从独立仓库 clone 并正常工作。

**回滚：** 在 `hbos-infra` 的 `docker-compose.yml` 中将 App 路径改回原 HBOS 仓库的本地路径，`git revert` 原 HBOS 仓库的删除提交。

---

### 阶段 3：其他 App 逐步抽离（按需）

**前置条件：** 阶段 2 完成并稳定运行。

**操作：** 每新增一个自定义 App，在创建之初就使用独立仓库，流程与阶段 2 相同。

**顺序规则：**
- 新 App 从第一天起就是独立仓库，不先放在 Monorepo 再拆分。
- 不需要一次性把所有 App 拆分完，按需推进。

**回滚：** 单个 App 的迁移回滚方式与阶段 2 相同。

---

### 阶段 4：原 HBOS 仓库归档

**前置条件：** 所有内容都已迁移到 `hbos-infra` 和各独立 App 仓库。

**操作：**

1. 确认原 HBOS 仓库中所有有价值的内容已迁移。
2. 在原 HBOS 仓库的 README 中添加归档说明，指向新仓库位置。
3. 在 GitHub 上将原 HBOS 仓库标记为 Archive（只读）。
4. 不删除仓库，保留历史记录供回溯。

**回滚：** 从 GitHub Archive 中取消归档即可恢复，无需额外操作。

## 7. 每阶段回滚方法汇总

| 阶段 | 回滚操作 | 影响范围 |
|------|---------|---------|
| 阶段 0 | 不需要 | 无 |
| 阶段 1 | 删除 hbos-infra 仓库，继续使用原 HBOS | 仅 hbos-infra |
| 阶段 2 | 在原 HBOS 仓库中恢复被删除的 apps/hb_attendance_app | 仅 hb_attendance_app |
| 阶段 3 | 与阶段 2 相同 | 仅单个 App |
| 阶段 4 | 取消 Archive 标记 | 原仓库恢复可读写 |

**关键原则：每一步可回滚，不做不可逆操作。** 原 HBOS 仓库在阶段 4 之前保持可读写。

## 8. 预计风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|:---:|:---:|---------|
| `git filter-repo` 提取历史时丢失数据 | 低 | 高 | 先在副本上操作，验证后再推送；原仓库不删除 |
| 迁移后环境搭建脚本不工作 | 中 | 中 | 阶段 1 验证时在干净机器上完整跑一遍 |
| 跨 App 改动需要协调多个仓库 | 中 | 低 | 改动涉及多个 App 时，先在各 App 仓库提 PR，最后在主仓库更新 apps.txt |
| 团队成员不适应多仓库工作流 | 中 | 低 | 提供 `dev-setup.sh` 一键脚本降低心智负担；文档明确说明提交流程 |
| 主仓库 apps.txt 与各 App 实际版本不一致 | 中 | 中 | 在主仓库 CI 中增加一致性检查：读取 apps.txt 并与实际 clone 的版本对比 |
