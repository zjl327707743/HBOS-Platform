# 服务自启与服务器部署

适用范围：把当前 Mac 上的三个外部服务（`hbos_ocr` / `hbos_production` / `hbos_production_ai`）迁移到公司服务器时的**自启与网络**方案。

本文只给方案与文件草案，**不修改任何运行配置**。真正上服务器时按本文执行。

## 一、先认清：现在是三套不同形态

macOS 用的是 **launchd**，Linux 上没有这个东西。三个服务在 launchd 里也不是同一种：

| 服务 | 形态 | 监听端口 | 当前自启 | Linux 对应 |
| --- | --- | --- | --- | --- |
| `hbos_production` | **常驻** HTTP 服务 | `127.0.0.1:8101` | launchd `KeepAlive`（2026-10-29 起） | systemd service 或 compose 服务 |
| `hbos_ocr` | **常驻** HTTP 服务 | `0.0.0.0:8100` | launchd `KeepAlive` | systemd service 或 compose 服务 |
| `hbos_production_ai` | **定时**脚本（无端口） | — | launchd 16:30 | systemd **timer** |
| `hbos_production.warm` | **定时**脚本（无端口） | — | launchd 07:10/16:40 | systemd **timer** |

两条硬性差异：

- **常驻 vs 定时不能混用同一套配置。** 常驻要 `Restart=always`，定时要 `OnCalendar=`；写反了要么起不来、要么反复跑。
- **定时脚本的 `WorkingDirectory` 很关键。** AI 服务用相对路径读 `.env`，工作目录错了就读不到配置。

## 二、两个网络决定（均已定）

### 决定 1：生产看板走 nginx 反代同源

**现状**：看板是浏览器直连 8101 的。核 `frontend/hbos-portal-web/src/services/productionBoard.ts`：

```ts
const SERVICE_ORIGIN = import.meta.env.VITE_PRODUCTION_SERVICE_ORIGIN   // 构建时写死
const url = `${SERVICE_ORIGIN}/production/monthly`
res = await fetch(url, ...)          // 浏览器直接发
```

两个后果：

- **`VITE_PRODUCTION_SERVICE_ORIGIN` 是构建时烘焙进 bundle 的**。换服务器必须**重新构建前端**，改 `.env` 后重启 Vite 不管用（生产构建尤其如此）。
- 服务当前绑 `127.0.0.1`，服务器上**浏览器根本连不到**。

**Owner 2026-10-27 决定：走 nginx 反代同源，不做浏览器直连。**

**为什么直连不可取**（三条，按严重度）：

1. **混合内容会被浏览器拦掉。** 看板是 HTTPS（`scripts/release/nginx.conf.template` 里 80 端口 308 跳 443）。浏览器从 HTTPS 页面请求 `http://内网IP:8101` 属于混合内容，**静默拦截**。直连就必须给 8101 单独配 TLS —— 等于再维护一套证书和续期。
2. **直连等于把「零鉴权」暴露到内网。** 生产取数服务目前没有任何身份校验，安全性全靠"只绑 127.0.0.1"。改成 `0.0.0.0` 后，任何能访问 8101 的机器 `curl` 一下就拿走产量、收率、质量、异常以及完整 AI 报告。**CORS 只是浏览器自律，对 curl 无效。**
3. **反代能顺手收回一半风险。** `productionBoard.ts` 的 fetch **没有写 `credentials`**，默认 `same-origin` —— 同源时自动带 Frappe session cookie，服务层或 nginx 就能校验会话。直连时 cookie 不会发。

| | 浏览器直连 8101 | nginx 反代同源（已选） |
| --- | --- | --- |
| 服务绑定 | 必须 `0.0.0.0` | 保持 `127.0.0.1` / 仅容器网络 |
| 防火墙 | 办公网段开 8101 | 只开 443 |
| TLS | **需第二张证书** | 复用现有 443 |
| CORS | 必须配 `HBOS_PRODUCTION_CORS_ORIGINS` | 不涉及 |
| 鉴权 | 做不到 | 同源 cookie 可校验 |
| 前端 bundle | 写死服务地址 | 可走相对路径 |

**代码前提（必须知道）**：`productionServiceConfigured` 的判据是

```ts
export const productionServiceConfigured = SERVICE_ORIGIN.length > 0
```

**所以「env 留空走同源」现在不成立** —— 留空会直接短路成 `not_configured`，压根不发请求。反代上线时二选一：

- 改 3 行：加 `VITE_PRODUCTION_SERVICE_MODE=same-origin`，把「未配置」与「同源」区分开（推荐）；
- 或把 env 写成完整公开域名 `https://hbos.example.com` —— 那确实是同源（scheme/host/port 全同），但域名被烘焙进 bundle，换域名要重新构建。

**nginx 片段**（Frappe 不占用 `/production` 前缀，已核对 `nginx.conf.template` 与 portal hooks，不冲突）：

```nginx
# scripts/release/nginx.conf.template 的 443 server 块内，location / 之前
location /production/ {
    proxy_pass http://hbos-production:8101;   # 不带尾斜杠 —— 保留 /production 前缀
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_read_timeout 180s;                  # 冷启动并发拉 13 张飞书表，实测 ~19s，留足余量
    proxy_buffering off;                      # 响应不大，关掉早点吐字
}
```

> 反代之后 `host.docker.internal` 这条依赖对生产看板**也不再需要**（服务在同一容器网络里）。
> 它只对 OCR 相关 —— 若 OCR 也进 compose，两条依赖一起消失。

### 决定 2：`host.docker.internal` 不能靠默认存在

这是迁移时**最容易照搬出事**的一条。

- Mac 上：Docker Desktop 自动提供 `host.docker.internal`（实测 → `192.168.5.2`）
- Linux 上：**默认解析不到**，必须在 compose 里显式声明

核过当前 `docker-compose.yml`：`extra_hosts` 与 `host-gateway` **一次都没出现**。直接搬过去，容器里 `curl host.docker.internal:8100` 会 DNS 失败，页面又报「识别服务不可达」——和这次排查了半天的那句话一模一样。

要么加：

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

要么把 OCR 做成 compose 服务，`HBOS_OCR_URL` 直接写 `http://hbos-ocr:8100`，这条依赖就彻底消失。

**已选后者** —— 服务器有 GPU（见第三节之一），OCR 进 compose。这样 `extra_hosts` 完全不需要；只有退回方案 B（OCR 留在宿主机）时才要补上这一条。

## 三、方案 A：全部进 compose（推荐）

**理由**：三个服务现在**都不在 compose 里**。全部收进去之后：

- 自启交给 Docker 的 `restart: unless-stopped`，不需要 systemd
- `host.docker.internal` 这层跳转消失
- 一条 `docker compose up -d` 起来全部
- 日志统一 `docker compose logs`

**代价**：OCR 的 ML 依赖要打进镜像（体积大）；服务器**已确认有 GPU**，需要装 NVIDIA Container Toolkit 做直通（详见「三之一、GPU 直通」）。

### 文件草案

```yaml
# docker-compose.yml 追加（片段，不是完整文件）

  hbos-ocr:
    build:
      context: ./services/hbos_ocr
      dockerfile: Dockerfile
    restart: unless-stopped
    environment:
      HBOS_OCR_BACKEND: ${HBOS_OCR_BACKEND:-c1_local_vlm}   # GPU 直通后可用本地大模型
      HBOS_OCR_HOST: 0.0.0.0
      HBOS_OCR_PORT: "8100"
      HBOS_OCR_SHARED_TOKEN: ${HBOS_OCR_SHARED_TOKEN}
      HBOS_OCR_C1_MODEL: /models/c1
    volumes:
      # 模型权重挂进来，不打进镜像
      - ./runtime/ocr-models:/models:ro
    networks: [frappe_network]
    # 不映射宿主端口 —— 只有容器网络内可见
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

  hbos-production:
    build:
      context: ./services/hbos_production
    restart: unless-stopped
    environment:
      # 只监听容器网络；对外一律经 nginx 反代（见第二节「已定」）
      HBOS_PRODUCTION_HOST: 0.0.0.0
      HBOS_PRODUCTION_PORT: "8101"
    volumes:
      - hbos-production-cache:/app/.cache
    networks: [frappe_network]
    # 不映射宿主端口。反代同源后 CORS 不再需要配置。

  # 定时任务：compose 里没有原生 timer，
  # 用「常驻 + 内部 cron」或由 systemd timer 调 `docker compose run`
```

**定时任务的两种做法**：

1. **systemd timer 调 docker compose**（推荐，语义清晰）：

```ini
# /etc/systemd/system/hbos-production-ai.timer
[Unit]
Description=HBOS 生产 AI 分析（每天 16:30）

[Timer]
OnCalendar=*-*-* 16:30:00
Persistent=true          # 关机/停机错过的，开机后补跑一次

[Install]
WantedBy=timers.target
```

```ini
# /etc/systemd/system/hbos-production-ai.service
[Unit]
Description=HBOS 生产 AI 分析

[Service]
Type=oneshot
WorkingDirectory=/opt/hbos
ExecStart=/usr/bin/docker compose run --rm hbos-production-ai
User=hbos
```

2. **容器内跑 cron/supercronic** —— 少一个 systemd unit，但日志与退出码不好看，**不推荐**。

## 三之一、GPU 直通（服务器已确认有 GPU）

服务器有 GPU 之后，**OCR 应该进 compose**，不再需要「留在宿主机」的折衷。这一步把方案 B 的最大理由消掉了。

### 前置（宿主机，一次性）

```bash
# 1) 驱动 + CUDA
nvidia-smi                                  # 能打出来就说明驱动 OK

# 2) NVIDIA Container Toolkit
sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# 3) 验证容器能看到 GPU
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi
```

第 3 步不通就先别往下做 —— 容器里看不到卡，OCR 会静默回落到 CPU，跑得极慢但不报错。

### 镜像里的后端选择

GPU 通了之后，「`c2_ocr` 还是 `c1_local_vlm`」的选择变了：

| 后端 | 依赖 | GPU 下表现 |
| --- | --- | --- |
| `c2_ocr`（PaddleOCR） | `paddlepaddle-gpu` | 能用，但 OCR 只是图文识别，读不出工艺语义 |
| `c1_local_vlm`（本地视觉大模型） | `mlx-vlm`（**Apple 专属**）/ 或 vLLM + 开源 VLM | **这才是 GPU 的价值**：能理解标签版式与上下文 |

当前 `c1_local_vlm` 走的是 MLX，**只能在 Apple Silicon 上用**。上 Linux + NVIDIA 需要换后端实现（vLLM / TensorRT-LLM 托管一个开源 VLM），这是**一笔真实工作量**，不是配个环境变量。

**建议**：服务器第一版仍用 `c2_ocr`（能跑、GPU 加速），把 `c1_local_vlm` 换后端作为独立一轮。不要在上线时同时换环境 + 换模型。

### 镜像基础

`c2_ocr` + GPU 时，基础镜像要带 CUDA，且 `paddlepaddle-gpu` 版本必须与驱动的 CUDA 版本匹配：

```dockerfile
FROM nvidia/cuda:12.4.0-cudnn8-runtime-ubuntu22.04

# 系统依赖：OpenCV 需要 libGL、glib
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3 python3-pip libgl1 libglib2.0-0 && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY requirements.txt .
# 注意：paddlepaddle-gpu 有自己的 CUDA 版本对应表，不能装错
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app
EXPOSE 8100
CMD ["python3", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8100"]
```

> 模型权重**挂在 volume 里**（`./runtime/ocr-models:/models:ro`），不打进镜像 —— 否则镜像几个 GB，每次改代码都要重推。

## 三之二、如果直通不成，退回方案 B

GPU 直通遇到过不去的坑时（驱动与内核不匹配、公司安全策略不允许 `--gpus`、CUDA 版本对不上），OCR 可以退回**宿主机 systemd**（第四节），生产看板与定时任务照旧进 compose。混用是可行的 —— 它们之间只靠 HTTP 通信。

判断顺序建议：

1. `docker run --rm --gpus all … nvidia-smi` 通 → OCR 进 compose（**推荐路径**）
2. 不通，且短期修不好 → OCR 走方案 B，其余进 compose
3. 长期要上 `c1_local_vlm` → 先确认 Linux 上的替代后端（vLLM 等）可行，再决定

## 四、方案 B：宿主机 systemd（OCR 留在宿主机时）

给「OCR 必须跑在宿主机（要 Metal/CUDA 直通）」或「不想打镜像」的情况。

### 常驻服务

```ini
# /etc/systemd/system/hbos-ocr.service
[Unit]
Description=HBOS 入库拍照识别服务
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=hbos
WorkingDirectory=/opt/hbos/services/hbos_ocr
# 复用现有脚本：它已经处理了「只挑 HBOS_OCR_*」「缺令牌 fail-fast」「默认绑 0.0.0.0」
ExecStart=/opt/hbos/services/hbos_ocr/scripts/start.sh
Restart=always
RestartSec=10
# 令牌从受限文件读，不写进 unit（unit 文件通常是 world-readable）
EnvironmentFile=/etc/hbos/hbos_ocr.env

[Install]
WantedBy=multi-user.target
```

```bash
# 启用
sudo systemctl daemon-reload
sudo systemctl enable --now hbos-ocr
systemctl status hbos-ocr
journalctl -u hbos-ocr -f
```

### 定时任务

```ini
# /etc/systemd/system/hbos-production-warm.timer
[Timer]
OnCalendar=*-*-* 07:10:00
OnCalendar=*-*-* 16:40:00
Persistent=true
```

```ini
# /etc/systemd/system/hbos-production-warm.service
[Service]
Type=oneshot
User=hbos
WorkingDirectory=/opt/hbos/services/hbos_production
ExecStart=/opt/hbos/services/hbos_production/.venv/bin/python -m app.warm
EnvironmentFile=/etc/hbos/hbos_production.env
```

AI 服务同理，`ExecStart=... -m app.main`，`OnCalendar=*-*-* 16:30:00`。

## 五、照搬会坏的三处

### 1. 绝对路径

三个 plist 里都是：

```
/Users/xinxianghaibinzhiliang/test/HBOS-Platform/services/...
```

服务器上必须改成 `/opt/hbos/services/...`（或实际路径）。

> 注：`services/hbos_production_ai/launchd/*.plist` 在仓库里还留着 `__VENV_PYTHON__` / `__SERVICE_DIR__` 占位符（安装到 `~/Library/LaunchAgents` 时已填成真实路径）。迁移时**别用仓库里那份原样拷**，会直接起不来。

### 2. venv 不能跨机器拷

`.venv` 里的 `bin/python` 是指向 uv 管理的解释器的符号链接：

```
.venv/bin/python -> /Users/xinxianghaibinzhiliang/.local/share/uv/python/cpython-3.12-macos-aarch64-none/bin/python3.12
```

到 Linux 上这条链接是断的。必须重新建环境（`uv sync` 或 `pip install -r requirements.txt`）。

OCR 尤其要注意：`paddleocr` / `paddlepaddle` 是平台相关的，Mac 的 wheel 在 Linux 上不能用。

### 3. `.env` 的位置

- OCR：`scripts/start.sh` 默认读**仓库根** `.env`（`HBOS_OCR_ENV_FILE` 可覆盖）
- production / AI：各自读**服务目录下**的 `.env`

服务器上建议统一放 `/etc/hbos/*.env`（`chmod 600`，属主 `hbos`），用 `EnvironmentFile=` 注入，**不要留在仓库目录**——部署包可能被打包/备份，密钥跟着走。

## 六、必须一起改的配置

迁移时这几个值不改，功能会静默失效：

| 配置 | 现在的值 | 服务器上 |
| --- | --- | --- |
| `HBOS_OCR_URL` | `http://host.docker.internal:8100` | `http://hbos-ocr:8100`（OCR 进 compose） |
| `extra_hosts` | **不存在** | 仅当 OCR 走方案 B（宿主机）时才需要 `host.docker.internal:host-gateway` |
| `HBOS_PRODUCTION_CORS_ORIGINS` | 只有 localhost:5178/5179 | 反代同源后**不再需要**；若最终仍走直连才要设成看板域名 |
| `VITE_PRODUCTION_SERVICE_ORIGIN` | `http://127.0.0.1:8101` | 反代同源：加 `VITE_PRODUCTION_SERVICE_MODE=same-origin`（需改 3 行）或写公开域名；改了要**重新构建前端** |
| `HBOS_AI_LOCK_PATH` | `/tmp/hbos_production_ai.lock` | 建议改到持久目录（`/var/lock/hbos/...`），否则多容器/多用户环境下 `/tmp` 可能隔离 |
| 缓存目录 | `.cache`（相对） | 挂 volume，否则容器重建就丢 |

### 两个决定的依据

**GPU**：服务器有 GPU 后，「OCR 留在宿主机」的唯一理由（Mac 拿不到 Metal 加速）消失，进 compose 更省事——自启、日志、网络都统一。

**反代同源**：直连 8101 会撞上混合内容（HTTPS 页面请求 HTTP 资源被浏览器静默拦掉，必须再配一张证书），而且等于把当前的「零鉴权服务」暴露到内网——任何机器 `curl` 就能拿走全部数据，CORS 拦不住。反代同源还能让同源 cookie 可用于鉴权。

### 还差一步代码

反代上线时必须改前端 3 行：`productionServiceConfigured` 现在只看 `SERVICE_ORIGIN.length > 0`，**env 留空会被判成「未接入」而不发请求**。需要加一个「同源模式」开关。这一步**故意没现在做**——本机 mock 模式不涉及，提前改反而增加分叉。

**这两个问题不定，服务器自启就没法定稿。** 建议在服务器采购/交付时一并确认。
