# HBOS 考勤判定规则文档

> 版本：2026-08-21
> 适用范围：海滨考勤系统（HBOS Attendance）自动考勤判定
> 代码位置：`apps/hb_attendance_app/hb_attendance_app/hbos_attendance/api.py`、`pairing.py`

---

## 一、判定流程总览

```
得力云考勤机数据同步
        ↓
Employee Checkin（打卡流水入库）
        ↓
HBOS 配对算法（regenerate_attendance）
        ↓
Attendance（考勤结果）
        ↓
报表 / 仪表盘 / 飞书同步
```

每天同步得力云数据后，系统自动运行配对算法生成考勤结果。算法可随时重跑，重跑会重新生成指定日期范围内的全部考勤记录。

## 三、打卡配对规则

### 3.1 去重

- 相邻打卡间隔 **< 2 小时（120 分钟）**视为重复打卡，保留最早的一条（Owner 2026-09-08 由 10 分钟放宽）
- 典型场景：进出厂门时连续刷两次卡；**下班不止打一次卡**（同机重复刷卡，间隔常达几十分钟）→ 合并为最早卡，避免多余下班卡落孤立、被误判缺勤（黄法普/于洋 9/7 案例：次日 08:09 + 08:27 同下班机两次刷卡，08:27 原落孤立判 Absent）
- **分机实施后（2026-08-15 起）**：上下班机方向不同的相邻卡**不合并**（陈雨欣 8/19 案例：17:33 上班机卡与 17:34 下班机卡相隔 84 秒，合并会吞掉唯一的下班机卡导致误判缺勤）

> 已知边界：无设备方向（SN 缺失/手机卡等）的相邻同向卡若间隔 >10 分钟但 <2 小时也会被合并、保留最早卡——出勤不受影响（合并只保留最早卡不误判缺勤），仅极端场景下可能影响迟到判定精度。

### 3.2 配对窗口

- 最短班次：**2 小时**（不足 2 小时的两张卡不配对，视为重复打卡）
- 最长班次：**14 小时**（超过 14 小时的两张卡不配对；正常班次最长 12 小时，14h 上限给 12 小时班加班留缓冲，同时防漏下班卡导致的假超长班——李明 8/19 无菌班加班 13.17h 案例确认放宽，冯慧杰 8/15 15.69h 仍拦截）

### 3.3 跨天夜班优先锁定（阶段 0）

先处理无歧义的夜班配对：

- 上班卡时间：**22:00 - 24:00**
- 下班卡时间：**次日 04:00 - 10:00**
- 配对时长：**4 - 12 小时**
- 固定早班群体（行政/安全/食堂）不参与此阶段

> 案例：李开新 8/7 23:57 上班 → 8/8 08:05 下班 = 夜班 8.11 小时。若不做优先锁定，08:05 会被误判为早班迟到。

### 3.4 早晨卡向前配对（倒班员工）

倒班员工（非固定早班群体）早晨 10:00 前的打卡，**优先向前一天配对**：

- 找前一天 **14:00 后**的上班卡（中班/晚班上班卡）
- 配对时长：**2 - 12 小时**
- 配对成功 → 判定为跨天班次（中班/晚班）

> 目的：消除「晚班下班卡被误判为早班迟到」。

### 3.5 零点夜班配对（2026-08-17 新增）

0-4 点的卡**向前配对失败后**，先尝试与当天 4:00-10:00 的下班卡配对：

- 夜班时间段：**0:00-8:00**，下班卡在 8:00 之后
- 配对时长：**2 - 12 小时**
- 迟到起算点：**0:00 整不算迟到，0:01 起算迟到**（Owner 确认，无宽限）
- 固定早班群体（行政/安全/食堂/豁免）不参与

> 案例：刘兴军 8/3 00:47 上班（迟到 47 分钟）→ 08:00 下班 = 零点夜班 7.23 小时。
> 修复前 0-4 点的卡只向前配对（视为前夜下班卡），配不上即判缺勤，零点班被误判。

### 3.6 主循环配对

剩余的卡按时间顺序贪心配对（**分机实施前**的回退路径，8/14 及之前）：

- 配对窗口：2 - 13 小时
- 跨天配对：仅允许中班/晚班（行政班禁止跨天）

### 3.7 纯设备方向顺序配对（2026-08-15 起，分机实施后）

8/15 起上下班打卡分机，方向由设备确定，不需要启发式（向前配对/时段锁定/猜班次）：

1. 上班机卡按时间顺序向后找**最近的未用下班机卡**组成一对
2. 跨天自然支持（23:44 上班 → 次日 08:39 下班）
3. 上班机卡孤立 = 缺勤（口径B）；下班机卡孤立 = 缺勤（口径B）
4. 间隔超过 14 小时不配对（异常数据，冯慧杰 8/15 15.69h 假超长班案例；李明 8/19 13.17h 无菌班加班正常配对）
5. 间隔不足 2 小时不配对（上下班机相邻连刷/误刷方向）
6. 某天完全没有下班机卡时回退按时间配对（设备规则失效兜底，如刘兴军 8/14 双上班机卡）
7. **孤立卡兜底（2026-08-21 修复）**：当天已有完整上下班结构（首次上班卡→末次下班卡间隔 2-14h）时，孤立卡视为重复打卡，不判缺勤（陈雨欣 8/19 案例：17:33 误刷上班机卡，当天 08:23-17:34 正常上下班，原算法误判 Absent）
8. **跨天夜班下班误刷（2026-08-21 修复）**：孤立上班机卡在 8-10 点、且前一日存在上班机卡（夜班上班，间隔 8-14h）时，视为前一夜班的下班误刷，不判缺勤（吕玉升 8/16 案例：8/15 20:24 夜班上班 → 8/16 08:36 下班误刷在上班机）

## 四、迟到判定规则

| 班次 | 迟到条件 |
|------|---------|
| 早班 | 上班卡 > 08:00 |
| 行政班 | 上班卡 > 08:30 |
| 中班 | 上班卡 > 16:00 |
| 晚班 | 上班卡 > 20:30（跨天场景）|
| 零点夜班 | 上班卡 > 00:00（0-4 点上班、8 点后下班）|

补充口径：

- 四班次人员（FOUR_SHIFT_NUMS）：**迟到不卡死，工作满 8 小时算正常出勤**；不足 8 小时置早退标记（Owner 2026-08-21）
- 行政班名单人员（ADMIN_NUMS）：08:31 起算迟到；20 点后与 0-4 点的跨天卡按晚班不判迟到（四车间杨迪/侯宇晓 08:0x 打卡被全局规则误匹配早班案例）
- 豁免人员：不判迟到
- 食堂人员：不判迟到
- 请假当天：不判迟到

## 五、缺勤判定规则

### 5.1 孤立卡缺勤

**有上班卡但无下班卡 → 判缺勤**（Owner 确认的业务规则）。

例外情况（不判缺勤）：
- 豁免名单人员
- 当天有请假记录
- 行政班人员周末（周六/周日）

### 5.2 零打卡缺勤

**全天无任何打卡 → 判缺勤**。

例外情况（不判缺勤）：
- 豁免名单人员
- 当天有请假记录 → 判「On Leave」而非缺勤
- 行政班人员周末（周六/周日）→ 双休豁免

### 5.3 下夜班休息日（2026-08-17 修订，原「孤卡补缺」已删除）

员工当天打卡**全部被前一夜班配对消耗**（典型场景：早晨 8 点的下班卡配给前晚夜班，当天白天不再上班）时，当天视为**休息日**，不再补判缺勤（Owner 确认）。

> 案例：刘兴军 8/2 只有一张 08:00 的下班卡（8/1 夜班收尾），修复前被补判 8/2 缺勤，修复后 8/2 无异常记录。

## 六、请假规则

- 数据源：HBOS Leave Record（飞书同步）
- 条件：`approval_status = 已通过`
- 请假日期范围内：不判缺勤，生成「On Leave」记录
- 请假当天有打卡：正常按打卡判定出勤（不计缺勤）

---

## 七、周末双休规则

仅适用于**行政班名单（ADMIN_NUMS）**：

- 周六、周日无打卡 → 不算缺勤（双休豁免）
- 周末有打卡 → 正常计入出勤（加班）

倒班人员（无菌/安全/其他倒班）无周末豁免。

## 八、豁免名单（EXEMPT_NUMS）

**54 个工号**，包含但不限于：

- 管理层：总经理、副总、各部门经理、主管
- 特殊岗位：AI 创新部、注册部等

豁免效果：
- 不判迟到
- 不判缺勤
- 孤立卡不判缺勤
- 零打卡不判缺勤
- **但正常出勤记录仍会生成**

## 九、得力云同步规则

### 9.1 匹配规则

- **工号优先匹配**：用打卡数据中的 `employee_num` 匹配员工
- **姓名兜底匹配**：工号为空时用 `member_name` 匹配
- **双重校验**：工号匹配到的员工姓名与打卡机 `member_name` 不一致时，跳过该记录（防止工号混搅）

> 案例：张习方打卡被考勤机录错工号（挂到李开新 11004052 名下），双重校验拦截了脏数据。

### 9.2 数据过滤

- 未来日期（2030+）的打卡跳过
- 重复时间戳跳过

### 9.3 分机上下班打卡规则（2026-08-14 起实施）

打卡记录保留设备信息：设备名写入 `device_id`，设备 SN 写入 `hbos_terminal_sn`。

| 上班打卡 | `13750CS_D7C69C16EC0B2447` | 办公楼外考勤机 |
| 上班打卡 | `13750CS_02281E713F33A9A8` | 厂区二道门西考勤机 |
| 下班打卡 | `13750CS_9FB66A86CF3487D7` | 办公楼内考勤机 |
| 下班打卡 | `13750CS_93C9390B9995FE8C` | 宿舍二楼东考勤机 |

- **2026-08-14 及之后**：打卡方向按设备 SN 判定（分机规则优先）
- **2026-08-14 之前**：分机未实施，方向回退配对算法推断（每班次第一张卡=上班、第二张=下班）
- 报表「打卡流水」的「打卡状态」列按上述规则显示「上班打卡 / 下班打卡」

### 9.4 夜班下班次日休息规则（2026-08-19 确认）

- 夜班下班日 = 早上 8:00-10:00 打下班卡的那天（跨天夜班/零点班收尾；8 点前打卡算早退）
- 夜班下班日之后的**第一个整天无打卡** = 休息日，不计缺勤
- 连续两天以上无打卡：第二天起按缺勤处理
- 本规则是通用规则（不限定部门），完全依据打卡配对结果判定

## 十三、考勤通知

> 本章描述每日出勤通知的**发送机制与呈现方式**，不涉及任何判定规则的改动。
> 判定规则以第二至十一章为准；本章所有数字与「谁算异常」的归桶判定，均由既有统计口径算出，通知侧不另立一套规则。
> 代码位置：`apps/hb_attendance_app/hb_attendance_app/hbos_attendance/attendance_notify.py`、`hbos_attendance/board_stats.py`

### 13.1 用途与时机

- 每个自然日 **09:00（北京时间）**，Frappe 调度器执行 `hb_attendance_app.hbos_attendance.attendance_notify.send_daily_report`，把**当日各部门到岗情况**推送到飞书群（群自定义机器人 webhook）。
- 目的：上班时间刚开始时，让管理者一眼看到「今天哪几个部门、哪几个人还没打卡」，便于及时联系。
- 调度定义在 `hooks.py`：cron `"0 9 * * *"`。Frappe cron 按**系统时区**判定，本环境系统时区为 `Asia/Shanghai`，故 `0 9` 即北京时间 09:00。**只挂一条**——`Scheduled Job Type` 以 `method` 为唯一键，同一方法挂多条会互相覆盖，谁胜出取决于遍历顺序。
- 任务内另有「北京时间小时 == 9」守卫作为**防御**：手动或误触发在非 9 点执行时直接跳过（`force=True` 可绕过，仅供干跑验证）。
- 群自定义机器人是**单向**的，通知只出不进，不支持在群里回查或对话。

### 13.2 消息形态（2026-09-11 卡片化）

- 消息类型由纯文本（`msg_type: text`）改为**飞书交互卡片**（`msg_type: interactive`）：列由卡片组件负责对齐，重点由版式负责凸显。
- 标题色由内容决定：**有异常 → 橙色（`orange`）**；**无异常 → 绿色（`green`）**。标题文本为 `考勤到岗 · <YYYY-MM-DD> <HH:MM>`。
- 卡片正文：

| 元素 | 内容 |
| --- | --- |
| 全厂汇总行 | `全厂 应出勤 N · 已到岗 N`；**未打卡 / 迟到为 0 时省略该字段**（不出现「迟到 0」这类占位） |
| 异常区 | 有异常时，分隔线下标出「⚠ 需处理（N 个部门）」，随后列出异常部门 |
| 异常部门行 | 一行标题：部门名 + **只显示有值的那一项计数**；下一行为人名（` · ` 分隔，缩进跟随） |
| 正常部门 | **不逐条列出**，统一收成一行「其余 N 个部门全部正常」（N = 应出勤 > 0 的部门数 − 异常部门数） |
| 全厂无异常 | 正文一行「✅ 各部门全部正常，无未打卡、无迟到」 |
| 当日无应出勤 | 正文只有一句「（今日暂无应出勤人员）」，不列部门、不附备注 |
| 口径备注 | 存在「未开始 / 仅下班卡 / 班次未定」人员时附一行（见 13.5），无应出勤人员时不附 |

- 部门顺序**沿用 `dept_summary` 的既有排序**（未打卡+迟到降序），不额外排序，保证卡片与部门看板同序。

**为何由纯文本改为卡片**（Owner 2026-09-11 反馈）：

| 问题 | 说明 |
| --- | --- |
| 列对不齐 | 旧版用空格补位手工对齐（按中文 2 格 / 西文 1 格算显示宽度），这套办法**只在等宽字体下成立**；飞书客户端使用**比例字体**，四列数字必然散开，无论怎么调空格都不可能对齐 |
| 找不到重点 | 旧版把全部部门平铺，正常部门与问题部门混在一起，坏消息被好消息淹没 |

改卡片后：对齐交给组件（根治错列），正常部门收成一行（突出异常）。

### 13.3 截断规则

防止极端情况把卡片撑爆。**两条截断都必须在卡片上显式写出被省略的数量，不得静默截断。**

| 位置 | 上限 | 超出时的呈现 |
| --- | --- | --- |
| 单个部门的人名 | 6 人 | `张三 · 李四 · 王五 · 赵六 · 孙七 · 周八 等 3 人` |
| 异常部门数 | 10 个 | 第 10 个之后加一行 `另有 N 个部门存在异常（详见部门看板）` |

- 人名**只放姓名，不放工号**：部门已在行首，工号在群里无人阅读，只会加长行宽。
- 重名问题本轮不处理（真出现再加区分字段）。
- 对应常量：`MAX_NAMES_PER_DEPT = 6`、`MAX_EXCEPTION_DEPTS = 10`。

### 13.4 降级行为

| 场景 | 行为 |
| --- | --- |
| 卡片 JSON 构造抛异常 | **自动降级**：改用纯文本（`msg_type: text`）**照常发出**，并把异常与文本一并记入 Error Log（标题「HBOS考勤通知卡片渲染失败(降级为纯文本)」）。原则是「**宁可丑，不能不发**」 |
| 卡片发送被飞书拒绝（body 里 code 非 0） | 按既有链路记 Error Log，**不自动补发纯文本**——code 非 0 通常意味着 webhook 地址或鉴权有问题，纯文本同样发不出去；次日自然再算。幂等位不变（失败时不落） |
| 未配 webhook | 静默跳过（见 13.6） |
| 干跑 `HBOS_NOTIFY_DRY_RUN=1` | 只写 Error Log **不发送**；日志中**同时**留纯文本与卡片 JSON，便于先核对版式再配地址 |

> 判定响应是否真的成功不能只看 HTTP 状态码：飞书失败时也可能返回 HTTP 200（如签名不匹配、被限流），错误码在 body 里。成功判据为「2xx 且 body 的 `code` / `StatusCode` 为 0 或缺失」；body 非 JSON（如自建网关返回纯文本）时 2xx 即视为成功。
>
> 因此：群里偶尔出现一条纯文本消息是**设计内的兜底**，不是故障——只在卡片渲染真的出错时才会发生。

### 13.5 口径来源（关键）

**通知不实现自己的判定规则。** 所有数字与「谁算异常」的归桶判定，全部来自 `hbos_attendance/board_stats.py`：

| 来源 | 作用 |
| --- | --- |
| `summarize_rows(rows)` | 逐行归桶与全厂 / 单行计数（应出勤 / 已到岗 / 未打卡 / 迟到 / 仅下班卡 / 班次未定 / 未开始 / 缺勤 …） |
| `dept_summary(rows)` | 部门聚合；通知的部门顺序直接沿用它的排序（未打卡+迟到降序），与部门看板同序 |
| `is_late(r)` | 迟到判定谓词（由 `summarize_rows` 内部调用） |

- 异常名录提取（`collect_exceptions`）对每行调用一次 `summarize_rows([r])`，**取它的 `late` / `noCard` 计数**作为该行的归桶判定，做到与统计口径**字面同源**；`board_stats.py` 一行未改。
- 卡片 / 文本里的**计数**直接取自 `dept_stats` / `stats`，通知侧不做二次汇总。

> 实现约束（防止口径漂移）：**不能**改用 `is_late(r)` 单独判迟到。`summarize_rows` 对非应出勤行（`exempt` / `rest` / `leave` / `unknown` / 非班次）直接跳过、不计任何桶，而 `is_late` 只看 `state` 与标签——一行「休假 + 迟到标签」会被 `is_late` 判为迟到、却被统计忽略，于是卡片列出看板不认的人，两处数字就会漂移。故必须以单行 `summarize_rows` 的 `expected` 为前置门槛。豁免部门（`anomaly_hidden`，如设备动力部）在提取前显式跳过，与看板一致。

**9 点口径**（归桶定义见 `board_stats`）：

- 晚班（20:00 上班）/ 夜班（0:00 上班）人员此时尚未到上班时间，落 `before_start`（未开始）桶；
- 跨天夜班只刷到下班机者落 `out_only`（仅下班卡）桶；
- 无排班 / 无绑定者落 `fact_none`（班次未定）桶；
- **三者都不计入「未打卡」**，故 09:00 通知里的「未打卡」是**真预警**。
- 卡片在存在上述三类人员时，正文末尾附一行口径说明（文案 `NO_CARD_HINT`）：「（晚班 20:00 / 夜班 0:00 上班，未到班次时间不计入未打卡）」。

> 直观对照（2026-09-10 09:00 实测，全厂 696 人）：按上述口径「未打卡」12 人，条条是真预警；若把上述三类人一并塞进「未打卡」，会得到 176 人，其中 164 人是夜班收工或班次未定，通知立刻失真。

### 13.6 环境变量与配置

配置放本机 `.env`（已被 `.gitignore` 忽略，**不入仓库**）：

| 变量 | 说明 |
| --- | --- |
| `HBOS_NOTIFY_WEBHOOK_URL` | 飞书群自定义机器人 webhook 地址。**未配置 → 静默跳过发送**（只记日志，不报错） |
| `HBOS_NOTIFY_TOKEN` | 可选。配置后作为 `Authorization: Bearer <token>` 请求头发送。飞书自定义机器人靠 URL 里的 key 鉴权，一般**无需**此项；保留以便接自建网关 |
| `HBOS_NOTIFY_DRY_RUN` | `=1` 时只把消息写入 Error Log 而**不发送**，供配地址前先核对内容；此模式下日志同时保留**纯文本与卡片 JSON** |

### 13.7 关闭方式

清空 `HBOS_NOTIFY_WEBHOOK_URL`（或从 `.env` 删除该行）即**静默不再发送**：任务照常执行、照常算数，只是跳过发送并记一行日志，不报错、不影响调度器。恢复时重新填上地址即可。

### 13.8 幂等

- 以 `frappe.cache` 键 `hbos_notify_sent:<YYYY-MM-DD>` 去重，**同一天只发一次**（防重复触发、防同日多条 cron 各发一遍）。
- **发送失败时不落幂等位**，与「失败不重试、次日再算」的策略一致。
- 幂等位写入失败单独兜底（只记日志）：消息已送达却因幂等位写失败而重发，比漏记幂等位更糟，故不让它把整次发送拖成失败。
- 干跑（`HBOS_NOTIFY_DRY_RUN=1`）按「已发送」处理，**同样会落下幂等位**；故同一天的 9 点窗口内，干跑之后真实发送会被幂等拦截（`force=True` 可绕过）。若要同日既干跑又实发，请用 `force=True`。
