## 1. 建议存储归属

复用现有 `hbos_portal` App 承载当前缺失的岗位、任职关系，关系服务与授权协议分包。建议关系服务包为 `hbos_portal.organization`，统一授权仍为已存在的 `hbos_portal.authorization`；两者可由 Portal / Desk 调用，不依赖页面状态或另建会话。DocType 使用既有 `HBOS Portal` 模块。此为下一段文件实现的落点建议，本次不创建目录、App 或对象。

| 数据 | 本方案的唯一权威来源 | 当前处理 |
| --- | --- | --- |
| 登录主体、账号启停及安全版本 | 现有 User 与账号服务 | 只引用，不复制密码 / MFA / 飞书身份；安全版本不充当授权增代 |
| 人员资料与员工关系 | 现有 Employee / Employee.user_id；无员工资料时为 User 投影 | 不建立第二张人员身份表，不凭手机号、工号或同名匹配 |
| 公司、部门、岗位类别 | Company、Department、Designation | 引用稳定主键，名称只用于展示；岗位类别不直接授予权限 |
| 具体部门岗位、任职事实 | 拟议关系服务及其受控记录 | 补齐已核实缺口，不复用 Shift Assignment 或考勤政策关系 |
| 角色组合、固定版本、岗位角色范围、批准及 Grant | 统一后端授权模块 | 与任职事实分开；当前均未落库 / 生效 |
| 业务资源归属、状态、职责分离 | 各业务 App | 平台不复制或推测检验组等业务主数据 |

该落点遵循 [ADR-0001](../adr/0001-use-frappe-erpnext-as-platform-base.md) 和 [ADR-0004](../adr/0004-open-source-reuse-and-frappe-hr-attendance-first.md) 的自定义 App 扩展原则，不改核心源码。后续人员 / 组织板块优先调用同一关系服务。只有确需换权威来源时，才另行审查来源切换：冻结旧写入、对账稳定 ID 与历史修订、核对授权影响、原子切换适配器；不能双写两套关系后择一放行。

## 2. 关系记录与历史

建议采用“稳定记录 + 不可改写的修订快照”。记录的主键由服务端生成不含业务意义的 UUID；`allow_rename=0`，不根据部门 / 岗位名称生成，不导入原型 ID。修订快照为独立 DocType，便于固定引用；不能只依赖原生 Version 日志或可编辑子表保留授权依据。

| 拟议 DocType | 稳定记录或快照 | 职责与后续阶段 |
| --- | --- | --- |
| HBOS Position | 稳定记录 | 当前具体部门岗位、并发修订和授权失效代次；基础关系实现 |
| HBOS Position Revision | 不可变快照 | 岗位每次已接受变更的完整事实、操作者、原因与摘要；基础关系实现 |
| HBOS Personnel Assignment | 稳定记录 | 一段人员任职事实，含主 / 兼任及时间；基础关系实现 |
| HBOS Personnel Assignment Revision | 不可变快照 | 任职事实历史及源账号关联依据；基础关系实现 |
| HBOS Position Role Binding | 稳定记录 | 具体岗位与一个角色组合的关联身份及失效代次；S02 授权存储实施 |
| HBOS Position Role Binding Version | 不可变版本内容 | 固定角色版本、逐组件范围、期限及内容摘要；S02 授权存储实施 |

后两项与角色版本、批准、Grant 一起实现，不提前制造空的“已授权”关联。批准 / 撤销事件独立记录，不在不可变内容行上改写“已批准”为另一套内容。本次不定稿全部授权 DocType 名称。

稳定记录保存当前已接受事实，`revision` 从 1 开始、每次成功变更递增；同事务追加同号完整快照，保存 `previous_revision`、`actor_user`、`reason`、`recorded_at_utc`、`content_digest`。草案尚未接受时不覆盖当前事实。页面角色的创建时间沿用稳定角色记录的 creation，不用新版本时间冒充首次创建时间。

### 2.1 具体岗位字段

| 字段 | 拟议 Frappe 类型 | 约束 |
| --- | --- | --- |
| name / position_id | 框架主键 / DTO 别名 | 同一个稳定 ID，禁止另生成第二个 position_id |
| title | Data，必填 | 展示名称；同部门允许同名但要提示核对，不据名称合并 |
| company | Link → Company，必填 | 由可信组织关系核对；没有通用 disabled 字段，不能编造启停判断 |
| department | Link → Department，必填 | 存在、未停用、归属公司一致；无公司分组根可展示树，不直接建为业务岗位 |
| designation | Link → Designation，可空 | 通用岗位类别；不能代替具体岗位 ID |
| status | Select | active / inactive / revoked；active 只代表岗位事实可用 |
| revision | Int | 服务端正整数，CAS 使用；拒绝布尔值与客户端指定下一号 |
| authorization_generation | Int | 从 1 开始，撤销 / 语义替换时递增；不复用 modified 或账号安全版本 |
| source_provider / source_key | Data | 服务端受信任来源与其精确 ID；首个关系来源固定为本服务，不接受任意 DocType / 函数路径 |

快照含上述事实及审计字段，`(position, revision)` 数据库唯一。岗位从一个部门移到另一个部门优先办理“旧岗位停用 + 新具体岗位”，保留原 ID 的历史含义；确需原 ID 移属时作为授权影响命令处理，旧 generation 失效，逐任职重新核对，不自动把旧业务范围换成新部门。

### 2.2 人员任职字段

| 字段 | 拟议 Frappe 类型 | 约束 |
| --- | --- | --- |
| name / assignment_id | 框架主键 / DTO 别名 | 一段任职一个稳定 ID；换具体岗位结束旧任职、创建新任职 |
| person_source_type | Select | 首批 Employee / User；未来来源须通过受信任适配注册，不接受客户端任意扩展 |
| person_source_id | Data | 精确来源主键，与类型合用；服务验证引用，不采用任意 Dynamic Link |
| subject_user | Link → User，可空 | 由可信关联解析；客户端不能自由指定受益账号 |
| position | Link → HBOS Position，必填 | 公司、部门从岗位取得；不复制一份可独立修改的任职部门 |
| is_primary | Check | 主岗 / 兼任事实；不是管理权或员工资格证明 |
| valid_from_utc / valid_until_utc | Datetime；开始必填、结束可空 | 使用第 3 节的显式 UTC 存储约定；半开区间，结束必须晚于开始 |
| status | Select | active / inactive / revoked；时间和资格另行判定，不把 active 直接翻译为有权 |
| revision / authorization_generation | Int | 同岗位的正整数与增代规则 |
| source_provider / source_key | Data | 关系来源可追溯，不拷贝人员敏感字段 |

任职快照还保存本次关联核对的来源引用、`source_modified` 原值、关联结果及内容摘要，用于追溯。资格结果是当时证据，不能成为永久资格缓存；授权执行须重新解析当前可信资格。`Employee.employee_number` 只展示工号，人员引用使用 Employee.name。

只有 User、尚无 Employee 时，可以记录待核对的任职草案；不接受为依赖内部员工资格的有效任职或生成 Grant。Employee 未关联 User 可在管理边界内接受任职事实，但没有账号的任职不产生业务授权。多 Employee 指向同一 User 时拒绝自动选第一条，保持 ambiguous，转人工核对。

### 2.3 岗位角色关联字段

Binding 稳定记录保存 `position`、状态、revision 和 authorization_generation；每个版本固定 `role_id`、`role_version`、`component_scopes`、有效期、内容摘要。`(binding, version)` 数据库唯一。批准记录引用固定版本和明确受益人员清单；存在版本不代表已经批准。

范围子行按 `(component_id, scope_type, schema_version, dimension, reference_type)` 标识一组条件，组内对象引用去重；各组 AND、完整 Grant 之间 OR。范围字段与对象类型由相应 App 的注册结构验证，空集合拒绝，不能解释为全部。不可变版本的子行与父记录一起禁止普通修改 / 删除；中文 scopeLabel 只由后端生成展示文字。

一个岗位可以关联多个角色；同岗位同角色的重复时间重叠关联默认拒绝。如确需同角色多组范围，在一个版本里保存完整且明确的组件结构，不靠重复记录拼接权限。增加角色功能、扩大范围或更新模板只生成新版本，不更改已有人员批准内容。

## 3. 时间与生命周期

API 接受带时区的 RFC 3339 时间，内部计算统一为 aware UTC；数据库新关系字段明确使用 `_utc` 命名，由专用编解码把 UTC 写为 Datetime 值、读回时显式附加 UTC。不能把原生无时区字符串直接当本机时间。Portal 由适配层转换为站点时区展示，原生 Desk 自动格式化不能成为授权时间解释器。Frappe Datetime 序列化、精度和普通导出须在 S02 实测；未通过时不启用该存储适配，不声称默认框架已替我们保证 UTC。

有效期为 `[valid_from, valid_until)`，所有判断使用服务端当前时间；null 只代表任职未设结束，不代表长期业务授权已批准。合成例：`2026-10-10T09:00:00+08:00` 入岗、`2026-11-01T00:00:00+08:00` 截止，对应存储 `2026-10-10T01:00:00Z` 至 `2026-10-31T16:00:00Z`；结束时刻已无效。

Employee 的 joining / relieving 为 Date。离职当天是否算有效、未来入职的资格何时开始仍待业务确认，不暗选“当天零点”或“次日零点”。任职开始时间不能替代员工资格；资格边界未定或当前来源无法确认时，依赖该资格的受管动作拒绝。无须该资格的既有功能按其明确迁移边界处理。

| 操作 | 事实与授权处理 |
| --- | --- |
| 新增主岗 / 兼任 | 明确人员、具体岗位和独立期限；通过事实结构检查后才可接受；授权另行批准 |
| 调岗 | 旧任职截止设为 T，新任职从 T 开始；两个半开区间可相接，不重叠；新任职不继承旧 Grant |
| 未来结束任职 | 立即接受新的权威截止 T；请求时旧批准期限与当前事实期限取交集，T 前仍受原批准限制，T 起拒绝，不能等定时任务停权 |
| 立即停用 / 撤销 | 同事务更新状态及 generation，旧来源立即无效；敏感写入参与共同锁 / 代次核对 |
| 延长或撤回已接受的截止 | 作为扩大事实边界处理，重新核对并增代；旧 Grant 不因恢复较长区间复活，新授权需重新批准 |
| 恢复已停用任职 / 岗位 | 新 generation，重新核对当前来源；不得复用旧批准恢复权限 |
| 改账号关联 | 旧、新主体一起核对并撤销旧受益来源；不搬运 Grant；手机号相同不构成依据 |
| 修改姓名 / 岗位显示名称 | revision 递增、保留快照；不增授权代次、不增加动作或范围 |

未来截止被缩短时，批准快照保持原样，当前事实只收窄许可；在生效前提交的新预览 / 批准也必须使用新修订。到期无需等待 generation 更新即可拒绝，后续归档任务可记录终止及增代，但不是停权条件。结束已发生后再改截止必须按恢复办理。未来部门移属、账号替换或角色切换不直接覆盖当前事实；先保存变更草案，使用对应截止 / 新关系和新的固定批准表达，基础服务首段不实现任意未来命令调度器。

新增兼任不调用 Employee.save，不修改 Employee.department / designation，不触发其更新账号启停或原生角色的 Hook。主岗和原生人事部门同步属于后续受控人员服务，不由 IAM 静默同步。

## 4. 修订、授权代次和并发

`revision` 回答“是否仍是我编辑的那份事实”；`authorization_generation` 回答“旧来源授权是否已失效”；`source_modified` 只表示原生来源的并发指纹，三者不能互换。预览、提交、批准、生效都核对当次依赖修订。已生效 Grant 保留原批准修订用于审计，请求时同时检查当前资格、代次、状态和期限；不能因纯显示修订不同而撤权，也不能仅凭历史快照放行。

建议管理命令传入 `expected_revision` 和幂等键，不接受客户端给下一修订 / 代次。第一次创建为 1；相同幂等键和相同规范化内容返回原结果，不同内容返回冲突。幂等键按操作者与命令命名空间隔离；日志不记录凭据或未脱敏人员明细。

受控事实写入顺序：验证会话与独立管理边界 → 锁定主体 / 关联来源及岗位 / 任职 → 重读可信来源与全部相关区间 → CAS → 更新当前事实、追加不可变快照及事件 → 交由外层事务提交。失败全部回滚，关系服务不自行 commit。新增不可变版本不等于调用批准或 apply_grant。

| 数据库约束 / 索引候选 | 用途与限制 |
| --- | --- |
| 稳定记录主键；来源 `(source_provider, source_key)` 唯一 | 防重复导入；来源标识必填且禁止更换指向 |
| 各快照 `(parent_record, revision)` 唯一；Binding `(binding, version)` 唯一 | 不可用“先查不存在再插入”替代物理唯一性 |
| 任职 `(person_source_type, person_source_id, status, valid_from_utc)`；另有 subject_user、position 索引 | 为相关区间查询服务，不宣称普通索引能防时间重叠 |
| 岗位 department / status；关联 position / status；有限截止字段索引 | 管理范围、引用查验及到期归档；请求时仍判定期限 |
| 命令收据 `(actor, command_type, idempotency_key)` 唯一 | 与事实、快照、事件同事务；具体收据载体在 S02 确定 |

主岗最多一条、同人员同岗位不重复重叠，使用 `a.start < b.end && b.start < a.end` 判定，null 结束为正无穷。仅接受给定集合的 S01-A 校验不能证明全库无冲突。全库写入须读取所有可生效事实区间，排除草案及已撤销段，不能只查询“此刻 active”的记录或当前页。

同一人员的并发任职，建议锁定现有身份来源行：有账号时先 User，无账号时 Employee；关联办理锁定旧、新 User 及相关 Employee。全系统候选锁序为：User（ID 排序）→ Employee（ID 排序）→ 主体授权修订 → Position → Assignment → Binding → 业务记录，各组 ID 排序。任何路径先持有后序锁后才需要前序锁，应回滚并从完整依赖集合重试，不能临时倒序加锁。初次建立主体修订、同人员来源别名以及批量影响集合须专项测试。

该锁序尚未验证，不承诺已实现并发撤权。原生 Employee 保存、改名、账号交接和其他服务未必遵守同一锁协议；必须覆盖其变更路径及事务最终重检，不能只锁新接口就宣称唯一人员关联已闭环。普通 DB 唯一索引无法单独保证时间区间不重叠，应用先查再插入也不够。

## 5. 来源适配与现有 S01-A 的差异

适配器只能由受信任代码选择，Site 来自当前服务端上下文，不接受请求指定其他 Site。source_id 为当前精确主键；原生 User / Department / Employee 可改名时，通过受控旧新映射迁移引用并核对受益主体，未覆盖改名路径则拒绝相关受管授权，不能按新名称猜回关联。

| 现有协议 | 拟议存储映射及补充 |
| --- | --- |
| SourceRef | 明确类型 + 精确源主键；可信 Site / provider、source_modified 放适配证据封装，不改变身份含义 |
| PositionProjection | name → position_id，department → Department SourceRef，title → label，status / revision 显式映射 |
| PositionProjection 尚无 company / designation / generation | 后续新增来源证据封装携带这些事实，或通过明确协议升级；不能假称现有 A 已验证这些字段 |
| AssignmentProjection | name → assignment_id；来源二元组、可信 subject_user、position、主岗、UTC aware 区间、状态、revision、generation 逐项映射 |
| qualification_status | 适配当次计算 unknown / unlinked / ambiguous / verified；verified 仍不是业务批准或完整 runtime_verified |
| PositionBinding | 固定 version / role_version 与逐组件范围；批准、当前代次、事实可用性由额外运行证据承载 |
| AssignmentSet.coverage | 继续为 provided_set_only；数据库全量校验与锁另行实现，不能改标志冒充覆盖 |

原生 modified 保留为不透明源指纹，不转正整数 revision；授权代次只来源于受控关系记录。Role / Role Profile、System User / Website User 不作为内部员工资格或管理权。Employee 为空时输出真实空 / 待关联状态，不创建演示员工填补。
