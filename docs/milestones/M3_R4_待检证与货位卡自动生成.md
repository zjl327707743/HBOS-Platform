## 二、设计要点

### 2.1 模板来源与版式

三个模板的版式**直接取自 Owner 提供的实物模板**（`待检证/`、`自产/`、`新版货位卡外购/`，共 311 个文件）。经解析确认三者结构：

| 模板 | 页面 | 结构 |
| --- | --- | --- |
| 待检证 | **75mm × 110mm**（小标签） | 10 行表格：标题+编码 / 品名 / 物料代码 / 供货单位 / 生产单位 / 批号 / 数量 / 储存条件 / 空行 / 操作人日期 |
| 自产货位卡 | A4 纵向 | 表头 4 行 + 状态 3 行（入库/待检/放行）+ 流水表（12 行）+ 备注 |
| 外购货位卡 | A4 纵向 | 表头 6 行 + 状态 3 行 + 流水表（12 行）+ 备注 |

三者均挂在 **`Batch`** 上——与"一个批号一张货位卡"的口径一致。

### 2.2 自产 / 外购的判别

两种货位卡结构不同，需明确判别依据。**新增 `Batch` 自定义字段 `hbos_source_type`（来源类型：自产 / 外购，默认自产）**。

原方案曾考虑用"是否有供应商"推断，但那是隐式判断、容易误判，故改为显式字段。函数的兜底逻辑仍保留推断（字段为空且有供应商时判为外购），不会因未填字段而打印错卡。

### 2.3 多货位的呈现方式（本轮定案）

**规则：一个批次散放多个货位时，在「货位号」单元格内逐行列出全部货位，不改变表结构。**

理由：纸质卡的「货位号」是**单个单元格**（自产卡与"入库/待检/放行"三行垂直合并，外购卡同理），若改为多列会破坏原表结构与打印适配。逐行列出既保留原版式，又能完整表达"一批散放多货位"。

实测：`TEST-M3R1-B001` 分处 `16-03-221` 与 `16-03-223`，卡片在该单元格内正确显示两行。

货位号显示为**短码**（去掉 ` - HB` 公司后缀），与纸质写法一致。

### 2.4 件数按容器类型汇总

纸质货位卡的「件数」是**按容器类型汇总**的。依据实物卡实际写法反推：

- 包装规格 `5.00kg*41件 1.34kg*1件 0.03kg*4听 0.02kg*1听 0.01kg*9瓶 0.007kg*1瓶`
- 对应件数 `42件5听10瓶`（41+1=42、4+1=5、9+1=10）

故实现为按 `container_type` 累加计数，输出顺序为首次出现顺序。

### 2.5 流水表只记真正的出库

货位卡的流水表（发出量 / 结存量）需要预填。**关键口径：按单据合并后取净减少。**

- 库内移库（`Material Transfer`）在同一张单据里一出一进，对该批次的**净影响为 0**；
- 若简单按"负值行"取，会把"换个货位放"误记成一次"发出"，与业务不符。

因此实现为按 `voucher_type + voucher_no` 汇总 `Serial and Batch Entry.qty`，**仅净减少的单据计入流水**。

实测：`TEST-M3R1-B001` 有一次移库 + 一次领用，流水表只出现领用那一行（发出 5.00，结存 95.00），移库未污染流水。

### 2.6 留空字段（系统无数据，供手写）

| 字段 | 原因 |
| --- | --- |
| 入库经手人 / 入库复核人 / 经手人 / 复核人 | 系统只有 `owner` 单值，无"经办 + 复核"双签 |
| 待检日期 | 系统未设该字段，由 QA 填写 |
| 去向（自产卡） | `Stock Entry` 无对应业务字段 |
| 领料单位 / 用途（外购卡） | 同上 |
| 流水表的件数列 | 系统按 kg 记账，不按每笔单据记件数 |

**已预填**：入库日期（取该批次最早入库记账日）、放行日期（`hbos_release_date`）、放行/不放行勾选（按放行状态）、复检期/有效期勾选（按 `Item.hbos_shelf_life_type`）。

## 三、实现方式

### 3.1 文件清单

| 文件 | 作用 |
| --- | --- |
| `hbos_inventory/print_utils.py` | 打印辅助方法（供 Jinja 调用），全部只读 |
| `hbos_inventory/print_format/HBOS待检证/HBOS待检证.json` | 待检证模板（Jinja + HTML 内嵌） |
| `hbos_inventory/print_format/HBOS自产货位卡/HBOS自产货位卡.json` | 自产货位卡模板 |
| `hbos_inventory/print_format/HBOS外购货位卡/HBOS外购货位卡.json` | 外购货位卡模板 |

三个模板均 `standard = "Yes"`、`print_format_type = Jinja`、`doc_type = Batch`，放在 `print_format/<名称>/<名称>.json`，由 Frappe 的 `sync_for` 自动同步（`print_format` 属 `IMPORTABLE_DOCTYPES`）。

### 3.2 Jinja 方法注册

`hooks.py`：

```python
jinja = {"methods": ["hb_inventory_app.hbos_inventory.print_utils"]}
```

**踩坑记录**：该注册机制会收集模块内**所有**函数，**包括 `import` 进来的函数**。因此 `print_utils.py` 只 `import frappe`，不 `from frappe.utils import flt, getdate, ...`——否则会把 `flt` / `getdate` 一并注册，**覆盖 Frappe 既有的同名 Jinja 全局**，影响其他模板。模块内一律用 `frappe.utils.xxx` 全限定调用。

### 3.3 主要辅助方法

| 方法 | 用途 |
| --- | --- |
| `hbos_packaging_spec(batch)` | 包装规格，如 `5.00kg*12件 4.33kg*1件` |
| `hbos_packaging_count(batch)` | 件数（按容器类型汇总），如 `13件3听1瓶` |
| `hbos_batch_bins_html(batch)` | 货位号单元格（多货位逐行） |
| `hbos_batch_flow(batch)` | 出库流水（按单据净减少） |
| `hbos_batch_date_cn(batch, 'in'/'release')` | 日期渲染（`2026年 9月 14日`），无值时出占位 |
| `hbos_shelf_life_marks(item)` / `hbos_release_marks(batch)` | 复检期/有效期、放行/不放行 的勾选标记 |
| `hbos_production_unit(batch)` | 生产单位：外购取批次字段，自产取物料上的生产车间 |
| `hbos_supplier_name(batch)` / `hbos_storage_condition(item)` / `hbos_item_workshop(item)` | 其余表头取值 |
| `hbos_batch_total_qty(batch)` / `hbos_batch_uom(batch)` | 数量与单位（`Kg` 统一显示为 `kg`） |
| `hbos_qty_with_count(batch)` | `数量/件数` 合并式，如 `95.00kg/13件3听1瓶` |

数据源沿用 M3-R1 实测结论：`Serial and Batch Entry` 关联 `Serial and Batch Bundle`（v16 中 `SLE.batch_no` 为空列不可用）。

## 四、验证结果（通过）

> ⚠ **补充更正（2026-09-17，M3-R6 期间发现）**
>
> 本节当时验的是「**能不能渲染、能不能出 PDF**」，**没有验纸型与页数**。
> 后续实测发现两个当时漏掉的问题：
>
> 1. **纸型根本没生效**。三个格式在「手动点打印」时**全都按 A4 出**——
>    模板里写的 `@page { size: 75mm 110mm }` 被 **wkhtmltopdf 忽略**。
>    待检证没有被印在 75×110mm 的实物标签纸上。
>    已在 2026-09-17 修复（纸型改为声明在 `.print-format` 上，Frappe 会读并传给 wkhtmltopdf）。
> 2. **待检证会溢出成 2 页**。Frappe 打印框架注入
>    `.print-format { min-height: 11.69in }`（=297mm A4 高），在 75×110mm 纸上必然溢出。
>    也已一并修复。
>
> 因此本节「通过」的准确含义是「**渲染与 PDF 生成通过**」，**不含纸型正确性**。
> 详见 `docs/milestones/M3_R6_入库拍照识别服务方案.md` 的「入库后自动生成」一节。
>
> ⚠ **再补一条更正（2026-09-23，Owner 验收发现）**
>
> 本节表格里那个「PDF 通过（17.5 KB）」的 PDF，**里面一个汉字都没有**——
> 后端容器没有任何中文字体（`fc-list :lang=zh` 为 0），wkhtmltopdf
> **静默丢弃所有汉字、只留 ASCII 与数字**。所以那几份 PDF 打印出来
> 只有 `Quarantine` / 英文副标题 / 批号 / 代码，中文全空，Owner 看到的就是这个。
>
> 三个格式**全部受影响**（含中文的字符种类：待检证 81、自产卡 52、外购卡 58）。
> 当时只数了「有没有生成 PDF、多大、几页」，**没验过字形**。
> 已修：容器挂载中文字体。详见 `M3_R6` 主文档**第九之十一节**。
>
> ⚠ **第三条更正（2026-09-23，照官方受控模板校对）**
>
> Owner 给了生成器参考工具后逐像素校对，**结构一直是对的**（模板与仓库
> `待检证/` 下的样板逐字节同构、页型同为 75×110mm），但**版式差得多**：
> 官方正文 **12pt**、内容占标签高 **90%**；我们当时 9pt、只占 **63%**
> （下面三分之一是空白）；官方是「只画横线、无竖线无外框」，我们是全格子。
> **已按官方重写 `HBOS 待检证` 模板**，9 条横线的位置与横向范围逐条对上。

## 五、实现中发现并修复的问题

| 问题 | 处理 |
| --- | --- |
| `hbos_production_unit` 误从 `Batch` 读 `hbos_workshop`（该字段在 `Item` 上） | 改为先读批次的 `item`，再从 `Item` 取生产车间 |
| 件数未按容器类型汇总，输出 `12件1件3听1瓶` | 改为按容器类型累加，输出 `13件3听1瓶` |
| 单位显示为 `Kg`，与纸质表的 `kg` 不一致 | 统一显示为小写 `kg` |
| 流水表把库内移库误记为「发出」 | 改为按单据净减少判断 |
| Jinja 方法注册会连带注册 `import` 进来的函数，可能覆盖 Frappe 同名全局 | 模块内只 `import frappe`，改用全限定调用 |
