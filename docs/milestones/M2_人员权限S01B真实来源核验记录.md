所有引用必须绑定服务端已核实的站点上下文；不能让客户端任意指定 Site 或把不同 Site 的同名主键合并。Frappe docname 允许受控重命名，并非永久不变：姓名标签修改保持引用；真实 rename / merge 则须通过后续迁移和撤权设计追踪旧新引用，不用新名字复活旧授权。

## 4. 原生控制器与生命周期风险

已读当前容器的 Employee、Department、Designation、User 控制器及 HRMS Override / Hook；只阅读方法，没有调用它们。

- Employee 的重复 user_id 校验查找其他 **Active** 员工，是应用层检查，不是数据库唯一约束。历史非在职关联、并发和导入旁路仍需可信适配核对；本次无员工样本，不声称这些场景已通过。
- 名为 validate_for_enabled_user_id 的当前方法实际只检查 User 是否存在，不能据方法名认为它验证了账号 enabled。
- 当前 Employee.on_update 会调用 update_user、update_user_permissions 和 update_user_status；非 Active 与 Active 状态变化可能同步 User.enabled。新增资料还可能走自动开账号路径，HRMS Hook 也可能修改审批角色。权限页不能为了“保存任职”直接保存 Employee，更不能靠 Active 重新启用账号或让旧授权复活。
- User 当前控制器会处理启停和会话失效；已有 Portal 账号安全及交接服务继续作为受控账号边界。认证会话失效不是完整岗位 Grant 撤销或 generation 校验。
- Department 支持树结构、停用和受控改名；这些变化可能影响组织展示及后续引用。不能仅刷新组织标签就认定业务范围已正确迁移。
- 当前 HRMS Override 改写员工命名，继承 ERPNext 生命周期。不能只读基础 DocType JSON 而忽略运行中的 Override / Hook。

系统时区已核实为 Asia/Shanghai。员工 Date 与任职的有时区半开区间是不同事实；离职日是否含当天、未来到岗日期及业务冻结边界需在后续人员流程明确，当前不自行把 relieving_date 转成任职批准截止。
