## 2. 技术方案

### 2.1 为什么不能直接用 Frappe 原生 Social Login Key

Frappe 原生 `login_via_oauth2` 走标准 OAuth 2.0：用 `client_id` + `client_secret` 直接向 `access_token_url` 换 token。飞书 OAuth 2.0（OIDC 授权码模式）与标准流程有两处差异：

1. 授权页参数名是 `app_id`（不是 `client_id`）。
2. 换 token 前必须先调 `app_access_token` 接口，再用 `Authorization: Bearer <app_access_token>` 头换用户 token。

因此不能直接配 Social Login Key 接入，需自定义代码补齐 `app_access_token` 前置步骤。

### 2.2 实现方式

- 复用 Frappe 原生登录闭环（`frappe.local.login_manager.login_as`），不另起 session 体系。
- 飞书身份写入 Frappe User 的 `social_logins` 子表（`provider=feishu`），与 Frappe 原生社交登录的账号绑定机制对齐。
- 登录页「飞书登录」按钮通过 `web_include_js` 注入，与原生邮箱密码登录并列，不替代。

### 2.3 飞书 API 三步流程

1. `POST /open-apis/auth/v3/app_access_token/internal`（`app_id` + `app_secret`）→ `app_access_token`。
2. `POST /open-apis/authen/v1/oidc/access_token`（`Authorization: Bearer <app_access_token>`，`grant_type=authorization_code` + `code`）→ 用户身份。
3. 身份字段优先读取 OIDC 返回中的 `union_id` / `open_id` / `name` / `avatar`；缺失时回退 `GET /open-apis/authen/v1/user_info`。

### 2.4 身份匹配策略

对齐 M1-R0 / M1-R7 已固化结论「优先使用稳定 ID，不建议仅用姓名匹配」：

- 稳定 ID：`union_id` 优先，`open_id` 兜底。
- 账号匹配优先级：飞书 ID 已绑定 → 邮箱已存在 → 新建（邮箱缺省时用内部合成邮箱兜底）。
- 不依赖 `contact:user.email:readonly`：`contact:user.base:readonly` 即返回 `union_id` / `open_id`，登录不强制要求邮箱权限。

## 5. 遗留事项（不阻塞本次登录验证）

1. **邮箱权限未生效**：飞书实际返回 `email=False`，尽管 Owner 已申请并发布 `contact:user.email:readonly`。当前登录不依赖邮箱（用 `union_id`/`open_id`），故不影响；后续如需按邮箱匹配员工，需在飞书侧复核权限发布/审批状态或账号是否绑定邮箱。
2. **临时默认角色 `Desk User`**：当前飞书新用户授予 `Desk User` 作为最小兜底角色（能进 Desk、无业务权限）。最终应授予 `Employee Self Service`，但 ERPNext 的 `validate_employee_role` 钩子会自动移除「无 Employee 映射」用户的该角色，故必须先完成「飞书身份 → Employee」匹配才能改用正确角色。
3. **飞书身份 → Employee 匹配未实现**：需在 Employee 上加飞书 `union_id`/`open_id` 字段，登录时匹配 Employee、回写 `Employee.user_id`，并据此分配正确角色。这是「登录后能看到员工与考勤数据」的前置条件。
4. **访问地址为临时隧道**：cpolar 免费版地址重启后变化，需同步改飞书后台重定向 URL 与访问地址。正式使用需域名 + HTTPS 证书（见 M1-R7 网络侧 blocker）。
