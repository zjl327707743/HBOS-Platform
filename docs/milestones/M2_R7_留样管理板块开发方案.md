### 2.2 规程疑点（已发现，需 QC/QA 确认，不阻塞方案设计）

1. **签批层级矛盾**：规程正文 4.4.1 写销毁审批为"QC 主管、QC 负责人和 QA 审核、质量管理负责人批准"（4 级）；但记录四《留样样品处理申请单》表单含 **5 个签署位**（QC 主管 / QC 负责人 / QA 审核人 / QA 负责人 / 质量管理负责人）。两份桌面方案均未发现此矛盾。本方案按表单 5 位设计（QA 负责人位可配置降级，见 6.3），待确认后定稿。
2. **变更历史编号错位**：08 版变更历史中"记录二=留样登记、记录三=留样观察"与现行记录编号（一=登记、二=观察）错位一格，疑为变更说明笔误。
3. **标签尺寸**：附件一 OCR 识别为"700mm×550mm"，疑为 70.0mm×55.0mm 小数点丢失。标签 Print Format 实现前需按原件确认。

## 三、桌面方案评审结论

两份桌面方案业务梳理质量高，本方案吸收其全部业务成果；技术路线与本平台架构不符的部分全部修正，不采纳。

### 3.1 采纳

- 法规 → 系统实现映射表（方案一 §1.1、方案二 §二）。
- 记录字段清单（方案二 §3.5）——数据模型字段设计的直接输入。
- 两条审批链梳理与触发场景（用户投诉 / 检验结果分析 / 生产异常 / 上市前研发 / 其他）。
- 风险点：全检量动态绑定、受托方留样标识、观察批选取模式、留样与稳定性样品隔离（方案二 §八）。
- "P2 登记先行是合规地基"的分期判断。

### 3.2 修正（不采纳原因）

| 桌面方案内容 | 修正 | 原因 |
| --- | --- | --- |
| SQL `CREATE TABLE` 建表（方案一 §2.1） | Frappe DocType JSON | HBOS 全部业务承载为 Frappe 原生 DocType（既有 13 个 DocType 先例），SQL 层由 Frappe 自动管理 |
| 独立标签表 / 库存变动表（方案一表 5/6） | 标签=Print Format；库存流水=Stock Log 子表 + Audit Log | 标签是登记单打印视图无需建表；库存变动以通用流水子表（第七节）覆盖使用/销毁/续留/调整全部来源，变更审计由 R6D 覆盖 |
| 自研/Activiti 工作流引擎（方案一 §6.2） | 状态字段 + whitelist 方法 + workflow_contract 状态机 | 与 M2-R3 已交付模式一致，零 Frappe 依赖可离线单测 |
| 12 周独立里程碑（方案一 §6.1） | M2-R7A~D 四个子轮，嵌入既有轮次体系 | 遵循项目"每轮可验证、可审查、可回滚"节奏 |

| 方案一"每年观察一次"未含基线 | 采纳方案二：0 月基线 + 每年一次 | 09 版变更历史明确新增 0 月观察 |

### 3.3 两份桌面方案均未覆盖、本方案补充

1. **与检验闭环衔接**：现有 `HBOS Sample` 的 sample_source 已含"留样"来源。留样登记支持从检验完成批次（HBOS Sample 关联）一键创建，打通"请验 → 检验 → 留样"链路，这是 GMP"留样应能代表被取样批次"的最强实现方式。映射规则见第九节。
2. **审计复用**：直接注册进 M2-R6D `HBOS Audit Log`（write-once + sha1 防篡改），不自建审计。
3. **前端路径**：遵循项目前端规范——原型先行、Owner 审查、Vue 复刻、生产部署（R6 系列已验证的流程）。

## 四、业务规则数字化定案

以下规则为系统校验逻辑的唯一口径，全部来自规程 v09，字段命名见第五节。

### 4.1 留样分类与数量规则

| 规则 | 系统实现 |
| --- | --- |
| 仅三类留样：关键物料 / 成品（原料药）/ 外售产品 | `HBOS Retention Product.category` 三选一；包装材料、中间产品不提供留样路径 |
| 每批留样，留样量 = 全检量 × 2 倍 | 登记时若录入全检量（Float + UOM）则自动计算 2 倍并允许人工复核；贵重 / 小批量样品按实际填写 |
| 全检量 < 1g 按 1g 计 | 登记校验：全检量数值 < 1 且 UOM 为 g 时提示按 1g 计（非硬拦截，留样量人工确认） |
| 独立包装：1 倍检验用量 = 1 个最小包装 | `package_count`（Int，最小包装数）+ `package_spec`（Data，包装规格）记录 |
| 液体物料不留样 | `Product.is_liquid=1` 时登记**硬拦截** |
| 委托生产样品由受托方留样 | `Product.is_outsource=1` 的产品登记时提示"由受托方留样"并可标记转出（不生成在库留样） |
| 国外药典 / 客户另有要求按其要求 | `retention_qty_rule` 允许"按客户要求"覆盖默认 2 倍 |
| 留样包装、储存条件与原物料一致 | 从 Retention Product 带出，可改可查 |
| **单位一致性** | 全部数量字段为 Float 数值 + 独立 UOM 字段；UOM 取自产品主数据；录入/申请/扣减时 UOM 与产品主数据不一致**硬拦截**（单位换算远期再做） |

### 4.2 期限与观察规则

| 规则 | 系统实现 |
| --- | --- |
| 留样期至 = 复验期/有效期 + 3 年 | 登记时自动计算（`retention_due_date`），允许人工修正并留痕 |
| 观察期至 = 复验期/有效期 + 3 年（与留样期同） | 观察计划以 `retention_due_date` 为终点 |
| 每 1 年观察一次外观性状，含 0 月基线 | 观察偏移（月）：0、12、24、36……直至观察期至；计划日期 = 留样日期 + 偏移月数 |
| 原料药成品每年每产品选 3 批作观察批 | R7B 手动指定 + 选取留痕（obs_selected_by / date / reason 字段，见 5.2）；自动选取（最新 3 批/随机）为后续配置项 |
| 外售产品每批都观察 | 该类产品登记时自动置 `observed_flag=1`，obs_selected_reason=外售产品每批 |
| 观察结果填《留样观察记录》，定期汇总报 QC 主管 | 观察记录 + 观察计划看板（应观察未观察标红） |
| 留样期间异常及时报告 QC 主管 | 观察记录异常结论必填异常描述，异常状态在看板置顶 |

### 4.3 使用审批链（记录三数字化）

```
触发场景（用户投诉 / 检验结果分析 / 生产异常 / 上市前研发 / 其他）
  → 申请部门填单（样品/批号/规格/数量 Float+UOM/原因）
  → QC 资源管理员确认留样库存量（预占 reserved_qty）
  → QC 负责人批准 → QA 负责人批准 → 质量管理负责人批准
  → 留样管理员取样（原子扣减，见第七节），库存操作流水留痕
  → 未经批准不得调用（无批准的申请单不产生任何库存扣减路径）
```

### 4.4 处理/销毁审批链（记录四数字化）

```
每季度：到期清单（留样期至 ≤ 季度末）
  → 留样管理员填处理申请（名称/批号/数量 Float+UOM/原因/方式/地点）
     原因三选一：留样期满销毁 / 留样期满继续留样 / 其他
  → QC 主管 → QC 负责人 → QA 审核 →（QA 负责人，待确认项 6）→ 质量管理负责人批准
  → 销毁：QA 现场监督，处理人/监督人双签，3 个月内完成（自 qm_approved_at 起算）
  → 续留：更新该留样"留样期至"新值（变更进审计日志 old/new value）
```

### 4.5 台账规则

- 《留样产品清单》（附件二）→ 主数据 `HBOS Retention Product`，每年 1 月由 QC 维护更新，修改全部留痕（DocType 修改历史 + 审计日志）。
- 留样标签（附件一）→ Print Format 打印 `HBOS Retention Sample`，字段：类别勾选、品名、批号、数量、来源、有效期/复验期、留样人、留样日期、留样期至、观察样品是/否。
- 稳定性考察样品**不属于留样**：不从"稳定性样品"类型的 HBOS Sample 生成留样（边界硬隔离，规则见第九节）。

## 五、数据模型（Frappe DocType）

新增 5 主 DocType + 1 子表（延续既有命名与风格：HBOS 前缀、naming_series、中文 label、Select 状态字段、主数据 `field:xx_code`）。数量字段一律 **Float 数值 + UOM 字符串**（rev2：数值化支撑 2 倍计算与 <1g 校验）。

### 5.1 HBOS Retention Product（留样产品主数据，附件二电子化）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| product_code / product_name | Data | 主数据命名 `field:product_code` |
| category | Select | 关键物料 / 成品（原料药）/ 外售产品 |
| storage_condition | Data | 储存条件（与物料一致） |

| full_test_qty | Float | 全检量参照（数值） |
| full_test_qty_uom | Data | 全检量单位 |

**观察计划说明（rev2）**：观察批选取粒度是"批次"，选取记录即留样记录本身，故选取字段（obs_year / obs_selected_by / obs_selected_date / obs_selected_reason）直接挂在留样主表，不另建计划 DocType；"应观察清单"由观察计划看板报表按 next_obs_due_date ≤ 今日 且未完成聚合导出。R7B 由此可证明"选了哪 3 批、为什么选、何时应观察"。

子表 **HBOS Retention Stock Log（库存操作流水）**（rev2：由使用流水泛化为全来源库存账）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| transaction_date | Date | 变动日期 |
| transaction_type | Select | 入库（登记）/ 使用出库 / 销毁出库 / 受托转出 / 手动调整 |
| source_doctype / source_name | Data + Data | 变动来源单据（Retention Sample / Usage Apply / Disposal Apply / 空=手动调整） |
| qty_delta | Float | 带符号变动量（入库 +，出库 −） |
| qty_uom | Data | 单位 |
| remaining_qty | Float | 变动后结存 |
| operator | Link User | 经手人 |
| remarks | Data | 手动调整原因必填 |

每次 current_qty 变化（登记入库、使用、销毁、续留不改量但改期、受托转出、手动调整）必须对应一条流水，代码层保证 current_qty 与流水累计一致。手动调整仅 LIMS Manager 可操作且原因必填、审计留痕。

## 六、状态机与角色矩阵（rev2 补全）

### 6.1 三条状态机（全转移表）

延续 `workflow_contract.py` 零 Frappe 依赖契约模式，新增三个 flow。**每级待审状态均可驳回；驳回为终态**（原单不可改，申请人可复制新单重提——对应 ALCOA+ Original，不留修改原单的口子）。

```
FLOW_RETENTION（留样在库生命周期）：
  在库     → {部分使用, 待处理, 已转出}
  部分使用 → {部分使用, 已用尽, 待处理, 已转出}
  已用尽   → {待处理, 已转出}
  待处理   → {已销毁, 在库}          # 在库=续留批准后回写
  已销毁 / 已转出 → 终态
  # 已转出入口（rev2）：受托方留样转出，仅 LIMS Manager 可执行，转出即出库流水留痕

FLOW_USAGE_APPLY（使用申请）：
  草稿       → {待库存确认, 已取消}
  待库存确认 → {待QC批准, 已驳回}
  待QC批准   → {待QA批准, 已驳回}
  待QA批准   → {待QM批准, 已驳回}
  待QM批准   → {已批准, 已驳回}
  已批准     → {已执行}
  已执行 / 已驳回 / 已取消 → 终态
  # 驳回/取消时释放 reserved_qty 预占

FLOW_DISPOSAL_APPLY（处理申请，QA 负责人位待确认项 6，默认含）：
  草稿         → {待QC主管审核, 已取消}
  待QC主管审核 → {待QC负责人审核, 已驳回}
  待QC负责人审核 → {待QA审核, 已驳回}
  待QA审核     → {待QA负责人审核, 已驳回}     # 若确认项 6 定为 4 级，本层由配置跳过
  待QA负责人审核 → {待QM批准, 已驳回}
  待QM批准     → {已批准, 已驳回}
  已批准       → {待执行}
  待执行       → {已完成}
  已完成 / 已驳回 / 已取消 → 终态
  # 销毁完成 = disposal_by + monitor_by 双签后置已完成并写销毁出库流水
  # 续留完成  = 回写留样 retention_due_date（审计 old/new）后置已完成，不出库
```

### 6.4 职责分离硬校验（rev2 新增）

## 七、库存一致性与并发控制（rev2 新增）

1. **预占机制**：库存确认（confirm_stock）时 `reserved_qty += apply_qty`，前置校验 `current_qty - reserved_qty >= apply_qty` 不满足即拒绝确认；驳回/取消时释放预占。
2. **执行时原子扣减**：execute_usage 在显式事务内执行：
   - `frappe.db.sql("SELECT current_qty, reserved_qty FROM `tabHBOS Retention Sample` WHERE name=%s FOR UPDATE", sample)` 行级锁；
   - 锁内复核 `current_qty >= apply_qty` 且该申请单预占仍在（防确认后库存被其他路径消耗）；
   - 扣减 `current_qty -= apply_qty`、`reserved_qty -= apply_qty`，同步写 Stock Log 流水（qty_delta 负值 + remaining_qty）；
   - commit。任何一步失败整体回滚，不留半扣减状态。
3. **单一写路径**：`current_qty` 的变更代码仅存在于 登记入库 / execute_usage / execute_disposal / transfer_out / adjust_stock 五个系统方法，DocType 层拦截用户手工编辑 current_qty 与 reserved_qty（permissions + validate 双保险）。
4. **账实一致**：Stock Log 流水累计（含 qty_delta 符号）+ 初始 0 = current_qty；留样台账报表提供"流水对账"校验列，不一致标红（运维兜底）。
5. **并发测试要求**：R7C 验收包含并发用例——两单同时对同一留样申请超出剩余量的总量，必须恰好一单成功一单拒绝，结存不为负。

## 八、数据完整性与审计设计

全部复用既有机制，不自建：

1. **审计日志**：5 个新 DocType 注册进 `hooks.py` doc_events（创建/修改/删除全捕获 → HBOS Audit Log write-once + sha1）。观察提交、每级审批签署、库存扣减、预占/释放、续留改期、手动调整均由业务方法埋点 `audit_log()`（old_value/new_value 记录库存与期限变化）。
2. **电子签名**：复用 `_signature(meaning)` 字段签名模式，扩展签名含义：留样人、审核人、观察人、QC 资源管理员、QC 主管、QC 负责人、QA 审核人、QA 负责人、质量管理负责人、处理人、监督人。国密 SM2/CA 留远期（与 MVP 决策一致）。
3. **防重复**：观察记录与留样登记的业务键单字段 unique（5.7）；使用/销毁申请执行幂等（已执行/已完成状态锁定，重复执行拒绝）。
4. **防越权调用**：库存扣减仅存在于第七节单一写路径；无批准单无扣减接口。对应规程"未经质量管理负责人批准不得挪为他用"。
5. **时限管控**：销毁 deadline = qm_approved_at + 3 个月（独立 Datetime 字段支撑，rev2），scheduler 每日扫描超期未完成清单，超期在报表标红（飞书推送待飞书集成阶段，不在本轮）。
