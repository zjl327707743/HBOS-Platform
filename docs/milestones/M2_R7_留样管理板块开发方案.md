## 三、桌面方案评审结论

两份桌面方案业务梳理质量高，本方案吸收其全部业务成果；技术路线与本平台架构不符的部分全部修正，不采纳。

### 3.1 采纳

- 法规 → 系统实现映射表（方案一 §1.1、方案二 §二）。
- 记录字段清单（方案二 §3.5）——数据模型字段设计的直接输入。
- 两条审批链梳理与触发场景（用户投诉 / 检验结果分析 / 生产异常 / 上市前研发 / 其他）。
- 风险点：全检量动态绑定、受托方留样标识、观察批选取模式、留样与稳定性样品隔离（方案二 §八）。
- "P2 登记先行是合规地基"的分期判断。

### 3.2 修正（不采纳原因）

| 桌面方案内容 | 修正 | 原因 |
| --- | --- | --- |
| SQL `CREATE TABLE` 建表（方案一 §2.1） | Frappe DocType JSON | HBOS 全部业务承载为 Frappe 原生 DocType（既有 13 个 DocType 先例），SQL 层由 Frappe 自动管理 |
| 独立标签表 / 库存变动表（方案一表 5/6） | 标签=Print Format；库存流水=Usage Log 子表 + Audit Log | 标签是登记单打印视图无需建表；库存每次使用已有子表流水，变更审计已由 R6D 覆盖，避免冗余表 |

### 3.3 两份桌面方案均未覆盖、本方案补充

1. **与检验闭环衔接**：现有 `HBOS Sample` 的 sample_source 已含"留样"来源。留样登记支持从检验完成批次（HBOS Sample 关联）一键创建，打通"请验 → 检验 → 留样"链路，这是 GMP"留样应能代表被取样批次"的最强实现方式。
2. **审计复用**：直接注册进 M2-R6D `HBOS Audit Log`（write-once + sha1 防篡改），不自建审计。
3. **前端路径**：遵循项目前端规范——原型先行、Owner 审查、Vue 复刻、生产部署（R6 系列已验证的流程）。

## 四、业务规则数字化定案

以下规则为系统校验逻辑的唯一口径，全部来自规程 v09，字段命名见第五节。

### 4.1 留样分类与数量规则

| 规则 | 系统实现 |
| --- | --- |
| 仅三类留样：关键物料 / 成品（原料药）/ 外售产品 | `HBOS Retention Product.category` 三选一；包装材料、中间产品不提供留样路径 |
| 每批留样，留样量 = 全检量 × 2 倍 | 登记时若录入全检量则自动计算并允许人工复核；贵重 / 小批量样品按实际填写 |
| 全检量 < 1g 按 1g 计 | 登记校验提示（非硬拦截，留样量人工确认） |
| 独立包装：1 倍检验用量 = 1 个最小包装 | 包装规格字段记录 |
| 液体物料不留样 | `Product.is_liquid=1` 时登记**硬拦截** |
| 委托生产样品由受托方留样 | `Product.is_outsource=1` 的产品登记时提示"由受托方留样"并可标记转出（不生成在库留样） |
| 国外药典 / 客户另有要求按其要求 | 数量规则允许"按客户要求"覆盖默认 2 倍 |
| 留样包装、储存条件与原物料一致 | 从 Retention Product 带出，可改可查 |

### 4.2 期限与观察规则

| 规则 | 系统实现 |
| --- | --- |
| 留样期至 = 复验期/有效期 + 3 年 | 登记时自动计算（`retention_due_date`），允许人工修正并留痕 |
| 观察期至 = 复验期/有效期 + 3 年（与留样期同） | 观察计划以 `retention_due_date` 为终点 |
| 每 1 年观察一次外观性状，含 0 月基线 | 观察周期点：0 月、12 月、24 月、36 月……直至观察期至 |
| 原料药成品每年每产品选 3 批作观察批 | R7B 先手动指定 + 留痕；自动选取（最新 3 批/随机）为后续配置项 |
| 外售产品每批都观察 | 该类产品登记时自动置 `observed_flag=1` |
| 观察结果填《留样观察记录》，定期汇总报 QC 主管 | 观察记录 + 观察计划看板（应观察未观察标红） |
| 留样期间异常及时报告 QC 主管 | 观察记录异常结论必填异常描述，异常状态在看板置顶 |

### 4.3 使用审批链（记录三数字化）

```
触发场景（用户投诉 / 检验结果分析 / 生产异常 / 上市前研发 / 其他）
  → 申请部门填单（样品/批号/规格/数量/原因）
  → QC 资源管理员确认留样库存量
  → QC 负责人批准 → QA 负责人批准 → 质量管理负责人批准
  → 留样管理员取样，登记使用量/结存（Usage Log）
  → 未经批准不得调用（无批准的申请单不产生任何库存扣减路径）
```

### 4.4 处理/销毁审批链（记录四数字化）

```
每季度：到期清单（留样期至 ≤ 季度末）
  → 留样管理员填处理申请（名称/批号/数量/原因/方式/地点）
     原因三选一：留样期满销毁 / 留样期满继续留样 / 其他
  → QC 主管 → QC 负责人 → QA 审核 →（QA 负责人，待确认）→ 质量管理负责人批准
  → 销毁：QA 现场监督，处理人/监督人双签，3 个月内完成（批准日起算）
  → 续留：更新该留样"留样期至"新值（变更进审计日志）
```

### 4.5 台账规则

- 《留样产品清单》（附件二）→ 主数据 `HBOS Retention Product`，每年 1 月由 QC 维护更新，修改全部留痕（版本即 DocType 修改历史 + 审计日志）。
- 留样标签（附件一）→ Print Format 打印 `HBOS Retention Sample`，字段：类别勾选、品名、批号、数量、来源、有效期/复验期、留样人、留样日期、留样期至、观察样品是/否。
- 稳定性考察样品**不属于留样**：不从"稳定性样品"类型的 HBOS Sample 生成留样（边界硬隔离）。

## 五、数据模型（Frappe DocType）

新增 5 主 DocType + 1 子表（延续既有命名与风格：HBOS 前缀、naming_series、中文 label、Select 状态字段、`field:xx_code` 主数据命名）。

### 5.1 HBOS Retention Product（留样产品主数据，附件二电子化）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| product_code / product_name | Data | 主数据命名 `field:product_code` |
| category | Select | 关键物料 / 成品（原料药）/ 外售产品 |
| storage_condition | Data | 储存条件（与物料一致） |
| retention_qty_rule | Select | 全检量 2 倍（默认）/ 按实际 / 按客户要求 |
| full_test_qty | Data | 全检量参照（登记时提示计算 2 倍） |
| is_liquid / is_outsource | Check | 液体不留样（登记拦截）/ 受托方留样（提示转出） |
| obs_rule | Select | 每批观察（外售产品）/ 每年选 3 批（原料药成品）/ 不观察 |
| is_active | Check | 停用产品不再登记新留样 |

### 5.2 HBOS Retention Sample（留样登记，记录一电子化）+ 子表

主表字段（对齐记录一表头）：naming_series `HBOS-RET-.YYYY.-#####`、retention_product（Link，带出类别/储存条件）、sample_name、material_code、batch_no、source、retention_date、expiry_type（有效期至/复验期至）、expiry_date、**retention_due_date**（留样期至，自动=expiry_date+3 年）、retention_qty、package_spec、storage_location（储存位置编号）、observed_flag、current_qty（当前结存，使用/销毁自动扣减）、retained_by、reviewed_by/reviewed_date（审核人/日期）、source_sample（Link → HBOS Sample，检验批次关联，可空）、status、remarks。

status 状态集：`在库 / 部分使用 / 已用尽 / 待处理 / 已销毁 / 已转出（受托方）`。

子表 **HBOS Retention Usage Log**（使用流水，对应记录一右侧"使用量/结存 × 多次"）：usage_date、usage_qty、remaining_qty、used_by、apply_no（关联使用申请单）、remarks。每次批准后的取样执行写入一条，结存由代码维护。

### 5.3 HBOS Retention Observation（留样观察记录，记录二电子化）

独立 DocType（每次观察独立留痕、独立审核，ALCOA+ Original）：naming_series `HBOS-RET-OBS-`、retention_sample（Link）、sample_name/batch_no（fetch）、storage_condition、test_standard（检验标准）、obs_period（0 月 / 1 年 / 2 年 / 3 年…）、obs_date、appearance（外观性状结果）、result（正常/异常）、abnormal_note（异常时必填）、observer、reviewed_by/reviewed_date、remarks。

**唯一性校验**：`unique(retention_sample, obs_period)` —— 同批同期不允许重复观察（方案二提出的防重复，落为 DB 级约束）。

### 5.4 HBOS Retention Usage Apply（留样使用申请单，记录三电子化）

naming_series `HBOS-RET-USE-`、retention_sample（Link）+ fetch 字段（样品名称/批号/规格/库存量）、apply_qty、reason_type（Select：用户投诉 / 检验结果分析 / 生产异常 / 上市前研发 / 其他）、reason_detail、apply_dept、applicant、apply_date、stock_confirm_by/stock_confirm_date/stock_qty（资源管理员库存确认）、qc_approval / qa_approval / qm_approval（三级签名，复用 `_signature` 模式：含义+用户+时间戳）、status。

### 5.5 HBOS Retention Disposal Apply（留样处理申请单，记录四电子化）

naming_series `HBOS-RET-DSP-`、retention_sample（Link）+ fetch 字段、disposal_type（留样期满销毁 / 留样期满继续留样 / 其他）、reason、disposal_method、disposal_location、qty、applicant/apply_date、qc_supervisor_sign / qc_manager_sign / qa_review_sign / qa_manager_sign（待确认是否保留，见 2.2 疑点 1）/ qm_sign、disposal_by/disposal_date（处理人）、monitor_by/monitor_date（监督人，QA 现场监控）、**deadline**（销毁时限 = 质量管理负责人批准日 + 3 个月，scheduler 扫描超期标红）、status。

### 5.6 标签与报表（无新 DocType）

- **Print Format「HBOS 留样标签」**：基于 Retention Sample 渲染（尺寸按第 12 节确认项 2 定稿）。
- **Script Report × 4**（延续既有报表模式）：留样台账（全字段筛选+导出）、留样观察计划看板（应观察未观察清单）、季度到期处理清单（留样期至 ≤ 季度末且未销毁）、销毁超期清单（deadline < 今日未完成）。

## 六、状态机与审批链

延续 `workflow_contract.py` 零 Frappe 依赖契约模式，新增三个 flow：

```
FLOW_RETENTION：在库 → {部分使用, 待处理}；部分使用 → {已用尽, 待处理, 部分使用}
               已用尽 → {待处理}；待处理 → {已销毁, 在库(续留)}；已销毁/已转出 → 终态
FLOW_USAGE_APPLY：草稿 → 待库存确认 → QC已批 → QA已批 → 已批准 → 已执行 / 已驳回
FLOW_DISPOSAL_APPLY：草稿 → QC主管已审 → QC负责人已审 → QA已审 → QM已批准
                   → 待执行 → 已完成 / 已驳回；续留分支：QM已批准 → 已完成(续留回写)
```

角色映射（**待 Owner 确认第 1 项**，两选项）：

- **方案 A（最小改动）**：沿用现有三角色。留样管理员=LIMS Analyst；QC 资源管理员/QC 主管/QC 负责人/QA=LIMS Reviewer；质量管理负责人=LIMS Manager。缺点：QC 线与 QA 线在权限层不可区分，靠用户配置自律。
- **方案 B（推荐）**：after_migrate 新增 `LIMS QA` 角色。QC 线=LIMS Reviewer，QA 线=LIMS QA，最终批准=LIMS Manager。QC/QA 职责分离是 GMP 审计常见关注点，规程分发范围即 QA 与 QC 两部门，建议权限层同步分离。成本仅为 setup.py 幂等新增一个 Role。

审批链不引入 Frappe Workflow 原生机制（与 M2-R3 决策一致：字段级锁定与签名需字段化，原生 Workflow 做不到）。

## 七、数据完整性与审计设计

全部复用既有机制，不自建：

1. **审计日志**：5 个新 DocType 注册进 `hooks.py` doc_events（创建/修改/删除全捕获 → HBOS Audit Log write-once + sha1）。观察提交、审批每级签署、库存扣减、续留改期均由业务方法埋点 `audit_log()`（old_value/new_value 记录库存与期限变化）。
2. **电子签名**：复用 `_signature(meaning)` 字段签名模式（检验人/复核人/批准人已验证），扩展签名含义：留样人、审核人、观察人、QC 资源管理员、QC 主管、QC 负责人、QA 审核人、QA 负责人、质量管理负责人、处理人、监督人。国密 SM2/CA 留远期（与 MVP 决策一致）。
3. **防重复**：观察记录 DB 级唯一约束（5.3）；使用/销毁申请单执行幂等（执行后锁状态）。
4. **防越权调用**：库存扣减只存在于"已批准申请单执行"这一条代码路径；无批准单无扣减接口。对应规程"未经质量管理负责人批准不得挪为他用"。
5. **时限管控**：销毁 deadline 字段 + scheduler 每日扫描超期未完成清单，超期在报表标红（飞书推送待飞书集成阶段，不在本轮）。
