M3 由 Owner 明确授权新开，与 M1-FIX（考勤功能补漏）并列，不替代、不阻塞 M1-FIX。

## 必须满足的前置条件

- M0 状态为 COMPLETED（已满足）。
- ERPNext `Stock` 模块可用（已满足；只读盘点确认 44 个非子表 DocType 存在）。

## M3 目标

把仓库产品库存信息数字化，形成"产品—批次—货位"对应台账，并在此基础上支持批次查询、出库核销、效期预警、盘点导出、待检证与货位卡生成、货位二维码与手机扫码查询、入库拍照识别。

## M3 范围

M3 允许做：

- 复用 ERPNext 原生 `Item`、`Batch`、`Warehouse`、`Bin`、`Stock Ledger Entry`、`Stock Entry`、`Purchase Receipt`、`Delivery Note`、`Stock Reconciliation`、`Quality Inspection` 等标准能力。
- 只读盘点、需求确认、货位与批次建模、原生配置、报表、`Print Format`、Frappe 原生 Web 页。
- 经 Owner 逐轮授权后，创建有限的海滨自定义 Frappe App（用于海滨特有规则，不用于重写 ERPNext 已有功能）。
- 经 Owner 逐轮授权后，建设外部 FastAPI + 视觉模型的入库拍照识别服务。

M3 不允许做：

- 修改 Frappe / ERPNext / HRMS 核心源码。
- 未授权创建任何自定义 Frappe App 或 DocType。
- 开发 MES、LIMS、QMS、EHS 等完整系统。
- 未授权启动 Vue / React 独立前端。
- 未授权执行飞书真实写入。
- 飞书集成优先通过后续 `hb_feishu_app` 统一管理，不得分散写入业务模块。
- 执行 `docker compose down -v`、删除 Docker volume、重建 `frontend` site。

  - 数据留存：照片**不出内网**，服务端识别后即释放，归档到 Frappe `Attach`；服务不开外网；

M3-R6 方案已交付：`docs/milestones/M3_R6_入库拍照识别服务方案.md`。方案指出门禁三项本质是同一问题（**标签照片能否出内网**），属合规决策须 Owner 拍板；并给出 A（云端多模态）/B（云端 OCR）/C（本地部署）三方案与推荐路径（先小样本试跑量准确率，再定长期方案）。

**部署环境已定**：识别服务**原生跑在 Mac 上**（非 Frappe 容器），`host.docker.internal` 实测可达。**风险**：Mac 为开发机、16GB 内存偏紧，作临时验证可行，**不适合长期生产**，正式使用前建议采购内网服务器。

**准确率验收标准已由 M3-R6 制定**（方案第七节）：批号 / 物料代码 ≥95%，生产日期 / 有效期 ≥90%，产品名称 ≥85%；全字段正确 ≥80%；**高置信度错误 ≤1%、低置信度召回 ≥90%**；单张 ≤10 秒。

**M3-R6 已开工**：服务骨架（`services/hbos_ocr/`）与**约束校验层**已交付并验证。后端可插拔（`stub` / `c1_local_vlm` / `c2_ocr`），**缺依赖不崩**。

**M3-R6 第四批：真实样本准确率已实测**（C2 后端，50 张真实标签、250 个字段）：

| 标准项 | 要求 | 实测 | 结论 |
| --- | --- | --- | --- |
| 批号 / 物料代码 | ≥95% | 100% / 98% | ✅ |
| 生产日期 / 有效期 | ≥90% | 94% / 96% | ✅ |
| 产品名称 | ≥85% | 92% | ✅ |
| 全字段正确 | ≥80% | 84% | ✅ |
| **单张耗时** | **≤10 s** | medium 35 s → **small 实测 7.0~9.0 s（均 8.1 s）** | ✅ **已达标** |
| 高置信度错误 / 低置信度召回 | ≤1% / ≥90% | — | ⚠ **无法测量** |

**accuracy 全部达标；耗时起初不达标（medium 35 s），已解决**——降分辨率走不通（有效期是小字，降了就废），但 **PaddleOCR 自带多档模型**：换到 `small` 档（**免装依赖，只是换个模型名**）后单张约 **7 s**，已进标准线，accuracy 仍达标（全字段 82%）。详见方案第九之五节「模型档位对照」。

> ⚠ **2026-09-21 口径更正（Owner 核对真实标签后）**：**上面那组准确率不能读成
> 「汉字识别准确率」**——5 个字段里 4 个是数字，只有品名是汉字，所以它**主要衡量数字**；
> 标签上的汉字（公司名 / 车间 / 储存条件 / 操作人）**从未进入该指标**，恰恰错得最多。
> 换 `medium` 档小字一样错，瓶颈是**小字成像质量**。详见方案第九之五节 ⚠ 小节。

**M3-R6 第四批补测：分档实测（2026-09-21）**——三档 `tiny`/`small`/`medium` 共用同一批 50 张样本、同一套口径，用归档识别原文测，**未重跑 OCR**。

| 档 | 大字（5 个结构化字段，全字段正确） | 小字（16 个模板恒定串 × 50 张，整串命中） |
| --- | ---: | ---: |
| `tiny` | 72% | 560/800 = 70.0% |
| `small` ← 选用 | **82%** | **668/800 = 83.5%** |
| `medium` | 86% | 682/800 = 85.2% |

**均值掩盖短板**（`small` 档）：字段名-执行标准 50/50，但**运输注意事项整句仅 25/50**、`【贮藏】：` 34/50、公司名(英) 35/50——**串越长、字越小，命中越低**。

**换 `medium` 不划算**：总量只多 1.7 个点，耗时却 8 s → 35 s，**每提 1 个点付 4 倍时间**，故**维持 `small`**。

**手写档给不出准确率**：无真值来源（标签内容逐张不同），人工转写在可获分辨率下同样辨认不出。只如实记录可观测事实——`操作人/日期` 标签后为空 **34/50**、`复核人/日期` 20/50、两行皆空 12/50、**姓名 50 张无一读出**；读到的日期多为相邻印刷字段串入，无真值无法区分读对与否。**结论：手写只能靠人工，不计入 OCR 成绩。** 详见方案第九之五·二节。

**仍测不了的是置信度两项**——**C2 是"OCR + 规则"、没有逐字段置信度的概念**。要满足这两条，得让它输出 OCR 逐行置信度并映射到字段，或改用 C1（VLM 天然有置信度）。

**结论：C2（`small` 档）在 accuracy 与性能上均已达标，但置信度两项无法测量**——须 Owner 就这一条决策（改用 C1 / 调整标准 / 接受现状 + 强制人工校对）。
