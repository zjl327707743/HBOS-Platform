## 2. 政策存储、批准与生命周期

主表保存稳定 UUID、Site / provider、具名 User、状态、revision / authority_generation / schema、有限 UTC 期限、规范政策 JSON 和固定内容摘要。JSON 包含完整规则及批准声明；主表冗余字段逐项与规范快照核对，时区 / 微秒按既有 UTC 合同转换。修订使用 policy_id + revision 的确定性 SHA256 主键并保存完整主表快照、快照摘要、前修订、实际运维人、原因、批准来源引用和 UTC 记录时间。

`PolicyApprovalPin` 是**由可信部署代码在人工核实后预配置的精确证据清单**，绑定 Site、数据库 SHA256、政策 UUID / 主体、revision / generation、完整内容摘要及完整批准声明。批准引用或摘要由请求自填不能单独通过；空清单、重复清单、错误绑定、本人 / Guest 批准、未来批准或旧批准均拒绝。当前没有配置任何真实清单、运维人或导入命令；隔离测试清单是明确标记的 SYNTHETIC、仅在测试进程内构造，测试后没有政策记录留存。

**该核对器不是业务审批系统、数字签名校验或真人认证。**它依赖服务端确已核实的配置来源；拥有任意服务端 Python / 数据库控制权的操作者不在此边界内。真实批准资料的收集、Owner 确认及安全配置交付仍是启用门禁，不能把通过合成清单测试写成真实批准已完成。

`ManagementPolicyStore` 默认关闭，且没有公开 RPC。写入的实际操作者取自原生 session.user，必须在显式服务端运维名单内且当前 User 启用；Administrator 不自动获准。新增要求 expected_revision=0、revision=1、generation=1；更新要求旧版本相符、revision 与 generation 都严格加一，主体不允许原地换绑。active 内容必须得到当前修订的精确批准且尚未到期，涉及的 User、Company、精确 Department 及其组织链必须当前有效。

停用 / 撤销会形成新修订、增加 generation 并保留旧批准声明及历史，不要求重新批准被收回的权力；即使旧政策的主体 / 部门已失效，也可在启用运维身份下撤销。重新 active 必须配置当前内容 / 版本的新批准，不能复活旧证据。每次修订都使旧证据失效，较规格最低要求更保守；没有政策委派功能。

主表和修订在同一既有 repository 保存点内写入；修订失败回滚主表。本服务不 commit，返回 transaction_pending=true、authorization_effect=none、runtime_verified=false。最外层失败回滚 / 提交前重新检查和提交结果未知处理仍须由后续实际请求边界实现。

## 3. 当前头与锁定加载

`FrappeManagementPolicyRepository` 默认关闭，必须绑定精确 Site、数据库 SHA256、MariaDB / REPEATABLE-READ 和两类 InnoDB 表，并持有同一个关系 repository 当前事务 / 根锁能力。沿用锁顺序：`relations-v1` 根锁 → 政策主记录及修订（稳定 ID）→ 固定来源顺序。没有自动初始化根锁、缓存许可、其他数据库连接或普通快照替代锁定读取。

`current_for_subject` 使用 session 主体的参数化查询取所有当前头，包括 inactive / revoked；不会从历史中挑选旧 active 版本。每个头都必须与其精确修订快照一致，缺历史、错摘要、错版本或 active 历史缺批准来源引用均拒绝。`LockedManagementPolicyLoader` 再从同连接读取原生来源，核对主体、批准人和精确组织以及批准清单；每次调用重新加载。它返回政策 DTO，**不是现有 RelationService 的 ManagementDecision 或事实写回调**。

原生来源仍沿用完整范围锁，成本及原生写入锁顺序限制保留。该加载器证明当前政策头 / 来源读取的事务约束，不能证明未来传入的事实上下文来自同一可信操作，也不能保证提交前时点；完整旧 / 新任职上下文、受益人和严格收窄检查需在下一段适配。

停用政策仍可撤销，与停用组织下的**任职事实清理**是两项不同工作。后者当前仍缺可靠历史归属证据，MG20 继续 PARTIAL；没有用政策撤销测试代替事实收窄验收。
