## 1. 本段结论与首批边界

继续复用统一 Frappe User、现有组织来源及已实现的岗位 / 任职事实。管理权限由具名 User 的独立、已批准、带版本和期限的管理政策提供；Administrator、HR Manager、System Manager、部门负责人字段以及普通业务角色均不自动取得这项政策。Portal 与 Desk 调用同一服务端边界，不另建 Portal 身份、会话或授权体系。

首批真实入口只办理具体部门岗位与任职事实，不修改账号、密码、User.enabled、Employee、Role / Role Profile，不创建角色组合、岗位角色关联或业务 Grant。任职状态 active 只表示任职事实，不表示员工 Date 资格已确认或岗位权限已生效；响应和页面必须明确这种区别。

本规格不替 Owner 选择[业务矩阵](../plans/权限管理_业务权限矩阵与授权流程草案.md)中的 Q1 / Q2，不绑定真实管理人或批准人。人员事实维护权、资料查看权、业务授权审批权和业务签署权分别验证。只有事实维护的合成验证可以先行；真实管理政策启用及任何业务授权依旧受各自门禁约束。

## 2. 管理政策的数据契约

### 2.1 政策主记录与不可变修订

建议后续在既有 hbos_portal App 中新增两类受保护存储：`HBOS Organization Management Policy` 与 `HBOS Organization Management Policy Revision`。它们是待实现的具体候选，不是已经创建的 DocType；不复用普通 Role 作为政策，也不新建 App。首批 rules 使用严格版本化的规范 JSON，与现有修订快照方式一致，暂不增加独立子表。

| 字段组 | 拟定字段 / 语义 | 必须验证的约束 |
| --- | --- | --- |
| 稳定身份 | policy_id、subject_user、source_provider | UUID；显式 User 主键，不按姓名 / 手机 / 岗位名称匹配；主体不可原地换绑 |
| 状态与版本 | status、revision、authority_generation | draft / active / inactive / revoked；正整数；版本比较更新；已批准内容不可原地修改 |
| 固定政策内容 | schema_version、rules_json、content_digest | 完整规则、固定操作及范围版本；规范序列化摘要由服务端重算，不信客户端摘要 |
| 期限 | valid_from_utc、valid_until_utc | UTC，开始包含、结束不包含；首版要求有限截止时间，未知 / 缺失 / 无时区拒绝；长期批准另行扩展 |
| 批准证据 | approval_ref、approved_by、approved_at_utc、approved_content_digest | 绑定具名批准人和完整修订；草稿允许为空，但缺失时不可 active；不能由事实写接口提交这些字段 |
| 修改审计 | actor、reason、recorded_at_utc、前后 revision | 实际操作者由可信上下文取得；原因必填；成功政策写入和不可变修订同事务提交 |

固定内容摘要覆盖主体、操作 / 规则与范围版本、完整范围和期限等批准内容，排除摘要自身及可变生命周期状态，避免循环计算。是否有独立的管理人员 Employee 资格要求属于批准政策 / 后续资格 profile 的显式内容；本规格不以员工 Date 未定条件默认批准任何管理人。首版纯判定至少要求启用 User 和完整批准事实，真实管理人员资格仍由具名启用门禁核实。

修订记录使用 policy_id + revision 的唯一键，保存固定内容、批准证据和前后修订；普通 ORM、REST、Desk、导入、rename / delete、flags 绕过都应拒绝。两表和唯一约束须经过后续隔离数据库验收，不能只依赖 Python 查询后插入。

政策停用 / 撤销或固定内容替换增加 authority_generation；既有历史批准不删除。恢复不得直接复活旧管理决定，必须明确批准当前固定内容。多个同时有效政策可以分别参与匹配，但不得拼接成更大的权力池。

### 2.2 每条规则必须完整匹配

每条规则保存：操作 ID 及语义版本、一个明确 Company、目标岗位的 Department ID 集合，以及任职操作所需的人员边界和任职截止上限。首版只支持列出的具体部门，**不默认包含下级**；空集合、通配符、ALL、未知 schema、自由 SQL / 表达式 / 方法路径均拒绝。组织树扩展后可以增加有版本的范围结构，旧批准内容不自动覆盖新增部门或新增功能。

| 目标 | 一条规则的必要条件 |
| --- | --- |
| 岗位创建 / 修改 / 读取 | 操作匹配；岗位公司等于规则公司；岗位部门属于本条规则明确部门集合；当前组织归属可核验 |
| 任职创建 / 修改 / 读取 | 同时覆盖目标岗位的公司 / 部门和该人员的 Employee 来源边界；不能只凭知道 Employee ID 维护全站人员 |
| 人员检索 | 独立的人员查看操作；Employee 公司 / 部门匹配本条规则；过滤先于分页、总数和联想结果 |

首版任职人员边界使用 Employee.company 和 Employee.department 的稳定引用，与岗位公司必须一致；可以在同一规则明确批准不同的人员部门和岗位部门，适配兼任，不由“属于本部门”推定可调任全公司。跨公司规则、无所属部门人员的例外及基于未来任职来源的范围，暂不启用；以后通过独立 schema / 来源版本扩展，不按空值解释为全量。

任职增加 / 恢复 / 延期还须在同一规则中明确 assignment_until_limit_utc，候选任职的有限截止不能超过该上限。首版不创建或延长无截止 active 任职，不将 null 当作已经批准长期；纯读取及严格收窄既有关系按各自语义检查，不为读取强加新增任职的期限要求。管理政策到期限制的是管理请求，不自动改写其任内记录的既有任职期限；任职和未来 Grant 的资格、期限及批准仍分别检查。

同一规则内，操作、目标范围、人员范围、时间、政策状态取 AND；完整匹配的规则 / 政策之间取 OR。A 政策的操作不能与 B 政策的范围、期限或批准拼接。active actor 是必要条件；Employee 身份是否适用于管理人本身须由批准政策明确，首版不得从 HR 角色推断员工资格，也不得把未知 Date 政策当作已确认。

操作属于 hbos_portal 的这一管理域，首批拟定 ID 为 `hbos.organization.position.read/create/update`、`hbos.organization.assignment.read/create/update`、`hbos.organization.person.lookup`，语义版本均为 1。这里列的是首批七个有边界的操作定义，不是全平台业务权限枚举；后续 App / 功能按受信任定义注册。旧政策只引用固定清单与版本，不因目录扩充而获得新增操作。S01-C 的运行注册仍未开始，不能声称跨 App 动作已经接入。

### 2.4 初始政策配置与禁止自委派

首批政策仅通过受控、无公开 RPC 的运维流程导入 Owner 已确认的固定内容：具名 User、允许操作、公司 / 部门、人员边界、起止时间、批准人及证据引用。先提供只读校验和内容摘要，取得真实批准后才执行写入。Owner 不是数据库用户名 Administrator 的别名；批准证据不能只靠客户端自填字符串或 approved=true。

首版事实管理 API 不提供政策新增、激活、范围扩大、延期或委派方法。运维执行人不能借技术身份自行选择批准内容；政策导入仍须留实际执行人、批准来源、摘要和版本，且不能声称它是已实现的业务审批系统。真实导入命令、批准来源核验方式和可执行身份须在该实施段明确并验收后启用，本段没有创建命令。

本人受益的增权仍须独立有权批准。初始事实接口对本人新增 active 任职、恢复 active、延长期限等潜在增权操作采取拒绝规则；收窄或结束本人既有任职也须有独立的事实维护边界，不能因是本人就绕过。身份关联无法核验时，不推定“不是本人”。修改本人所在岗位的事实不产生新角色或 Grant；未来加入角色关联后须重新实现全影响人员及间接自审批检查。

## 3. 与现有服务衔接的必要改动

当前 [RelationService](../../apps/hbos_portal/hbos_portal/organization/relation_service.py) 的 ManagementDecision 只有 actor、命令、公司、部门、person_source_id 与 policy_ref；合成回调证明字段匹配和第二次拒绝，**不证明真实政策已批准、未撤销或完整覆盖本次变更**。

后续内部管理请求上下文应包含服务端解析的 command、actor、目标岗位 / 任职及旧 revision、人员来源、旧事实与候选事实摘要、当前组织归属和服务器 UTC 时间。管理决定补充 policy_id / revision / generation、规则 ID、固定内容摘要及对应请求摘要；这些都由可信代码返回，公开请求不能自填。

当前管理回调在人员证据解析前执行，且参数不含旧 / 新任职状态、期限、实际关联 User。实施时须将必要来源和变更上下文先解析，再做完整政策 / 自受益检查；写入和幂等重放前再次检查。不能把现有回调直接换成“有这四个字符串就允许”。同一请求前后决定须可追溯到锁定政策版本。

现有来源适配会拒绝停用组织，任职服务也拒绝关联变更 / 歧义。这会影响已经停用部门、离职或换绑人员的事实结束清理。后续必须区分增加 / 恢复与严格收窄清理：增加仍要求当前完整来源；清理仅针对已有稳定记录、既有受益人、旧 revision 和已覆盖的历史范围，不向新账号转移关系。未实现这项区分前，不开放这些清理入口，不把普通 update 命令当作已覆盖所有生命周期撤销。

## 4. 受控管理接口契约

以下均为拟定能力和固定方法映射，尚无公开 Python 方法。未来候选模块为 `hbos_portal.api.organization_relations`，复用既有 Frappe 会话 / CSRF 和 [Portal 响应契约](../../apps/hbos_portal/hbos_portal/contracts/errors.py)。Portal 和 Desk 入口一致检查，不接受任意方法路由。

| 能力 | 方法及输入 | 返回 / 服务端要求 |
| --- | --- | --- |
| get_management_context | GET；无 actor 参数 | 仅当前用户可用操作和获准范围的最小展示摘要；能力未接入时明确不可用；不是可提交回服务器的许可令牌 |
| list_positions | GET；受限筛选、分页 | 独立 position.read；获准位置最小字段、过滤后总数；不能借公司 / 部门参数扩权 |
| get_person_assignments | GET；Employee 稳定 ID、分页 | 独立 assignment.read，并覆盖目标人员和岗位；无权与不存在采用不泄漏存在性的响应 |
| lookup_people | GET；受限姓名 / ID 筛选、分页 | 独立 person.lookup；服务端脱敏；手机精确检索 / 明文显示不随此操作自动开放 |
| create_position / update_position | POST；事实 payload、幂等键、expected_revision、原因；更新另有稳定 record_id | 方法固定绑定 create_position / update_position，不从客户端读取命令或处理函数 |
| create_assignment / update_assignment | POST；Employee / Position 引用、主岗标记、UTC 期限、状态、幂等键、expected_revision、原因；更新另有 record_id | User 由可信关联解析；不接受 actor、subject_user、批准人、policy_ref、ignore_permissions 或审批状态 |

字段白名单继续采用当前关系服务的严格形状，未知字段拒绝。创建 expected_revision=0，修改必须为正整数；UUID 幂等键按 Site + actor + 固定命令隔离。同键同内容可重放，同键不同内容冲突；重放仍重新检查当前管理政策、来源和查看边界，不能用旧收据绕过撤销。

角色管理页暂时继续读取前序原生角色资料并展示只读状态；这不表示页面角色组合 / 新业务模板已建成。岗位 / 任职事实响应必须返回 `authorization_effect="none"` 和 `position_authorization_connected=false`；不将事实保存提示为权限生效。已提交的 API 成功结果与内部 `transaction_pending=true` 要区分，只有外层提交完成才可以对浏览器声称保存成功。

当前 [people_access](../../apps/hbos_portal/hbos_portal/api/people_access.py) 使用 Frappe 原生权限过滤。新管理政策不自动扩大该接口，也不能把其“原生可读”当作本规格的独立管理授权。新入口切换前，须逐项明确既有列表、详情、统计、原生 Report / REST / Desk 的同域范围；没有覆盖的入口不能宣称统一管理隔离完成。

## 5. 事务、撤销与错误响应

### 5.1 锁和完整请求边界

政策导入 / 停用 / 撤销与关系写命令共用既有 `relations-v1` 根锁，首版统一顺序为：根锁 → 政策主记录及固定修订（按稳定 ID）→ User / Employee / Company / Department / Designation 固定来源顺序 → 岗位 / 任职 / 收据。所有引用核对和政策加载在同一数据库连接内使用锁定读，不通过其他连接、缓存或普通旧快照证明仍有权。

政策新增也必须经过根锁；无有效政策时不因“未找到锁行”临时创建权限。已存在根锁的初始化仍是受控部署任务。政策加载不能先取允许缓存再等锁；失效来源、未知版本、加载失败均拒绝依赖的操作。普通失败回滚保存点后，HTTP 写边界仍须结束整次失败请求；事务已被数据库终止的异常按下一节处理。

现有全范围来源锁成本和原生写入锁顺序限制保留。政策检查至少在来源解析后及写入 / 重放前执行，外层提交前重取 UTC 时间核对期限，避免长请求用旧时点继续提交；不能据此宣称所有原生写入、业务 Grant 或毫秒级到期时点已闭环。政策撤销先取得共同锁并提交时，后续请求拒绝；写请求先持锁完成时，撤销随后生效，不回滚已提交事实。该时序是待验收契约，尚未运行真实政策并发测试。

### 5.2 写接口不能直接复用通用错误包装

现有 [call_safely](../../apps/hbos_portal/hbos_portal/api/_utils.py) 捕获异常并转为普通返回，本身没有显式回滚。它用于现有只读接口，不是已证实存在部分写入的漏洞；但不能直接把关系写命令放入这个包装后就认为框架一定会看到异常并回滚。

后续写请求执行器必须拥有完整事务边界：认证 / CSRF / 固定方法校验 → 根锁及可信上下文 → 来源与政策检查 → 关系主表 / 不可变修订 / 收据 → 提交前复核 → **最外层受控提交成功** → 构造成功响应。关系服务和政策判定函数仍不得自行 commit；最外层与实际 Frappe 请求生命周期的衔接必须在 Preview HTTP 验收中核对。

任何提交前领域拒绝、未知异常或事务冲突，都应先完整 rollback，再生成统一错误响应；不捕获后继续执行，不把 `transaction_pending=true` 转成已保存。不在失败事务里顺手写拒绝日志并 commit；拒绝审计须在干净事务或隔离日志渠道中，经单独验证，且不能把审计失败变成允许。

rollback 自身失败时不能继续返回可正常提交的请求；必须终止该事务 / 连接并进入故障处理，具体框架生命周期行为列入 MG23。不能为生成友好错误而吞掉回滚失败。

真实提交遇到连接丢失可能结果未知，不能承诺“所有错误都没有落库”。此时不生成新幂等键、不自动撤销；提示保存结果待确认，由同一会话、同一幂等键及固定内容重新核对，并重新检查当前权限。HTTP 响应丢失也按此规则处理。

### 5.3 事务重启和领域错误

保持 Frappe `message` 中的 `ok / data / error.code / retryable / trace_id` 形状，不在本段修改全局 HTTP 状态。认证、CSRF 和方法限制可能由框架先返回 4xx；领域错误使用以下拟定映射并做客户端兼容测试。`retryable=true` 只表示允许用户重新发起完整请求，不授权浏览器拦截器自动重放写操作。

| 内部结果 | 对外拟定错误 | 重试要求 |
| --- | --- | --- |
| 未登录 | UNAUTHENTICATED | 仅该类会话事实触发重新登录 |
| 没有管理政策 / 越范围 / 自受益拒绝 / 目标不可见或不存在 | FORBIDDEN，统一不暴露目标存在性 | retryable=false；不返回内部政策内容、隐藏人员或 SQL |
| 参数 / 时间 / 字段不合法 | INVALID_REQUEST | 修改输入后新提交；不输出任意底层异常路径 |
| REVISION_CONFLICT / IDEMPOTENCY_CONFLICT | 同名错误 | retryable=false；重新读取获准对象，不能自动换新幂等键覆盖变更 |
| RELATION_TRANSACTION_RETRY_REQUIRED / SOURCE_CHANGED_RETRY | RELATION_TRANSACTION_RETRY_REQUIRED | retryable=true；整次请求终止，重新取来源、政策、版本；保留原幂等键及固定内容 |
| 加载不可用 / 提交结果未知 | SOURCE_UNAVAILABLE | retryable=true；同键完整重验，不假报保存成功或确定未写入 |
| 服务关闭 / schema 或操作未接入 | CAPABILITY_UNAVAILABLE | retryable=false；明确未接入，不降级原生角色放行 |
| 未分类故障 | PROVIDER_ERROR | 先回滚；只给稳定提示和 trace_id，不自动重放 |

旧快照的 1020 错误可能已经丢弃整个外层事务；repository 已将其转换为 RELATION_TRANSACTION_RETRY_REQUIRED，并处理保存点遮蔽及嵌套锁失效。HTTP 层不能只重试某个 SQL、复用旧来源快照或按旧 policy_ref 继续执行。幂等重放前的政策撤销依然优先拒绝。

新管理客户端候选 `organizationApi.ts` 使用 [PortalMethodError / unwrapPortalMethod](../../frontend/hbos-portal-web/src/services/frappeClient.ts) 处理领域包装，保留真实会话客户端；不要把 FORBIDDEN、版本冲突或来源不可用一律当登录过期。现有人员管理表格结构、弹窗和岗位关联原型已确认，此处不另做复杂配置页面。
