### 4.2 储存条件（规程 3.2）

以主数据 `HBOS Stability Condition` 承载（避免硬编码）。

**长期（3.2.1）**：25±2℃/60±5%（Ⅱ）、30±2℃/65±5%（Ⅳa）、冷藏 5±3℃、冷冻 -20±5℃、**超低温 -70±5℃**（新版新增）。
**加速（3.2.2）**：常温品 40±2℃/75±5%；冷藏品 25±2℃/60±5%；超低温品 5±3℃。
> **加速 6 个月内出现显著变化 → 必须进行中间条件试验**（3 月/6 月点判定显著变化后自动提示）。
**中间（3.2.3）**：条件1 = 30±2℃/65±5%（Ⅳa）；条件2 = 30±2℃/75±5%（Ⅳb）；条件3 = -20±5℃（新版新增）。
**影响因素（3.3.1）**：高温（高于加速温度 ≥10℃，取 0/5/10/30 天）；高湿（25℃、RH 90±5%、10 天，第 5/10 天取样，吸湿增重 >5% 改 RH 75±5% 复试）；强光（4500 lx±500，总照度 ≥1.2×10⁶ lux·hr，近紫外 ≥200 W·hr/m²）。

### 4.3 检测频率与时间点（规程 3.3.1）

**表 A：新产品/工艺验证类、变更类、其它类**

| 类别 | 加速 | 长期 / 中间 |
| --- | --- | --- |
| 新产品/工艺验证类 | 0、3、6 月 | 第一年每 3 月、第二年每 6 月、以后每年（0/3/6/9/12/18/24/36/48 月…）直至有效期 |

| --- | --- |

### 4.4 重点考察项目与检测方法（规程 3.3.2、4.2.2）

| 剂型 | 重点考察项目 |
| --- | --- |
| 原料药 | 性状、熔点、含量、有关物质、吸湿性及品种特定项 |
| 片剂 | 性状、含量、有关物质、崩解时限/溶出度/释放度 |
| 胶囊剂 | 性状、含量、有关物质、崩解时限/溶出度/释放度、水分（软胶囊查内容物沉淀） |
| 注射剂 | 性状、含量、pH、可见异物、不溶性微粒、有关物质、**无菌** |
| 吸入粉雾剂 | 性状、含量、pH、可见异物、不溶性微粒、有关物质、**无菌** |
| 口服混悬剂 | 性状、含量、沉降体积比、有关物质、再分散性 |

- **项目选择原则（4.2.2）**：贮存中易变化且影响安全有效性；须含理化项目。
- **不变项目仅首末全检**：重金属、炽灼残渣、硫酸盐、残留溶剂等，**仅首次与末次全项检测**（以 `HBOS Stability Test Item.is_full_test_only` 配置，生成时间点时中间点自动排除）。
- **检测方法原则上同放行方法**；如不同须在方案说明且为药典或已验证方法。
- **方案须经批准**方可开始研究（4.2.3，硬校验）。

### 4.5 用量、包装与时限（规程 3.4）

### 4.7 报告、变更与监督管理（规程 4.6、6、8、9）

- **报告（4.6）**：年度稳定性考察**每年出具趋势分析报告**；客户另有要求按其要求。工艺验证稳定性报告要素：研究目的 / 研究范围 / 考察说明 / 实验条件 / 质量标准 / **趋势分析** / **杂质概况分析** / 评价与结论。
- **趋势图（4.6.5）**：含**规格限 + 数据折线 + 线性趋势线**（`SOP-QA-2-00-005`）。
- **有效期外推（4.7）**：按 ICH Q1E 决策树给建议（7.6），**最终由 QA 判定并签署**。
- **变更（6）**：变更申请（记录三）→ 影响评估 → 分级审批（**重大变更 → 质量受权人 QP；一般变更 → QA 经理**）→ 实施 → 后评估。
- **稳定性室管理（8）**：上锁专人管理；温湿度记录（每工作日上下午各一次）；设备确认/校准/维护。
- **监督管理（9）**：每年汇总分析稳定性数据，形成**产品年度质量回顾报告（APQR）**。

  #   已有在途件时再 revise_result / record_result 一律拒绝。

  #     (a) 清 is_current → (b) 清 Timepoint Item.current_result → (c) 写审计（生效结果作废）
  #     → (d) 判定该 Timepoint 是否需要重开
  #   重开判定【按必检项目粒度，不是"整点已无生效结果"】：
  #     若该 Timepoint 存在【任一必检项目当前没有生效结果】(含本次被作废项目、含尚未录入项目)，
  #     则**再判当前状态**（P1-1 rev11）：
  #       - status = 已完成 → 调用 `reopen_timepoint` 回退为「检测中」（合法转移）
  #       - status = 检测中 → **保持原状态、不调用**（本就可重录，调用会构成非法转移）
  #       - 其他状态（待取样/待检测/已取消）→ 不应出现（作废仅针对已有结果的项目），出现即报错
  #   多项目举例：某时间点 3 个必检项目 A/B/C 均已批准（Timepoint=已完成）；只作废 A
  #     → A 无生效结果 → **回退为「检测中」**，A 可重录；B/C 的生效结果与指针不受影响。
  #   （原写法"整点不再有任何生效结果才重开"在多项目时会漏判，已废止。）
  #   重开动作 action = `reopen_timepoint`，审计事件 = `时间点重开`。
  # 提交时硬校验：actual_test_date ≥ plan_test_date（不得提前）
  #               且 actual_test_date ≥ actual_sample_date（不得早于取样，S6）
  #               且 actual_test_date ≤ effective_test_due（见 7.3）
  # SoD：analyst ≠ reviewed_by；reviewed_by ≠ approved_by

## 七、关键算法、冻结快照与一致性

### 7.1 时间点与计划检测日期生成（P1-2 修订：触发时机、中间条件、追加闭环）

**生成规则（按 `study_conditions` 逐条件展开）**

```
输入：category, vd_months, study_conditions[], start_date(开始考察日期)
  新产品/工艺验证类 → 加速 [0,3,6]月；长期 第一年每3月、第二年每6月、之后每12月，直至 vd_months
  变更类/其它类     → 加速 [0,3,6]月；长期 缺省同新产品规则
  年度持续稳定性类   → 按 VD 分档（4.3 表 B）
  中间条件          → [0, 6, 9, 12]月（规程 4.3：建议考察 12 个月、至少 4 个时间点、
                       须含全部重点考察项目）；末点可依方案延至 12 个月满
  影响因素          → 高温 [0,5,10,30]天；高湿 [5,10]天；强光 按 Study Condition.exposure_days（P3 新增字段）

计划检测日期 plan_test_date 生成：
  plan_sample_date = start_date + (value, unit)          # 见 7.2 取整与月末规则
  plan_test_date   = plan_sample_date                    # 默认"取样当日即可检测"
  # 例外：若方案规定取样后需恢复至室温或指定静置期，
  #        plan_test_date = plan_sample_date + protocol.room_temp_recovery_days（默认 0）
```

**触发时机（P1-2 定稿）**

- **方案批准只是前置资格**，不直接生成时间点——`HBOS Stability Timepoint.stability_sample` 为必填，且计划日期由 `Sample.start_date`（入箱时才产生）推导、并发生成锁在样品行（7.8）。
- **实际生成发生在样品入箱登记之后**：`register_stability_sample`（入箱登记）保存成功后**自动触发** `generate_timepoints`；亦提供**手动重跑** `generate_timepoints`（补登、失败重试）。
- **失败语义（P3-9 明示）**：登记与生成**不在同一事务**——**登记先提交**（进箱是物理事实，不因生成失败而回滚），随后触发生成；生成失败**不回滚登记**，改为**写审计事件（`时间点生成失败`）+ 在样品上置告警标记**，由稳定性管理员用**手动重跑**兜底。因此"样品已入箱但时间点为 0"是**可恢复的正常中间态**，不是异常数据；看板对"在箱但无时间点"的样品单列提示。
- **年度持续稳定性考察类**无 Protocol，前置资格为 Notice 已批准（4.2.5）。

**幂等与重生成**

- 幂等：已存在的 `sample_cond_point_key` **跳过**；**不覆盖已有实际取样/检测记录的节点**。
- 普通重跑（同一前置资格下）只补缺失节点。
- **追加条件 / 时间点**（`append_conditions`）——覆盖规程强制的两条进行中变更路径：
  - **加速 3/6 月点显著变化 → 须开中间条件**；
  - **高湿吸湿增重 >5% → 改 RH 75±5% 复试**；
  - **效期后取样点**（4.1）同样走此路径。
  - **前置校验（P1-9 修订：解除循环）**：追加动作是**变更实施的组成部分**，不是"已实施之后"的独立前置。定为**变更实施原子事务**——`implement_change`（已批准 → 已实施）在**同一事务内**先执行内部函数 `_append_conditions_impl` 完成追加，再置 `已实施`；两步同成同败。`append_conditions` 仅作为**内部函数暴露的受控入口**：单独调用时要求变更单 `status = 已批准 且 change_scope ∈ {涉条件与时间点, 涉方案}`，且**不自行推进变更单状态**（状态由 `implement_change` 推进）。原"必须先已实施、而实施又要先追加"的循环由此消除。
  - **锁内幂等**：样品行 `FOR UPDATE` 内按 `sample_cond_point_key` 仅**新增**，已存在节点一律跳过，绝不覆盖、不改期、不删。
  - 动作登记进 6.3 动作矩阵，事件进 8.1 审计枚举。

- 日期计算统一用 `dateutil.relativedelta`（月末溢出，如 1/31 + 1 月 → 2/28 或 2/29）。
- 影响因素用 `天`、长期/加速/中间用 `月`，字段与公式统一按 `time_point_value + time_point_unit` 处理（4.3）。

### 7.2 时间单位、取整、月末与工作日历（P1-6 修订）

| 项 | 规则 |
| --- | --- |
| 时间单位 | `time_point_unit ∈ {天, 月}`；`天` 直接用 `timedelta`，`月` 用 `relativedelta(months=n)` |
| **2/3 效期取整** | 年度持续类 `VD≤0.5` 档的 `2/3 效期`：`ROUND_HALF_UP(vd_months * 2 / 3)`，**四舍五入到整月**；若算出 0 月则取 1 月。**待 QA 确认取整方向**（待确认第 4 项）。**P2-6**：与 7.3 一致，契约层统一显式 `ROUND_HALF_UP`（本档无 .5 情形，但保持口径一致） |
| 月末日期 | `start_date + N 月` 用 `relativedelta`，自动收敛到目标月最后一天（如 1/31 + 1 月 → 2/28、闰年 2/29） |
| 闰年 | 由 `relativedelta` 天然处理；边界测试覆盖 2/29 起算 |
| 工作日历 | 引用 Frappe 原生 **Holiday List**（公司节假日表）计算"工作日"；趋势评估 5 个工作日以该表为准 |
| 节假日 | 取样计划遇节假日按 4.6 延期规则处理（延期上限与节假日无耦合，节假日只影响"5 个工作日"与提醒） |
| 时区 | 服务器与容器统一 `Asia/Shanghai`（R7 已完成迁移）；所有日期字段服务端生成，禁止前端回填 |

### 7.3 取样/检测期限、物理约束与延期审批（M2 / S6 修订）

**期限与截止日定义**

| 量 | 公式 / 规则 |
| --- | --- |
| **`planned_due_date`**（计划日期） | 取样：`plan_sample_date`；检测：`plan_test_date`。**本身不是截止日**，只是计划锚点 |
| `delay_limit_days`（取样政策放宽上限） | `min(ROUND_HALF_UP(value_in_days × 0.1), 15)`，其中 `value_in_days = time_point_value`（单位 `天`）或 `time_point_value × 30`（单位 `月`）。1 月 → 3 天；3 月 → 9 天；6 月及以上 → 15 天。**P2-6**：显式 `ROUND_HALF_UP`（`decimal`），禁用银行家舍入——影响因素 5 天 × 10% = 0.5 应取 **1 天** |
| **`policy_latest_due_date`**（政策最新截止日 = **硬上限**） | 取样：`planned_due_date + delay_limit_days`；检测：`planned_due_date + 30 天`（锚定计划检测日期，取样延期不自动顺延）。委外项目按 `outsourced_test_window_days` |
| **`approved_due_date`**（审批后实际允许日期） | 延期审批通过后的实际允许日期，**硬约束 `≤ policy_latest_due_date`**——**审批不得突破规程上限** |
| **`effective_due_date`**（有效截止日） | `= approved_due_date`（该类型有有效批准行时）**或** `policy_latest_due_date`（无批准行时） |
| **延期日期链不变式（P1-2 rev11）** | `planned_due_date ≤ requested_due_date ≤ approved_due_date ≤ policy_latest_due_date`——**四段全链校验**：申请不得早于计划日、批准不得早于申请日、批准不得突破政策上限。任一违反即拒绝（同步门禁 7 / 12 / 18） |
| **强制规则一** | 实际日期 **> `effective_due_date`** → **一律拒绝** |
| **强制规则二（P0-2 关键）** | 实际日期 **> `policy_latest_due_date`** → **无论有无审批一律拒绝**（审批不可越过政策上限，硬上限成立） |
| **超出政策上限怎么办** | **不属本板块"延期"范畴**——如需突破规程上限，属**偏差/超限**场景，走后续独立模块（第十二节"明确不做"），本板块不提供入口 |
| 待确认 | 落在 `(planned_due_date, policy_latest_due_date]` 区间内**是否必须审批**：本方案默认**需审批**（授权使用政策宽容期）；若 QC/QA 认为规程 4.3.1/4.3.2 的 10%/15 天/30 天属**自动允许**（无需审批，仅需记录原因），则本板块简化为"记录 + 审计"（见第十五节待确认第 5 项） |

**提交结果时的硬校验**（`submit_result`，任一不满足即拒绝）

| # | 校验 | 来源 | 0 月点是否豁免 |
| --- | --- | --- | --- |
| 1 | `actual_test_date ≥ plan_test_date` | **不得提前**（规程 4.3.2） | **豁免**（见下） |
| 2 | `actual_test_date ≥ actual_sample_date` | **不得早于实际取样日**（S6：物理约束） | **豁免**（见下） |
| 3 | `actual_test_date ≤ effective_test_due`（`= approved_due_date` 或 `policy_latest_due_date`），**且 `actual_test_date ≤ policy_latest_due_date`（硬上限）** | 规程 4.3.2 + 7.3 期限模型 | 按 `source` 分派（见下） |
| 4 | **0 月点免取样路径**：`is_zero_month=1` 且来源为出厂全检/委外时，不要求 `record_sampling` 记录 | **P1-1 新增** | — |

**0 月点专属口径（P1-1 修订）**

0 月数据取自该批**出厂放行检验**，其检测日期必然**早于**进箱日（`start_date`），按上表 #1/#2 字面必然被自家校验拒绝。故定义专属口径：

| 项 | 规则 |
| --- | --- |
| 触发 | `is_zero_month=1` 且 `source ∈ {出厂全检, 委外}` |
| 取样 | **跳过 `record_sampling`**（不产生取样流水，不写 `HBOS Stability Sample Log` 取样行） |
| `actual_sample_date` | 记为**放行检验的检测日期快照**（用于日期展示与报表一致性），非实际取样动作 |
| 校验 #1/#2 | **豁免**，并在审计日志写独立事件 `0月数据豁免校验`（含单号、时间点、来源单据） |
| 校验 #3 | 不适用原 30 天窗口；若 `source=委外` 则按可配置的**委外检测窗口** `outsourced_test_window_days` 判定（默认 30 天，配置为空表示不限制），规程 4.3.2"委外检测项目视具体情况定"即此 |
| 落库 | 新增动作 `import_zero_month_result`（6.3）：创建 Result（`is_zero_month=1`、`source`、`baseline_doctype`/`baseline_name` 指向放行 `HBOS Test Result`/COA）（第 5.4.1 节） |
| 源数据缺失 | 0 月点无放行数据可引用时，**必须在进箱后补检**（此时按普通时间点口径走 #1/#2/#3），并记录评估结论（5.3.1 评估四件套） |

**取样执行的对应校验**（`record_sampling`）

- `actual_sample_date ≤ effective_sample_due`（`= approved_due_date` 或 `policy_latest_due_date`），**且 `actual_sample_date ≤ policy_latest_due_date`（硬上限，审批不可越过）**；不满足须先提交延期申请，且**申请不得突破政策上限**。
- **0 月免取样路径不调用本动作**（P1-1）：`is_zero_month=1 且 source ∈ {出厂全检, 委外}` 时直接走 `import_zero_month_result`，本校验不适用。

**双延期模型（M2 修订）**——取样延期与检测延期**分开建模**，各自独立申请、独立截止日、可分别发生：

| 维度 | 取样延期 | 检测延期 |
| --- | --- | --- |
| 承载 | `HBOS Stability Timepoint Delay.delay_type = 取样延期` | 同子表 `delay_type = 检测延期` |
| **`planned_due_date`**（P2-1 统一字段名） | `plan_sample_date` | `plan_test_date` |
| **`policy_latest_due_date`**（硬上限） | `plan_sample_date + delay_limit_days` | `plan_test_date + 30 天`（委外按 `outsourced_test_window_days`） |
| 触发动作 | `record_sampling` 发现超限 | `record_result` / `submit_result` 发现超限 |
| **申请动作（P1-1 补）** | `apply_delay(delay_type=取样延期)` | `apply_delay(delay_type=检测延期)` |
| **批准动作（P1-1 补）** | `approve_delay(delay_type=取样延期)` | `approve_delay(delay_type=检测延期)` |
| **驳回动作（P1-1 补）** | `reject_delay(delay_type=取样延期)` | `reject_delay(delay_type=检测延期)` |
| 批准后可放宽 | `effective_sample_due` | `effective_test_due`（仅此项影响 `submit_result` 校验 3） |

**通用规则**

- 同一 `delay_type` 在任一时刻**最多一条在途（待批准）**——Timepoint 行锁内校验（7.8）。
- **多条已批准行的处置（P1-6 重订：单一、无歧义口径）**：同一 `delay_type` 历史上可有多条已批准行（如先延至 3 天、后经重新评估延至政策上限），有效截止日**只按一个规则取**——
  **按「批准时间」(`approve_at`，Datetime) 降序取最后一条已批准记录的 `approved_due_date`**（P2-3：用 Datetime 而非 Date，同日多次批准也有确定顺序）。
  配套硬约束：**禁止批准时间倒退**——新批准行的 `approve_at` 必须 ≥ 该类型上一条已批准行的 `approve_at`，且其 `approved_due_date` 必须 ≥ 上一条已批准的 `approved_due_date`；违反即拒绝并提示"延期不得回退"。**不叠加、不累加、不取最大值**（原写法并列两条规则，已废止）。
- SoD：`apply_by ≠ approver_by`（6.4）；每次延期独立成行，形成完整延期历史。
- 驳回后该 `delay_type` 仍按原截止日判定；可重新申请（新行）。

> **P1-10 修订（延续）**："检测超期拦截**或**强制理由 + 审批"的二义已消除——**必须先有已批准的检测延期，否则拒绝提交**，规则唯一。
>
> **S6 修订**：补 `actual_test_date ≥ actual_sample_date` 物理约束，并明确检测 30 天窗口**锚定计划检测日期**（不随取样延期自动顺延）。

### 7.4 显著变化判定（P1-7 修订）

判定按 `HBOS Stability Test Item.significant_change_rule` **配置驱动**，不再硬编码。

| 项 | 规则 |
| --- | --- |
| **基线选择** | 优先级：① 该样品该条件的 **0 月点已批准结果**；② 0 月点缺失时取 `source=出厂全检` 的结果；③ 均缺失时取**首个已批准点**。基线值写 `result_baseline`，来源类别写 `baseline_ref`，**具体来源单据写 `baseline_doctype` + `baseline_name`（M5）** |
| **相对变化超阈值**（含量等数值项） | `abs(result − baseline) / baseline × 100 ≥ change_threshold`（默认 5%）→ 显著变化。除零保护：`baseline ≤ 0` 时不做相对判定，转为超规格限度判定 |
| **超规格限度**（有关物质/降解产物/pH/溶出度等） | 按 `result_contract.py` 既有判定：超出 `spec_limit` → 显著变化 |
| **定性不符标准**（性状/外观等） | 与标准的**定性描述**逐项比对，不符即显著变化 |
| **不参与判定** | 该时间点不触发显著变化（仅记录结果） |
| **非数值 / 文本结果** | `result_type ∈ {定性型, 文本型}` 时不做相对变化计算，走定性比对或仅记录 |
| **缺失值** | 结果为空 → 不判定；该点结果完备性进看板提示，不自动置显著变化 |
| **复测** | 复测走 `FLOW_STB_RESULT` 的修订链（新 `revision_no` + `supersedes`）；原结果置 `已修订`，**不复用同一行**。判定以当前生效版本为准 |
| **记录** | 判定结果写 `is_significant_change` + `significant_change_basis`（依据文本），并写审计事件 |

**加速侧联动**：加速 3 月或 6 月点判定显著变化 → 提示"须开中间条件考察"。

### 7.5 趋势图与控制限（P1-7 修订）

- 按产品 × 质量属性 × 条件，汇总各时间点**已批准**结果；图中含**规格限（上下限）+ 数据折线 + 线性趋势线**。
- **术语分层（P1-7）**：
  - **规格限**（Specification Limit）= 来自 `HBOS Specification`，系统可直接绘制；
  - **统计控制限**（Control Limit）= 需按 `SOP-QA-2-00-005` 计算，**口径待 QA 确认前不计算、不展示**；
  - **线性趋势线** = 最小二乘拟合，可绘制。
- **命名约束**：在 QA 确认 `SOP-QA-2-00-005` 统计口径前，功能命名统一为「**稳定性趋势图**」，**不得称"控制图"**；确认后再启用"控制图"命名与控制限计算。
- 前端用 ECharts 渲染；后端 `get_stability_trend` 返回时间点序列、规格限、趋势线拟合参数。

### 7.6 有效期外推助手（ICH Q1E；仅建议不定值）

| 情形 | 建议 |
| --- | --- |
| 3 个月加速发生显著变化 | 不能外推；缩短再检测日期/保质期；长期数据有变异性 → 统计分析 |
| 6 个月加速发生显著变化 | 看中间条件结果；长期数据支持时 Y ≤ 1.5X 且 ≤ X+6 月 |
| 长期与加速均微小变化/无变化，且有统计分析与相关数据支持 | Y ≤ 1.5X 且 ≤ X+6 月 |
| 得到相关性数据支持 | Y ≤ X+3 月 |
| 长期数据充分支持 | Y ≤ 2X 且 ≤ X+12 月；冷藏品 Y ≤ 1.5X 且 ≤ X+6 月 |

> X = 覆盖长期稳定性数据的时间段；Y = 建议的再检测日期/有效期。系统只输出**建议值 + 依据分支 + 所用数据点**，写入 `proposed_validity_months` / `proposed_validity_date` / `proposed_validity_type` / `proposed_validity_basis`（**S8 修订**：由单一 `Data` 拆为月数 / 日期 / 类型，便于排序与计算）；`final_validity_months` / `final_validity_date` / `final_validity_type` 由 QA 在报告批准时人工填写。

### 7.7 冻结快照与版本链（P0-3 新增）

| 对象 | 冻结内容 | 冻结时机 | 不可变规则 |
| --- | --- | --- | --- |
| `Protocol` | `vd_months_snapshot`、`spec_version`、`method_version`、条件行、项目行 | 批准（`approve_protocol`）时快照 | 批准后**字段级只读**；修改须新建版本（`version+1` + `supersedes`），原版置 `已作废` |
| **`Notice`** | `spec_ref`/`spec_version`/`method_version`/`limits_snapshot`/`vd_months_snapshot` | 批准（`approve_notice`）时置 `snapshot_frozen=1` | **P1-8 新增**：年度持续类**无 Protocol**，标准/方法/限度/有效期一律由此承载；冻结后只读，修改须新版本（`version+1` + `supersedes`） |
| `Sample` | `condition_snapshot`（条件文本）、`storage_cond` Link 快照 | 入箱登记时快照 | 快照字段只读 |
| `Result` | `spec_limit` / `spec_version` / `test_method` / `method_version` / `item_snapshot` | 结果创建时**复制落库**（非纯 Link），来源链按类别分派（见下） | 批准后只读；修订走 `revision_no` + `supersedes` |
| `Room Log` | `temp_min/temp_max/humidity_min/humidity_max` | 记录创建时从 Room 快照 | 快照字段只读 |

**快照来源链（P1-8 修订：按类别分派）**

| 类别 | 标准 / 方法 / 限度来源 |
| --- | --- |
| 新产品、变更类、其它类（有方案单） | `Timepoint → Sample → Protocol → HBOS Specification` |
| **年度持续稳定性考察类（无方案单）** | `Timepoint → Sample → Notice(snapshot_frozen=1) → HBOS Specification` |

> `Result` 创建时按样品所属类别选择来源链；年度类**不得**回溯 `Protocol`（年度类本就不建方案单，原链路会断裂）。

- **一般原则**：凡影响质量判定的引用（标准、方法、限度、条件），一律**复制为快照值**，不保留"实时 Link 漂移"。
- **校验**：`Result.spec_limit` 必须等于其 `method_version` + `spec_version` 对应值；不一致（说明版本被改）时拒绝提交并提示走变更。

**生效版本指针的维护与作废处置（P2-5 修订）**

| 场景 | 规则 |
| --- | --- |
| 新建修订 | 同 `(timepoint, item_code)` 下 `revision_no = max(已存在 revision_no) + 1`（**不从 1 重起**，否则撞 `result_version_key` unique）。**P0-1**：`revise_result` **不改旧版状态、不触碰任何指针**——旧版仍为「**已批准 + `is_current=1`**」，仅新增一条草稿。同一 `(时间点, 项目)` **至多一条在途**（草稿/已提交/已复核），有在途时拒绝再建 |
| 生效切换 | **P0-1 修订**：仅当新草稿走完 `已批准` 才切换。Timepoint 行锁内**同一事务**完成**六步**：(a) 旧版 `status: 已批准 → 已修订`、(b) 旧版 `is_current: 1 → 0`、(c) 新版 `status: 已复核 → 已批准`、(d) 新版 `is_current: 0 → 1`、(e) 回写 `Timepoint Item.current_result` = 新版、(f) commit。**草稿/已提交/已复核期间一律不切换**。首版（无旧版）时仅执行新版侧四步 |
| **不变式（P0-1）** | 任一时刻，`Timepoint Item.current_result` 指向的记录**必须同时满足 `is_current=1` 且 `status=已批准`**；不存在"已修订 + `is_current=1`"的中间态。校验失败即拒绝（11.2 门禁 15） |
| **当前生效版本被作废** | `is_current` 置 0、`Timepoint Item.current_result` **清空**并写审计事件（`生效结果作废`）。**不自动回指上一版**——回指会造成"旧数据被静默复活"，违反 ALCOA+；如需回退为旧版生效，须**走变更单**显式指定并留痕 |
| 作废后重录 | 按同一 `revision_no = max + 1` 规则分配新版本号，`supersedes` 指向被作废的版本 |
| 报表/趋势图取数 | 一律取 `is_current=1` 的版本；`is_current=0` 的历史版本仅供修订链追溯展示 |

### 7.8 库存与并发一致性

- 数量语义与 R7 一致：`init_qty` / `current_qty`（落库）/ 流水 `qty_delta` / `remaining_qty`。
- **单一写路径**：`current_qty` 仅由 入箱 / 取样出库 / 返还 / 销毁 / 手动调整 五个系统方法变更；DocType 层拦截手工编辑。
- **四步锁协议**（与 R7 一致）：无锁校验 → `SELECT … FOR UPDATE` 锁行 → 锁内复核 → 写入 + 流水 + commit；任何一步失败整体回滚。
- **并发锁协议（P1-10 修订：统一锁对象与顺序）**：

| 操作 | 锁对象 | 锁内动作 |
| --- | --- | --- |
| `generate_timepoints` / `append_conditions`（含 `_append_conditions_impl`） | **Sample 行** | 校验 `sample_cond_point_key` 唯一后新增节点（配合 DB unique 双保险） |
| `record_sampling` / `return_sample` / `dispose_sample` / `adjust_stock` / `transfer_out` | **Sample 行** | 复核 `current_qty` 后写流水（7.8 前述） |
| `record_result` / `submit_result` / `review_result` / **`return_result`** / `revise_result` / `void_result` | **Timepoint 行** | 校验时间点状态、`revision_no` 分配、`result_version_key` 唯一（**P3-5**：`return_result` 补入，防与 `submit_result` 并发时的状态竞争窗口） |
| **`approve_result`（指针切换）** | **Timepoint 行** | 同事务内：旧版 `is_current=0` → 新版 `is_current=1` → 回写 `Timepoint Item.current_result` → commit（P0-1） |
| `implement_change`（跨对象） | **先 Sample 后 Timepoint**（固定顺序） | 落点回写 + 置 `已实施` 同事务 |

  - **锁顺序固定为 Sample → Timepoint**：同一事务需两把锁时一律按此顺序获取，避免死锁。
  - **指针切换必须在同一事务内完成**（旧版降级、新版提升、子表指针回写三者不可分离），否则存在"两个生效版本"或"无生效版本"的中间态。
  - 数据库 unique（`sample_cond_point_key` / `result_version_key`）作为**兜底**，不替代锁内校验。
- **账实一致**：流水累计 + 0 = `current_qty`；台账报表提供"流水对账"校验列。

### 7.9 变更实施落点（P1-3 新增）

变更单审批通过只是"批准了要改"，**真正的业务回写**由 `HBOS Stability Change.change_scope` 分派，实施完成后变更单才置 `已实施`：

| `change_scope` | 实施动作 | 影响对象 | 备注 |
| --- | --- | --- | --- |
| 涉方案 | 生成 **Protocol 新版本**：`version+1`、`supersedes` 指向原版、原版置 `已作废`；按需调 `append_conditions` 追加时间点 | Protocol / Timepoint | 不改原版字段（冻结快照 7.7） |
| 涉通知单 | **另立新 Notice**（原 Notice 保持不变） | Notice | 适用考察范围/批次调整 |
| 涉条件与时间点 | 调 **`append_conditions`**（7.1）：锁内按 `sample_cond_point_key` **仅新增**，不覆盖已有实际记录 | Timepoint | 覆盖"加速显著变化→开中间条件""高湿增重>5%→RH 75±5% 复试""效期后取样点" |
| 涉样品 | **另立新 Sample**（按新条件/包装重新入箱） | Sample | 原样品记录不动 |

- **原子事务（P1-9 修订）**：`implement_change` 为**单一原子事务**——在同一事务内 (a) 按 `change_scope` 执行落点回写（含内部函数 `_append_conditions_impl`），(b) 写审计事件，(c) 置变更单 `已实施`；任一步失败**整体回滚**，变更单停留 `已批准`，不产生"改了业务对象但变更单没实施"的半成品。**原循环（"追加要求已实施，已实施又要求先追加"）由此消除。**
- **前置**：`change_scope` 在变更申请时必填；校验变更单 `status ∈ {已批准}`。
- **幂等**：`_append_conditions_impl` 重复执行只补缺失节点（按 `sample_cond_point_key` 跳过已存在）。
- **审计**：每个落点动作写独立事件（`变更实施-方案升版` / `变更实施-追加条件` / `变更实施-新通知单` / `变更实施-新样品`），并写一条 `变更实施回写` 汇总事件。
- **受控入口**：`append_conditions` 单独调用时（补录/重试场景）要求变更单 `已批准 且 change_scope ∈ {涉条件与时间点, 涉方案}`，**不推进变更单状态**；状态推进只由 `implement_change` 负责。

### 8.2 电子签名——能力边界声明（P0-4 修订）

> **上一版将 `_signature()` 作为 21 CFR Part 11 / EU Annex 11 合规依据，属过度声明，本版更正。**

**现状（R6D/R7 已实现）**：签名字段为「用户名 + 时间戳 + 含义串」的**展示型签名**，服务端在业务方法内写入，配合 `HBOS Audit Log`（write-once + sha1 校验）形成操作留痕。

**与 GMP 电子签名要求的差距**：

| 要求 | 现状 | 差距 |
| --- | --- | --- |
| 签名时重新认证（re-authentication，输入口令/二次确认） | 无 | **缺** |
| 签名与记录内容绑定（签名后内容不可变、可校验） | 有快照 + 审计，但不构成密码学绑定 | **部分** |
| 不可抵赖（non-repudiation，数字签名/证书） | 无 | **缺**（国密 SM2/CA 留远期） |
| 记录生命周期控制（禁止删除、版本受控） | 本版新增删除拦截（8.3）+ 版本链（7.7） | **本版补齐** |
| 审计追踪不可关闭、不可篡改 | 有（sha1 校验） | 已具备 |

**本阶段定性（写入方案与培训口径）**：

- 本板块提供的是**平台操作签名 + 审计追踪**，属"记录可归属、可追溯"层级；
- **不等同于 21 CFR Part 11 / EU GMP Annex 11 规定的合规电子签名，不构成合规生产放行依据**；
- 用于 GMP 放行的报告/方案，**仍需按现行纸质签批流程补签**，系统记录作为电子副本索引。

**若后续要求系统直接承担 GMP 电子签名（路线 ②）**，须实现（列入第十二节"明确不做"）：签名时重新认证、签名与记录密码学绑定、PKI/CA 或国密 SM2 验签、签名验证报告、受控配置管理、CSV 验证。

> **Owner 决策（2026-09-15）**：本板块走**路线 ①**。GMP 合规电子签名（路线 ②）**由平台后续统一专项实施**——待权限体系与密码/证书授权完善后，**各板块统一上电子签名**。届时本板块 6.3 各审批动作即为签名接入点，**签名点已按"含义串 + 用户 + 时间"结构化设计，接入时无需重构业务逻辑**，仅在签名写入处替换为带重新认证与密码学绑定的实现。

### 8.5 防重复与防越权

- 防重复：三个业务键单字段 unique（5.6）；时间点生成/结果提交在锁内校验（7.8）；取样/销毁执行幂等（终态锁定）。

### 8.6 禁止绕过业务服务（P2-4 新增）

状态机与一致性规则全部位于 `stability_service.py` 的 whitelist 方法内；**必须防止通过 Frappe 原生路径绕过**：

| 绕过路径 | 防护 |
| --- | --- |
| **表单直接 `save()`**（Desk 表单、`doc.save()`） | 系统字段一律 `read_only=1` 且在 DocType 控制器 `validate` 中校验：`status` / `is_current` / `current_result` / `current_qty` / `reserved` 类字段 / 各业务键字段 **只允许在 `doc.flags.allow_system_fields=True` 时变更**（对齐 R7 既有 `allow_system_fields` 守卫模式），否则抛错 |
| **REST / API 直接更新**（`PUT /api/resource/...`） | 同上——Frappe REST 走同一 `validate` 链路，`read_only` + 控制器守卫即覆盖 |
| **数据导入**（`Data Import`） | 走 ORM，受 `validate` 约束（含 `allow_system_fields` 守卫） |
| **低层写入**（`frappe.db.set_value` / `frappe.db.sql` / `bench execute`） | **P2-4 强化：不能依赖 DocType `validate`**——`frappe.db.set_value` 与裸 SQL **按设计绕过 ORM 校验**，`validate` 对它们无效。故本板块的防绕过**不以此为防线**，改用：① **受控 API**——所有状态/指针/结存变更只经 `stability_service.py` 的 whitelist 方法，服务内部再统一走 `_lock_row` + 契约校验；② **权限隔离（P1-3 rev11 更正）**——**DocType 仍按业务需要授予 create/write**（否则草稿无法创建、普通字段无法编辑）；仅**系统字段**（`status`、`is_current`、`current_result`、`current_qty`、各业务键字段）置 `read_only=1`，并由控制器 `validate` 守卫 + `allow_system_fields` 标记，仅允许 whitelist 服务写入。**采用"服务专用写入模式"（整表收权 create/write）的仅限以下三类表**，逐张列明：`HBOS Stability Sample Log`、`HBOS Stability Timepoint Delay`、`HBOS Stability Fault Sample`——它们无用户直接填单场景，全部由服务方法写入（与 8.3「流水表特例」一致）；其余 DocType 一律保留常规 create/write；③ **运维约束**——迁移/修复脚本改这些字段属**越权操作**，须走变更单、显式置 `allow_system_fields` 并写审计（8.1），由 SOP 约束而非系统阻断；④ **专项负向测试**——11.2 门禁 16 覆盖 `set_value` 路径，**断言其影响可被后续一致性校验（流水对账 / 指针不变式）检出并告警**，而非声称"已阻断"；⑤ **运行期一致性扫描（P2 rev12）**——每日 scheduler 扫描不变式违反并告警（见本节下方「运行期一致性扫描」），不停留在测试期发现 |
| **直接 SQL** | 不提供；运维层 SQL 变更须走变更单并记录（超出系统边界，由 SOP 约束） |
| **绕过状态机的状态直写** | `status` 只能由 6.3 矩阵对应动作变更；`validate` 比对"上次落库状态 + 本次动作"，非法转移即拒绝（契约层 `can_transition` 校验） |

> 本表为**硬约束**（写入实现验收）：ORM 路径（表单/REST/Data Import）由门禁 16 以"**直写拦截**"负向用例覆盖；低层路径（`set_value`/裸 SQL）**无法拦截**，由门禁 16 以"**低层直写后果检测与告警**"负向用例覆盖（P2-5 措辞更正，不再笼统称"已覆盖直写拦截"）。

**运行期一致性扫描（P2 rev12 补强：不止于测试期发现）**

低层直写无法阻断（上表第 4 行），故除测试期负向用例外，**运行期**由 `stability_service.scheduler_scan` 每日执行**一致性校验扫描**，把"可被检出"落实为持续机制：

| 校验项 | 不变式 | 来源 |
| --- | --- | --- |
| 生效指针不变式 | `Timepoint Item.current_result` 指向的 Result 必须 `is_current=1` 且 `status=已批准`；每个 Result `is_current=1` 必须被某指针引用；同一 `(时间点, 项目)` 至多一条 `is_current=1` | 7.7 / 门禁 11、15 |
| 流水对账 | Sample `current_qty` 与 Sample Log 累计收支一致；Delay 子表在途行 ≤ 1/`delay_type` | 7.8 / 门禁 7、8 |
| 日期链 | 存量 Delay 已批准行满足 `planned ≤ requested ≤ approved ≤ policy_latest` | 7.3 / 门禁 18 |
| 业务键唯一 | 三业务键在 DB unique 之外再做应用层抽查（防低层写入绕过 unique 索引） | 5.6 |

- **告警落点**：异常写入**审计事件 `一致性异常`**（8.1 枚举，含 DocType / 名称 / 违反的不变式），并进 8.4 scheduler 的**「一致性扫描异常」**清单（检测进度看板旁路展示）；
- **处置责任**：清单由 **QA 每日复核**——确认为低层直写所致的，按 8.6 第 4 行运维约束走**变更单 + `allow_system_fields` 修复 + 审计**；无法即时修复的登记偏差（引用 `deviation_ref`），**修复前相关数据不作为报告/外推依据**；
- **不自动修复**：扫描只**检出与告警**，不做任何自动写回（避免扫描器自身成为绕过服务层的写路径）。

### 8.7 违规动作审计的独立持久化（P2-5 新增）

拦截类动作的审计若与主事务同事务，**会随 `frappe.throw` 触发的回滚一起丢失**，导致"越权/删除尝试无痕"，违反 8.1 与门禁 6。统一处置：

| 场景 | 规则 |
| --- | --- |
| **删除拦截**（8.3 `on_trash` 抛错） | 抛错**之前**先调用 `_audit_commit(...)`——**独立事务提交**审计行，再 `frappe.throw`。审计不随回滚丢失 |
| **越权拦截 / SoD 拦截**（`_check_action` 失败、同人连签、自审自批） | 同上，`_audit_commit` 先落审计 |
| **状态机非法转移被拒** | 同上 |
| 实现依据 | 复用 R7 已交付的 `_audit_commit` 模式（违规尝试独立提交），本板块沿用，不自建 |

> 11.2 门禁 17 以"回滚后审计仍在"负向用例覆盖。
