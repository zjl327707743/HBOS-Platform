### 2.7 库存台账粒度核对（重要修正）

在复核"批次 × 货位 → 数量"能否由原生表直接承载时，只读查询了实际表结构，结果与初稿假设不同，特此修正：

**`tabBin` 的实际结构**（只读 `information_schema`）：

- 列为 `item_code`、`warehouse`、`actual_qty`、`projected_qty`、`reserved_qty`、`stock_value` 等。
- 唯一索引：`unique_item_warehouse (item_code, warehouse)`。
- **`Bin` 没有 `batch_no` 列**，粒度是"物料 × 货位"，不含批次。

**`tabStock Ledger Entry` 的实际结构**：

- 同时含 `warehouse` 与 `batch_no`（varchar），以及 `actual_qty`、`qty_after_transaction`、`posting_date` 等。
- 因此"批次 ↔ 货位"的多对多关系**真实存在于 `Stock Ledger Entry`**，不在 `Bin`。

**标准报表**：`Stock Balance`、`Warehouse Wise Stock Balance` 均为 `is_standard = Yes`，`Stock Balance` 支持按批次维度分组。

**修正结论**：

- 初稿"`Bin` 原生承载批次 × 货位多对多台账"的说法**不准确，已更正**。
- 准确说法：`Bin` 提供"物料 × 货位"的即时结存；**"批次 × 货位 → 数量"需要聚合 `Stock Ledger Entry`**（它同时有 `warehouse` 和 `batch_no`），或复用标准报表 `Stock Balance` 的批次维度。
- 这不改变"优先复用原生"的总体结论，但改变了 M3-R2 的实现量：批次级货位查询需要一个聚合视图 / 自定义报表，而不是直接读 `Bin`。

**三处重要发现**（文档一二均未明确，货位卡暴露）：

**发现一：存在"待检 → 放行/不放行"的状态门禁（已由 Owner 明确规则）。** 货位卡同时有"待检 年 月 日"和"放行□ / 不放行□ + 日期"两组字段。说明物料入库后处于**待检**状态，经质量判定后才能**放行**。

Owner 已明确判定依据：**看是否有 QA 出具的放行手续和合格证——有则可出库，没有则不可出库。**

即这是一条**硬门禁**，不只是"生成一张待检证"的凭证问题：

- 待检证 / 货位卡是**凭证**；
- **QA 放行手续 + 合格证是出库的前置条件**——缺任一项即拦截。

M3-R3（出库核销）必须实现该校验，M3-R4（待检证）负责凭证生成。两轮的实现方式（是否与 ERPNext `Quality Inspection` 或 `Batch` 状态联动）待 M3-R2 定。

**发现二："件数"是同一批物料的"包装构成"，与批次、货位都无关（已由 Owner 说明）。**

初稿对此描述不清，此处重写。以其中一张卡为例，**同一批物料**：

| 容器类型 | 单件重量 | 件数 | 小计(kg) |
| --- | --- | --- | --- |
| 件 | 5.00 kg | 33 | 165.00 |
| 件 | 4.33 kg | 1 | 4.33 |
| 听 | 0.03 kg | 3 | 0.09 |
| 瓶 | 0.001 kg | 1 | 0.001 |
| **合计** | | **34件3听1瓶** | **169.421 ≈ 入库数量 169.42** |

Owner 对各类容器的说明：

| 容器 | 说明 |
| --- | --- |
| **件** | 包装好的 **5 kg 一桶**；物理上**两桶装在一个纸箱**里（纸箱为外包装） |
| **尾桶** | 一批料分装到最后**剩余不足 5 kg** 的物料，**单独放一个桶**——这就是同一批里出现 `4.33 kg` 的"件"的原因，属正常情况 |
| **听 / 瓶** | **小件样品**，供 **QC 取样或客户取样** 用 |

关键定性：**件、听、瓶都是同一批次，放在一起（同货位）**。所以"件数"描述的是**这批货怎么分装的**，不是批次概念，也不是货位概念。

**为什么 ERPNext 原生装不下**：ERPNext 的双 `UOM` 是**一个固定换算系数**（1 件 = N kg）。这里的"件"不固定重量（整桶 5.00 与尾桶 4.33 并存），"听""瓶"又是另外的容器类型，单一系数无法表达"34件3听1瓶"。

**承载方案要点（M3-R2 定）**：需能表达"容器类型 + 单件重量 + 件数"三要素的明细行；`入库数量`（kg）作为权威数量，件数明细作为包装描述与打印依据。

**发现三：货位卡与多货位的关系（已由 Owner 澄清）。** 货位卡只有一个"货位号"栏，而同一批物料可散放多个货位。Owner 已明确：**一个批号只对应一张货位卡，不论该批次物料放在多少个货位上**。即"一批一卡"，卡上的货位号需能呈现该批涉及的**全部货位**（版式实现待 M3-R4 设计）。

**其他字段映射**：`生产车间`（六车间B线）与 `复检期/有效期` 均为产品级属性，`Item` / `Batch` 原生无对应字段，需自定义字段。

### 3.9 批号规则（来自 Owner 提供的图片）

Owner 提供了批号编制规则表，转发如下（原文为中英双语，此处摘录中文口径）：

规则表按**产品种类**分三行，且三行的编码结构各不相同：

#### 类型一：原料药 / 中间体（API and intermediate）

**编码结构**：`生产线 - 年 - 月 - 流水号（三位数）`

| 要素 | 规则 |
| --- | --- |
| 生产线 | 生产线代号（字母前缀） |
| 年 / 月 | 两位年、两位月 |
| 流水号 | **三位数，001–999**；各品种流水号的制定与分配依据相关文件管理；**同一月内同一品种流水号逐渐递增，不随日期更改**；**换月重新开始编制** |

**日期口径**：生产日期 = **投料当天日期**；有效期自投料当天起算。

#### 类型二：混粉（多成分混粉 Mixture）

**编码结构**：`生产线 - 产品中主要两组份的汉语拼音首字母 - 年 - 月 - 流水号（三位数）`

注意：混粉的编码**多插了一段"主要两组份拼音首字母"**，与原料药/中间体的结构不同。

**业务定义与日期口径**：多成分混粉 = **不同原料或（和）辅料经混合均匀得到的产品**；**有效期从混料当天起算，生产日期为混料当天日期**。

#### 类型三：亚批次（Sub batch）

**编码结构**：`大批次批号 + "-1" / "-2" / "-3" …`，按**生产时间顺序**加后缀。

**日期口径**：有效期自投料当天起算，生产日期为投料当天日期。

#### 有效期规则按产品种类区分（不是冲突）

规则表本身就是**按产品种类**组织的，不同种类适用不同有效期口径，这是设计如此：

| 产品种类 | 有效期规则 | 生产日期 |
| --- | --- | --- |
| 原料药 / 中间体 | 从**投料当天**起算 | 投料当天 |
| 混粉（多成分） | 从**混料当天**起算 | 混料当天 |
| 亚批次 | 从**投料当天**起算 | 投料当天 |
| 〔相同原料、不同批次混合〕 | 按混合批次中**有效期最短**的批次计 | 混粉当天 |

初稿曾把这里登记为"口径不一致（需确认）"，**属表述不当**：规则按产品种类分列，不同种类口径不同是正常的，文档之间不矛盾。已修正。

**对仓储系统的实际含义只有一条**：每个产品需知道自己适用哪种效期口径（**复检期 / 有效期**）与**期限**（2 年 / 3 年等），来源即该产品的**质量标准**——这正是 Owner 已说明的"效期预警要根据产品来看，有质量标准"。落到系统里就是产品主数据上的两个字段，随 M3-R1 产品主数据一并定义。

**一处低优先级确认**：〔相同原料不同批次混合〕的"取最短"是一条**派生计算**（不是"生产日期 + 期限"），且发生在混合产出新批时。需确认它是车间 / QA 侧的产出规则、仓库只接收结果，还是仓库系统也需参与计算。这属于混粉来源批次承载（第 18 项）的一部分，不单列阻塞。

#### 格式验证

两份货位卡实例的批号均符合**类型一（原料药 / 中间体）**结构——字母前缀（生产线）+ `26`（年）+ `09`（月）+ 三位流水号，其中年 `26`、月 `09` 与开单月份一致，**验证通过**。（按项目数据安全规则，批号原值不写入仓库。）

**三处结构问题的结论（均已收口）**：

**风险一（已排除）：批号不会撞号。**

初稿担心的问题：`Batch.batch_id` 在 ERPNext 中是**全局唯一**（只读核对：`tabBatch` 唯一索引 `batch_id`，`NON_UNIQUE = 0`；`Batch.batch_id` 字段 `unique = 1`），而流水号按"同一月内同一品种"编制，若同一条生产线轮产多个品种就可能撞号。

**Owner 已明确答复：不存在撞号的可能。**

因此本风险**排除**，结论：

- `Batch.batch_id` 可直接承载业务批号，**无需组合键**；
- **"按批号查货位"可以以批号为唯一键**——项目的核心功能成立；
- 不需要绕开 ERPNext 的全局唯一约束。

旁证：混粉的编码特意插入"主要两组份拼音首字母"以标识品种，说明该体系本身已确保品种可区分，与"不会撞号"一致。

**风险二（已解除）：混粉不需要在仓库侧做特殊建模。** 初稿担心混粉是"多来源混合"，而 `Batch.parent_batch` 是单条 Link 装不下，并据此提出 A/B/C 三个方案。

**Owner 已明确：混粉与成品完全一样，登记流程完全相同。** 含义：

- 仓库对**所有产品种类（原料药、中间体、混粉、成品、亚批）使用同一套登记流程**——登记批号、品名 / 物料代码、生产日期、有效期、数量、货位，**不做分类差异处理**。
- **混配的配方与来源批次追溯不发生在仓库**：混配在车间完成，批号与有效期由车间 / QA 产出，仓库只接收结果并按批登记。
- 因此 M3 **不需要**为混粉做来源批次子表，也不需要 `Stock Entry` 组件追溯。初稿的候选方案 A / B / C **全部不需要**。
- `Batch.parent_batch` 仅在日后确有追溯需要时才用，属**可选**。

**风险三（降级为可选）：亚批次同样按统一流程登记。** 亚批编码 = 主批号 + `-1` / `-2` / `-3`，仓库按**同样的流程**单独登记即可，无需特殊处理。若日后需要体现"亚批属哪个主批"的追溯，`Batch.parent_batch`（单父结构）原生可满足，属**可选增强**，不是必需。

**本轮的重要简化**：所有产品种类走**同一套入库登记流程**，M3-R2 无需按产品种类分支。这一条同时消掉了初稿凭空引入的混粉特殊建模。

**对前面口径的修正**：第 3.8 节曾把"生产日期"归为"待自定义字段"，此处更正——`Batch.manufacturing_date` 原生存在且语义正好是"投料当天"；需要自定义的是**生产车间**与**效期类型（复检期 / 有效期）**。

### 5.1 存放模式澄清（更正初稿的"口径冲突"）

初稿曾把"固定货位 vs 动态管理"登记为口径冲突，**该判断有误，此处更正**。参考文档中的"动态管理"指的是**产品 / 批次放哪个格子**是动态的（按入库节奏就近找空位、允许换位），**不是指格子本身不固定**。两类"固定"必须分开看：

| 维度 | 是否固定 | 依据 |
| --- | --- | --- |
| 货位（物理格子） | **固定** | 203 个编码、按层组织的平面布局图、每个货位长期粘贴二维码标签 |
| 产品 / 批次 ↔ 货位 的对应关系 | **不固定（随机存放）** | "货物摆放位置随入库节奏动态调整，缺乏固定的货位对应关系"；操作人"选择或扫描当前存放的货位号"；"库存产品如果更换货位，可支持货位信息变更" |

结论：16 号楼产品库是**固定货位 + 随机存放**模式。文档所说的缺口是"**缺系统化记录**"（"产品入库后缺乏系统化的位置记录，库存分布依赖人员记忆"），不是缺货位。

**这对建模是好消息**：货位是稳定主数据，可一次性建好并长期复用，不需要为"货位频繁变化"额外设计机制。

### 5.2 方案定案：方案 A（`Warehouse` = 货位）

Owner 已确认走方案 A。落地形态：

- `16号楼产品库 - HB` 下挂 203 个货位 `Warehouse`，名称即货位编码。
- 每个货位 = 一条 `Warehouse` 记录，长期存在；新增货架时增补。
- 批次 ↔ 货位多对多由 `Stock Ledger Entry` 承载（见 2.7）；货位级即时结存由 `Bin` 提供。
- 货位移库 = 原生 `Stock Entry`（Material Transfer），天然支持批次。
- "层"信息：Owner 已确认**需要按层管理**，层作为 `Warehouse` 树的一级承载（方案 A1），见 5.3。

方案 A 的已知取舍（已向 Owner 说明）：

1. 200+ 个 `Warehouse` 记录会进入各类下拉框与按仓库分组的报表；缓解方式是树形层级 + 父级过滤。
2. `Warehouse` 名称默认带公司后缀（如 `16-03-377 - HB`）；扫码页与打印件用短码展示规避。
3. `Warehouse` 在 ERPNext 中有估值 / 会计语义，货位数量多会使按仓库维度的财务报表变长；海滨场景下按货位管存货本身即需求，可接受。
4. 布局图中的"工作台""退回产品区"不是"层"上的货位；Owner 已确认**也建成 `Warehouse`**（作为叶子直接挂在库区下），否则落在这些区域的物料无法记账。见 5.3。

方案 B（`Inventory Dimension`）与方案 C（自定义 DocType）本轮不定案，保留为备选；若方案 A 实机中发现 `Bin` / 报表表现不可接受，再回退评估。

### 5.3 层管理方案（方案 A1）与非货位区域

Owner 已确认：**需要按层管理**，且"层"通过 `Warehouse` 树的一级承载，不另加自定义字段。

**为什么层必须显式记录、不能靠编码推导**：只读分析了布局图的行（层）与编码的对应关系，结论是**不存在可靠的推导规则**：

- 序号 205–282 严格遵循"奇数 = 第一层、偶数 = 第二层"，规则干净。
- 但从 285 起，层号随序号跳变且**不单调**：285–315 是第三层，316–359 是第四层，**360–368 又回到第三层**，369 起才是第五层。
- 中间还缺 283、284。

因此层必须作为**显式数据一次性录入**（数据源就是布局图）；M3-R1 不得实现"按码段推算层"的规则。

**层分布**（只读统计，用于 M3-R1 建树后的校验）：

| 层 | 货位数 |
| --- | --- |
| 第一层 | 39 |
| 第二层 | 39 |
| 第三层 | 39 |
| 第四层 | 43 |
| 第五层 | 43 |
| 合计 | 203 |

**目标树形结构**：

```
All Warehouses - HB
└── 16号楼产品库 - HB            (group)
    └── 03区 - HB                (group，本试点唯一库区)
        ├── 第一层 - HB           (group，39 个货位)
        │   └── 16-03-221 - HB    (leaf，可存货)
        │   └── ...
        ├── 第二层 - HB           (group，39)
        ├── 第三层 - HB           (group，39)
        ├── 第四层 - HB           (group，43)
        ├── 第五层 - HB           (group，43)
        ├── 工作台 - HB           (leaf，不属任何层，可存货)
        └── 退回产品区 - HB        (leaf，不属任何层，可存货)
```

关键点：

- 层节点是 `is_group = 1` 的**分组节点，本身不能存货**；存货只发生在叶子（货位 / 工作台 / 退回产品区）。这正好满足"按层管理"：按层筛选、按层分组报表天然可用，而层本身不参与记账。
- "工作台""退回产品区"是布局图中仅有的两个非货位标记（只读分析确认，详见 3.3）。它们不属于任何层，作为叶子直接挂在库区下。
- 层作为树的一级后，原生报表（`Stock Balance`、`Warehouse Wise Stock Balance`）按父级筛选即可得出"整层库存"，无需自定义报表。
- 若 M3 后期某张自定义报表需要扁平的"层"列，可再加一个从父级取的派生字段——这是纯增量，不需要重整 203 个节点。这也是选 A1 而非 A2 的原因：**树可以推出字段，字段推不出树**。

方案 A2（层作为 `Warehouse` 自定义字段）本轮不定案，保留为备选。
