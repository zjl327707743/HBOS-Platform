## 1. 目标与边界

**目标**：让飞书调休审批进入系统，并按海滨口径完成「加班日提取 → 打卡核实」，产出一份可人工复核的结论清单。

**业务规则**（Owner 2026-09-21 确认）：

```
调休日 = 飞书「开始时间 ~ 结束时间」的日期区间（结构化字段说了算）
加班日 = LLM 从「说明」自由文本里提取（可多个；说明里常以他人名字列在同一单据内）
核实   = 每个加班日当天是否存在【完整的一对上下班打卡】
全部加班日都有完整配对 → 已核实 → 可豁免
任一缺失 / 解析失败 / 无加班日 → 核实不通过 → 不豁免，转人工
```

**与请假的关键差异**（Owner 原话：「模板一样，但调休是调休，请假是请假，两者的判定逻辑不一样」）：

| | 请假 | 调休 |
| --- | --- | --- |
| 数据表 | `HBOS Leave Record` | `HBOS Rest Leave Record` |
| 判定前提 | 审批通过即豁免 | 审批通过 **+ 加班日核实通过** 才豁免 |
| 是否需要 LLM | 否 | **是**（仅用于解析加班日） |
| 按小时判定 | 不做 | **不做**（见 §5） |

**本轮范围**

- 新建纯逻辑模块 `rest_leave.py`；DocType 加 4 个字段；`sync_rest_leave.py` 建三段（同步 → LLM 解析 → 核实）。
- 退休从未生效的 `HBOS Rest Leave Record` 旧形态与换班（`HBOS Shift Swap Record`）全部产物。
- 三段挂上 `*/30` 调度。

**本轮明确不做**

- 不做加班模块本体（加班审批、加班余额、加班与调休的抵扣核对）。
- 不做额度校验：飞书审批通过即视为合法来源，系统不核对加班余额。
- 不做半天/小时级调休的时段判定。
- 不改 `pairing.py`、`board_stats.py`、`api.py`、月度汇总与考勤结果报表。
- 不写回飞书（只读同步）。

### 3.3 说明字段的可解析性

104 条说明**全部非空**，但形式极杂：

| 特征 | 条数 |
| --- | --- |
| **「月+号」写法（`8月2号加的班`）** | **71** |
| 「月+日」写法 | 13 |
| 点号日期（`2026.08.02`） | 18 |
| 斜杠（`8/2`） | 1 |
| 完全没有日期 | 9 |
| **多行批量说明（2~4 行）** | **36** |

**为何非 LLM 不可**：那 36 条多行说明是「一张单子里列了十几个人的加班→调休对」，且**行内人名未必是本条记录的员工**（如记录属于陈坤顺，说明里是「贺文雅8月1号加的班…／魏雨8月3号加的班…」）。这类自由文本理解，规则解析写不出来。

**实测暴露的一个关键坑**：**65 条只用「号」不用「日」**。初版解析器只认「日」，会让 **63% 的真实数据落到「解析失败」**。已在修复轮补上。

**复用已有能力**：`ai_review.py` 的 OpenAI 兼容通道与 `HBOS_AI_BASE_URL/MODEL/API_KEY` 三个环境变量已在容器内配置，本轮直接复用，未新建通道。

**状态机**：

```
待解析 ──(LLM 调成功且有日期)──→ 待核实 ──(加班日全部有完整配对)──→ 已核实
   │                                  └──(任一缺失)──────────────→ 核实不通过
   ├──(LLM 调成功但无日期)──────────→ 解析失败
   └──(LLM 调用失败)──→ 留在待解析，下轮重试（不写 parsed_at）
```

**关键设计约束**：**LLM 结果必须落库，判定热路径永不调用 LLM**。考勤每 10 分钟重算一次，在热路径调 LLM 成本与延迟都不可接受，且同样输入未必同样输出——判定必须基于稳定的落库结论。为此加 `PARSE_BATCH_SECONDS=1200` 时间预算，超预算即停、剩余记录留下轮继续（不计入失败）。

**核实判据**：复用系统**已经算出来的**考勤结果（`status='Present'` 且 `working_hours >= 2`），不在本模块另写一套「什么算完整配对」——两套定义必然漂移。

## 7. 测试策略变更（值得记下）

本轮之所以反复发现「代码在、运行态为零」这类问题，根因是原来的测试是**静态断言**——检查源码里有没有某字符串，**永远为真**。它只能证明「代码在」，无法证明「能用」。

本轮改为测真实行为，其中纯逻辑部分（日期展开、加班日解析、核实判定）在 CI 中可跑，不需要数据库。逐任务审查累计拦下 **8 个会进生产的问题**，其中 **5 个源自计划或调度指令本身写错**：

| 我写错的地方 | 若没拦下的后果 |
| --- | --- |
| 解析器只认「日」不认「号」 | **63% 的真实说明永远解析失败** |
| 「说明变更→重新解析」条件恒为假 | 改了说明永远不重算，一直用旧加班日 |
| 循环体大部分在 `try` 外 | 一条坏记录 → 整批中止 + 摘要丢失 + 调度链打断 |
| `get_doc` 在 `try` 外（同上） | 记录被删即整批崩 |
| 修复指令引入 `record.get` 回归 | `except` 内二次异常逃逸 |
| brief 指向不存在的 `hooks.py` | 测试永远不可能变绿 |
| parse 段两处 DB 调用无守卫 | 同文件两套策略且无理由 |
| 落地记录命名撞号（`M1-FIX-C`）| 台账出现两个不同含义的 C |

**结论**：纯逻辑 + 逐任务审查 + 独立复查这套流程，在本轮是有效的，不是走过场。
