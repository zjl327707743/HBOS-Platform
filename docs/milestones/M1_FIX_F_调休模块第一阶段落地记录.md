## 1. 目标与边界

**目标**：让飞书调休审批进入系统，并按海滨口径完成「加班日提取 → 打卡核实」，产出一份可人工复核的结论清单。

**业务规则**（Owner 2026-09-21 确认）：

```
调休日 = 飞书「开始时间 ~ 结束时间」的日期区间（结构化字段说了算）
加班日 = LLM 从「说明」自由文本里提取（可多个；说明里常以他人名字列在同一单据内）
核实   = 每个加班日当天是否存在【完整的一对上下班打卡】
全部加班日都有完整配对 → 已核实 → 可豁免
任一缺失 / 解析失败 / 无加班日 → 核实不通过 → 不豁免，转人工
```

**与请假的关键差异**（Owner 原话：「模板一样，但调休是调休，请假是请假，两者的判定逻辑不一样」）：

| | 请假 | 调休 |
| --- | --- | --- |
| 数据表 | `HBOS Leave Record` | `HBOS Rest Leave Record` |
| 判定前提 | 审批通过即豁免 | 审批通过 **+ 加班日核实通过** 才豁免 |
| 是否需要 LLM | 否 | **是**（仅用于解析加班日） |
| 按小时判定 | 不做 | **不做**（见 §5） |

**本轮范围**

- 新建纯逻辑模块 `rest_leave.py`；DocType 加 4 个字段；`sync_rest_leave.py` 建三段（同步 → LLM 解析 → 核实）。
- 退休从未生效的 `HBOS Rest Leave Record` 旧形态与换班（`HBOS Shift Swap Record`）全部产物。
- 三段挂上 `*/30` 调度。

**本轮明确不做**

- 不做加班模块本体（加班审批、加班余额、加班与调休的抵扣核对）。
- 不做额度校验：飞书审批通过即视为合法来源，系统不核对加班余额。
- 不做半天/小时级调休的时段判定。
- 不改 `pairing.py`、`board_stats.py`、`api.py`、月度汇总与考勤结果报表。
- 不写回飞书（只读同步）。

**状态机**：

```
待解析 ──(LLM 调成功且有日期)──→ 待核实 ──(加班日全部有完整配对)──→ 已核实
   │                                  └──(任一缺失)──────────────→ 核实不通过
   ├──(LLM 调成功但无日期)──────────→ 解析失败
   └──(LLM 调用失败)──→ 留在待解析，下轮重试（不写 parsed_at）
```

**关键设计约束**：**LLM 结果必须落库，判定热路径永不调用 LLM**。考勤每 10 分钟重算一次，在热路径调 LLM 成本与延迟都不可接受，且同样输入未必同样输出——判定必须基于稳定的落库结论。为此加 `PARSE_BATCH_SECONDS=1200` 时间预算，超预算即停、剩余记录留下轮继续（不计入失败）。

**核实判据**：复用系统**已经算出来的**考勤结果（`status='Present'` 且 `working_hours >= 2`），不在本模块另写一套「什么算完整配对」——两套定义必然漂移。

## 8.6 上线过程中发现并修复的三个问题

### 问题一：LLM 模型已下线（阻断性）

`.env` 的 `HBOS_AI_MODEL=deepseek-v4-flash` 上游已不再提供，解析全批 119 条失败（`HTTP 503 model_not_found`）。

**未凭猜测改**，而是拿 20 条真实说明对 4 个候选模型做了对比：

| 候选模型 | 提取到日期 | 错误 | 提取日期总数 |
| --- | --- | --- | --- |
| **`deepseek-flash`** | 16/20 | 1 | **22** |
| `qwen35` | 16/20 | 0 | **90**（明显过度提取） |
| `GLM-5.3-Flash` | 15/20 | 2 | 21 |
| `kimi-k3` | 0/20 | 20 | — |

**选 `deepseek-flash`**。决定性证据是一条「7月11日周六上班，7月29日调休」——`deepseek-flash` 只抽出 `07-11`（正确），`qwen35` 把 `07-29` 调休日也当成加班日（错误）。`qwen35` 抽出 90 个日期也说明它在把**他人**的加班日一并抓入。

**更值得注意的是我们的容错表现**：119 条全部失败，但一条都没被误标、函数没崩、正常返回摘要、每条失败都带记录标识记了日志。**第一次真实故障就验证了这套错误处理是对的。**

### 问题二：定时任务根本跑不起来（严重，且极隐蔽）

排查日志发现 `*/30` 触发时 `parse_pending_rest_leaves` **耗时 0.35 秒**——119 条要调 119 次 LLM，不可能。0.35 秒等于走了「未配置 AI」的提前返回分支。

**根因**：`HBOS_AI_BASE_URL/API_KEY/MODEL` 三个变量**只注入给了 backend**，`scheduler` 与两个 `queue` 都没有。

| 容器 | 修前 | 修后 |
| --- | --- | --- |
| backend | ✅ | ✅ |
| scheduler | ❌ | ✅ |
| queue-long | ❌ | ✅ |
| queue-short | ❌ | ✅ |

**为何单漏这三个**：`HBOS_AI_*` 是后加的（给「AI复核」用），而该功能跑在 backend 的网页请求里，当时只加了 backend——**此前从无定时任务使用 AI，所以从未暴露**。

**为何极隐蔽**：
1. 任务显示「**成功**」，不报错，只是没做事；
2. 用 `bench execute` 在 backend 里手动跑是**正常的**——手动测永远测不出来；
3. Frappe 机制是 scheduler 只负责**入队**、真正执行在 **RQ worker**（queue 容器），故变量要加在 queue 上。

已补入 `docker-compose.yml` 并重建，四个容器实测 `HBOS_AI_MODEL` 均已生效。

> **同类风险提醒**：任何「定时任务要用、但只在网页请求里用过」的 env，都可能踩同一个坑。列入后续排查项。

### 问题三：`nginx -s reload` 才是 502 的正解（文档写错了）

容器重建后登录页 502 约 2 分钟。根因：`/etc/nginx/conf.d/*.conf` 里写的是 `server backend:8000`（**域名**），nginx 启动时解析一次并缓存，而 backend 重建后 IP 变为 `172.18.0.8`。

**这推翻了 `docs/HBOS考勤判定规则.md` §13.9 的结论**：

> 原文：用 `restart` 保持容器 IP，避免 nginx 连旧 IP 致 502

**`restart` 并不保证 IP 不变**——本轮实测两次都变了。真正管用的是 **reload nginx**。当时那次没出问题纯属巧合（IP 恰好未变），不是方法正确。已修正该文档。

## 7. 测试策略变更（值得记下）

本轮之所以反复发现「代码在、运行态为零」这类问题，根因是原来的测试是**静态断言**——检查源码里有没有某字符串，**永远为真**。它只能证明「代码在」，无法证明「能用」。

本轮改为测真实行为，其中纯逻辑部分（日期展开、加班日解析、核实判定）在 CI 中可跑，不需要数据库。逐任务审查累计拦下 **8 个会进生产的问题**，其中 **5 个源自计划或调度指令本身写错**：
