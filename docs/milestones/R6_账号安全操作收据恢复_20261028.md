## 问题

已合并基线的成功收据只写 Redis（`hbos:account:write-result:<sha256(user:request_id)>`，TTL 900 s，写失败静默吞）。900 s 后浏览器无法证明“该请求是否已提交”，而客户端未决标记 fail-closed，导致永久阻断；共享 `RECOVERY_TTL` 同时约束密码恢复链接，不可延长。受影响写：`set_password`、`unlink_feishu`、`admin_issue_recovery`、`update_password` 的 key 恢复分支。

## 合同

- 新 DocType/表 `HBOS Account Write Receipt`（仅受控模块写入；无角色权限、rename/export 面）。
- 认领（claim）先于副作用并独立提交；业务写与其成功收据在同一 SQL 事务结算（`_write_password`/解绑/管理员签发内部显式 commit 之前插入）。回滚即无成功收据；结算时对收据行加锁，若期间被结束则业务事务回滚，不越过封存状态提交。
- Redis 只在 SQL 提交后发布，作为兼容旧前端的加速；读路径 Redis 失效/缺失时回退数据库；数据库不可用失败关闭。旧 v1 缓存仍按“已提交”兼容读取；数据库状态优先。
- 幂等命名空间绑定 site + actor + request_id；Guest 恢复绑定一次性恢复上下文句柄（HMAC），裸 request_id 不是凭据；跨账号同 UUID 隔离。
- 意图绑定：action/目标 + 新密码键控指纹（HMAC，不存明文，不可离线猜测）；同编号异意图拒绝且不重写。
- 状态：`PENDING`（租约内=处理中，超租约=未知）、`COMMITTED`、`ABORTED`（确定未执行，可同编号重试）、`SEALED`（显式结束未知请求，旧编号永不派发）。
- 新命令 `seal_unknown_write(request_id, action, confirm="unknown-outcome")`：当前主体 + 新鲜密码 proof + 明确确认；仅解除该条阻塞，不声称成功；并发结算有行锁判定。
- 旧请求结果丢失：提供上述封存路径；Guest 页面响应丢失时凭仍然持有的恢复上下文核对；上下文丢失则走既有受控恢复（新链接/管理员/邮箱），不以清存储/换号作为恢复。
- 不自动清理防重最小记录；不延长 `RECOVERY_TTL`/proof/恢复链接；不弱化会话撤销与 proof 语义。
- 证明/epoch/会话撤销/新会话属于 SQL 事务之外的副作用：失败后按实际能力说明，不承诺数据库回滚会恢复它们；密码哈希与收据、审计同事务。
