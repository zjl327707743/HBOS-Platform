## 二、业务口径（Owner 2026-10-01 确认）

设备动力部的 12 小时倒班存在**连班**：早班 08:00 上班之后直接接晚班，不刷 20:00 的下班卡，直到**次日 08:00 前后**才刷下班卡。打卡表现为：

```text
D   08:0x–08:3x   上班机卡（上班）
D+1 08:3x–08:5x   下班机卡（下班）
间隔约 23.5–25.5 小时
```

该间隔超过统一配对上限 18 小时，于是上班卡与下班卡**各自落孤立**，两天各判一次缺勤（员工 10009023 9/25、员工 10009022 9/24 一类）。

**修复口径**：只对 `LONG_DUTY_DEPTS`（= 设备动力部）放开这一种形状。其余超长间隔仍按「漏下班卡」处理——**孤立卡维持判缺勤**。

## 三、实现

### `pairing.py`

新增模块常量：

```python
LONG_DUTY_DEPTS = {"设备动力部"}
LONG_DUTY_START_HOURS = (7, 9)     # 上班卡时刻窗口 [7, 9)
LONG_DUTY_END_HOURS = (7, 10)      # 次日下班卡时刻窗口 [7, 10)
LONG_DUTY_MAX_GAP_HOURS = 26
```

`pair_employee_checkins()` 新增 `long_duty=False` 形参（默认关闭，向后兼容）。在原「间隔超过上限即放弃配对」处放行，**但要求同时满足连班形状**：

```python
_is_long_duty = (
    long_duty
    and LONG_DUTY_START_HOURS[0] <= cks[i]["time"].hour < LONG_DUTY_START_HOURS[1]
    and _out_dt.date() != cks[i]["time"].date()
    and LONG_DUTY_END_HOURS[0] <= _out_dt.hour < LONG_DUTY_END_HOURS[1]
    and gap <= LONG_DUTY_MAX_GAP_HOURS
)
```

形状判定是必需的：否则「上午误刷的上班卡 + 次日同时刻下班卡」也会被配成假 24 小时班（员工 11008011 9/4 的 17:32 形状即为此类反例，已用测试固定）。

### `api.py`

`regenerate_attendance` 按部门开关：

```python
long_duty = (cks[0].get("department") or "") in LONG_DUTY_DEPTS
```

`cks[0].get("department")` 取值可靠——打卡记录由 `api.py:327` 的 SQL `JOIN tabEmployee` 取出 `emp.department` 并 `as_dict=True` 返回，每张卡都带该字段。

### 测试

`tests/test_pairing.py` 新增 `LongDutyPairingTest` **7 个用例**：开启时配对成功、关闭时与现行行为一致、默认关闭、反例（17:32 形状不得配对）、结束时刻窗口边界（次日 09:30 在窗内 / 10:30 出窗口）、常量存在。

## 四、实测（真实数据，只读）

新增只读工具 `tools/verify_long_duty_dryrun.py`：从运行中数据库读真实打卡，离线跑新旧两种口径做对照，**不写数据库**。

**范围**：`2026-08-15` ~ `2026-10-01`，`status='Active'` 员工。

### 连班形状确实存在

按「上班机卡 07–09 点 → 次日 下班机卡 07–10 点、间隔 > 18h」的**方向+时刻**双重判据统计（只按时刻会误算，见下）：

- **156 条**真实连班形状，分布于设备动力部。
- **663 条**超长间隔**被守卫挡住**（多为「上午上班卡 → 次日 20 点下班卡」等 36 小时形状），说明放行口收得很窄。

逐条抽样复核（原始打卡为证）：

| 人员 | 形状 | 间隔 |
|---|---|---|
| 员工 10009023 | 09-25 08:20 → 09-26 08:34 | 24.23h |
| 员工 10009022 | 09-24 08:22 → 09-25 08:33 | 24.19h |
| 员工 11008005 | 08-17 08:29 → 08-18 08:31 | 24.03h |
| 员工 10009018 | 08-15 08:14 → 08-16 07:4x | 约 23.2h |

员工 11008005的原始打卡（机器方向已展开）与形状判定完全吻合：

```text
08-17 08:29  上班机
08-18 08:31  下班机     ← 24.03h
08-19 08:32  上班机
08-19 12:31  下班机     ← 3.98h（正常短班）
08-20 08:27  上班机
08-21 08:33  下班机     ← 24.10h
```

### 判定差异（同批数据，旧口径 vs 新口径）

| 指标 | 条数 |
|---|---|
| 受影响员工 | **17 人**（全部属设备动力部） |
| 非连班部门员工受影响 | **0 人** |
| Absent → Present | **143 条**（修复目标） |
| Present → Absent | **0 条**（无回退） |
| 新增记录（原无 → 有） | 4 条 |
| 移除记录（原有 → 无） | 143 条 |

读法：每处连班在旧口径下产生**两天**错误缺勤——上班卡那天（孤立上班卡）与下班卡那天（孤立下班卡）。修复后上班卡那天变为 `Present`（工时 ≈ 24h），下班卡那天不再有记录（该卡已被配对消耗，与夜班下班次日的既有处理一致）。

**「非连班部门 0 人受影响」是本轮的关键安全断言**：部门开关按 `api.py` 的口径逐人判定（首版工具曾把 `long_duty=True` 施加给全员，一度出现「人事行政部员工新增 Present」「无菌车间员工新增 Absent」的假象——那是工具自身的缺陷，已修正为逐部门开关；修正前后的差异恰好证明了这个门闩是有效的）。

**4 条「新增记录」**已抽样核对（员工 11008005 08-17），其原始打卡是货真价实的 24 小时连班，属正确配对而非误配。

### 工具的已知偏差（未覆盖 api.py 的哪些部分）

工具是**近似复算，不是重放**：未接固定班次绑定与 `HBOS Shift Rule`（班次名不在核对范围）、未接请假 / 排班休息 / GPS 打卡集合 / `now_dt` 的实时性。这些遗漏只会让 `api.py` **少判**缺勤，不会多判，故「新口径把 Absent 变成 Present」的方向与量级不受影响。

## 五、代码审查发现

| 项 | 结论 |
|---|---|
| `department` 取值可靠性 | **可靠**（见第三节） |
| 设备方向交互 | **正确**。放行发生在「上班机卡 → 向后找下班机卡」分支内，配对伙伴必须是下班机卡；`terminal_role` 已保证 |
| 与去重窗口的关系 | **无冲突**。去重窗口 120 分钟，连班间隔约 24 小时，不会被合并 |
| 下班卡那天的缺勤来源 | **已消除**。旧口径由配对分支的「孤立下班卡 → 缺勤」产生；卡被消耗后该分支不再触发。当天另有打卡，故「零打卡缺勤」兜底也不会补判 |
| `present→absent` 回退 | 实测 **0 条** |
| 向后兼容 | `long_duty` 默认 `False`，未传参调用者行为不变（有测试） |
| **`打卡流水` 报表未同步（记录，不修）** | `report/打卡流水/打卡流水.py:53` 是 `pair_employee_checkins` 的**第二个调用点**，未传 `long_duty`（也未传 `max_gap_hours`，用默认 16——这是**改动之前就存在**的分歧）。**当前无可见影响**：该报表的方向列优先取设备 SN（`role_from_terminal`），8/15 之后设备直接定方向，配对推断只作兜底。若将来有设备未知的卡，兜底路径才会与判定口径不一致 |
| **旧诊断脚本会误报（记录，不修）** | `audit_misjudgments.py` 的第 1 条规则是「Present 且 `working_hours > 12` 即疑似误配超长班」。本修复会**故意**产出 `working_hours ≈ 24h` 的 Present，故该脚本若再被手动执行，会把设备动力部的连班全部列为「超长班」。全仓库检索确认该脚本**无任何引用**（只在 docstring 里给了 `bench execute` 用法），是历史诊断遗留，不构成功能回归 |
| 26h 上限与时刻窗口的交叠 | 「07:00 上班 → 次日 09:59 下班」= 26.98h，会被 26h 上限挡掉。属有意的保守取舍（近 27 小时的班更可能是数据异常），已记录 |

## 七、运行态尚未生效（重要）

`apps/hb_attendance_app` 以 **bind-mount** 进入运行中的容器，即工作区改动**位于生产路径上**。但 Python 进程只在启动时加载模块，故当前状态是：

- 常驻进程（backend / scheduler / queue，`Up 3 days`）内存中仍是**旧代码**；
- 任何**新起进程**（`bench execute`、新 worker）会读到**新代码**。

这正是 2026-09-28 已记录过的「同一数据两个答案」失效模式。**在容器重启或重算之前，不要用 `bench execute` 的口径去核对页面显示的数字。**

本修复要真正生效，需要两件事，均**需 Owner 授权**：

1. **重载代码**：重启承载判定进程的容器（`backend` / `scheduler` / `queue-long` / `queue-short`；重启后按既有经验需 `nginx -s reload`，否则 502）。
2. **重算数据**：定时任务的重算窗口是「本月 1 日 → 昨天」，**覆盖不到 9 月**的员工 10009023 9/25、员工 10009022 9/24 等既有错误记录，需按时间**升序**做定向重算。**注意 `regenerate_attendance` 的清理语句会删除 `attendance_date > range_end` 的全部记录**，窄窗口乱序执行会摧毁后续数据（2026-09-24 已发生一次，见 `M1_FIX_F` 落地记录 §A4）。
