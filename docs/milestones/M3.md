# M3 仓储库存数字化管理

项目名称：新乡海滨智能运营管理平台。

## 里程碑定位

M3 由 Owner 明确授权新开，目标是把仓库产品库存信息数字化，形成"产品—批次—货位"对应台账，并在此基础上支持批次查询、出库核销、效期预警、盘点导出、待检证与货位卡生成、货位二维码与手机扫码查询、入库拍照识别。

M3 与 M1（考勤）为并列里程碑，不替代、不阻塞 M1-FIX。

## 目标

1. 建立产品主数据与批次（批号、生产日期、有效日期）口径。
2. 建立货位编码体系，形成"产品—批次—货位"对应台账。
3. 支持按批号快速查询货位及数量。
4. 支持出库核销、效期预警、盘点导出。
5. 依据关键信息自动生成待检证、货位卡。
6. 生成货位二维码并支持手机扫码查询货位信息。
7. 支持入库拍照识别产品名称、批号、代码、日期，人工校对后入台账。

## 范围与不做事项

见 `docs/milestones/M3_START_GATE.md` 的"范围"和"门禁条件"章节。

核心边界：

- 不修改 Frappe / ERPNext / HRMS 核心源码。
- 未经 Owner 逐轮授权，不创建自定义 Frappe App、不创建 DocType、不启动独立前端、不接飞书真实写入。

方案核心：

- 门禁三项（部署位置 / 模型选型 / 数据留存与脱敏）**本质是同一个问题：标签照片能不能出内网**，属**合规决策而非技术决策**，须 Owner 拍板。
- 识别范围收敛：**AI 只负责 5 个字段**（产品名称 / 批号 / 产品代码 / 生产日期 / 有效期至）；入库时间由系统记录，货位号扫码录入（M3-R5 已落地），数量与操作人由系统或人工提供。
- 关键技术判断：这不是"固定版式表单识别"，而是"版式多样、需语义理解的标签识别"——实测 **94 个物料、自产/外购两套版式、中英混排、11 种单位**。因此 **OCR + 规则（方案 B）维护成本会随产品数增长**，多模态模型（方案 A）对版式变化更鲁棒。
- **推荐：先用方案 A 做 20–50 张样本试跑，量出准确率后再由 Owner 决定长期走 A 还是 C**（本地/内网部署）。避免拍脑袋。
- **核心工程价值：识别后端可插拔**——A / B / C 同一契约，切换不重写服务；把"数据出不出内网"变成配置问题。
- 环境现状（实测，影响方案 C）：承载环境是本机 Docker（非公司服务器），Apple M4 / 16GB / **无 NVIDIA GPU**；bench 内无 `cv2` / `paddleocr` / `torch` / `numpy`。**方案 C 目前没有可部署的硬件**。
- 沿用项目既有规范：`docs/team/05_开源代码二次开发与升级规范.md` 的**优先级 5（外部服务）**，FastAPI 为既定技术栈；接口契约含幂等键、超时重试、失败日志、权限边界（服务不直连数据库）。
- 人工校对为强制环节：返回每字段置信度，低置信度高亮，**识别结果不直接入账**；照片归档到 Frappe `Attach`，服务端不长期留存。
- 脱敏不适用：批号与代码正是识别目标，**脱敏即失去意义**，故"是否出内网"是二选一。

待 Owner 确认 6 项：照片是否出内网（核心）/ 选哪家服务 / 若无内网服务器则部署在哪 / 样本从哪来 / 准确率验收标准 / 使用范围（全产品还是原料药中间体先试点）。
