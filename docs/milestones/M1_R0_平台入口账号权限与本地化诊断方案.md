## 飞书登录目标定位

HBOS 的目标不是让员工维护一套新的账号密码体系。

目标是：飞书登录为主，HBOS 内部账号自动映射，Frappe 权限体系承接系统权限和审计。

- 飞书应作为员工侧主登录入口之一，优先级高于本地账号登录。
- 普通员工目标体验是：点击“飞书登录”或从飞书工作台进入 HBOS，即可完成登录。
- 不要求员工单独注册 HBOS 账号。
- 不要求员工记住 HBOS 本地密码。
- HBOS 内部 User 仍然需要存在，用于权限、审计、DocType owner、流程记录和操作追踪。
- HBOS User 应通过飞书身份自动创建、自动绑定，或由管理员批量预同步，而不是让员工手动创建。
- System Manager 等少量管理员账号保留本地账号密码登录能力，用于飞书故障、SSO 配置错误、权限事故时恢复系统。

## 账号体系设计

账号体系分为五层：

| 层级 | 对象 | 定位 |
| --- | --- | --- |
| 员工体验层 | 飞书账号登录 | 员工主要登录体验，不要求维护 HBOS 本地密码 |
| 平台身份层 | Frappe User | 系统登录主体，承载会话、owner、审计和权限入口 |
| 人事主数据层 | Employee | 员工主数据，承载公司、部门、岗位、在职状态、工号和考勤相关字段 |
| 权限控制层 | Role / Permission | 控制可见、可改、可审批、可导出和可管理范围 |
| 飞书身份映射层 | open_id / union_id / user_id | 连接飞书身份、HBOS User 和 Employee |

建议原则：

- Employee 作为员工主数据。
- User 作为登录账号和系统审计主体。
- User 与 Employee 必须建立稳定关联。
- 飞书身份映射应保存到受控字段或后续集成对象中，避免仅依赖姓名。
- 各业务模块不得重复造账号体系，不得绕过 Frappe User / Role / Permission。

目标流程：

- 入职：人事创建或导入 Employee；系统通过飞书身份自动创建 / 绑定 User，或由管理员预同步 User。
- 账号开通：普通员工优先通过飞书首次登录触发自动创建或绑定；高权限账号由管理员配置或审批。
- 调岗：Employee 部门 / 岗位变化后，同步调整 Department Manager、Attendance Manager 等角色或权限范围。
- 离职：Employee 标记离职后，应禁用对应 User 或撤销登录能力，并清理高权限角色。

账号类型差异：

- 本地管理员账号：保留本地登录密码，拥有系统维护与应急恢复能力，不作为普通员工体验。
- 普通员工账号：通过飞书登录进入，默认只获得 Employee / 普通员工权限。
- 人事账号：通过飞书登录或管理员配置进入，需额外授予 HR Manager / HR User 等权限。
- 部门主管账号：通过飞书登录进入，但主管权限必须由组织关系、管理员配置或受控同步规则授予。

## 首次飞书登录账号自动开通流程

目标流程：

1. 员工点击“飞书登录”，或从飞书工作台进入 HBOS。
2. 飞书返回授权用户身份。
3. 系统读取 open_id / union_id / user_id。
4. 系统查找是否已有绑定的 HBOS User。
5. 若已有绑定，则直接登录。
6. 若无绑定，则按规则查找 Employee。
7. 若能匹配 Employee，则自动创建或绑定 User。
8. 若不能匹配 Employee，则进入待审核、禁止登录或管理员补全流程。
9. 登录成功后按角色权限进入对应 Workspace。

身份匹配策略：

- 优先使用稳定 ID：union_id 或 user_id，具体取决于飞书开放平台能力和企业内应用场景。
- open_id 可用于单应用场景，但跨应用或长期统一身份时需要评估稳定性。
- 不建议仅用姓名匹配。
- 手机号、邮箱、工号可作为辅助匹配字段。
- Employee 应作为员工主数据，User 是登录账号，二者需要建立稳定关联。

权限开通策略：

- 普通员工首次登录后默认只获得 Employee / 普通员工权限。
- 人事、考勤管理员、部门主管等高权限角色不得仅凭飞书登录自动授予。
- 高权限角色必须由管理员配置、审批或通过受控通讯录规则同步。
- 离职、调岗、部门变更需要同步禁用或调整权限。

## 角色权限初版规划

| 角色 | 能看什么 | 能改什么 | 不能做什么 | 原生复用建议 | 是否需要海滨自定义角色 |
| --- | --- | --- | --- | --- | --- |
| System Manager / 系统管理员 | 全局配置、用户、角色、系统状态、关键 DocType | 系统配置、用户启停、权限配置、应急处理 | 不应直接代替业务人员录入考勤结论，不应绕过审批常态处理业务 | 直接复用 Frappe 原生 System Manager | 暂不需要，后续可增加运维只读角色 |
| HR Manager / 人事管理员 | Employee、Department、Company、Leave、Attendance、HR Workspace | 员工主数据、人事配置、HRMS 基础规则 | 不应修改系统底层配置，不应管理非 HR 模块全局权限 | 优先复用 HRMS / ERPNext 原生 HR Manager | 可能需要海滨 HR 管理边界角色 |
| HR User / 人事经办 | 员工、请假、考勤、部分报表 | 按职责录入和维护 HR 数据 | 不应审批自身敏感变更，不应配置系统角色 | 优先复用 HRMS 原生 HR User | 可能需要按岗位细分 |
| Attendance Manager / 考勤管理员 | Attendance、Employee Checkin、Shift Type、Shift Assignment、考勤报表 | 维护班次、导入测试打卡、处理考勤异常 | 不应管理薪资、系统设置、飞书密钥 | 先评估 HRMS 原生角色是否足够 | 很可能需要海滨自定义角色，但 M1-R0 不创建 |
| Department Manager / 部门主管 | 本部门员工、排班 / 考勤摘要、异常提醒、待办 | 审核本部门请假或异常，后续按流程确认 | 不应查看全公司敏感 HR 数据，不应配置全局规则 | 部分复用原生角色 + 权限规则 | 可能需要按部门范围自定义权限 |
| Employee / 普通员工 | 本人信息、本人考勤、本人请假、个人待办 | 提交个人申请，维护允许自助维护的信息 | 不应查看他人敏感信息，不应改考勤结果，不应授予角色 | 复用 Employee / Self Service 类权限思路 | 暂不需要，先用原生和权限规则验证 |
| Auditor / 审计或只读检查人员 | 关键业务记录、权限配置、审计线索、报表 | 原则上只读，可导出受控报表 | 不应修改业务数据，不应启停账号，不应配置系统 | 可用只读角色和报表权限组合 | 可能需要海滨审计只读角色 |

初版策略：

- 先复用 Frappe / HRMS 原生角色和 Permission。
- 对海滨特有的“部门范围”“考勤异常处理”“审计只读”等场景，先记录为后续自定义角色候选。
- M1-R0 不创建角色、不修改权限，只做规划。

## 飞书 SSO 可行性分析

本轮只做方案，不实现，不保存密钥，不写 `.env`。

### A. 推荐目标方案：飞书 OAuth / SSO 登录 + 自动创建或绑定 User + 关联 Employee

路径：

- 使用飞书 OAuth / SSO 登录作为员工侧主入口。
- 首次登录时读取飞书身份，查找 HBOS User 和 Employee。
- 已绑定则直接登录；未绑定但可匹配 Employee 时自动创建或绑定 User。
- 无法匹配时进入待审核、禁止登录或管理员补全流程。

优点：

- 符合员工体验目标，不让员工维护 HBOS 本地密码。
- Frappe User 仍保留，能承接权限、审计、owner 和流程记录。
- 后续可与飞书工作台入口、消息通知和通讯录同步衔接。

风险：

- 需要确认 Frappe Social Login / OAuth 能力与飞书 OAuth 参数、回调、用户信息接口的适配程度。
- 需要定义稳定身份字段和 Employee 匹配规则。
- 需要设计失败兜底和管理员审核流程。

### B. 过渡方案：管理员提前从飞书通讯录同步员工和 User，员工仍通过飞书登录

路径：

- 管理员先批量同步飞书通讯录、Employee 和 Frappe User。
- 员工登录时只做飞书身份校验和已绑定 User 登录。
- 高权限角色由管理员配置或按受控规则同步。

优点：

- 首次登录风险较低。
- 可以提前清洗手机号、邮箱、工号、部门和主管关系。
- 适合正式上线前的数据准备。

风险：

- 需要通讯录读取权限。
- 需要处理员工新增、离职、调岗的同步策略。
- 如果同步不及时，员工登录可能失败或权限滞后。

### C. 兜底方案：少量管理员保留本地账号密码登录

路径：

- System Manager、运维管理员等少量账号保留本地密码登录。
- 仅用于飞书故障、SSO 配置错误、权限事故和系统维护。
- 不作为普通员工主登录路径。

适用场景：

- 飞书 OAuth 不可用。
- 回调配置错误。
- 员工身份映射事故。
- 需要紧急禁用账号或回滚权限。

不推荐作为员工主方案：

- “员工先使用本地账号，再绑定飞书”只能作为历史迁移或管理员兜底方案。
- 新员工目标体验不应包含 HBOS 本地注册、设置密码或记住本地密码。

后续需要用户提供或确认：

- 飞书企业应用 `app_id`。
- 飞书企业应用 `app_secret`。
- redirect URL。
- 通讯录权限。
- 用户 ID 类型选择：open_id / union_id / user_id。
- 测试用户范围。
- 是否允许读取手机号、邮箱、工号、部门和直属主管。
- 首次登录无法匹配 Employee 时的策略：待审核、禁止登录或管理员补全。

安全要求：

- 真实飞书写入和通讯录读取必须用户明确授权。
- `app_secret` 不得提交仓库。
- 本轮不得写 `.env`。
- 本轮不得真实接入飞书。
- 本轮不得保存密钥。
- 本轮只做方案和诊断，不实现 SSO。

## 中文化 / 本地化诊断

用户反馈：ERPNext / Frappe / HRMS 即使设置语言后，仍有英文按钮和英文文本。

本轮只做诊断，不修改源码，不修改中文翻译源码。

可能原因：

- System Settings language 未统一设置，或仅设置了部分默认语言。
- 用户个人语言设置与系统语言不一致。
- 已安装 App 的翻译覆盖不完整。
- 自定义字段、Workspace、Report、Button、Action、Print Format 文案未翻译。
- Frappe / ERPNext / HRMS 原生中文包覆盖范围有限。
- 缓存或前端资源影响，导致语言切换后页面仍显示旧文案。
- 某些第三方前端资源或 HRMS 页面中的文本未走 Frappe 标准翻译链路。

后续诊断清单：

- 检查 System Settings language。
- 检查 Administrator 和测试用户的个人语言。
- 检查 Translation / Custom Translation 是否可用。
- 检查 Workspace、DocType label、字段 label、Report、Dashboard、Button 和 Action 文案。
- 检查 HR Workspace 与常用 HRMS 页面是否存在硬编码英文文本。
- 检查切换语言后是否需要 clear-cache、clear-website-cache 或前端资源刷新。
- 评估是否需要通过后续自定义 App 承载本地化覆盖，但不得直接修改 Frappe / ERPNext / HRMS 核心源码。

## 风险与决策点

| 风险 / 决策点 | 说明 | M1-R0 建议 |
| --- | --- | --- |
| 飞书 SSO 与 Frappe 原生 OAuth 适配风险 | 飞书 OAuth 参数、用户信息、回调和 Frappe Social Login 能力可能需要适配 | M1-R0 只做方案；实现前先做小范围技术验证 |
| HRMS 原生权限与海滨实际权限差异 | HRMS 原生角色可能无法完整表达部门范围、考勤管理员和审计只读边界 | 先复用原生角色，记录自定义角色候选 |
| 中文化覆盖不完整风险 | 原生中文包、Workspace、Report 和按钮文案可能覆盖不完整 | 先诊断，不改核心源码 |
| 直接改核心源码升级风险 | 修改 Frappe / ERPNext / HRMS 核心源码会影响升级、维护和排障 | 明确禁止，优先配置、Custom Translation、低代码和后续自定义 App |
| 过早创建自定义 App 风险 | 未验证原生能力前创建 App 会重复造轮子，造成边界混乱 | M1 初期不创建 `hb_attendance_app` |
| 飞书身份自动开通安全风险 | 自动创建 User 如果缺少审核和匹配规则，可能造成越权或错误开户 | 普通员工低权限自动开通，高权限必须审批或管理员配置 |
| 管理员兜底缺失风险 | 全量依赖飞书登录会在 SSO 故障时锁死系统 | 保留少量 System Manager 本地登录能力 |
