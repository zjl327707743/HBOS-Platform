## 二、出库放行门禁（核心）

### 2.1 业务规则

**出库须有 QA 出具的放行手续与合格证，缺任一项不可出库。**（Owner 明确）

### 2.2 实现方式

新增 `hb_inventory_app/hbos_inventory/release_gate.py`，通过 `hooks.py` 的 `doc_events` 挂在**出库单据的 `before_submit`**。

选择 `before_submit` 而非 `validate` 的原因：草稿仍可自由保存与修改，仅在**提交**时拦截，不阻断备货过程。

### 2.3 判定范围（有意收窄）

| 单据 | 是否门禁 | 理由 |
| --- | --- | --- |
| `Delivery Note`（非退货） | **门禁** | 销售发货路径，属真正出库 |
| `Stock Entry` 且 `purpose = Material Issue` | **门禁** | 非销售领用 / 出库路径 |
| `Stock Entry`（Material Receipt） | 不门禁 | 待检物料本就该能入库 |
| `Stock Entry`（Material Transfer） | 不门禁 | 库内 / 货位间流转，含移入不合格品库 |
| `Delivery Note`（is_return） | 不门禁 | 退货是入库方向 |

### 2.4 批次取法

优先取明细行 `batch_no`；取不到则回落到 `serial_and_batch_bundle` 查 `tabSerial and Batch Entry`。

依据 M3-R1 实测结论：ERPNext v16 中 `Stock Ledger Entry.batch_no` 为空列，批次数据实际在 `Serial and Batch Bundle` / `Serial and Batch Entry`（详见 M3-R1 主文档第四节）。

### 2.5 校验逻辑

对涉及的每个批次读取 `Batch.hbos_release_status` 与 `Batch.hbos_certificate_no`：

- 状态须为 **`已放行`**；
- 合格证编号须**非空**。

任一不满足即中止提交，并给出明确提示，例如：

> 以下批次未取得 QA 放行手续或合格证，不可出库：
> `TEST-M3R1-B002`（放行状态为「待检」、无合格证编号）
> 请先在批次上录入放行状态（已放行）、放行日期与合格证编号后再提交。

### 2.6 验证结果（通过）

| 场景 | 预期 | 实测 |
| --- | --- | --- |
| 待检批次出库核销 | 拦截 | **已拦截**，提示准确 |
| 已放行批次出库核销 | 通过 | 通过（`MAT-STE-2026-00005`） |
| 待检批次内部移库 | 不拦 | 通过（未触门禁） |
| 待检批次入库 | 不拦 | 通过（未触门禁） |

## 四、效期预警报表

新增脚本报表 **`效期预警`**。

**数据源**：`Serial and Batch Entry` 关联 `Serial and Batch Bundle`（同「按批号查货位」）。

**筛选**：预警天数（默认 90）、是否含已过期、货位、物料、放行状态。

**列**：紧急度 / 剩余天数 / 有效期至 / 生产日期 / 物料代码 / 物料名称 / 批号 / 货位 / 数量 / 单位 / 效期类型 / 放行状态。

**紧急度分级**：`已过期` → `紧急（≤30 天）` → `关注（≤90 天）` → `正常`。

**效期类型**列取自 `Item.hbos_shelf_life_type`（复检期 / 有效期），对应 Owner 确认的"按产品种类区分，且分复检期与有效期两类"。

**验证**：以 `TEST-M3R1-B003`（有效期 = 今天 + 20 天）验证，报表正确返回该批次、剩余 20 天、紧急度「紧急（≤30 天）」。

## 五、库级盘点三对账报表

新增脚本报表 **`库级盘点三对账`**，对齐仓库现有纸质《物料及产品盘存记录》的口径。

**筛选**：库位 / 货位（可勾选含下级）、物料。

**列**：库位 / 物料代码 / 物料名称 / 批号 / 单位 / **ERP数量** / **货位卡数量** / **实物数量** / **差异（实物-ERP）** / 有效期至 / 放行状态。

**关键口径**：

- **按库位盘点**，不细到货位——与盘存表实际列结构一致（盘存表无货位号列）。
- **ERP数量由系统给出**（`Serial and Batch Entry` 聚合）；
- **货位卡数量与实物数量不来自系统**（分别是纸质卡记录与实盘结果），故**留空**，由现场在导出的 Excel 中填写；差异列同理。

使用流程：运行报表 → 用 Desk 报表右上角「导出」导出 Excel → 现场填写两列 → 比对差异。

**验证**：对 `3904 六车间中间库`（含下级）运行，正确返回 4 行（3 个批次分布于 3 个货位），ERP 数量正确，货位卡 / 实物列为空。

### 6.1 实现过程中踩到的两个坑（已修复，供后续复用）

1. **`Desktop Icon.link_to` / `sidebar` 必须指向已存在的 `Workspace Sidebar`**，否则抛 `LinkValidationError`。修正为指向同名工作台侧边栏。
2. **配色取值受限**：`Desktop Icon.bg_color` 仅允许 `gray` / `blue`（不是 green）；`Workspace Shortcut.color` 亦有固定枚举。初版用 `green` / `Orange` / `Grey` 导致 migrate 失败，已改为合法值。

### 6.2 ⚠ 入口缺陷更正（2026-09-23，Owner 验收发现）

Owner 报「点进去会跑到库存模块，桌面又找不到仓储库存工作台、回不来」。核查后确认**两个独立缺陷**，其中第二个是**桌面上一个入口都没有**的直接原因。

#### 缺陷一：顶层图标与 ERPNext 原生 Stock 撞图

顶层图标用了 **`stock`**——与 **ERPNext 原生 Stock 模块图标完全相同**。桌面上两个一模一样的方块并排，点错即进原生库存模块；而**原生模块没有本 App 的侧边栏**，用户回不来。

**已修**：`DESKTOP_ICON` 改为 **`warehouse`**。

#### 缺陷二：桌面图标被 Frappe **静默丢弃**（这是主因）

`frappe/desk/doctype/desktop_icon/desktop_icon.py` 的 `get_desktop_icons()` 有**两条容易踩空、且失败时完全不报错**的规则：

```python
# 规则 A：图标 label 必须能在 bootinfo 的侧边栏映射里查到
sidebar = bootinfo.workspace_sidebar_item.get(s.label.lower())
permitted = bool(sidebar and sidebar["items"])

# 规则 B：父图标不在放行集合里，挂在它下面的图标也一起出不来
user_icons = [s for s in permitted_icons
              if not s.parent_icon or s.parent_icon in permitted_parent_labels]
```

本 App 当时踩的是：

| 踩空点 | 事实 | 结果 |
| --- | --- | --- |
| **规则 A** | 图标 label 是 `仓储库存`，但侧边栏叫 `仓储库存工作台` → 映射里查不到 | 图标被丢弃 |
| **规则 B** | 后续想补的 `仓储库存工作台` 条目 `parent_icon = 仓储库存`，而父图标已被规则 A 丢掉 | **连工作台条目也一起被过滤** |

**净效果：桌面上一个入口都没有。** 而且两条规则都不抛异常、不打日志，只表现为「图标就是不出现」——所以第一次核查时误判成「图标没生效」，改错了方向。

**已修**：`DESKTOP_LABEL = WORKSPACE_TITLE`，让 **工作台 / 侧边栏 / 桌面图标三者同名**（与 ERPNext 原生 `Stock` 的做法一致）；并在 `_sync_desktop_icon()` 里**显式 `icon.parent_icon = ""`**——已存在的文档会带着旧值，不覆盖就残留（这一条是修完第一次仍不见效的原因）。

#### 顺带清理

删掉陈旧的 `仓储库存` 图标（不指向任何侧边栏、永远不显示，但会让挂在它下面的图标一起消失）。

#### 根因

`hb_attendance_app` 有 `tests/test_workspace_contract.py` 把「入口必须可达」锁住，本 App **当时没建对应测试**，缺陷一路带到验收。

#### 验证

用**真实的 boot 流程**复现验证（不是只看数据库）：

```
get_bootinfo() → get_desktop_icons('Administrator', bootinfo)

桌面可见图标数: 46 → 47
含 仓储库存工作台: True
  → {label: 仓储库存工作台, icon: warehouse, link_type: Workspace Sidebar, parent_icon: '', hidden: 0}
```

> ⚠ **第一次验证是无效的**：当时直接调 `get_desktop_icons()` **没传 bootinfo**，
> 而 `if bootinfo:` 为假时 `permitted_icons` 恒为空 —— 于是输出「一个都不显示」，
> 得出了错误结论。**验证桌面图标必须走 `get_bootinfo()`**，这个坑记在这里。

契约测试扩到 **9 条**，新增「label 必须等于侧边栏名」「`parent_icon` 必须显式清空」「陈旧图标必须清理」三条——改回去就红。

**未在真实浏览器验证**（需登录）。Owner 可用直达链接确认：`http://192.168.0.179:8080/app/仓库工作台`。

### 6.3 改名：`仓储库存工作台` → `仓库工作台`（2026-09-23，Owner 指示）

Owner 要求把名字改短、并换一个图标。

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 名称（三者同名） | `仓储库存工作台` | **`仓库工作台`** |
| 图标 | `warehouse` | **`boxes`** |

**改名不是单纯的字符串替换**：`Workspace` / `Workspace Sidebar` / `Desktop Icon` 的
`name` **都等于标题**，换标题等于**换主键**——旧记录不会自动消失。

留下的旧 `Desktop Icon` 会变成 6.2 节说的那种**僵尸图标**：label 在侧边栏映射里查不到
→ 被 `get_desktop_icons()` 静默丢弃（不显示但记录还在），而**挂在它下面的图标会跟着一起消失**。
所以新增 `_cleanup_legacy_objects()`，在同步**之前**按
`图标 → 侧边栏 → 工作台` 的顺序删掉历史标题下的对象；删图标前先解除子图标的
`parent_icon` 指向，避免留下悬空引用。

历史标题登记在 `LEGACY_TITLES = ("仓储库存工作台", "仓储库存")`,
**只删登记过的名字**，不做泛化清理，避免误伤其他 App。

> 本节 6.1 / 6.2 的正文保留了当时的原名（那是历史记录）；**当前名称为「仓库工作台」**。
> `docs/` 其余提到该入口处已同步改名。

**改名后补修的一处遗漏（2026-09-23 同日）**：改名时同步改了拍照识别页的 `.js`
（返回按钮 → `Workspaces/仓库工作台`），**但没推该页 `.json` 的 `modified`**，
于是浏览器侧的缓存永远不失效——服务端明明下发了新页，用户看到的仍是旧按钮
（指向已不存在的旧路由）。已推版本戳并 `bench migrate` 修掉。
**教训与同类修复详见 `M3_R6_入库拍照识别服务方案.md` 第九批。**
