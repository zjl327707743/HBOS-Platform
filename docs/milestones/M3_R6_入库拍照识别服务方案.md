## 二、业务背景与识别目标

### 2.1 识别字段（Owner 在 M3-R0 已明确）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 产品名称 | 是 | 支持人工修正 |
| 批号 | 是 | 查询核心索引，需确保准确 |
| 产品代码 | 是 | 与物料主数据（SAP 8 位代码）匹配 |
| 生产日期 | 否 | 标签含此字段时识别 |
| 有效期至 | 否 | 用于效期预警 |
| 入库时间 | 是 | **由系统自动记录拍照上传时间**，不从标签识别 |
| 货位号 | 是 | 手动选择或扫码（**扫码页已在 M3-R5 落地**） |
| 入库数量 | 是 | 人工填写，按货位分别记录 |
| 操作人 | 是 | 当前登录账号 |
| 标签照片 | 是 | 留存原始凭证便于追溯 |

即：**AI 只负责 5 个字段**（产品名称、批号、产品代码、生产日期、有效期至），其余由系统或人工提供。

### 2.2 标签的实际复杂度（决定技术选型的关键）

从 M3-R2 的实测数据看，标签版式差异很大：

| 维度 | 情况 |
| --- | --- |
| 来源 | 有**自产**与**外购**两套版式；但**本识别只做自产**（见下） |
| 产品数 | 5 个库位合计 **94 个物料代码** |
| 语言 | 中文为主，部分含英文（USP / EP / JP / CEP 等药典后缀） |
| 批号格式 | 三类结构（原料药/中间体、混粉含拼音首字母、亚批带 `-1/-2`），还有外购的**原厂批号 + 进厂批号**双批号 |
| 物料代码 | 8 位数字，但**前缀语义需按库位区分**（1100 包材 / 120x 辅助用品等） |
| 单位 | 11 种（KG / 个 / 套 / 瓶 / 支 / 双 / 卷 / 张 / L / BT） |

**结论：这不是"固定版式的表单识别"，而是"版式多样、需要语义理解的标签识别"。**

这一点直接决定了方案优先级——详见第四节。

> **识别范围（Owner 已明确）**：**只做自产**。
> 外购物料到货时**已有现成的待检证与货位卡**，**不经过本识别流程**，
> 因此外购标签不在识别范围内，也无需取样测试。

## 三、三个候选方案

### 方案 A：云端多模态大模型 API

把标签照片上传到云端**视觉语言模型**，模型直接返回结构化 JSON（含各字段与置信度）。

| 优点 | 缺点 |
| --- | --- |
| 对**版式变化鲁棒**——不需要为每种标签写规则 | **照片离开内网** |
| 直接输出**结构化字段**，不是文字块 | 按次计费；依赖外网与第三方可用性 |
| 无需 GPU，建设最快 | 识别结果稳定性受模型版本影响 |
| 能"理解"语义（如分辨哪个是批号、哪个是代码） | 需确认服务商条款（是否用于训练、留存多久） |

### 方案 B：云端专用 OCR API（百度 / 腾讯 / 阿里等）

只做**文字识别**，返回文本行；字段结构化需自己写规则。

| 优点 | 缺点 |
| --- | --- |
| 便宜、快、印刷体准确率高 | **照片同样离开内网** |
| 通用文字识别成熟 | **返回的是文字块，不是字段**——需为每种版式写解析规则 |
| | 维护成本**随产品数增长**（94 个物料） |
| | 无法判断"这个数字是批号还是代码" |

### 方案 C：本地 / 内网部署开源模型

在**公司内网**部署（PaddleOCR，或量化的本地多模态模型如 Qwen-VL）。

| 优点 | 缺点 |
| --- | --- |
| **照片不出内网**——对药企合规最友好 | **需要 GPU 服务器**（见 3.1 现状） |
| 长期无按次费用 | 部署与调优工作量大 |
| 可离线运行 | 准确率需实测；版式变化时需自行迭代 |
| | 需长期运维投入 |

### 3.1 部署环境实测（方案 C 的前提）

Owner 已定：**暂不采购服务器，先部署在这台 Mac**（Mac mini M4）。实测约束如下：

| 项目 | 实测值 | 影响 |
| --- | --- | --- |
| 硬件 | Apple **M4**，**16 GB** 统一内存，无 NVIDIA GPU | 可用 Metal / CPU，**不能用 CUDA** |
| Docker 虚拟机内存上限 | **7.7 GB** | Frappe 全栈已占用其中约 0.8 GB |
| 宿主机内存 | 当前空闲约 **49%**；系统压缩器已占约 6.3 GB | **内存是主要瓶颈**，模型需选小的 |
| 容器访问宿主机 | `host.docker.internal` → `192.168.5.2` **可解析** | ✅ **验证通过**：FastAPI 可原生跑在 Mac 上，Frappe 容器能直接调用 |
| bench 内可用依赖 | 仅 `requests`、`PIL`；无 `cv2` / `paddleocr` / `torch` / `numpy` / ML 框架 | ML 依赖须装在**独立服务**里，不污染 Frappe |

**架构结论**：识别服务**原生运行在 Mac 上**（而非塞进 Frappe 容器），原因：

1. 容器是 Linux arm64，**拿不到 Metal 加速**，模型只能跑 CPU，慢；
2. 模型依赖重（torch / paddle），塞进 backend 会显著拖慢 Frappe；
3. `host.docker.internal` 已验证可达，通信无障碍。

**风险提示（须 Owner 知悉）**：这台是**开发机**，且 16 GB 内存同时承载 Frappe 全栈 + 本地模型**偏紧**。作临时验证可行，**不适合长期作为生产服务**——一旦 Mac 休眠或内存吃紧，仓库端拍照入库会中断。正式使用前建议采购一台内网服务器（M3 之外）。

## 四、方案 C 下的两条实现路线

照片不出内网既然已定，A / B 出局。剩下的问题是：**本地怎么识别**。两条路线：

### 路线 C1：本地多模态模型

在 Mac 上跑量化的视觉语言模型（如 Qwen2.5-VL-3B / 7B 的 4-bit 量化版），走 **MLX**（Apple 官方推理框架，能吃满 M4 的 Metal 与神经网络引擎）。

| 优点 | 缺点 |
| --- | --- |
| 直接输出**结构化字段**，不吃版式差异 | 16 GB 内存下只能跑小模型；**小模型在密集小字标签上会漏读/串行** |
| 能分辨"哪个是批号、哪个是代码" | 需下载数 GB 模型权重 |
| 换版式不改代码 | 单张耗时较长（数秒） |

### 路线 C2：本地 OCR + 结构化规则 + **主数据约束匹配**

用 **PaddleOCR**（本地、CPU 可跑、成熟）识别文字，再做三层加工：

1. **格式规则**：批号有**三类已知结构**（M3-R0 已确认）；物料代码是**8 位数字**；日期是日期格式。用格式把候选筛出来。
2. **主数据约束匹配**（关键杠杆）：本厂物料代码是**已知的 94 个**（且会随 SAP 主数据增长）。OCR 出的乱码可以**按编辑距离匹配到最近的合法代码**——"1300O215"（字母 O）自动纠正为 "13000215"（数字 0）。
3. **位置与版式线索**：同一来源的版式相对固定，字段位置可作为辅助。（本识别只做自产，故只需吃透自产版式）

| 优点 | 缺点 |
| --- | --- |
| 内存占用小（1–2 GB），CPU 即可 | 需**针对版式写解析规则** |
| 印刷体文字识别准确率高 | 版式一变要改规则（**但只两套版式**） |
| 可解释——出错能看出错在哪一步 | 规则维护有长期成本 |
| **主数据约束能纠错**，这是纯 OCR 没有的 | |

### 4.1 推荐：**两条路线都实现，用同一测试集比，看数据选**

理由：

- **都在本地，成本很低**——不像 A vs C 那样涉及"要不要买机器"，本轮没有额外代价；
- 服务骨架本就设计为**识别后端可插拔**，多实现一个后端只是多一个类；
- 这正是本方案的核心工程价值：**把选型变成可测量的实验，而不是拍脑袋**。

**先量后决**：两个后端跑同一批样本，产出一张准确率对照表，Owner 看着数字定。

### 4.2 无论选哪条，都要套一层"约束校验"

这一点独立于 C1 / C2，是**准确率的放大器**：

- **物料代码 → 形近字母纠错**（`O`→`0`、`l`→`1`、`S`→`5`、`B`→`8` …）+ 8 位长度校验 + 纯数字校验。**因代码全为数字，此步无需主数据即可纠正绝大多数 OCR 错字**（详见 7.8 八）；
- 批号 → 三类结构格式校验，格式不符就**标红**；
- 日期 → 日期格式与合理区间校验。

即：**模型负责"读"，规则负责"筛"，人负责"定"**。这样即使原始识别率只有 90%，**经约束校验后能进人工确认环节的字段可用率会显著更高**。

### 4.3 后端可插拔（不变的设计）

```
POST /recognize  →  { fields: {...}, confidence: {...} }
```

C1 / C2 乃至将来换模型，都实现同一契约。**服务骨架不因选型变化而重写。**

## 五、架构与集成方式（沿用项目既有规范）

`docs/team/05_开源代码二次开发与升级规范.md` 已确立**优先级 5：外部服务**的做法，且明确 FastAPI 为外部服务技术栈。本方案完全沿用：

```
┌──────────────────────┐   HTTP (JSON)   ┌────────────────────────┐
│  hb_inventory_app     │ ───────────────→ │  拍照识别服务            │
│  (Frappe 容器)         │ ←─────────────── │  (FastAPI，原生跑在 Mac) │
└──────────────────────┘   结构化 JSON     └────────────────────────┘
        │                                              │
        └── host.docker.internal（实测可达）───┘        └── 照片不出内网
```

### 5.1 接口契约（草案）

**请求**：`POST /api/v1/recognize`
- `image`：图片（multipart 或 base64）
- `hints`（可选）：已知线索，如 `source_type`（自产/外购）

**响应**：

```json
{
  "ok": true,
  "request_id": "…",
  "backend": "c1_local_vlm",
  "fields": {
    "product_name": "…",
    "item_code": "…",
    "batch_no": "…",
    "manufacturing_date": "YYYY-MM-DD",
    "expiry_date": "YYYY-MM-DD"
  },
  "confidence": { "product_name": 0.98, "batch_no": 0.71, "item_code": 0.95 },
  "validated": { "item_code_matched": true, "batch_no_format_ok": false },
  "raw_text": "…"
}
```

**工程要求**（依 `docs/AI技能路由规范.md` 对 API / 集成开发的要求）：

- 明确的**接口契约**，字段命名与 M3 已落地的对齐（`item_code` / `batch_no` / `manufacturing_date` / `expiry_date`）；
- **超时与重试**：识别为耗时操作，需设合理超时；
- **幂等键**（`request_id`），避免重复识别产生重复台账；
- **失败记录**：识别失败落日志，便于排查；
- **权限边界**：服务**不直连数据库**，只收图片返结果，落库由 Frappe 侧负责。

### 5.2 人工校对（Owner 明确要求）

- 返回**每字段置信度**；
- Frappe 侧录入界面**高亮低置信度字段**，提示复核；
- **识别结果不直接入账**，必须经操作人确认后才写入；
- 保留 `raw_text` 与照片，便于追溯是"识别错"还是"人工改错"。

### 5.3 标签照片留存

- 照片保存在 Frappe（`Attach`，本司内网），挂在批次或入库单据上作原始凭证；
- **识别服务端不长期保存照片**（识别后即释放）。

## 六、数据留存与脱敏规则

Owner 已定**照片不出内网**，因此规则大幅简化——**不需要再考虑服务商条款、跨境传输、是否用于训练**：

| 项目 | 规则 |
| --- | --- |
| 照片是否出内网 | **不出**（Owner 已定）。这是本方案最关键的合规边界 |
| 服务端留存 | **识别后即释放，不落盘**（仅内存处理） |
| 照片归档 | 保存到 Frappe `Attach`，随批次 / 单据走 |
| 服务日志 | **不记照片内容、不记批号与产品名**；只记 `request_id` / 耗时 / 成功失败 / 错误类型 |
| 出网能力 | 识别服务**不开任何外网访问**（不下载模型之外的流量；模型权重一次性预下载） |
| 脱敏 | **不适用**——批号与代码正是识别目标，脱敏即失去意义 |

## 七、识别准确率验收标准（Owner 授权本轮制定）

### 7.1 为什么不能只定一个总准确率

5 个字段的**重要性和难度差异很大**：批号错了找不到货，产品名称错了能从代码回填。因此**分字段定标准**，并额外设**安全底线**与**性能线**。

### 7.2 字段级标准（模型原始输出 vs 人工标注真值）

| 字段 | **及格线** | **目标** | 定这个数的理由 |
| --- | --- | --- | --- |
| **批号** | **≥ 95%** | ≥ 98% | **核心查询键**——错了就定位不到货，是整个系统的主索引 |
| **物料代码** | **≥ 95%** | ≥ 98% | 须与 SAP 主数据严格一致，错了会记到错误产品上 |
| **生产日期** | ≥ 90% | ≥ 95% | 效期推算的时间基准 |
| **有效期至** | ≥ 90% | ≥ 95% | 效期预警的直接依据 |
| **产品名称** | ≥ 85% | ≥ 95% | 容错最高——**可由物料代码从主数据自动回填**，识别错了也能纠正 |

### 7.3 单据级标准（整张标签）

| 指标 | 及格线 | 说明 |
| --- | --- | --- |
| **5 个字段全部正确** | **≥ 80%** | 即 5 张里有 4 张"拍照后可直接确认入账" |

### 7.4 安全底线（硬性，不可放宽）

这两条比准确率更重要——**它们决定错误会不会被人发现**：

| 指标 | 要求 | 为什么 |
| --- | --- | --- |
| **高置信度错误率** | **≤ 1%** | 批号 / 代码被认错、**但模型给出高置信度（≥0.9）** 的比例。这类错误**不会触发人工复核**，是最危险的失败模式 |
| **低置信度召回率** | **≥ 90%** | 真实出错的字段中，至少 90% 被标为低置信度。即"**模型知道自己不确定**" |

> 通俗说：允许模型不会，**不允许模型自信地错**。

### 7.5 性能线（本地 Mac 承载）

| 指标 | 要求 |
| --- | --- |
| 单张识别耗时 | **≤ 10 秒**（P95） |
| 连续运行 | **100 张无崩溃、无内存泄漏** |
| 并发 | 支持 **1–2** 人同时使用（仓库场景，非高并发） |

### 7.6 测试集要求（标准的前提，缺一不可）

没有合格的测试集，上面的数字都没有意义：

| 要求 | 说明 |
| --- | --- |
| 规模 | **≥ 50 张**真实标签照片 |
| 真值 | **人工逐字段标注**（这是最费工的一步，但必须做） |
| 覆盖来源 | **只需自产**（外购到货时已有现成的待检证与货位卡，不走本识别流程） |
| 覆盖语言 | 含英文后缀（USP / EP / JP / CEP）的与纯中文的都要有 |
| 覆盖产品 | **≥ 10 个不同产品**，含原料药 / 中间体 / 混粉 / 成品 |
| 覆盖拍摄条件 | 正拍 / 斜拍 / 反光 / 轻微磨损或褶皱，模拟现场真实情况 |
| 存放 | **不进 Git**，放仓库工作区之外（含真实批号与产品名） |

### 7.7 验收结论怎么用

两个后端（C1 / C2）跑**同一测试集**，产出一张对照表：

| 后端 | 批号 | 物料代码 | 生产日期 | 有效期 | 产品名称 | 全字段正确 | 高置信度错误 | 单张耗时 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| C1 本地 VLM | ? | ? | ? | ? | ? | ? | ? | ? |
| C2 OCR+规则 | ? | ? | ? | ? | ? | ? | ? | ? |

**达标者入选；两个都达标选内存占用低、耗时短的；都不达标则如实报告，不硬上**（此时可退回复核：是否采购内网服务器跑更大的模型）。

### 7.8 仓库实地取样清单（可直接照做）

Owner 已确认：**样本只能去仓库实地获取**。取样需要专门跑一趟仓库，因此把清单写细，**争取一趟拿全、不返工**。

#### 一、数量与覆盖（目标 ≥50 张）

| 维度 | 要求 | 理由 |
| --- | --- | --- |
| 总数 | **≥50 张**（最低可用 30 张，但结论置信度下降） | 样本太少，准确率数字没有统计意义 |
| 自产 : 外购 | 各约一半 | 两套版式差异大，都要覆盖 |
| 产品数 | **≥10 个不同产品** | 单产品测不出换产品的鲁棒性 |
| 种类 | 覆盖原料药 / 中间体 / 混粉 / 成品 | 批号三类结构各要出现 |
| 语言 | 含英文后缀（USP / EP / JP / CEP）与纯中文都要 | 英文混排是识别难点 |
| 单位 | 尽量含件类单位（包材 / 备品） | M3-R2 实测有 11 种单位 |

#### 二、同一标签多拍（**关键**）

对**至少 3 个代表产品**，每个拍 **4 张不同条件**的：

1. **正对、光线好** —— 理想情况，作为准确率上限
2. **斜拍**（偏 15–30 度）
3. **有反光或有阴影**
4. **标签有褶皱 / 磨损 / 局部遮挡**

**为什么要这组**：现场拍摄条件不可控。这组能测出「**理想 vs 现实**」的准确率落差——落差大，说明必须强化人工校对与约束校验；落差小，说明可以放心用。

#### 三、就按现场真实方式拍

- 用**仓库实际要用的那部手机**，不要用专业相机
- **不要打光、不要修图、不要把标签摆正**
- 拍到什么算什么 —— 这才是真实输入

#### 四、命名约定（省后期人力）

建议 `来源-产品代码-序号.jpg`，例：`自产-1300****-01.jpg`。命名里带产品代码，后期标注与核对快很多。

#### 五、⚠ 同时把真值填了（**最重要的效率建议**）

**不要等回来对着照片猜真值** —— 那时人已离开标签，看不准。

在现场**拍一张、填一行**，用手机备忘录或纸质表格都行：

| 文件名 | 品名 | 物料代码 | 批号 | 生产日期 | 有效期至 |
| --- | --- | --- | --- | --- | --- |

**理由**：真值必须以**标签上实际印的字**为准，**不是以系统里的为准**。要测的正是"印在照片上的能不能读对"——如果拿系统数据当真值，就测不出标签本身的识别难度了。

#### 六、存储与安全

- 照片与真值表**都含真实批号与产品名**
- **绝不提交 Git**；放**仓库工作区之外**（如 `~/Documents/M3R6样本/`）
- 真值表虽被 `.gitignore` 覆盖（`*.csv` / `*.xlsx`），**仍建议不要放进仓库目录**

#### 七、回来后

把目录路径告知，即可跑两个后端、产出准确率对照表（见 7.7）。

#### 八、附带依赖：C2 的约束匹配**不需要主数据清单**

**Owner 补充：物料代码是全数字的，不存在含字母的情况。**

这一条**大幅简化了 C2 的实现**。关键洞察：

**"全数字"本身就是一个极强的约束——不需要 94 个合法代码的清单。**

OCR 最常见的错误是把数字认成**形近字母**：

| 真实数字 | 常被误认成 |
| --- | --- |
| `0` | `O`、`o`、`D` |
| `1` | `l`、`I`、`i` |
| `5` | `S`、`s` |
| `8` | `B` |
| `6` | `G`、`b` |
| `2` | `Z`、`z` |
| `4` | `A` |

既然**代码只可能是数字**，就可以**无条件把字母映射回形近数字**：

```
1300O215  →  13000215     （O → 0）
13O00215  →  13000215
130002l5  →  13000215     （l → 1）
l3000215  →  13000215
13OOO215  →  13000215
```

**这不需要知道任何合法代码是什么，纯按字符映射就能纠。** 比"编辑距离匹配到最近合法代码"更简单、更稳、不依赖主数据。

**因此 7.8 第八节原先写的三个方案（从盘存表提清单 / 实时查 Frappe / 先不匹配）全部不需要。**

补充规则（同样不需要主数据）：

- **长度校验**：代码固定 **8 位**，纠完长度不对就标红；
- **纯数字校验**：纠完仍含字母，说明是别的字段被误读进来了，标红；
- 主数据匹配（"这 8 位数是不是真的存在"）**降级为可选项**——即便做了，也只是"提示这个代码尚未建档"，不是识别正确性的判据。

**同一手法可推广到批号**：批号虽含字母（生产线前缀），但**字母与数字各自的位置有规律**（按三类批号结构），也可做形近纠错。不过批号的难度高于代码，C2 对批号主要靠**格式校验 + 低置信度标记**，纠错为辅。

### 验证中发现并修复的一个真实缺陷

**问题**：`_attach_photo` 原先只用 `file_url` 定位 `File` 记录——

```python
frappe.get_doc("File", {"file_url": file_url})   # ← 有歧义
```

而**内容相同的两次上传会产生两条 `File` 记录共用同一个 `file_url`**（FRAPPE 的存储层去重）。此时按 `file_url` 取会拿到不确定的那一条，**可能把别人已挂的附件改挂走**。

**验证**：修复后新草稿挂到正确的 `File` 记录（`J4: True`），且**旧草稿的附件未被抢走**（`J5` 确认仍在）。

> 这个缺陷在真实使用中很难触发——仓库每张标签照片都不同，不会出现同内容去重。但既然发现了就修掉了。

### ⚠ 这张表的数字**不能**读成「汉字识别准确率」（2026-09-21 Owner 核对后补充）

Owner 对着真实标签照片核对后指出「很多汉字都是错的」——**是对的**。
上表容易被误读，必须在这里说清：

**① 5 个字段里 4 个是数字**（批号 / 物料代码 / 生产日期 / 有效期至），
**只有「品名」是汉字**。所以 **94.4% 主要衡量的是数字，不是汉字**。
拿它当「OCR 认字准不准」的证据是**错误口径**。

**② 标签上大量汉字从未进入这个指标**——公司名、生产车间、储存条件、
操作人/日期、运输注意事项等，都不在这 5 个字段里，错了也不扣分。
而**它们恰恰是错得最多的**（见下）。

**③ 错误集中在「小字印刷」与「手写」**，大字基本正确。Owner 逐字核对一张真实标签的结果：

| 标签上印的 | OCR 读成 | 类型 |
| --- | --- | --- |
| `操作人/日期` | 只读到 `作` | 小字印刷，漏读 |
| `Pharmaceutical Co., Ltd` | `heraceutical Co., Ltd` | 英文小字 |
| `六车间B线车间` | `过果线` / `HEB`（同一行两种读法） | 中文小字 |
| 手写人名 + 日期 | `早420511.07` | 手写 |
| `【贮藏】` | 丢字，只剩 `有效` | 小字印刷 |
| `13000520`（某一遍） | `13W8520` | 数字认成字母 `W` |

**④ 数字的高分还被「冗余」撑高**：物料代码在标签上印 2~3 遍，
抽到的那一遍读对即记为「命中」，**读错的那些遍不扣分**。
所以 98% 的含义是「**至少有一遍读对了**」，不是「每次都能读对」。

**⑤ 校验层救不了这类错**：`13000520 → 13W8520` 是把数字读成字母 `W`，
而校验层的形近字符表里**没有 W**（只有 O/D/Q/I/l/Z/A/S/G/B/g/q/T 等），
该遍直接判为无效。能对上，靠的是另一遍印的读对了。

**结论（影响后续工作的两条）**：

- **报告口径改为「分大小字」**：不再给单一「准确率」。分档实测见下「九之五·二」；
- **`储存条件` / `生产车间` / `供货单位` 等小字汉字字段，从设计上就不该指望 OCR**。
  拍照识别页已把这些标成「**须人工填写**」（2026-09-21 改），不是「可补」。

**⑥ 换更大模型解决不了这个**：`medium` 档实测**同一张图小字一样错**
（`heraceutical` 那个错两档完全相同），耗时却从 8 s 涨到 35 s。
真正的瓶颈是**小字的成像质量**（分辨率 / 对焦 / 反光），属「**怎么拍**」的问题，
不是「用哪个模型」的问题。

### 九之五·三、品名抽取规则修复（2026-09-21）

**起因**：Owner 报「识别汉字的正确率太低了」，给的例子是
**「品名」读成「名」**、**「美罗培南」读成「美罗第南」**。

**先分清两件事**（这决定了能修什么）：

- **原始识别文本读错字**（`美罗培南 → 美罗第南`）——这是**模型能力上限**，
  改规则救不了。但它在**抽取层被挡住**：`美罗培南` 在标签上印 2~3 遍
  （`50.txt` 里第 2 行读成 `美罗第南`、第 18 行读成 `美罗培南`），
  锚定规则取到的是**读对的那一遍**。实测 `50.txt` 最终 `品名` 是**正确的**。
- **抽取规则自己造出来的错**——**这个能修，而且确实错了。**

**逐张核对后，抽取规则查出三个真缺陷**（都只在 `small` 档暴露，命中 5 张里的 4 张）：

| # | 缺陷 | 证据 | 后果 |
| --- | --- | --- | --- |
| ① | **值里含 ASCII 就把整条丢掉** | 真值 `美罗培南 (B)`，OCR 读出 `美罗培南（B）`，因含字母 `B` 被判无效 | 把**读对的答案扔了**，再退化到频次法抓回一串噪声（`防水、防潮，轻拿、轻放，`） |
| ② | **标签与值被切成两行时取不到** | `1.txt` 是「`品`」「`名：`」「`美罗培南`」**三个独立的框**；旧正则要求冒号后至少一个字符（`.+`），这种标签**根本不被识别成标签** | 值永远取不到，退化到频次法 |
| ③ | **频次法没有长度下限** | 标签上没读到品名时，它从残渣里挑 2~5 字的碎片交差：`避免硫碰。`、`存新件`、`合证` | **把「没读到」谎报成「读到了」**，操作员看到的是凭空冒出来的品名 |

**③ 是最有害的一条**：前两条只是「没取到」，③ 是**编一个答案**。

**修法**：

- ① 判据从「含 ASCII 就丢」改成**看汉字占比 ≥ 50%**，容忍「（B）」这类少量 ASCII；
- ② 正则的值部分改为**允许为空**，为空时**往后回看最多 3 行**取第一个像品名的；
  **撞上任何带冒号的行就停**（否则会把 `生产批号：` 当成品名——实测踩到过）；
- ③ 频次法加**汉字长度下限 4**（本厂品名 `美罗培南` / `美罗培南混粉` 都在 4 字以上）。
  **宁可返回 None**：主数据那层会把品名补上，让人照标签核对，
  也远好过给一个错的。

**效果（`small` 档，50 张）**：

| | 品名准确率 | 错答 | 空 |
| --- | ---: | ---: | ---: |
| 修前 | 90%（45/50） | **4** | 1 |
| 修后 | **92%（46/50）** | **0** | 3 |

**百分比只涨了 2 个点，但真正变的是「错答归零」**：修前那 4 处错答里
**3 处是规则编出来的**（`避免硫碰。`、`存新件`、`合证`），现在全部变成诚实的「空」。
剩下 3 处空（`4` / `10` / `12`）是 OCR **确实没读到品名**（真值 `美罗培南混粉` 在原文里
根本不出现），这 3 张由 `_enrich_from_master` **用物料主数据补上**，操作员看到的名字仍然正确。

> 第 4 处原「错答」是 `13`：OCR 读 `美罗培南（B）`、真值 `美罗培南 (B)`——
> **字全对，只是全角/半角括号之差**，不是误读。严格逐字符比会判错，
> 全半角归一后计为命中（上表按严格口径）。

**这一修对 `tiny`/`medium` 没有帮助**：那两档的失败是**真的读错字**
（`美罗信网混粉`、`携件人中期`、`自丽代城`、`美罗培南湿粉`、`美罗老`），
规则层挡不住——再次印证**瓶颈在成像，不在规则**。

**单测**：新增 4 条覆盖上述三个缺陷（切两行的标签、含 ASCII 括号的品名、
回看不越界取字段名、频次法下限返回 None），总数 89 → **93 条全通过**。

| 批号 | ≥95% | **100%** | ✅ 达标 |
| 物料代码 | ≥95% | **98%** | ✅ 达标 |
| 生产日期 | ≥90% | **94%** | ✅ 达标 |
| 有效期至 | ≥90% | **96%** | ✅ 达标 |
| 产品名称 | ≥85% | **92%** | ✅ 达标 |
| **全字段正确** | ≥80% | **84%**（42/50 张） | ✅ 达标 |
| **单张耗时** | ≤10 s | medium 35 s → **small 实测 7.0~9.0 s（均 8.1 s）** | ✅ **已达标（换模型档位，见下）** |
| 高置信度错误 ≤1% | — | — | ⚠ **无法测量** |
| 低置信度召回 ≥90% | — | — | ⚠ **无法测量** |

**accuracy 全部达标。** 耗时起初不达标（medium 35 s），已通过**换轻量模型档位**解决（small 实测 7~9 s、均 8.1 s），详见下文「模型档位对照」。

最后两项测不了的原因：C2 是"OCR + 规则"，**没有逐字段置信度**这个概念——
`confidence` 目前返回空字典。要满足这两条，要么让 C2 输出 OCR 逐行置信度并映射到字段，
要么改用 C1（VLM 天然给置信度）。**这是选型时绕不过去的一条。**

### 发现并修复的三个真实缺陷

**① 只到月的日期被整条丢弃（最严重）**

实测 **39/50 张**标签的有效期**只印到月**（如「2028年11月」），日根本没印。
原校验层只认三种成分齐全的日期，这类值**直接返回 None**——三分之二的有效期会丢。

修复：补成**当月最后一天**，并在 `hints` 里明说「日是按月末推定的，请核对」。

> 取月末而非月初，是为了不把效期提前一个月——否则还能用的批次会被预警先拦下。

**Owner 已确认（2026-09-16）**：按月末推定；并明确**不加「粒度」字段**——
系统存的就是月末那天，不再区分标签原本印到月还是印到日。

由此产生一处**已知取舍**（如实记录）：打印件（待检证 / 货位卡）会把
`2028年6月` 呈现为 `2028-06-30`，比标签原印信息更细；
因不加粒度字段，系统无法在打印时还原原粒度。

**② 签核日期顶掉生产日期**

标签上有「操作人/日期」「复核人/日期」两类**人员签核日期**。它们与物料日期
混在一起参与「取最早作生产日期」的判断，导致某张标签的复核日期（被 OCR 误读成
`2021.06.27`）把真正的生产日期挤到了"有效期"位置上。

修复：含「操作人 / 复核人 / 核发人 / 签名」的行**不进日期候选**。

> 副作用要如实记录：有 1 张的效期由**「读错」变为「留空」**。
> 按"命中"计不增不减，但**留空比读错安全**——空会促使人补录，读错会静默污染效期预警。

**③ C2 后端按 2.x 写的，在 3.x 上完全失效**

PaddleOCR 3.x 删掉了 `use_angle_cls` / `show_log` 参数与 `.ocr(path, cls=)`，
且返回结构从嵌套列表变成 dict 风格的 `OCRResult`（文本在 `rec_texts`）。
已按 3.x 重写 `_flatten` / `_extract`，并保留 2.x 结构的兼容分支。

### 剩余 10 处未命中的根因（已逐张核对识别原文）

| 根因 | 处数 | 例子 |
| --- | ---: | --- |
| **OCR 读错或漏读** | 8 | 代码少读一位（`1300090`，缺末位）；生产日期 `2024.08.01` 读成 `08.03`；品名行整行未读出 |
| 规则误配 | 2 | 见上①之外的「取最早」边界，已修 |

**结论：剩余误差主要是 OCR 本身的能力上限，不是规则没写好。**
继续提高只能换更强的识别模型（C1），或接受现状 + 人工校对。

### 性能实测（重要，影响选型）

| 分辨率 | 单张耗时 | 小字（有效期）是否还能读对 |
| --- | --- | --- |
| 4096×3072（原图） | **约 35 s** | 能 |
| 3200 px | 22 s | 开始丢 |
| 2000 px | 10 s | **读错**（如 2028.11 读成 2005.12.2） |

**不能用降分辨率提速**——有效期是小字，降了就废。

> 说明：35 s 是**单张热启动识别**的耗时，含 PaddleOCR 对 4096×3072 大图的检测与识别。

### 模型档位对照（耗时问题的正解）

降分辨率这条路走不通，但 **PaddleOCR 自带多档模型**——换档**不需要装任何新依赖**，
只是换个模型名。用同一批 50 张实测：

| 档位 | 单张耗时 | 品名 | 代码 | 批号 | 生产日期 | 有效期 | **全字段** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `medium` | **35 s** | 92% | 98% | 100% | 94% | 96% | **84%** |
| `small` ← **选用** | **8 s** | 90% | 98% | 100% | **94%** | 90% | **80%** |
| `tiny` | **3 s** | 88% | 94% | 96% | 84% | 80% | 72% |

**`small` 是唯一的帕累托最优点**：耗时压进 10 s 标准线（实测 7.0~9.0 s，均 8.1 s，**且全部低于 10 s**），全字段正确率只比 `medium` 低 4 个点。
`tiny` 虽然更快，但有效期掉到 80%、全字段 72%，**不值得**。

**决定：默认档位改为 `small`。** 换档能力已做成配置（`c2_ocr:small` / `HBOS_OCR_C2_MODEL`），
随时可切回 `medium`。

### 一处必须如实记录的诊断更正

`small` 与 `medium` 的差异，**初判为"small 会编造日期"**——依据是两张标签的
生产日期分别输出成 `2026-09-30`、`2026-08-31`，而真值是 9月7日、8月10日，
看起来像是把日编成了月末。

**逐张核对识别原文后，这个判断是错的。** 真实原因是两类：

1. **漏读日**——`small` 只读出了「2026年09月」，**日被整个漏掉**。
   于是**本层的月末推定逻辑**替它补了 30 / 31。
   **那个日是"我们"补的，不是模型编的**，而且原文里确实只有年月，无从判别。
2. **取错日期**——有标签上存在多个日期，`small` 挑了另一个（如把登记号里的
   `2020.11.07` 当成生产日期）。这个日期**确实印在标签上**。

两类都**不是编造**，且都**拦不住**（数字在原文里找得到，或日是我们按规则补的）。

**由此发现一个真问题并已修复**：提示语原本写「**标签只印到月**（2026年9月），
已按月末推定日」——但标签上其实印了日，是模型漏读。**这句话在对着人撒谎**，
会让人误以为标签上真没有日。已改为：

```
识别只读到了年月（2026年9月），已按**月末**推定日；若标签上其实印了日，请按标签填写
```

说的是"我们读到了什么"，不是"标签上印了什么"——**这一点必须分清**。

> 量化：`small` 全 50 张里，模型只读到年月的场合共 39 处，
> 其中**标签确实只到月 37 处**、**标签其实印了日 2 处**（即上面那两个）。
> `medium` 的对应数字是 38 / 0。

### 修复：生产日期被噪声顶掉（第四批的后续修正）

**发现方式**：Owner 授权做实地演示时，样本 A 的输出里生产日期是 `2020-11-07`，
而真值是 `2025年6月25日`——**而且 `needs_review` 是 False，没有任何警告**。

**根因**（逐张调识别原文核对）：标签上出现了三个日期

```
2020.11.07   ← OCR 把某段印刷内容切出来的噪声
2025.06.25   ← **真正的生产日期，模型读对了**
2028.06.24   ← 有效期
```

旧规则是「**取最早**当生产日期」——于是噪声被当成了生产日期，
**读对的正确值反被扔掉**。而且这个日期格式合法、原文里确实有这串数字，
**任何格式校验都拦不住**。

**这是规则错，不是模型能力不足。** 先前"剩余误差主要是 OCR 能力上限"的归因**据此更正**：
重新逐条归因后，日期类失败 9 处里有 **4 处是规则选错**（可修）、5 处是模型没读出来。

**修法**：改用**保质期常识**筛噪。本厂标签效期 2~3 年，那么"离效期 5 年以上"的日期
当生产日期就不合常理，判为噪声剔除；剩下的候选里再取最早。全被剔光时退回不筛，
宁可给个日期也不弄丢。

> 中途试过另一种改法——"取早于有效期的最晚一个"——**实测反而更差**
> （生产日期 92% → 86%），因为它会选到靠近生产日期的另一个噪声日期。
> 已弃用，改回极值法 + 保质期筛。

**效果**：生产日期 **92% → 94%**（修好样本 A，其余样本无回归），
整体 **94.0% → 94.4%**。补 4 条单测覆盖该规则（含"全被剔光不能丢日期"的边界）。

### 日期溯源校验（保险，非修复）

本批还加了一道校验：**识别出的日期，其数字必须真的出现在识别原文里**，
否则清空转人工。

VLM 的典型失效模式正是凭空生成一个格式合法、原文里却没有的日期。

不夸大它的作用，也不假装它解决了什么问题。

## 九之六、执行记录（第五批：入库后自动生成货位卡与待检证）

**背景**：M3-R4 做了三个 Print Format，但**只能在 `Batch` 表单上手动点打印**；
M3-R6 做了拍照识别入口能生成草稿入库单，但**入库完就断了**，仓库还得自己去找批次逐个打印。
本轮把两截接上。

| 产物形式 | **合并成一个 PDF**（一次打印出一套） |
| 触发范围 | **所有 Material Receipt 入库单**（不限拍照识别建的） |

### 已交付

| 文件 | 说明 |
| --- | --- |
| `hbos_inventory/doc_gen.py`（新建） | 生成本体：渲染、合并、挂附件、防重复、防阻断 |
| `hooks.py`（改） | `Stock Entry.on_submit` 挂 `generate_for_stock_entry`；注册 `doctype_js` |

### 设计要点

- **为什么挂在 `on_submit`**：`frappe/model/document.py` 的 `compose()` **先跑控制器方法、再跑 doc_events 钩子**，
  所以 ERPNext 的 `StockEntry.on_submit`（建 SLE）跑完才轮到本模块——货位卡的货位明细、
  入库数量、入库日期、流水表**都能查到真实数据**。生成草稿时这些**都还不存在**。
- **一个批号只出一张卡**：同一批次可能拆成多行（不同货位），按批次去重后再生成（M3-R0 已定「一卡一批」）。
- **失败不阻断入库**：`on_submit` 抛异常会**回滚整个提交**。生成 PDF 是附加动作，
  绝不能因为渲染失败让人入不了库。故整段吞异常、记 `Error Log`，
  并在界面上**如实提示哪几个批次失败、去批次页点按钮补生成**。
- **不堆附件**：生成前按文件名精确匹配删掉上一份（`HBOS-<批号>-待检证+货位卡.pdf`），
  **人工上传的附件名字不会长这样，动不到**。amend 重提也不会越堆越多。

### 顺带修复：M3-R4/R5 的纸型缺陷（重要）

做本例时发现，M3-R4 三个格式与 M3-R5 的货位二维码**在手动点打印时全都按 A4 出**——
模板里写的 `@page { size: 75mm 110mm }` **被 wkhtmltopdf 忽略**。
M3-R4/R5 当时验的是「能不能出 PDF」，**没验纸型与页数**。

另有一个更隐蔽的：Frappe 打印框架会注入

```css
.print-format { min-height: 11.69in; padding: 0.75in }   /* 11.69in = 297mm，A4 高 */
.print-format td { padding: 6px !important }
```

`min-height: 297mm` 是**给 A4 屏幕预览**设计的，放在 75×110mm 的纸上必然溢出成 2 页——
**跟模板写得好不好无关**。

**修法**（已实施，`HBOS待检证`）：纸型改声明在 `.print-format` 上——
Frappe 会读这几个 CSS 属性并传给 wkhtmltopdf（见 `frappe/utils/pdf.py::read_options_from_html`）。
**注意 margin 必须用长写法**，简写不会被读取。

```css
.print-format {
    page-width: 75mm; page-height: 110mm;
    margin-top: 4mm; margin-bottom: 4mm; margin-left: 5mm; margin-right: 5mm;
    min-height: 0 !important; max-height: none !important;
    max-width: none !important; padding: 0 !important;
}
.print-format td, .print-format th { padding: 2px 3px !important; }
```

修复后实测：待检证手动打印 **1 页 75×110mm**；两张货位卡 **1 页 A4 无回归**。

### 同批修复：货位二维码小标签（M3-R5 遗留）

同样加了纸型声明后，二维码**纸型对了（60×40mm）但内容仍溢出**（实测需约 60mm）。
根因有两层：

1. `hbos_bin_qr_svg` 生成的内联 SVG 自带 `520×520`（≈138mm），
   而模板里写的 `svg { width: 26mm }` **在 wkhtmltopdf 里不生效**；
2. 标签内容本身就偏多——URL 行（109 字符）换行后占了约 8mm。

**修法**（已实施）：

- `qr_utils.hbos_bin_qr_svg` 新增 `size_mm` 参数，**把尺寸写进 SVG 的 width/height 属性**；
- 尺寸定为 **20mm**（该标签可用高约 34mm，20mm 刚好放得下「码 + 货位号 + 提示」）；
- **去掉 URL 文本行**——内容已在二维码里，小标签上印长 URL 既不可读又占地方；
- **去掉 `name` 行**——实测 `hbos_bin_code` 恒等于 `warehouse_name`，
  那个 `{% if %}` 永假、从未渲染，是死代码。

修复后实测（**全量，非抽样**）：**224 个货位 / 库位的标签全部为 1 页 60×40mm**，
渲染出的 SVG 带的是 `width="20mm" height="20mm"`（不再是自带的 520×520 像素）。
同批回归另三个格式，均无回归：待检证 1 页 75×110mm、自产货位卡 1 页 A4、外购货位卡 1 页 A4。
**这四项都是走「手动点打印」那条路验的**（不注入任何覆盖 CSS，纸型完全由模板自己声明决定）——
自动生成那条路由 `doc_gen.py` 显式传参，是另一条路。

> 验证方式：`frappe.get_print(..., as_pdf=False)` 取 HTML → `get_pdf()` → 用 `pypdf`
> 读每页 `mediabox` 实际物理尺寸（不是看模板里写了什么）。

### 一个必须知道的操作坑

**改完 `hooks.py` 必须清缓存，新钩子才生效。** 第一次跑验证时钩子完全没触发（附件 0 个），
`bench clear-cache` 之后立刻正常。同类地，改 Print Format 的 app 文件后要让
`modified` 比库里新，`bench migrate` 才会重新导入（标准 Print Format 不能直接改库）。

### 标签原文：为什么要可编辑、并且要存下来

OCR 会读错字（实测把「贮藏：避免硫碰」读成过品名）。**只读展示的话，操作员看得到错但改不了**，
校对就成了走过场。所以逐行拆成输入框。

校对后的文本存到 `Batch.hbos_label_text`（新增 Long Text 字段，空行与行首尾空白自动去掉）。
理由是**照片与文字各有各的用处**：

| | 照片（已有） | 校对后的原文（本批新增） |
| --- | --- | --- |
| 地位 | **原始凭证**，挂在入库单上 | **转录件** |
| 能不能搜 | **不能**——要人眼一张张翻 | **能**——文字可以检索、可以比对 |

**它不参与打印**（已实测：待检证与两张货位卡上都不出现）。只是给日后查证留一条可检索的线索。

### 六个必须知道的实现要点

做这一批时踩到/避开的坑，都写进代码注释了，此处汇总：

1. **子表不能用 `frappe.db.set_value` 写**。`db.set_value` 对 Table 字段会发出
   `UPDATE tabBatch SET hbos_packaging = ...`，MariaDB 直接报「未知列」。
   必须走 `frappe.get_doc()` → `append()` → `save()`。顺带 `save()` 也跑一遍
   `Batch.validate()`，是好事。
2. **包装构成必须「替换式」而非「追加式」**。`hbos_packaging_count` /
   `hbos_packaging_spec`（print_utils.py）都是**汇总求和**的——同一批次重复入库若只
   `append`，件数会翻倍、包装规格会重复打印。故先 `set("hbos_packaging", [])` 再写。
3. **「仅补空」不能用「先读再写」**。那有 TOCTOU 竞态：两个操作员同时给同一物料入库、
   都读到空，后提交的就会覆盖前者，与承诺矛盾。改成把「为空」写进 `WHERE` 条件、
   用 `ROW_COUNT()` 确认是否真写了。实测：先到者留下，后到者不覆盖。
4. **`SELECT` 值要先校验**。`hbos_shelf_life_type` 是 Select，裸 SQL / `set_value` 都
   不走校验，非法值会直接进主数据。已用 `frappe.get_meta` 读 options 比对。
   容器类型、件数 > 0 同理（在 `_parse_packaging` 里）。
5. **裸 SQL 不走 Frappe 的文档缓存失效**，需显式 `frappe.clear_document_cache()`；
   且**不产生 Version 记录**，主数据会改得无声无息——故补写一条 `Comment` 留痕。
6. **品名这个输入框原本是假的**。页面渲染了可编辑的「产品名称」，但**从未把它传给
   后端**；而打印取的是 `Item.item_name`，`Batch.item_name` 又是 `fetch_from` 快照、
   已有批次不会重取。也就是说操作员改了它**什么也不会发生**。已改为**只读对照展示**
   （「标签上读作 X」vs「主数据中 Y」），把认错的风险摆出来，而不是假装可改。
   > 顺带发现：`Item.item_name` 并非必填，为空时**两个货位卡的品名会印成空白**。
7. **改了页面 `.js`，浏览器不一定看得到（这个坑真踩了）。**
   第一次改完页面，操作员反馈「人工校对还是老样子」。排查后确认**服务端下发的一直是新
   `.js`**（`Page.load_assets()` 每次请求都**从磁盘重读**，实测 22063 字符、内容正确），
   卡在**浏览器端**：

   Frappe 会把整个 Page 定义（含 script / style）**缓存进 `localStorage`**，键为
   `_page:<name>`。除非 `frappe.boot.developer_mode` 为真，**它一律读缓存、不发请求**：

   ```js
   // frappe/views/pageview.js:23
   } else if (localStorage["_page:" + name] && frappe.boot.developer_mode != 1) {
       frappe.model.sync(JSON.parse(localStorage["_page:" + name]));   // ← 读缓存，改文件无效
   ```

   而缓存的失效**只认 `Page` 记录的 `modified`**，不认 `.js` 文件的改动
   （`frappe/desk.js:345` 的 `sync_pages()`：`page_info[name].modified != p.modified` → 才 `delete`）。

   **所以：改了页面 `.js` / `.css` 之后，必须把 `.json` 里的 `modified` 也推新、再 `bench migrate`。**
   本批一开始漏了这一步，`.json` 的 `modified` 还停在 2026-09-14，于是无论改多少遍 `.js`，
   浏览器拿到的都是缓存里的旧版本。已把该文件的 `modified` 推新并迁移验证。

   > 与本批第 6 条（Print Format 要推 `modified` 才会被 `migrate` 重导）是**同一类陷阱**：
   > Frappe 这套文件，**内容变了不等于元数据变了**——凡是有缓存的环节，都得把版本戳一起推。

## 十、风险与注意事项

| 风险 | 说明 | 应对 |
| --- | --- | --- |
