## 一、门禁三项待确认（本轮方案的核心）

`docs/milestones/M3_START_GATE.md` 规定，进入 M3-R6 前必须确认三项：**部署位置、模型选型、数据留存与脱敏规则**。

因此本轮方案先把这个决策摆出来，再给技术选项。

## 二、业务背景与识别目标

### 2.1 识别字段（Owner 在 M3-R0 已明确）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 产品名称 | 是 | 支持人工修正 |
| 批号 | 是 | 查询核心索引，需确保准确 |
| 产品代码 | 是 | 与物料主数据（SAP 8 位代码）匹配 |
| 生产日期 | 否 | 标签含此字段时识别 |
| 有效期至 | 否 | 用于效期预警 |
| 入库时间 | 是 | **由系统自动记录拍照上传时间**，不从标签识别 |
| 货位号 | 是 | 手动选择或扫码（**扫码页已在 M3-R5 落地**） |
| 入库数量 | 是 | 人工填写，按货位分别记录 |
| 操作人 | 是 | 当前登录账号 |
| 标签照片 | 是 | 留存原始凭证便于追溯 |

即：**AI 只负责 5 个字段**（产品名称、批号、产品代码、生产日期、有效期至），其余由系统或人工提供。

### 2.2 标签的实际复杂度（决定技术选型的关键）

从 M3-R2 的实测数据看，标签版式差异很大：

| 维度 | 情况 |
| --- | --- |
| 来源 | **自产**与**外购**两套版式 |
| 产品数 | 5 个库位合计 **94 个物料代码** |
| 语言 | 中文为主，部分含英文（USP / EP / JP / CEP 等药典后缀） |
| 批号格式 | 三类结构（原料药/中间体、混粉含拼音首字母、亚批带 `-1/-2`），还有外购的**原厂批号 + 进厂批号**双批号 |
| 物料代码 | 8 位数字，但**前缀语义需按库位区分**（1100 包材 / 120x 辅助用品等） |
| 单位 | 11 种（KG / 个 / 套 / 瓶 / 支 / 双 / 卷 / 张 / L / BT） |

**结论：这不是"固定版式的表单识别"，而是"版式多样、需要语义理解的标签识别"。**

这一点直接决定了方案优先级——详见第四节。

## 三、三个候选方案

### 方案 A：云端多模态大模型 API

把标签照片上传到云端**视觉语言模型**，模型直接返回结构化 JSON（含各字段与置信度）。

| 优点 | 缺点 |
| --- | --- |
| 对**版式变化鲁棒**——不需要为每种标签写规则 | **照片离开内网** |
| 直接输出**结构化字段**，不是文字块 | 按次计费；依赖外网与第三方可用性 |
| 无需 GPU，建设最快 | 识别结果稳定性受模型版本影响 |
| 能"理解"语义（如分辨哪个是批号、哪个是代码） | 需确认服务商条款（是否用于训练、留存多久） |

### 方案 B：云端专用 OCR API（百度 / 腾讯 / 阿里等）

只做**文字识别**，返回文本行；字段结构化需自己写规则。

| 优点 | 缺点 |
| --- | --- |
| 便宜、快、印刷体准确率高 | **照片同样离开内网** |
| 通用文字识别成熟 | **返回的是文字块，不是字段**——需为每种版式写解析规则 |
| | 维护成本**随产品数增长**（94 个物料、自产/外购两套版式） |
| | 无法判断"这个数字是批号还是代码" |

### 方案 C：本地 / 内网部署开源模型

在**公司内网**部署（PaddleOCR，或量化的本地多模态模型如 Qwen-VL）。

| 优点 | 缺点 |
| --- | --- |
| **照片不出内网**——对药企合规最友好 | **需要 GPU 服务器**（见 3.1 现状） |
| 长期无按次费用 | 部署与调优工作量大 |
| 可离线运行 | 准确率需实测；版式变化时需自行迭代 |
| | 需长期运维投入 |

### 3.1 当前环境现状（实测，影响方案 C 可行性）

| 项目 | 现状 |
| --- | --- |
| 承载环境 | **本机 Docker（开发机），非公司服务器** |
| 硬件 | Apple **M4**，内存 **16 GB**，**无 NVIDIA GPU** |
| bench 内可用依赖 | `requests`、`PIL`；**无** `cv2` / `paddleocr` / `torch` / `numpy` / `onnxruntime` |
| 内网服务 | 目前仅有本机容器；**无公司内网服务器** |

**含义**：方案 C 目前没有可部署的硬件。要走 C，需先解决"部署在哪台机器"——这是 M3 之外的基础设施问题。

## 四、推荐方案

### 4.1 推荐：**先用方案 A 做小样本试跑，用数据决定长期方案**

具体分两步：

**第一步（M3-R6 本轮）**：搭好 FastAPI 服务骨架（模型后端**可插拔**），用**少量真实标签样本**（建议 20–50 张，覆盖自产/外购、中文/英文、不同产品）跑通链路，**测量识别准确率**，产出数据。

**第二步（Owner 决策后）**：拿到准确率数据后，Owner 再决定长期走 A 还是 C。因为：

- 走 A 的判断依据是"准确率够用且能接受照片出内网"；
- 走 C 的代价是"需要一台 GPU 机器 + 调优周期"——**这个代价值不值，取决于 A 的准确率到底差多少**。

先量后决，避免拍脑袋。

### 4.2 为什么推荐 A 而不是 B

**B 的核心问题不是准确率，是"返回的不是字段"。** 标签版式多样（自产/外购、94 个物料、中英混排），OCR 只给文字块，**必须为每种版式写解析规则**，且版式一变就要改规则——**维护成本随产品数上升**。

A 直接输出结构化字段，对版式变化天然鲁棒，更贴合"94 个物料、两种来源"的现实。

### 4.3 关键设计：模型后端**可插拔**

服务内抽象出识别后端接口，A / B / C 三种实现同一契约：

```
POST /recognize  →  { fields: {...}, confidence: {...} }
```

这样**从 A 切到 C 不需要重写服务**，只换一个后端实现。这是本方案的核心工程价值——**把"数据出不出内网"变成配置问题，而不是重写问题**。

## 五、架构与集成方式（沿用项目既有规范）

`docs/team/05_开源代码二次开发与升级规范.md` 已确立**优先级 5：外部服务**的做法，且明确 FastAPI 为外部服务技术栈。本方案完全沿用：

```
┌──────────────────┐   HTTP (JSON)   ┌─────────────────────┐
│  hb_inventory_app │ ───────────────→ │  拍照识别服务         │
│  (Frappe App)     │ ←─────────────── │  (FastAPI)           │
└──────────────────┘   结构化 JSON     └─────────────────────┘
```

### 5.1 接口契约（草案）

**请求**：`POST /api/v1/recognize`
- `image`：图片（multipart 或 base64）
- `hints`（可选）：已知线索，如 `source_type`（自产/外购）、期望的物料代码

**响应**：

```json
{
  "ok": true,
  "request_id": "…",
  "fields": {
    "product_name": "…",
    "item_code": "…",
    "batch_no": "…",
    "manufacturing_date": "YYYY-MM-DD",
    "expiry_date": "YYYY-MM-DD"
  },
  "confidence": {
    "product_name": 0.98,
    "batch_no": 0.71,
    "item_code": 0.95
  },
  "raw_text": "…"
}
```

**工程要求**（依 `docs/AI技能路由规范.md` 对 API / 集成开发的要求）：

- 明确的**接口契约**与字段命名（与 M3 已落地的字段对齐：`item_code` / `batch_no` / `manufacturing_date` / `expiry_date`）；
- **超时与重试**：识别为耗时操作，需设合理超时，失败可重试；
- **幂等键**（`request_id`），避免重复识别产生重复台账；
- **失败记录**：识别失败要落日志，便于排查；
- **权限边界**：服务**不直连数据库**，只接收图片、返回识别结果；数据落库由 Frappe 侧负责。

### 5.2 人工校对（Owner 明确要求）

- 服务返回**每字段置信度**；
- Frappe 侧录入界面**高亮低置信度字段**，提示人工复核；
- **识别结果不直接入账**，必须经操作人确认后才写入；
- 错识别的留痕：保留 `raw_text` 与照片，便于追溯是"识别错"还是"人工改错"。

### 5.3 标签照片留存

- 照片保存在 Frappe（`Attach`），挂在批次或入库单据上，作原始凭证；
- **服务端不长期保存照片**（见 6.2）。

## 六、数据留存与脱敏规则（建议，待 Owner 确认）

### 6.1 照片里有什么

标签照片含**真实产品名称、批号、物料代码、供应商**。这属于**供应链业务数据**，不是个人隐私数据——但仍是公司资产。

### 6.2 建议规则

| 项目 | 建议 |
| --- | --- |
| 服务端照片留存 | **识别后即释放，不落盘**（仅内存处理）；如需排查，最多保留 7 天且仅限管理员 |
| 照片归档位置 | 保存到 **Frappe 的 `Attach`**（本司内网），随批次/单据走 |
| 服务日志 | **不记录照片内容、不记录识别出的批号与产品名**；只记 `request_id` / 耗时 / 成功失败 / 错误类型 |
| 出内网的字段 | 若走方案 A：**整张照片**会出内网（无法只传字段——字段就是识别结果） |
| 服务商条款 | 需确认：**是否用于模型训练**、留存时长、是否跨境传输 |
| 脱敏 | **不建议对标签图像做脱敏**——批号与代码正是识别目标，脱敏即失去意义。因此**"是否出内网"是二选一，不能靠脱敏折中** |

### 6.3 这一条必须 Owner 拍板

**"标签照片能不能传到公网 API"是合规决策，不是技术决策。** 本方案给出选项与代价，但不替 Owner 决定。

## 七、M3-R6 交付边界（待授权确认）

**计划做**：

- 编写 FastAPI 服务骨架（含可插拔的识别后端抽象、接口契约、幂等键、失败日志）。
- 实现**一个**后端（默认建议云端多模态模型，或按 Owner 选择）。
- Frappe 侧：拍照上传入口 + 识别结果**人工校对**界面 + 低置信度高亮 + 确认后写入。
- 照片归档到 Frappe `Attach`。
- 用**少量真实标签样本**实测准确率并产出数据。

**不做**：

- 不做批量导入 / 批量识别；
- 不做离线队列与断网续传；
- 不自动创建 `Item`（识别到的未知物料只提示，不擅自建主数据）；
- 不做识别结果**自动入账**（必须人工确认）；
- 不改动 M3-R1~R5 已交付的货位、台账、打印、扫码功能；
- 不修改 Frappe / ERPNext / HRMS 核心源码；
- 不接飞书真实写入；
- 不启动独立前端。

## 九、风险与注意事项

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **数据合规** | 照片出内网可能触碰公司保密要求 | 必须 Owner 明确授权后才实施；方案 C 为合规兜底 |
| 识别准确率不达预期 | 标签版式复杂、可能反光/倾斜/磨损 | 强制人工校对；先小样本量测；低置信度高亮 |
| 依赖外网 | 云端 API 不可用时无法拍照入库 | 保留**人工录入**通道作为降级路径（M3-R2 已具备） |
| 混淆批号与代码 | 两者都是数字串，外购还有双批号 | 提示 `source_type`；高亮低置信度 |
| 成本 | 云端按次计费 | 先小样本估算单张成本，再评估全年量级 |
| 服务运维 | 新增一个服务需长期维护 | 保持服务**无状态**，便于重启与迁移 |
