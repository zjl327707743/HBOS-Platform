## 二、业务背景与识别目标

### 2.1 识别字段（Owner 在 M3-R0 已明确）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 产品名称 | 是 | 支持人工修正 |
| 批号 | 是 | 查询核心索引，需确保准确 |
| 产品代码 | 是 | 与物料主数据（SAP 8 位代码）匹配 |
| 生产日期 | 否 | 标签含此字段时识别 |
| 有效期至 | 否 | 用于效期预警 |
| 入库时间 | 是 | **由系统自动记录拍照上传时间**，不从标签识别 |
| 货位号 | 是 | 手动选择或扫码（**扫码页已在 M3-R5 落地**） |
| 入库数量 | 是 | 人工填写，按货位分别记录 |
| 操作人 | 是 | 当前登录账号 |
| 标签照片 | 是 | 留存原始凭证便于追溯 |

即：**AI 只负责 5 个字段**（产品名称、批号、产品代码、生产日期、有效期至），其余由系统或人工提供。

### 2.2 标签的实际复杂度（决定技术选型的关键）

从 M3-R2 的实测数据看，标签版式差异很大：

| 维度 | 情况 |
| --- | --- |
| 来源 | **自产**与**外购**两套版式 |
| 产品数 | 5 个库位合计 **94 个物料代码** |
| 语言 | 中文为主，部分含英文（USP / EP / JP / CEP 等药典后缀） |
| 批号格式 | 三类结构（原料药/中间体、混粉含拼音首字母、亚批带 `-1/-2`），还有外购的**原厂批号 + 进厂批号**双批号 |
| 物料代码 | 8 位数字，但**前缀语义需按库位区分**（1100 包材 / 120x 辅助用品等） |
| 单位 | 11 种（KG / 个 / 套 / 瓶 / 支 / 双 / 卷 / 张 / L / BT） |

**结论：这不是"固定版式的表单识别"，而是"版式多样、需要语义理解的标签识别"。**

这一点直接决定了方案优先级——详见第四节。

## 三、三个候选方案

### 方案 A：云端多模态大模型 API

把标签照片上传到云端**视觉语言模型**，模型直接返回结构化 JSON（含各字段与置信度）。

| 优点 | 缺点 |
| --- | --- |
| 对**版式变化鲁棒**——不需要为每种标签写规则 | **照片离开内网** |
| 直接输出**结构化字段**，不是文字块 | 按次计费；依赖外网与第三方可用性 |
| 无需 GPU，建设最快 | 识别结果稳定性受模型版本影响 |
| 能"理解"语义（如分辨哪个是批号、哪个是代码） | 需确认服务商条款（是否用于训练、留存多久） |

### 方案 B：云端专用 OCR API（百度 / 腾讯 / 阿里等）

只做**文字识别**，返回文本行；字段结构化需自己写规则。

| 优点 | 缺点 |
| --- | --- |
| 便宜、快、印刷体准确率高 | **照片同样离开内网** |
| 通用文字识别成熟 | **返回的是文字块，不是字段**——需为每种版式写解析规则 |
| | 维护成本**随产品数增长**（94 个物料、自产/外购两套版式） |
| | 无法判断"这个数字是批号还是代码" |

### 方案 C：本地 / 内网部署开源模型

在**公司内网**部署（PaddleOCR，或量化的本地多模态模型如 Qwen-VL）。

| 优点 | 缺点 |
| --- | --- |
| **照片不出内网**——对药企合规最友好 | **需要 GPU 服务器**（见 3.1 现状） |
| 长期无按次费用 | 部署与调优工作量大 |
| 可离线运行 | 准确率需实测；版式变化时需自行迭代 |
| | 需长期运维投入 |

### 3.1 部署环境实测（方案 C 的前提）

Owner 已定：**暂不采购服务器，先部署在这台 Mac**（Mac mini M4）。实测约束如下：

| 项目 | 实测值 | 影响 |
| --- | --- | --- |
| 硬件 | Apple **M4**，**16 GB** 统一内存，无 NVIDIA GPU | 可用 Metal / CPU，**不能用 CUDA** |
| Docker 虚拟机内存上限 | **7.7 GB** | Frappe 全栈已占用其中约 0.8 GB |
| 宿主机内存 | 当前空闲约 **49%**；系统压缩器已占约 6.3 GB | **内存是主要瓶颈**，模型需选小的 |
| 容器访问宿主机 | `host.docker.internal` → `192.168.5.2` **可解析** | ✅ **验证通过**：FastAPI 可原生跑在 Mac 上，Frappe 容器能直接调用 |
| bench 内可用依赖 | 仅 `requests`、`PIL`；无 `cv2` / `paddleocr` / `torch` / `numpy` / ML 框架 | ML 依赖须装在**独立服务**里，不污染 Frappe |

**架构结论**：识别服务**原生运行在 Mac 上**（而非塞进 Frappe 容器），原因：

1. 容器是 Linux arm64，**拿不到 Metal 加速**，模型只能跑 CPU，慢；
2. 模型依赖重（torch / paddle），塞进 backend 会显著拖慢 Frappe；
3. `host.docker.internal` 已验证可达，通信无障碍。

**风险提示（须 Owner 知悉）**：这台是**开发机**，且 16 GB 内存同时承载 Frappe 全栈 + 本地模型**偏紧**。作临时验证可行，**不适合长期作为生产服务**——一旦 Mac 休眠或内存吃紧，仓库端拍照入库会中断。正式使用前建议采购一台内网服务器（M3 之外）。

## 四、方案 C 下的两条实现路线

照片不出内网既然已定，A / B 出局。剩下的问题是：**本地怎么识别**。两条路线：

### 路线 C1：本地多模态模型

在 Mac 上跑量化的视觉语言模型（如 Qwen2.5-VL-3B / 7B 的 4-bit 量化版），走 **MLX**（Apple 官方推理框架，能吃满 M4 的 Metal 与神经网络引擎）。

| 优点 | 缺点 |
| --- | --- |
| 直接输出**结构化字段**，不吃版式差异 | 16 GB 内存下只能跑小模型；**小模型在密集小字标签上会漏读/串行** |
| 能分辨"哪个是批号、哪个是代码" | 需下载数 GB 模型权重 |
| 换版式不改代码 | 单张耗时较长（数秒） |

### 路线 C2：本地 OCR + 结构化规则 + **主数据约束匹配**

用 **PaddleOCR**（本地、CPU 可跑、成熟）识别文字，再做三层加工：

1. **格式规则**：批号有**三类已知结构**（M3-R0 已确认）；物料代码是**8 位数字**；日期是日期格式。用格式把候选筛出来。
2. **主数据约束匹配**（关键杠杆）：本厂物料代码是**已知的 94 个**（且会随 SAP 主数据增长）。OCR 出的乱码可以**按编辑距离匹配到最近的合法代码**——"1300O215"（字母 O）自动纠正为 "13000215"（数字 0）。
3. **位置与版式线索**：自产 / 外购两套版式，字段位置相对固定，可作为辅助。

| 优点 | 缺点 |
| --- | --- |
| 内存占用小（1–2 GB），CPU 即可 | 需**针对版式写解析规则** |
| 印刷体文字识别准确率高 | 版式一变要改规则（**但只两套版式**） |
| 可解释——出错能看出错在哪一步 | 规则维护有长期成本 |
| **主数据约束能纠错**，这是纯 OCR 没有的 | |

### 4.1 推荐：**两条路线都实现，用同一测试集比，看数据选**

理由：

- **都在本地，成本很低**——不像 A vs C 那样涉及"要不要买机器"，本轮没有额外代价；
- 服务骨架本就设计为**识别后端可插拔**，多实现一个后端只是多一个类；
- 这正是本方案的核心工程价值：**把选型变成可测量的实验，而不是拍脑袋**。

**先量后决**：两个后端跑同一批样本，产出一张准确率对照表，Owner 看着数字定。

### 4.2 无论选哪条，都要套一层"约束校验"

这一点独立于 C1 / C2，是**准确率的放大器**：

- 物料代码 → 必须能在主数据中找到，找不到就把最接近的候选**提示给人**；
- 批号 → 做格式校验（三类结构），格式不符就**标红**；
- 日期 → 日期格式与合理区间校验。

即：**模型负责"读"，规则负责"筛"，人负责"定"**。这样即使原始识别率只有 90%，**经约束校验后能进人工确认环节的字段可用率会显著更高**。

### 4.3 后端可插拔（不变的设计）

```
POST /recognize  →  { fields: {...}, confidence: {...} }
```

C1 / C2 乃至将来换模型，都实现同一契约。**服务骨架不因选型变化而重写。**

## 五、架构与集成方式（沿用项目既有规范）

`docs/team/05_开源代码二次开发与升级规范.md` 已确立**优先级 5：外部服务**的做法，且明确 FastAPI 为外部服务技术栈。本方案完全沿用：

```
┌──────────────────────┐   HTTP (JSON)   ┌────────────────────────┐
│  hb_inventory_app     │ ───────────────→ │  拍照识别服务            │
│  (Frappe 容器)         │ ←─────────────── │  (FastAPI，原生跑在 Mac) │
└──────────────────────┘   结构化 JSON     └────────────────────────┘
        │                                              │
        └── host.docker.internal（实测可达）───┘        └── 照片不出内网
```

### 5.1 接口契约（草案）

**请求**：`POST /api/v1/recognize`
- `image`：图片（multipart 或 base64）
- `hints`（可选）：已知线索，如 `source_type`（自产/外购）

**响应**：

```json
{
  "ok": true,
  "request_id": "…",
  "backend": "c1_local_vlm",
  "fields": {
    "product_name": "…",
    "item_code": "…",
    "batch_no": "…",
    "manufacturing_date": "YYYY-MM-DD",
    "expiry_date": "YYYY-MM-DD"
  },
  "confidence": { "product_name": 0.98, "batch_no": 0.71, "item_code": 0.95 },
  "validated": { "item_code_matched": true, "batch_no_format_ok": false },
  "raw_text": "…"
}
```

**工程要求**（依 `docs/AI技能路由规范.md` 对 API / 集成开发的要求）：

- 明确的**接口契约**，字段命名与 M3 已落地的对齐（`item_code` / `batch_no` / `manufacturing_date` / `expiry_date`）；
- **超时与重试**：识别为耗时操作，需设合理超时；
- **幂等键**（`request_id`），避免重复识别产生重复台账；
- **失败记录**：识别失败落日志，便于排查；
- **权限边界**：服务**不直连数据库**，只收图片返结果，落库由 Frappe 侧负责。

### 5.2 人工校对（Owner 明确要求）

- 返回**每字段置信度**；
- Frappe 侧录入界面**高亮低置信度字段**，提示复核；
- **识别结果不直接入账**，必须经操作人确认后才写入；
- 保留 `raw_text` 与照片，便于追溯是"识别错"还是"人工改错"。

### 5.3 标签照片留存

- 照片保存在 Frappe（`Attach`，本司内网），挂在批次或入库单据上作原始凭证；
- **识别服务端不长期保存照片**（识别后即释放）。

## 六、数据留存与脱敏规则

Owner 已定**照片不出内网**，因此规则大幅简化——**不需要再考虑服务商条款、跨境传输、是否用于训练**：

| 项目 | 规则 |
| --- | --- |
| 照片是否出内网 | **不出**（Owner 已定）。这是本方案最关键的合规边界 |
| 服务端留存 | **识别后即释放，不落盘**（仅内存处理） |
| 照片归档 | 保存到 Frappe `Attach`，随批次 / 单据走 |
| 服务日志 | **不记照片内容、不记批号与产品名**；只记 `request_id` / 耗时 / 成功失败 / 错误类型 |
| 出网能力 | 识别服务**不开任何外网访问**（不下载模型之外的流量；模型权重一次性预下载） |
| 脱敏 | **不适用**——批号与代码正是识别目标，脱敏即失去意义 |

## 七、识别准确率验收标准（Owner 授权本轮制定）

### 7.1 为什么不能只定一个总准确率

5 个字段的**重要性和难度差异很大**：批号错了找不到货，产品名称错了能从代码回填。因此**分字段定标准**，并额外设**安全底线**与**性能线**。

### 7.2 字段级标准（模型原始输出 vs 人工标注真值）

| 字段 | **及格线** | **目标** | 定这个数的理由 |
| --- | --- | --- | --- |
| **批号** | **≥ 95%** | ≥ 98% | **核心查询键**——错了就定位不到货，是整个系统的主索引 |
| **物料代码** | **≥ 95%** | ≥ 98% | 须与 SAP 主数据严格一致，错了会记到错误产品上 |
| **生产日期** | ≥ 90% | ≥ 95% | 效期推算的时间基准 |
| **有效期至** | ≥ 90% | ≥ 95% | 效期预警的直接依据 |
| **产品名称** | ≥ 85% | ≥ 95% | 容错最高——**可由物料代码从主数据自动回填**，识别错了也能纠正 |

### 7.3 单据级标准（整张标签）

| 指标 | 及格线 | 说明 |
| --- | --- | --- |
| **5 个字段全部正确** | **≥ 80%** | 即 5 张里有 4 张"拍照后可直接确认入账" |

### 7.4 安全底线（硬性，不可放宽）

这两条比准确率更重要——**它们决定错误会不会被人发现**：

| 指标 | 要求 | 为什么 |
| --- | --- | --- |
| **高置信度错误率** | **≤ 1%** | 批号 / 代码被认错、**但模型给出高置信度（≥0.9）** 的比例。这类错误**不会触发人工复核**，是最危险的失败模式 |
| **低置信度召回率** | **≥ 90%** | 真实出错的字段中，至少 90% 被标为低置信度。即"**模型知道自己不确定**" |

> 通俗说：允许模型不会，**不允许模型自信地错**。

### 7.5 性能线（本地 Mac 承载）

| 指标 | 要求 |
| --- | --- |
| 单张识别耗时 | **≤ 10 秒**（P95） |
| 连续运行 | **100 张无崩溃、无内存泄漏** |
| 并发 | 支持 **1–2** 人同时使用（仓库场景，非高并发） |

### 7.6 测试集要求（标准的前提，缺一不可）

没有合格的测试集，上面的数字都没有意义：

| 要求 | 说明 |
| --- | --- |
| 规模 | **≥ 50 张**真实标签照片 |
| 真值 | **人工逐字段标注**（这是最费工的一步，但必须做） |
| 覆盖来源 | 自产 / 外购 **各约一半** |
| 覆盖语言 | 含英文后缀（USP / EP / JP / CEP）的与纯中文的都要有 |
| 覆盖产品 | **≥ 10 个不同产品**，含原料药 / 中间体 / 混粉 / 成品 |
| 覆盖拍摄条件 | 正拍 / 斜拍 / 反光 / 轻微磨损或褶皱，模拟现场真实情况 |
| 存放 | **不进 Git**，放仓库工作区之外（含真实批号与产品名） |

### 7.7 验收结论怎么用

两个后端（C1 / C2）跑**同一测试集**，产出一张对照表：

| 后端 | 批号 | 物料代码 | 生产日期 | 有效期 | 产品名称 | 全字段正确 | 高置信度错误 | 单张耗时 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| C1 本地 VLM | ? | ? | ? | ? | ? | ? | ? | ? |
| C2 OCR+规则 | ? | ? | ? | ? | ? | ? | ? | ? |

**达标者入选；两个都达标选内存占用低、耗时短的；都不达标则如实报告，不硬上**（此时可退回复核：是否采购内网服务器跑更大的模型）。

## 八、M3-R6 交付边界（待授权确认）

**计划做**：

- FastAPI 服务骨架：**可插拔后端抽象**、接口契约、幂等键、超时重试、失败日志、**不开外网**。
- 实现**两个**后端：C1（本地量化 VLM）+ C2（PaddleOCR + 规则 + 主数据约束）。
- 约束校验层：物料代码主数据匹配、批号格式校验、日期格式校验。
- Frappe 侧：拍照上传入口 + 识别结果**人工校对**界面 + 低置信度高亮 + 确认后写入。
- 照片归档到 Frappe `Attach`。
- 用测试集实测两个后端，产出对照表。

**不做**：

- 不做批量导入 / 批量识别；
- 不自动创建 `Item`（未知物料只提示，不擅自建主数据）；
