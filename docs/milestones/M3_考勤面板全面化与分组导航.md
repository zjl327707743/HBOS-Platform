# 考勤面板全面化与分组导航实施记录

项目名称：新乡海滨智能运营管理平台。

分支：`feature/hbos-portal-workbench`。

状态：**REVIEWING**（等待 Owner 验收；未 closeout）。

## 一、编号与定位

M3-PORTAL-R1 的后续交付，不新开里程碑号（理由同前两批：`R1`~`R4` 已被 M3-PORTAL-R1 用作内部阶段号）。

Owner 2026-10-08 决定：**把考勤在 Desk 侧的 11 个后台面全部做进门户**，导航从 3 个页签改为分组侧栏。这**推翻两处既有决定**（见第八节），已按新决定执行。

## 二、解决了什么问题

门户里的考勤此前只有 3 个入口（仪表盘 / 人员管理 / 部门看板）。考勤在 Desk 侧实际有 **14 个可达面**——4 张报表、4 个列表、3 个操作页、3 个概览——其余 **11 个在门户里一个都点不到**，只能跳到 Desk。

## 三、导航：分组侧栏

**14 个入口分 4 组**（分组依据是「用户来干什么」，命名与后台既有的「海滨考勤工作台」侧栏保持一致）：

| 分组 | 入口 |
|---|---|
| 概览 | 考勤仪表盘 · 人员管理 · 部门看板 |
| 报表 | 月度考勤汇总 · 打卡流水 · 考勤结果 · 月度汇总 / 对账暂存 |
| 数据与导入 | 导入考勤机导出表 · 上传月度考勤表 · 考勤导入日志 · 飞书请假 / 加班 / 调休记录 |
| 配置 | 班次管理 |

- **导航数据单一来源**：`src/services/attendanceNav.ts`。侧栏、移动端抽屉、面包屑都从这里取，避免同一份菜单在多处各写一遍后漂移（本项目为「一个业务含义只留一份名单」专门收敛过行政班名单，同一道理）。
- **形态与 LIMS 一致**：复用既有的 `.app-local-sidebar` / `.app-layout-grid`，用户在两个应用间往返时不用重新学导航。
- **新增 `AttendanceSidebar.vue`**，并把 `AttendanceLayout.vue` 从「3 个页签」改为「侧栏 + 内容区」两栏。

### 侧栏滚动（实测修复）

共享样式给侧栏定的是 `height: calc(100vh - 116px)` 且**没有 overflow**。LIMS 不到 10 个入口够用，考勤有 15 个——超出的部分被裁掉，底部的「班次管理 / 管理后台」点不到（Owner 实测发现）。

改法：**中间的 nav 滚动，首尾钉住**（品牌/返回固定、管理后台钉底）。没有做成整栏滚动——那样要滚到底才看得到「管理后台」，用户会以为它不存在。`min-height: 0` 是必需的：flex 子项默认 `min-height: auto`，不加不会收缩。

## 四、11 个后台面：从 iframe 改为原生

### 为什么改

原方案是**同域 iframe 内嵌 + 注入 CSS 隐藏 Desk 外壳**。实测下来问题集中：

1. **外壳剥离依赖 Desk 的 DOM 类名**，Frappe 升级就要跟着改；
2. **缓存陷阱**：Desk 页面脚本缓存在浏览器 localStorage，改完看不到效果且不自愈（`FRONTEND_IMPLEMENTATION_GUIDE.md` §1.1.1）；
3. **iframe 内的观感始终是"别人的页面"**——即使换了配色，表格结构、交互、间距仍是 Frappe 的；
4. Owner 明确要求「用上 Ant Design 组件」。

### 怎么做（三段，每段都遵守同一原则）

**核心原则：取数逻辑一行不重写。** 报表调报表自己的 `execute()`，列表走 `frappe.get_list()`。若门户另写一套查询，两处口径必然漂移。

| 段 | 后端 | 前端 | 数量 |
|---|---|---|---|
| 报表 | `report_data.py`：薄包装 `execute(filters)`，返回 `(columns, data)` 的 JSON | `AttendanceReportView.vue`：`a-table` + `a-select` + `a-range-picker` | 4 |
| 列表 | `list_data.py`：列白名单 + 服务端分页 + `frappe.get_list()`（**自带权限过滤**，比 `db.get_all` 安全） | `AttendanceListView.vue`：`a-table` + 枚举筛选 | 4 |
| 操作 | 复用既有端点（导入日志的 `preview_import`/`run_import`；月度上传的 `process_excel`） | `AttendanceImportView.vue`（三步流程）、`AttendanceMonthlyUploadView.vue` | 3 |

**权限**：Frappe 的报表权限检查在**视图层**（Report 文档的 roles），不在 `execute()` 里——直接调 `execute()` 会绕过它。故每个新端点都带自己的角色门禁。

**默认日期窗口**：不加过滤时报表会全量返回（打卡流水实测 61815 行、数 MB JSON）。按报表分别给默认窗口（流水 7 天、其余 30 天、月度汇总用本月）。

## 五、实测中发现并修复的缺陷

### (a) 筛选条件被后端静默丢弃（最严重）

门户经查询参数发筛选，到达后端时 `filters` 是 **JSON 字符串**；而 `_clean_filters()` 只判 `isinstance(raw, dict)`——字符串直接返回空字典。

**后果：用户在页面上选的日期、部门全部被丢掉，报表永远返回全量数据。**

实测对照（打卡流水）：

| | 行数 |
|---|---|
| 带日期筛选（修复前） | **61815**（全量，筛选形同虚设） |
| 带日期筛选（修复后） | **4914** |
| 不带筛选 | 61815 |

### (b) `row-key` 用错字段

写死 `row-key="employee_number"`，但打卡流水/考勤结果里**一个人有多行**（多天、多张卡），拿它当 key 会产生重复键，翻页时行会串。改为按「员工 + 日期/时间 + 批次」逐级拼。

### (c) 侧栏 15 个入口被裁掉

见第三节。

### (d) 入口页的 `on_page_load` 包裹错误

为修「人员管理与班次管理抢同一个顶层 `renderPage`」，把两页函数收进 IIFE，**但 `on_page_load` 赋值留在闭包外**，而它在闭包内调 `renderPage` → `ReferenceError`、页面整个空白。症状从「旧界面」变成「白页」一度误导排查方向，靠控制台报错才确认。已修，并对六页做了 IIFE 边界自检。

### (e) AntD 默认英文 locale

空表格显示 `No data`、日期选择器英文月份、分页 `Page 1 of 3`。整个门户是中文界面，在根组件（`App.vue`）统一换成 `zh_CN`——否则每页各配一次、迟早漏掉一处。

## 六、CSRF：为什么需要新增一个只读端点

Frappe 对非安全方法做 CSRF 校验（`frappe/auth.py`的 `validate_csrf_token`）。放行只有三条路：配置 `ignore_csrf`、请求头 token 与会话一致、或 Referer 命中 `allowed_referrers`——**本环境三条都不成立**。

Desk 页面能上传，是因为 `frappe.csrf_token` 由 `desk.html` 直接内联下发；门户是独立 SPA，拿不到。

**Owner 2026-10-08 裁定选方案 A**：新增 `file_api.get_csrf_token`——只读、要求已登录、只回当前会话的 token。这是 CSRF token 的本来用途（Desk 对每个用户本来就下发）。上传本身仍走 Frappe 内置的 `upload_file`，权限与文件校验由框架负责，不重复实现。

前端 `frappeUpload.ts` 带 403 自动重取一次的逻辑（会话轮换后自愈），**只重试一次**——真没权限时反复重试没有意义。

**两个上传页通路不同，不可共用封装**：导入页先 `upload_file` 拿 `file_url` 再调 `preview_import`；月度上传页直接把**原始文件字节** POST 给 `process_excel`（它自己读 multipart）。

## 七、班次管理：保留 Desk 实现（Owner 2026-10-08 裁定「甲」）

14 项里唯一**不**原生的，原因：

1. **它是编辑器不是展示页**——前面 13 项都是读数据，统一观感收益最大；它是改数据（改班次时间会改判定口径），评判标准不该一样。
2. **写接口风险**：13 个写接口中 `bind_employee_shifts` / `update_shift_rule` 会改判定口径。写坏不是「页面难看」，是**考勤算错**。
3. **低频页**（设一次管很久），不像报表要天天看。
4. 它是**一个页面两个页签**，拆开做会导致「一半门户风格、一半 Desk 风格」并在同一屏，比现在更割裂。

**这是一个有意的例外，不是遗漏。** 门户里它仍从侧栏进入，同域 iframe + 外壳剥离 + 配色映射照常生效（实测：Desk 侧栏已隐藏、班次 UI 完整）。

## 十五、另发现：AI 复核对部分 prompt 返回空（**非本次引入，待决定**）

复核功能**在服务端就已失效**，门户与 Desk 同样受影响。实测取证：

```
prompt: 【员工】李芸 … 【班次规则】…行政班（周末双休、不判缺勤） 【打卡流水】无打卡记录
        待复核异常：2026-10-07|缺勤
返回:   HTTP 200, finish_reason=length, content 长度 0, reasoning 长度 1749
        completion_tokens 1200（全部是 reasoning_tokens）
```

**机制**：当前模型 `deepseek-flash` 是**推理模型**，其 thinking 计入 `max_tokens`。该 prompt 下模型反复推演「2026-10-07 是星期几」（因为规则提到周末双休），1200 token 预算被推理烧光，`content` 为空 → `parse_review` 得到 `{}` → 界面显示「AI复核失败：无有效返回」。

**为什么以前没暴露**：2026-09-22 上游 `deepseek-v4-flash` 下线后换成 `deepseek-flash`（见 M1-FIX-F 落地记录），推理模型的输出预算语义与前者不同。当时只验证了「能调通」，没有逐类 prompt 验证「能出结论」。

**可选的修法（均未实施）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| 甲 | 提高 `max_tokens`（如 4096） | 推理可能仍然吃满；成本上升 |
| 乙 | 关闭思考（`chat_template_kwargs.enable_thinking=false`，若上游支持） | 需确认上游支持该参数 |
| 丙 | **把星期写进 prompt**（模型正是在算这个） | 改动最小、成本最低；但只消除已知的一处推理 |
| 丁 | 换回非推理模型 | 需确认该服务商有可用的非推理模型 |

倾向丙 + 甲：丙消除已观测到的推理诱因，甲给未知情况留余量。**但这属于 AI 功能口径调整，不在「补回按钮」的范围内，等 Owner 决定。**

### 已修复（Owner 2026-10-09 裁定「丙 + 甲」）

**丙 —— 把星期写进 prompt。** 新增 `weekday_cn()`，把待复核日期渲染成
`2026-10-07（星期三）`；prompt 里同时加一句「日历事实已在下文给出，无需推算。
直接逐条作答，不要展开推理过程」。

**甲 —— 提高输出预算。** `max_tokens` 由硬编码 1200 提为常量 `AI_MAX_TOKENS = 4096`。

**顺带补强 `parse_review` 的日期归一化**：prompt 现在给的是带星期的形态，模型可能
原样回抄、只回 `YYYY-MM-DD`、或回 `MM-DD`。三种都要能对上 `anomaly_keys`——
对不上是**静默丢结果**（整批被当成「不在待复核集里」），比报错更难查。已支持
中文括号、ASCII 括号、以及 `MM-DD` 补全年份。

**实测（同一用例，修前修后对照）**：

| | 修前 | 修后 |
|---|---|---|
| 李芸 10/07 缺勤 | `finish_reason=length`、content 空、显示「无有效返回」 | **「属实：该员工为行政班，2026-10-07 为星期三工作日，非双休日；当日无任何打卡记录，全天未出勤，系统判定缺勤成立。」** |

更大样本（生产部 3 人、含多日异常）**3/3 成功**，且结论有业务价值——例如
牛文平被识别为「国庆法定假期（10-01～10-07）内不判缺勤，系统误判」。
单批 3 人耗时约 21 秒。

**测试**：`test_ai_review.py` 由 13 → **23 用例**（星期格式与非法输入、
prompt 确实带上星期、日期归一化的四种写法、`max_tokens` 常量与调用点）。
已做**变异验证**：把 `max_tokens` 改回 1200 时测试失败。
