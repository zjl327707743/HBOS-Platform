## 三、为什么必须有「形状守卫」

实测对比（8/15–10/8 真实数据，664 人 / 50814 条打卡）：

| 口径 | Absent→Present | Present→无记录（误伤） |
|---|---|---|
| 无守卫，直接放宽到 26h | 162 | **3** |
| **有形状守卫（本次采用）** | 162 | **0** |

两者收益相同，差别是纯粹的风险。

### 为什么必须「单次、且 range_end 取数据最大日期」

`regenerate_attendance` 的清理含**两条 DELETE**：

```sql
DELETE ... WHERE name LIKE 'HBOS-ATT-%' AND attendance_date BETWEEN range_start AND range_end
DELETE ... WHERE name LIKE 'HBOS-ATT-%' AND attendance_date > range_end
```

第二条会**删掉 range_end 之后的全部记录**——2026-09-24 的窄窗口乱序重算事故就是这么发生的（一度删除 8/15–9/21 全部记录）。

**取 range_end = 数据最大日期（10/08）时，第二条 DELETE 删不到任何东西**，危险自动消解；单次调用则不存在顺序问题。

## 十、`2026-09-30` 整日缺失——根因已查明（2026-10-09）

**结论：月末边界 bug。定时重算的窗口 `[本月1日, 昨天]` 永远覆盖不到上个月的最后一天，而 2026-09-02 引入的第二条 DELETE 会主动把它删掉。**

### 机制

`sync_delicloud_checkin`（每 10 分钟）调用：

```python
yesterday   = (_dt.now() - _td(days=1)).strftime("%Y-%m-%d")
month_start = _dt.now().replace(day=1).strftime("%Y-%m-%d")
regenerate_attendance(month_start, yesterday)
```

而 `regenerate_attendance` 先删后建：

```sql
DELETE ... WHERE attendance_date BETWEEN range_start AND range_end   -- ①
DELETE ... WHERE attendance_date > range_end                        -- ②
```

**9/30（月内最后一天）**，窗口 = `(2026-09-01, 2026-09-29)`：
- ② 删掉 `> 9/29` → **9/30 被删**
- 重建只覆盖 `9/01 ~ 9/29`

**10/01（跨月第一天）**，窗口 = `(2026-10-01, 2026-09-30)` —— **区间倒置**：
- ① 匹配不到任何行
- ② 也删不到东西
- 重建时 `in_range = '2026-10-01' <= ds <= '2026-09-30'` **恒为假** → 一条都不生成

→ **9/30 掉进「9 月的昨天」与「10 月的月首」之间的空洞，再也不会被重建。**

### 证据链

| 证据 | 内容 |
|---|---|
| `git blame` | 第二条 DELETE 由 `64da0aa`（**2026-09-02**）引入；此前只有 `BETWEEN` 那条 |
| 7/31 | **502 行**（早于引入日 → 幸存） |
| 8/31 | **494 行**（早于引入日 → 幸存） |
| 9/30 | **0 行**（引入之后的第一个月末 → 被删） |
| 全历史 7/28–10/08 | 9/30 是**唯一**的整日缺失 |
| 窗口模拟 | 10/01 的 `month_start(10-01) > yesterday(09-30)` 确认倒置 |

「8/31 幸存而 9/30 被删」这一非对称现象，正是引入日期卡在两者之间的直接印证。

### 影响面

- 已损失：仅 9/30 一天（本次重算已补回 510 行）。
- **潜在未爆：`10/31` 会在 `11/01` 被同样删掉**，此后每个月末都会。bug 仍在。
- 逐日删除「今天」本身是**设计如此**（今天数据不完整，避免全员假缺勤），问题只出在月末——「明天重建」跨到了下个月，而下个月的窗口从 1 号开始。

### 修复选项（**未实施，待 Owner 决定**）

| 方案 | 做法 | 效果 |
|---|---|---|
| **甲（推荐）** | 窗口改为滚动 N 天：`range_start = yesterday - 34d` | 上个月最后一天次日就被重建，**根治** |
| 乙 | 倒置时直接跳过 | 防止空跑，但**不恢复**丢失的那天 |
| 丙 | ② 只删「今天」而非 `> range_end` | 题意相同（数据不可能是未来），**不解决问题** |

甲有代价：每 10 分钟重建 35 天而非本月 1 日起（当前约 8 天）。参考量级——手动重算 55 天耗时约 12 秒，故 35 天约 8 秒，可接受，但**需 Owner 权衡调度频率与负载**。

### 已实施修复（Owner 2026-10-09 裁定「甲」）

窗口由「本月 1 日 → 昨天」改为**滚动回溯 35 天**：

```python
REGENERATE_LOOKBACK_DAYS = 35   # 必须 > 31，否则上个月最后一天仍会掉进跨月空洞
gen_start = (yesterday - _td(days=REGENERATE_LOOKBACK_DAYS)).strftime("%Y-%m-%d")
gen_result = regenerate_attendance(gen_start, yesterday)
```

- **根治**：上个月最后一天在次日即落入窗口并被重建；窗口永不倒置。
- **代价**：每 10 分钟重建约 35 天（原为「本月 1 日起」约 8 天）。参考量级——手动重算 35 天耗时约 8 秒。
- **测试**：新增 `tests/test_regenerate_window.py`（7 用例）——逐月扫描全年月末、断言窗口不倒置、窗口终点仍是「昨天」（不能把今天算进去）、以及源码级断言调用处不得再用「本月 1 日」。已做**变异验证**：把回潮改回本月 1 日时测试确实失败。
- **实测**：2026-10-09 的新窗口为 `2026-09-03 ~ 2026-10-08`，9/30 在窗口内；按该窗口实跑一次后 **9/30 保持 511 行**（不再被删）。整体规模无异常：34829 行、覆盖 73 天、HRMS 原生行 1690 未动。
