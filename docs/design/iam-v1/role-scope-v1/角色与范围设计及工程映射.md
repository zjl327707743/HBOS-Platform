状态：`IAM_ROLE_SCOPE_DESIGN_REVIEW_READY / PENDING_OWNER`（设计候选）。角色持久化、授予/迁移、部门/公司考勤及 LIMS 新授权：`NOT_AUTHORIZED / NOT_RUN`。本文件不是实施批准。

## Owner 审阅的三处页面

1. 员工详情→应用权限→考勤/LIMS：先看结果表，再设置。添加多条角色，每条独立选范围、期限；固定 SELF 不二选。部门继承项只读，个人项可明确移除。暂停为次级总限制。可载入个人拒绝示例，核对恢复默认可能增加访问。LIMS 演示复核 A / 检验 B，不能复核 B。
2. 部门管理→默认应用权限：与部门成员并列。每位普通成员默认员工自助—本人；不提供部门考勤员、人事考勤管理员批量模板。未默认授予与明确禁止分别预览。LIMS 入口/基础身份不含检验/复核/QA 资格。
3. 应用权限→考勤/LIMS→使用人员/角色模板：轻量目录，显示稳定 ID、版本、功能、允许范围、原生对应和接入状态。没有角色中心 CRUD。其他员工资料/账号页签仅提示保留现有产品，不假装完成额外设计。

视觉承接现有 HBOS Shell 的16px正文、14px辅助信息、紫色操作、浅色表格、720px抽屉；正式承接仍 Vue3 + Ant Design Vue。设计评审不更换生产框架。

## 最小模型与命令差异（尚不实施）

复用原生 User/Session、Employee、Company/Department、密码与 External Identity。继续唯一 Employee↔User；兼岗不改主部门。原生 Role 是 DocType 粗权限，Role Profile 是原生角色组合，它们不能单独表达“复核 A / 检验 B”。

建议服务端只读版本化模板目录（例如 `iam/role_templates.py`）：稳定 template_id、不可变 version、app_id、明确 operation_id 列表、每动作 scope 类型/资格/SoD 要求、native_role/profile 引用、integration_status。版本增加不自动追加已有分配的动作；升级需差异预览。没有通用任意角色 CRUD，不新增第二份用户目录。

建议仅增加一个受控 `HBOS IAM Role Assignment` 模型：`subject_type(User/Department)`、原生 subject_name、app_id、template_id、template_version、scope_type、scope_ref、valid_from/until、enabled、origin_kind/origin_ref、version。**一条分配对应一个模板版本和一个明确范围**；多对象多条分配。部门主体只允许经目录标为普通默认的固定 SELF 模板，范围解释为每个成员本人，不能解释成整部门记录。

身份、范围与来源均结构化校验，不能把任意 JSON 当第二套权限真相。可以直接由同一 IAM evaluator 联合求值分配与存量规则；若性能需要规则投影，另增最少的 source_assignment/source_version 引用，投影只由受控事务生成，不能源和投影分别编辑。实施前必须比较两种方案并固定一种，当前不增加这些字段。

最少候选命令：`list_role_templates(app)`、`preview_role_assignments(subject, app, touched_assignments, expected_version, context)`、`save_role_assignments(..., request_id)`、`preview_template_upgrade`。现有同一安全 proof/MFA/CSRF、管理目标及可授范围、版本、请求幂等、单事务和一条审计继续复用；不得借新模板绕过重要操作流程。

文件候选：IAM目录模板/evaluator/commands，现3处 Vue局部/iamWork/types，Attendance对应受限查询/报表/导出/后台执行守卫，原生 Role/DocPerm 的必要只读映射与资格注册。LIMS按领域已有命令注册，不整包合并#37；Knowledge/Twin只预留 registry scope 类型，本轮不改其业务。知识原文下载禁令不因管理员/新角色取消。

当前 A 的摘要契约 `revision_digests` schema2 已记录 role_extension=not_integrated；未来必须加入当前 User 的 assignment版本、template版本、每条成对范围和期限、原生必要角色/资格变化与注册版本。不能只修改显示角色标签而略过撤权或缓存失效链。

## 来源撤销、兼容与迁移停点

| 当前事实 | 候选语义 / 保留规则 | 迁移处理 |
| --- | --- | --- |
| 没有部门默认 allow | 没有自动授予；个人独立合法来源继续可用 | 可对应“无默认模板”，不得新增 deny |
| 部门/个人明确 deny | 当前硬限制；按明确对象范围继续压过 allow | 原行和审计保留；不能自动改成“未授予”或清空所有个人 deny |
| 个人普通例外 / 特殊期限 | 现有优先与过期不回落合同继续有效 | 分类映射、逐项预览来源，复杂项保留旧执行链待审 |
| 应用暂停 app.enter deny ALL/* | 员工该 App 的总限制；解除后重算其他来源 | 保留原规则语义；不是仅隐藏入口，也不是恢复全部功能 |
| 多条同动作合法角色 | 任一仍有效来源可贡献明确对象；全局硬限制优先 | 移除 assignment A 只撤 A 贡献，B来源仍可追溯；审计列贡献差异 |
| 主部门调岗 | 默认跟随新主部门；具名负责部门 A 不自动改成 B | 默认来源撤销/新来源加入；具名职责建议暂保留并标待复核，Owner可选择转岗即暂停；逐条来源说明 |
| 历史考勤 | 原 Employee 外键和已有打卡/结果保留 | 建议事件发生时的部门归属；缺可靠时点来源时拒绝新的部门历史扩权，不能按当前部门重写过去 |

先做只读盘点和 dry-run 迁移清单（原生ID、来源、动作、对象、期限、预期差异），仅合成 Site 验证；无差异不写，有歧义停在设计。迁移前备份、版本化dry-run摘要、单对象原子执行、可逆来源映射；回滚撤新分配贡献并恢复精确旧行，不覆盖后续合法新变更。不存在“迁移顺便修复历史 deny”。

相同 User 从 Portal、Desk、REST、report、export/File、RQ后台访问时均在同一范围执行链核验。原生粗 Role 不作纳管撤权后的后门。管理 IAM 不授读考勤；考勤业务角色也不授 IAM 管理。

## Owner 只需确认的四项

1. 首批按本人 + 具名部门只读 + 具名公司只读落地，修改/审批/导入/导出另列动作审批，是否符合实际职责。
2. 部门只默认普通员工自助；跨员工的部门/公司职责逐人授予。无默认与明确禁止分别保留，历史 deny 不自动迁移清理。
3. 每条角色独立绑定范围/期限、版本固定；模板升级需明确差异。是否接受最小分配模型以保留来源和单独撤销能力。
4. 具名兼岗调岗后建议保留且待复核，或改为转岗即暂停；部门历史建议按事件时点归属，缺证据不开放历史查询。

确认固定设计与工程范围后另启实施，本轮不把按钮接到真实 API。
