## 3. 当前考勤归属链与风险

### 3.1 定时得力云同步

`apps/hb_attendance_app/hb_attendance_app/hooks.py:20-22` 将 `api.sync_delicloud_checkin` 挂到每 10 分钟调度。本轮仅阅读，未确认现场调度实际启用。

当前链路：`check_data.employee_num` → `Employee.employee_number` → `Employee.name` → `Employee Checkin.employee`。`api.py:242-248` 在工号无值或未匹配时，仍直接按姓名取一个 Employee；没有查询全部候选，也没有公司过滤。`:251-255` 的姓名一致校验只在来源工号和姓名同时非空时运行，因此不能阻止“缺工号但同名”被认领；有一个同名结果也不证明是同一人。

`api.py:267-290` 以 `employee+time` 查已有打卡，并在已有记录空字段上回填设备/事件信息，否则插入打卡。该机制没有证明外部人员身份，也不能纠正已经落错 Employee 的历史记录。当前是否存在同名误归属、源事件重复或同秒事件合并，均 `NOT_RUN`。

### 3.2 Employee Checkin 与 Attendance

`api.py:389-401` 通过 `ec.employee=Employee.name` 拉取并按 Employee 分组；`:656-658` 直接向 Attendance.employee 写入该 Employee。HRMS 自动考勤调用在 `api.py:306-310`，其精确上游行为本轮未取得源代码证据。

打卡流水 `report/打卡流水/打卡流水.py:105-126`、考勤结果 `report/考勤结果/考勤结果.py:41-65` 都以 Employee 外键联结；名称和工号是输出属性，不能作为本人授权键。本人服务应从 `frappe.session.user` 解析唯一已确认的 Employee 后限制 `employee`，不能接受调用方替换主体，不能使用记录 owner 判断归属。

月度考勤汇总 `report/月度考勤汇总/月度考勤汇总.py:33-38,53-67` 以 Attendance.employee 联结 Employee，部门筛选使用**当前** Employee.department。它不证明主管有权读取该员工全部历史，也没有提供历史任职/事件部门归属证据。另有异常导出 `report/月度考勤汇总/export.py:183-197,263` 用 `(工号,姓名,当前部门)` 聚合展示；不得把该展示组合重新当人员唯一键。

### 3.3 月度对账暂存与其他导入入口

`doctype/hbos_attendance_import_log/hbos_attendance_import_log.py:383-405` 收集姓名、工号、部门文本；`:435-441` 将汇总 JSON 暂存到 Import Log，不写 Employee Checkin 或 Attendance。其 `matched_rows/success_rows` 计数是暂存行数，**不等于已完成 Employee 匹配数**。

`report/hbos_月度汇总暂存（对账）/hbos_月度汇总暂存（对账）.py:16-47,51-68` 直接遍历暂存 JSON，按文本部门/工号过滤，没有确认 Employee 外键。该暂存目前不能作为可信本人考勤结果来源，真实本人接口先不开放这些行。

同时存在其他姓名归属路径：导入器 `_match_or_create_employee` `:638-653` 在工号和 device ID 不命中时以唯一同名接受；`_find_employee` `:901-909` 在无工号时以唯一同名接受。`:660-672` 还存在创建 Employee 并填固定出生/入职日期的历史路径。它们均仅为源码风险证据，本轮不执行、不继承到 R4 正式开户流程，也不依据这类缺省值建立真实员工。

## 4. A2 推荐关系及最小兼容补丁候选

推荐保持一条链：

`已确认的考勤来源人员标识 → 已有 Employee.name ← Employee.user_id → 唯一 User.name ← 飞书身份 / 密码登录`

优先采用现有工号链路与原生 Attendance Device ID，不为“整齐”重命名 Employee 或重写已正确历史。本轮选择为**原生优先、有证据才关联**：在 B 隔离合成场景先证明完整链路；真实来源映射在取得命名空间和唯一性证据前保持待核对。

| 候选情况 | 最小处理 |
|---|---|
| 来源已确认是企业级可靠工号，且在批准公司/来源范围内精确匹配唯一 Employee | 复用 employee_number，保留来源字符串；将 Employee.name 作为业务外键 |
| 来源是已确认独立考勤人员 ID，已有正确 attendance_device_id | 复用该原生字段；不强制把它改为 HR 工号 |
| 多来源、编号复用、同号跨公司/设备、有效期变化或一人多个外部 ID | 才申请考勤接入域的最小映射扩展：source、namespace、external person ID、Employee、状态、有效期、确认来源；不是第二员工库或登录凭据库 |
| 缺可靠标识、命中不唯一、姓名不一致、标识复用或 namespace 未确认 | 异常候选，不自动选第一条、不按姓名/拼音/手机/邮箱补绑，不向本人接口暴露该来源历史 |

交给考勤线的补丁范围候选，A 阶段不实施：

1. 将 `api.py:242-255` 归属部分替换为一个严格解析器：按批准 namespace/company 查询明确标识并检查候选数；0 条、2 条及以上、来源冲突均返回可解释的待核对原因。保留姓名只做差异提示，不作匹配兜底。同样收口原始导入 `_match_or_create_employee` / `_find_employee` 的归属入口，避免新路径仍能按唯一同名认领。
2. 字符串按来源协议处理，保留前导零；不做数值化、截断、大小写/空白规范化后自动认定同人。未经批准的类型或格式进入异常。Employee 工号与考勤设备人员 ID 使用不同字段和明确来源，禁止通用 OR 匹配静默择一。
3. 处理游标兼容性：现有未匹配仅 `skipped`（`:248`），`:298-303` 只在 `write_failed==0` 时推进游标。直接删除姓名兜底会使未映射事件被越过。须先形成受控持久待处理收据，或在没有该能力时让含身份异常的批次暂不推进游标并依靠既有幂等重拉；会造成的积压由考勤线评估。不能为避免积压继续错误归属，也不能本轮擅停同步。
4. 保留已正确记录与外键，不批量回填、清空、重算；历史纠错先出私有证据及数据变更批准。新解析器、冲突和重试策略应有合成的同名、同号不同公司/来源、缺号、前导零、同秒不同事件及失败回滚测试。

上述候选只描述兼容改动，未创建模型/字段/patch，未改变任何调度与游标。
