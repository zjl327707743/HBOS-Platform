## 2026-10-18 R3 候选规则

本次修复封闭旧编码中已经复现的字段分隔符碰撞，以及检测到既有锚点不一致后仍能追加新锚的问题。它不迁移旧审计行、不修改旧指纹版本、不重写旧锚文件，不改变业务审计与业务事务共同提交或回滚的规则。

| 对象 | 版本 | 校验与兼容行为 |
| --- | --- | --- |
| 审计行 | v1，包括原来的空版本 | 保留原 SHA-1 七字段算法和原字节编码；部分载荷未覆盖，分隔符边界也不完整。 |
| 审计行 | v2 | 保留原 SHA-256 十字段算法和原字节编码；未转义的 `\|` 可能使不同字段载荷得到相同指纹。 |
| 新审计行 | v3 | SHA-256 使用带字段名的规范 JSON；字段边界明确，换行、分隔符、零值不会被错误折叠。 |
| 旧锚点 | 缺少版本字段的 v1 | 保留原历史摘要与锚链算法；仅覆盖每行的 `name / created_at / checksum`，不覆盖完整载荷，也不绑定锚点时间 `at`。 |
| 新锚点 | 显式 v2 | 直接覆盖当时读取的完整审计载荷、行名、指纹、指纹版本和创建时间；锚链也绑定版本、锚点时间、来源和前一锚。 |

只有审计行的 `null` 或空字符串版本沿用 v1；`0`、`false` 和其它未知版本不能回退成已知算法。未知审计版本会列入 `unknown` 与 `mismatched`；未知锚版本对账失败，写入方拒绝追加。

`verify_audit_integrity` 保留原有 `checked / mismatched / legacy` 字段，其中 `legacy` 仍只统计 v1。新增 `versions / weak_legacy / unknown / coverage_note`；`weak_legacy` 同时计入 v1 与 v2，避免把“旧算法匹配”误读成旧覆盖问题已经消除。

## 旧历史如何建立新快照

写入新锚之前，服务先验证旧锚链和它实际覆盖的历史前缀。已有前缀不一致时，拒绝追加，原文件字节保持不变。校验通过后，可以在原文件尾部追加 v2 锚；既有行、指纹、版本和锚记录原样保留。取得文件锁后才读取历史总数和新快照，历史总数限定读取的前缀。写入与对账均拒绝覆盖行数倒退，避免旧快照排在新快照后面隐藏已经锚定的尾行。

旧 v1/v2 的不足无法通过重新计算一个新锚得到追溯证明。新 v2 锚只绑定**建立时点所见的载荷**：它能检测此后被覆盖的数据库载荷、指纹、删行、插入或排序变化；不能证明建立时点之前的旧载荷从未改变。旧锚不能检测的 v2 碰撞不会阻止建立一个诚实标记的新快照。接口的 `payload_coverage / coverage_note` 保留此边界。

新增审计行不改变已锚定的历史前缀，可由后续锚继续覆盖。锚点之后还未被覆盖的新行、能够同时修改数据库和本机锚文件的主机权限、远端存证以及法律意义上的签署，不属于本机制的保证。

## 验证材料与运行限制

`apps/hb_lims_app/tests/test_audit_canonical.py` 直接调用实际源码中的审计函数，以原算法固定向量、碰撞反例、版本分派和真实临时文件验证离线行为；数据库接口仅用于可控数据夹具，不能代替原生权限或数据库证据。

`apps/hb_lims_app/tests/test_audit_canonical_runtime.py` 提供独立的 9 项原生验证，复用隔离 Site 的具名 LIMS Manager。合成审计夹具通过实际内部审计服务创建；数据库故障注入全部用保存点恢复，并比较完整审计行与临时锚文件字节。测试不会操作站点默认锚文件。原有 32 项原生套件仍单独执行、计数；其中旧 5 项审计用例仅更新新写版本的期望，保留原业务断言。

此文说明候选规则与验证方法，不宣称原生执行已通过。当前候选、CI 和最终合并事实以 [PR #43](https://github.com/zjl327707743/HBOS-Platform/pull/43) 及 [R3 原生验证 PR #56](https://github.com/zjl327707743/HBOS-Platform/pull/56) 的最新精确来源记录为准。
