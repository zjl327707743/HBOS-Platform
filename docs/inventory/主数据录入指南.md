## 一、主数据是什么

**主数据（Master Data）** 指那些**相对稳定、被单据反复引用**的基础档案。

与「业务数据 / 流水」相对：

| | 主数据 | 业务数据 |
| --- | --- | --- |
| 例子 | 供应商、客户、物料、货位 | 采购订单、入库单、出库单 |
| 变化频率 | 低（建一次，偶尔改） | 高（每天几十张） |
| 作用 | **被引用**——单据上填的是它的名字 | **引用别人**——单据上挂着主数据的链接 |
| 没有它 | 单据**开不出来**（下拉是空的） | 只是少几张单 |

**类比**：主数据是「通讯录」，业务数据是「通话记录」。通讯录里没有这个人，你打不出去。

## 二、供应商怎么录入

### 2.1 两条路径

| 路径 | 适用 | 操作 |
| --- | --- | --- |
| **逐条建**（推荐） | 几十家 | Desk → 「供应商」列表 → 新建 → 填表 → 保存 |
| **批量导入** | 几百家 | Desk → 「数据导入」→ 选 `Supplier` → 下载模板 → 填好上传 |

**建议先走逐条建。** 理由见 2.3——供应商信息**不止一张表**，批量导入比想象中麻烦。

### 2.2 关键结构：供应商信息分散在 3 张表

这是**最容易踩的坑**。ERPNext 里一家供应商的信息不是存在一张表里：

```text
Supplier（供应商主体）
  ├─ 名称 / 类型 / 分组 / 税号 / 付款条件 …
  │
  ├─ Address（地址）  ← 独立 DocType，用「动态链接」挂到供应商
  │     地址行 / 城市 / 省份 / 国家 / 邮编
  │
  └─ Contact（联系人）← 独立 DocType，用「动态链接」挂到供应商
        姓名 / 手机 / 邮箱 / 职务
```

**后果**：

- 在 Desk 的表单上，地址和联系人区显示的是**悬浮按钮**（「新增地址」「新增联系人」），点开是**另一个表单**；
- **批量导入时，`Supplier` 的 CSV 里放不下地址和联系人**——它们是独立的 DocType，要单独导；
- 所以「一个 CSV 搞定全部供应商信息」**做不到**。

### 2.3 一个必须知道的字段陷阱

`Supplier` 表单上有 `mobile_no`（手机号）和 `email_id`（邮箱）两个字段，看起来能直接填。

**但它们是 `Read Only`（只读）。** 我核对了活库字段定义：

| fieldname | label | fieldtype |
| --- | --- | --- |
| `mobile_no` | Mobile No | **Read Only** |
| `email_id` | Email ID | **Read Only** |
| `supplier_primary_contact` | Primary Contact | Link → `Contact` |

**含义**：这两个字段的值**来自主联系人的 Contact 记录**，不能在供应商表单（或导入 CSV）里直接写。写了也不会生效。

**正确做法**：先建 `Contact`，再在供应商上把 `supplier_primary_contact` 指过去，手机和邮箱会自动显示出来。

> 这正是项目反复提醒的那类问题——**假设了不存在的结构**。字段名看着对，实际是只读投影。已实核对，不是推测。

### 2.4 建议的操作顺序

```text
第 1 步  建 Supplier 主体（名称 / 类型 / 分组 / 税号）
第 2 步  在供应商表单上点「新增地址」→ 建 Address
第 3 步  在供应商表单上点「新增联系人」→ 建 Contact
第 4 步  回供应商表单，确认「主联系人」已指向刚建的联系人
         → 此时手机 / 邮箱才会显示出来
```

地址和联系人**可以先不做**——采购下单只需要供应商主体。

## 三、有没有模板

### 3.1 Frappe 原生有模板功能

Desk → **数据导入**（Data Import）→ 选 DocType `Supplier` → 点**「下载模板」**，
系统会**按该 DocType 的全部字段**自动生成一个 CSV 表头。

活库核对：`Data Import` 表当前 **0 条**——即**还没人用过，没有现成模板**。

### 3.2 但原生模板不好用

`Supplier` 有 **44 个字段**（活库实测计数，已排除分节符）。原生模板会**把它们全列出来**，
其中绝大多数（`tax_withholding_*`、`warn_rfqs`、`prevent_pos`、`customer_numbers`…）
海滨现在**根本用不到**，看着会很乱。

### 3.3 建议用这个精简模板（已生成文件）

只保留实际会用到的 6 列。**模板文件已生成**：

```text
docs/inventory/供应商导入模板.csv
```

内容（含 1 行示例，导入前删除）：

```csv
供应商名称,供应商类型,供应商分组,国家,税号,备注
（示例）虚构XX有限公司,Company,原料药,China,91100000000000000X,示例行 导入前请删除
```

| 列名 | 含义 | 取值 |
| --- | --- | --- |
| `供应商名称` | 供应商名称 | 自由文本 |
| `供应商类型` | 供应商类型 | `Company` / `Individual` / `Partnership` |
| `供应商分组` | 供应商分组 | 见 §4.2 已重建的 8 个分组 |
| `国家` | 国家 | `China` |
| `税号` | 税号 | 统一社会信用代码 / 纳税人识别号 |
| `备注` | 备注 | 自由文本 |

**列名可以直接用中文**——Frappe 数据导入支持按「标签」匹配字段，不强制用字段名。

**注意**：这个模板**不含地址和联系人**（原因见 2.2），也不含手机 / 邮箱（原因见 2.3）。
**文件已带 UTF-8 BOM**，直接用 Excel 打开不会乱码。

> **该文件不会被提交到 Git**：`.gitignore` 第 25 行有全局 `*.csv` 规则，已实测确认被忽略。
> 填入真实供应商名单后也请只留在本地。

### 3.3.1 每一列到底要不要填（实测结论）

**结论：6 列里只有「供应商名称」是真正必须填的。** 其余空着不影响导入。

已核对 Frappe 导入器的实际行为（`importer.py` 的 `_parse_doc`）：**空单元格会被整个跳过**，
字段保留系统默认值，不会因为空值报错。

| 列 | 必填 | 空着会怎样 |
| --- | --- | --- |
| **供应商名称** | ✅ **必须** | 无默认值，空着必定失败。**且必须唯一**（见 3.3.2） |
| 供应商类型 | ➖ 可空 | 系统**自动补 `Company`**（字段默认值即为它） |
| 供应商分组 | ➖ 可空 | **保持空**——没有默认值。建议填，否则以后分组为空 |
| 国家 | ➖ 可空 | 系统**自动补 `China`**（全局默认已是 China） |
| 税号 | ➖ 可空 | 保持空。建议填，采购对账常用 |
| 备注 | ➖ 可空 | 保持空 |

**供应商类型的可选值**（只有 3 个，写错会报错）：

| 值 | 含义 |
| --- | --- |
| `Company` | 企业（**默认值，绝大多数供应商都是这个**） |
| `Individual` | 个人 |
| `Partnership` | 合伙企业 / 合伙人 |

> 以上为**内存实测**（`frappe.new_doc("Supplier", as_dict=True)` 观察默认值填充），未写库。

### 3.3.2 ⚠️ 一个必须告诉采购的坑：供应商名称必须唯一

活库核对 `tabDefaultValue` 的全局设置：

```text
supp_master_name = "Supplier Name"
```

**含义**：ERPNext 当前配置为**用「供应商名称」直接作为系统内部编号（单据 ID）**。

后果：

| | 说明 |
| --- | --- |
| **名称必须唯一** | 两家都叫「XX有限公司」会**报重复错误**，整行导入失败 |
| **没有 `SUP-` 编号** | 名称本身就是 ID |
| **改名成本高** | 以后改供应商名称等于改单据 ID，会牵连所有引用它的单据 |
| **名称即显示名** | 列表、下拉里显示的就是这一列 |

**给采购的提示**：供应商名称请写**工商全称**，并注意**同名不要重复**。
若同一集团有多个主体，名称里要能区分（例如带厂区 / 分公司后缀）。

> 如果更希望用 `SUP-2026-00001` 这类自动编号、名称只当普通字段，
> 需要改 `supp_master_name` 全局设置为「Naming Series」。**这属配置变更，需你决定**——
> 现在改成本低（供应商 0 条），以后有单据了再改会很痛。

### 3.4 联系人与地址的模板（可选，需要时再用）

因为联系人和地址是**独立 DocType**，要单独导。**同样只用得到几列**：

**联系人模板**（`docs/inventory/联系人导入模板.csv`）：

```csv
姓名,供应商,职务,手机号,邮箱
（示例）张XX,（示例）虚构XX有限公司,采购主管,13800000000,zhang@example.com
```

| 列名 | 含义 | 备注 |
| --- | --- | --- |
| `姓名` | 联系人 | 必填 |
| `供应商` | 关联到哪个供应商 | **填供应商名称**，需与已导入的供应商完全一致 |
| `职务` / `手机号` / `邮箱` | — | 可选 |

**地址模板**（`docs/inventory/地址导入模板.csv`）：

```csv
地址行1,城市,省份,国家,邮编,供应商
（示例）XX路 1 号,新乡市,河南省,China,453000,（示例）虚构XX有限公司
```

| 列名 | 含义 | 必需 |
| --- | --- | --- |
| `地址行1` | 地址 | 是 |
| `城市` | 城市 | 是 |
| `国家` | 国家 | 是（填 `China`） |
| `省份` / `邮编` | — | 否 |
| `供应商` | 关联到哪个供应商 | 是 |

**导入顺序**：先导供应商 → 再导联系人 → 再导地址。因为后两个要引用供应商名称。

## 四、需要哪些信息（字段清单）

### 4.1 必填——实际只有 1 个

ERPNext 标记为必填（`reqd=1`）的有两个字段：

| 字段 | 标签 | 取值 |
| --- | --- | --- |
| `supplier_name` | 供应商名称 | 自由文本 |
| `supplier_type` | 供应商类型 | `Company` / `Individual` / `Partnership` |

**但实测下来，真正必须填的只有 `supplier_name`。**

原因：`supplier_type` 带有**字段默认值 `Company`**，Frappe 导入器在建单时会自动套用，
空着也能通过校验。实测记录见 §3.3.1。

**所以：只填「供应商名称」一列，就能成功导入一条供应商。**

### 4.2 建议填——海滨实际会用到的

| 字段 | 标签 | 说明 |
| --- | --- | --- |
| `supplier_group` | 供应商分组 | **已于 2026-09-29 重建为海滨口径 8 个**：`原料药` / `辅料` / `包材` / `中间体` / `辅助用品` / `设备备品` / `服务类` / `其他`。原有 ERPNext 默认 7 个（`Distributor` / `Electrical` / `Hardware` / `Local` / `Pharmaceutical` / `Raw Material` / `Services`）已删除——它们**没有被任何真实数据引用**。分组与现有 `Item Group`（原料药 / 包材 / 中间体 / 辅助用品）对齐 |
| `country` | 国家 | 默认 `China` |
| `tax_id` | 税号 | 统一社会信用代码 |
| `supplier_details` | 备注 | 自由文本 |

**关于分组**：分组已按 Owner 决定重建为海滨口径，与现有 `Item Group` 对齐。
**若 8 个分组仍不够用，随时可加**——`Supplier Group` 可继续新增子节点，不影响已有数据。

### 4.3 通过 Contact 录入的（不在这张表）

| 信息 | 存在哪 | 说明 |
| --- | --- | --- |
| 联系人姓名 / 手机 / 邮箱 / 职务 | `Contact` | 见 2.3，**不能**在供应商表单直接填 |
| 地址行 / 城市 / 省 / 邮编 | `Address` | 见 2.2 |

### 4.4 以后再说——当前不需要

| 字段 | 为什么先不做 |
| --- | --- |
| `default_currency` / `default_price_list` / `payment_terms` | 属财务口径，**你已定「只做库存流水、不接发票」**，暂不需要 |
| `default_bank_account` | 同上，付款才用 |

| `is_transporter` / `is_internal_supplier` / `portal_users` | 特殊场景，用不到 |
| `naming_series` | 默认 `SUP-.YYYY.-` 已可用，不用动 |

## 六、物料代码规则（重要）

> **Owner 2026-09-29 定**：物料代码重复的，**按各自的物料代码使用**；
> **品名重复不代表真实货品是重复的**；**库存不合并**。

### 6.1 规则本身

**物料代码才是物料身份，品名不是。**

| 事实 | 含义 |
| --- | --- |
| 同一品名可以有多个代码 | 这是**正常**的，不是数据质量问题 |
| 每个代码独立记账 | **库存不合并**，也不应该合并 |
| 品名重复 ≠ 货品重复 | 可能是不同车间 / 不同规格 / 不同来源 |
| 系统只按代码找物料 | 品名是「显示用」的，不承担识别职责 |

**所以：不要提议「同名物料归一」「合并重复代码」。** 那会破坏真实业务语义。

**建档查重按「代码」查，不是按品名查。** 新品名不构成「重复」。

### 6.2 活库现状（2026-09-29 实测）

129 个 `Item` 里，**18 个品名有 2 个以上代码**，共 48 个代码（多出 30 个）：

| 品名 | 代码数 | 差异在哪 |
| --- | --- | --- |
| `亚胺培南` | **5** | 4 个是「六车间B线」，1 个车间字段为空 |
| `美罗培南混粉` | **5** | 3 个六车间B线，其余为空 |
| `美罗培南` | **4** | 全部「六车间B线」，其余字段相同 |
| `美罗培南粗品` | **4** | 车间字段为空 |
| `原料药泡沫箱` | 3 | 包材 |
| `无水碳酸钠` | 3 | 仅其中一个填了「储存条件：密封保存」 |
| `75%乙醇` | 2 | **原料药 / 单位 Kg** ‖ **辅助用品 / 单位 个**（明确是两种东西） |
| `无菌碳酸钠` | 2 | **深圳海滨五车间** ‖ **六车间B线**（车间不同） |
| `活性炭（供注射用）` | 2 | 字段完全相同 |
| 其余 9 个品名 | 各 2 | 亚胺培南收集粉 / 亚胺培南粗品 / 亚胺培南西司他丁钠混粉 / 无菌乳胶手套 / 板框滤膜 / 美罗培南晶种 / 美罗培南粗品（B）/ 药用低密度聚乙烯无菌袋 / 活性炭滤芯 |

**多数差异来自生产车间（`hbos_workshop`）**，但也有一批字段完全一致、**只能靠代码区分**。

### 6.3 系统是否受影响（已逐处核对）

**结论：不影响运行，且现有实现与该规则一致。**

| 位置 | 按什么找物料 | 是否受同名影响 |
| --- | --- | --- |
| 拍照识别入库（`api.py`） | **按代码**——注释明确写「物料代码是所有印刷信息里最可靠的一项」，品名以主数据为准 | 否 |
| 货位卡 / 待检证打印 | 印 **`{{ doc.item }}`（物料代码）**，不只印品名 | 否，打印件能区分 |
| `print_utils.py` 全部取值 | `get_value("Item", item, …)`——按代码 | 否 |
| 四张报表 | 查 `item_code` / `item_name` 并列输出 | 否，只是多几行 |
| 出库 / 入库单据 | **按批次选**（`Batch.name` 全局唯一，18 个批次无重名） | 否，选批次即确定物料 |
| **物料浏览页** | 人按**品名**挑 | **⚠️ 唯一风险点，见 6.4** |

### 6.4 唯一的风险点：人按品名挑物料

`InventoryItemView` 物料浏览页一行显示：

```text
亚胺培南          ← 品名（大字）
13000493          ← 物料代码（小字）
```

## 十一、清单改版后能不能更新（机制核对）

**问题**：合格供应商清单是**受控文件**（如 `JXH-21-QA-OTR-011`），会出第 12 版、13 版……
新版生效后，系统里的 `Supplier` 能不能跟着更新？

**答案：能更新，但要按改动的类型分开处理——其中「改名」这一种不能靠导入。**

### 11.1 机制核对（已读 Frappe 源码 + 活库验证）

`Data Import` 的导入类型**只有两种，且互斥**：
`Insert New Records`（新建）与 `Update Existing Records`（更新）。

匹配身份用的字段，活库实测：

```text
Supplier 导入时用于匹配的 ID 字段 -> {'label': 'ID', 'fieldname': 'name'}
Supplier meta.autoname -> 'naming_series:'
全局 supp_master_name   -> 'Supplier Name'
```

**含义**：因为全局配置用「供应商名称」当单据 ID（见 §3.3.2），
导入器实际是**按「供应商名称」匹配**的——名称就是主键。

两种模式的实际行为（源码位置：`frappe/core/doctype/data_import/importer.py`）：

| 模式 | 记录已存在 | 记录不存在 |
| --- | --- | --- |
| **新建**（`insert_record`） | **报重复错误**（`new_doc.insert()` 撞同名） | 正常插入 |
| **更新**（`update_record`） | 正常更新（只写有变化的字段） | **抛 `DoesNotExistError`**（活库已验证） |

**两条必须知道的运维事实**：

1. **不能一次搞定「新增 + 更新」的混合名单。** 新建模式遇到已存在会报错，
   更新模式遇到不存在也会报错。每次导入前要**先按名称把名单分成「已有」和「没有」两批**，分两次导。
2. 单行失败**不会中断整批**，导入结果会标记为 `Partial Success`，失败明细在导入日志里。

### 11.2 按改动类型分类处理

受控清单的版本差异，无非这四种。**只有前两种能靠标准导入解决**：

| 改动类型 | 举例（源文档第 10–12 版的真实变更） | 怎么处理 | 能否用标准导入 |
| --- | --- | --- | --- |
| **新增供应商** | 「M3 增加生产商：河北世星化工有限公司」 | 新建模式导入 | ✅ 可以 |
| **修改属性** | 分组、税号、备注变了 | 更新模式导入 | ✅ 可以 |
| **改名** | 「潍坊奥通药业有限公司**更名为**富祥（山东）新材料有限公司」 | **不能用导入**——见 11.3 | ❌ **不行** |
| **撤销资格** | 「连云港连特化工营业执照吊销，撤销其供应商资格」；「撤销 45 个物料及供应商」 | 置 `disabled = 1`（或 `on_hold = 1`）**停用，不删除** | ⚠️ 需单独操作 |

**关于撤销**：ERPNext 的惯例是**停用而非删除**。已核对 `Supplier` 有 `disabled` / `on_hold` /
`hold_type` / `release_date` 四个字段可用。删除会被链接拦住——清理虚构供应商时就
实测到过 `LinkExistsError`（「You can disable this Supplier instead of deleting it」）。

### 11.3 ⚠️ 改名是唯一的真麻烦

**导入器不会「改名」，它只会新建。** 如果第 13 版把某家改了名：

- 用**新建**模式导 → 系统里出现**两条**：旧名一条、新名一条，都是有效供应商
- 用**更新**模式导 → 新名不存在 → 该行**报错**

**正确的改法是 `rename_doc`**（Frappe 的改名接口），它会把所有引用旧名的单据一起改过去。
但这个**不能通过导入模板完成**，需要脚本调用。

**为什么这条对这个场景特别要紧**：源文档版本变更里，「更名」**出现频率很高**
（第 10 版 3 处、第 11 版 2 处）。也就是说，**每次改版多半都要处理改名**。

### 11.4 建议：等生效版一次导，别导两遍

既然改名要靠脚本、而每版几乎都有改名，**先导一版、过几天再导新版 = 改名成本付两次**。

而且还有两个额外的理由：

1. **这是 QA 受控文件。** 未生效版导进去，系统里就存在**「尚未生效」的合格供应商记录**，
   而这个系统里没有「文件生效日期」的概念——它只知道供应商是有效的。
   审计时说不清「这条是按哪一版录的」。
2. **16 号楼物料还没建档**，「物料 ↔ 合格供应商」的对应关系现在也建不了。
   而 ERPNext 里这个对应关系的原生落点是 `Item` 的**子表 `Item Supplier`**
   （字段只有 `supplier` + `supplier_part_no`，活库当前 **0 行**）。
   供应商单独导进去，也还只是半张清单。

**所以推荐的工作方式**：

```text
现在：你把未生效版发我 → 我只解析、核对、出差异清单，不导入
生效后：一次导入（新增 + 更新 + 改名 + 停用 一次处理完）
```

**如果将来确实需要「按版本增量更新」**，正确做法不是 Data Import，而是**写一个导入脚本**，
它能一次性处理四种改动：

```text
读新版清单
  ├─ 名称已存在且属性有变  → 更新字段
  ├─ 名称已存在但换了名    → frappe.rename_doc("Supplier", 旧名, 新名)  ← 关键
  ├─ 名称不存在            → 新建
  └─ 旧版有、新版没了      → disabled = 1（停用，不删）
```

**这属于「写代码」，需你明确授权后另起一轮做。**
