## 二、结论速览

1. **大体能做到，但「招标」是唯一的真缺口。** 除招标外，各环节对应的原生单据全部存在、模块全部已启用——不需要开发 ERPNext 没有的东西。**招标没有原生对应**，要不要自建见 3.2.1。
2. **真正缺的是主数据**，不是功能：`Customer` 0、`Supplier` 0。（`BOM` 0 与 `Quality Inspection Template` 0 **已不阻塞**——只到领料不上 BOM，请验暂不走模板。物料侧的采购 / 销售开关**已核，不阻塞**。）
3. **领用已经在做了。** 「库存单据」页已支持入库 / 领用出库 / 移库（见 `P4_Inventory前端完成度与未决问题.md` §3）。缺的是**上游的申请单**。
4. **请验是唯一有硬边界的一项**——放行权在 LIMS，仓库侧只能发起和看板，不能自己写（见第四节）。
5. **仓库工作台不该被扩成总开单台**（9-28 口径已定）。全套应按角色拆成开单台 + 仓库交接台；**建议合成一个开单台，不拆三个**（见第六节）。

| **招标** | **无原生对应** | — | ❌ **真缺口，见 3.2.1** |
| 签合同 | `Contract`（`party_type` = Supplier） | 采购开单台 | 单据在，**0 条**，**有保留**（见 3.2.2） |

**顺手核到一条有用的原生能力**：`Supplier Quotation Comparison` 报表**已存在**（标准报表，`ref_doctype = Supplier Quotation`）。即「多家报价摆在一起比价」是 ERPNext 原生就有的，不用自己写。

#### 3.2.1 招标：唯一的真缺口

只读核对 `Buying` 模块全部非子表 DocType，**只有 5 个**：

```text
Purchase Order
Request for Quotation
Supplier
Supplier Quotation
Supplier Scorecard（+ 4 张子表）
```

**没有任何招标 / 投标 / 评标 / 中标 相关 DocType。** 全库按 `Tender` / `Bid` / `Award` / `Procure` 模糊匹配也是空。

三个可选做法：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | **不做独立招标**，用 `RFQ` + `Supplier Quotation Comparison` 充当简化招标 | 零开发。多家询价 + 比价表本来就接近「比价」这件事，但缺「标书归档 / 开标记录 / 评标结论 / 中标通知」的痕迹 |
| B | 用 `Request for Quotation` 的 `message_for_supplier` + 附件承载标书，比价结论人工写在备注 | 零开发，但把非结构化信息塞进备注，后续查不了 |
| C | 自建 `HBOS 招标` DocType（招标单 / 投标 / 评标 / 中标） | **需新建 DocType 与界面**，是这套链路里唯一要写业务代码的地方 |

**建议先按 A 走**。理由是：真正的招标管理（标书、开标、评标委员会、中标通知书）是大型企业采购的形态；以你们的体量，「多家询价 → 比价表 → 定一家 → 下 PO」就是实际做法，`RFQ` + `Supplier Quotation Comparison` 已经覆盖。**若确实有对外招标、需要留下评标痕迹的场景，再走 C**——这是第七节的决策项。

#### 3.2.2 签合同：`Contract` 可用，但有保留

`Contract` DocType **存在**，字段核对如下：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `party_type` | `Customer` / `Supplier` / `Employee` | **支持供应商合同** |
| `party_name` | Dynamic Link | 指向具体供应商 |
| `start_date` / `end_date` | Date | 合同期 |
| `signee` | Data | 签署人 |
| `contract_terms` | Text Editor | 合同条款正文 |
| `document_type` | 可选 `Purchase Order` 等 | **可与采购订单挂钩** |
| `status` | Unsigned / Active / Inactive / Cancelled | 状态 |

**保留有两点**：

1. 它在 **`CRM` 模块**，不在 `Buying`。功能上能用，但「采购合同」出现在 CRM 模块下，导航与权限归属会有点怪。
2. 它是**轻量合同记录**，没有：合同编号规则、盖章件归档、审批流、履约跟踪。若你们的合同管理有这些要求，`Contract` 只能承载「登记」，不能承载「管理」。

#### 3.2.3 「待收货」看板是什么

**先说清楚：这是我发明的词，不是 ERPNext 的术语。** 它在第三节里作为**占位概念**出现，目的是把「采购收货 ↔ 仓库入库」的交接问题具象化。

它指的是这样一块界面：

```text
待收货（仓库工作台里的一块看板）
  列出：已下采购订单、货还没到（或只到一部分）的
  每行显示：供应商 / 物料 / 订单数量 / 已收数量 / 预计到货日期 / PO 号
  用途：货送到仓库门口时，仓管能「对着单收货」，而不是凭送货单猜是哪张订单
```

**数据来源**：ERPNext 原生就有——`Purchase Order` 的 `per_received < 100` 即「未收齐」，无需自建表。原生报表 `Purchase Order Analysis` 也覆盖这个口径。

**它到底要不要做，取决于第七节决策项 1**：

| 交接方式 | 需要「待收货」看板吗 |
| --- | --- |
| (a) 采购收货即入库——`Purchase Receipt` 由采购开，货到就是入库 | **不需要**。仓管看不到 PO，也不需要看 |
| (b) 采购下 PO → 货到仓库 → **仓管开入库单** | **需要**。否则仓管无法把实物对上订单，只能事后补录，对账时说不清 |

**我倾向 (b) + 做这块看板**，因为你们的实物流程是「送货到仓库」，收货动作发生在仓库，而不是采购员的电脑上。但这一条要你拍板——它直接决定仓管要不要碰 PO。

| 检验结论与放行 | LIMS 投影到 `Batch.hbos_release_status` | **LIMS** | ✅ 已实现（15 待检 / 3 已放行） |
| 出库门禁 | `release_gate.validate_release` | 仓库工作台 | ✅ 已实现 |

**硬边界（来自 `quality_projection.py`）**：

```python
def guard_batch_projection(doc, method=None):
    """Reject direct/user mutation of LIMS-owned release projection fields."""
    frappe.throw(_("质量放行字段由 LIMS 投影维护，不能在 Batch 中直接修改：{0}"))
```

写入口 `apply_release_projection` **刻意不加 `@frappe.whitelist()`**——只有 LIMS 侧内部能调。

**因此在仓库工作台上，请验只能是「发起」和「看板」，不能是「在此放行」。** 详见第四节。

## 四、请验与放行的界面归属（专项）

这一节单独写，因为它是**唯一一个「技术上能做、但架构上不让做」**的地方，容易被误解成缺口。

### 4.1 已定的架构事实

- 放行字段归 **LIMS** 所有，`Batch` 上的守卫会 throw。
- 仓库 App 的写入口**故意不暴露**。
- 仓库侧已有能力：`Batch` 按 `hbos_release_status = 待检` 查询可得（当前 **15 批**），字段齐全。
- `P4_Inventory剩余六项可行性与优先级评估.md` §2 已判定：「待检与放行」**不能做成表单，只能做成只读看板**。

### 4.2 真正的缺口只有一处：请验的「发起」

现状是从「到货入库」直接落到「等待 LIMS 放行」——**中间没有一张「仓库已提请检验」的单据**。

可选的三种做法：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 入库即自动置「待检」，不设独立请验单 | 零开发，但没有「已请验 / 未请验」的时间与责任人痕迹 |
| B | 仓库侧加「请验」动作，向 LIMS 投一条消息 / 记录 | 需 LIMS 侧接收约定，跨 App 契约 |
| C | 用原生 `Quality Inspection` 承载请验单 | 需引入 `Quality Inspection Template`（当前 0），且与 LIMS 的放行投影重叠，**有二次权威风险** |

**建议**：先按 A 跑通，把「谁提的请验、什么时候提的」作为**后续**议题。理由是当前 15 批待检都没有走请验单，说明业务上暂时没这个动作；贸然加 C 会造出第二套权威。

**关键判断**：

- ① 的仓库侧**几乎不用开发**，只多一个「显示别人给我下的单、我据此发货 / 收货」的交接看板（即 3.2.3 的「待收货」）。
- ②③④ 的工作量在界面，不在后端（单据都是原生的）。
- **合成还是分开——我的建议是合成一个。** 理由见 6.1。

### 6.1 建议：合成一个「业务开单台」，不拆三个

Owner 问的是「三个合成一个还是分开」。**建议合成一个**：

| 理由 | 说明 |
| --- | --- |
| 骨架重复 | 三个台子的登录、权限、导航、设计令牌、构建与部署**完全一样**。拆三个 = 三份骨架、三套构建、三处部署，维护量是 3 倍，功能量却只有 1 倍 |
| 角色很可能重合 | 以你们体量，采购与销售、甚至生产计划很可能同一个人兼。拆三个台子，这个人要来回切三次；一个台子按标签页切更顺 |
| 权限不靠「拆 App」管 | 权限边界用 **Frappe 角色 + 前端路由守卫**就够（采购员看不到销售标签页即可）。不需要用「三个独立 App」这种重手段来做权限隔离 |
| Portal 已提供切换 | Portal 的 App Switcher / App Center 已经存在。「业务开单台」作为一个 App 注册进去，比塞三个 App 更清爽 |
| 数据本就联动 | 生产要料触发采购、采购到货触发入库——这条链在一个台子里能直接串起来，拆开反而要在 App 之间跳 |

**反过来，什么情况该拆**：只有当**使用者完全不相干、且各自的功能量都很大**时才值得拆。目前看两条都不成立。

**建议的合成形态**：

```text
业务开单台（一个 App，三个标签）
  ├─ 生产   车间要料申请 → 状态：待发料 / 已发料
  ├─ 采购   采购申请 / 询价 / 比价 / 采购订单 / 收货
  └─ 销售   销售订单 / 发货单
```

### 6.2 但更前置的一个问题：这三个台子**现在真的需要自定义前端吗**

按 `CLAUDE.md` 与 `docs/frontend/FRONTEND_IMPLEMENTATION_GUIDE.md` 的规则：

> Frappe Desk 后台页面不要强行重做成独立前端。
> Desk 后台页面不得为了「好看」被整体重写成独立前端。

这条规则值得在动手前过一遍，因为两类用户的处境**完全不同**：

| | 仓管（已做前端） | 采购 / 销售 / 生产计划 |
| --- | --- | --- |
| 在哪用 | 库房现场，手机 / 平板 | 办公室，桌面 |
| 任务形态 | 扫码、拍照、几步搞定一张单 | 开单、比价、看报表、批量操作 |
| Desk 原生好不好用 | 表单太重，现场不适用 → **所以要前端** | 列表视图 / 筛选 / 批量 / 打印 / 比价报表**本来就强** |
| 自定义前端的收益 | 高 | **待验证** |

**所以我的建议是分两步**：

1. **第一步不写前端**：先用 ERPNext 原生 Desk 把采购 / 销售 / 生产的角色、工作台（Workspace）、权限配出来，让业务**先真实跑起来**。这一步零前端代码，还能顺便把主数据录进去。
2. **第二步只补真缺的**：跑一段时间后，看哪些页面业务确实嫌难用，**再针对那几页**做前端。多半会是「比价」「要料申请」这两类；`Purchase Order` 这种标准表单大概不需要重做。

**如果一步到位做前端**，风险是：花几个月做了三个台子，最后发现业务实际只用 Desk 就够——而这类「重做成漂亮前端」正是项目规则反复提醒要避免的。**这条建议与「合成一个」不冲突**：合成一个是「如果要做」的答案，6.2 是「现在该不该做」的答案。

### 6.3 前端实施流程提醒

按 `docs/frontend/FRONTEND_IMPLEMENTATION_GUIDE.md`，三个新开单台属**独立前端**，必须走：

```text
原型 / 视觉方案 → Owner 人工审查 → 前端复刻 → 功能接入
```

不能直接开写。仓库侧的新增看板同理。
