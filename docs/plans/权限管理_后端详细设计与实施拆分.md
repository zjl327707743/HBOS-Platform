| 模块候选 | 职责 | 与现有实现的关系 |
| --- | --- | --- |
| definitions / registry | 校验已安装 App 的动作、范围结构、绑定和可用状态 | 参考现有 Provider Hook 注册模式，独立于 Portal 传输能力枚举 |
| templates / grants / requests | 受控模板版本、完整授权、固定申请修订及审批 | 不把原生 Role / Role Profile 当成已带范围的授权 |
| policy / query | 按完整 Grant 判定动作，编译资源查询条件 | 共享语义；由 App 实现可信归属和查询适配 |

| 概念对象 | 最小字段组 | 关键约束 |
| --- | --- | --- |

| 授权申请 | 目标 User、模板版本、范围子行、期限、理由、申请修订、审批策略版本、固定内容摘要 | 每次审批绑定固定修订；修改目标、范围或期限重新审批 |
| 完整 Grant | subject_user、app_id、模板版本、完整范围、期限、状态、revision、批准申请引用、撤销事实 | User 必须存在；申请修订对应唯一生效结果；不把动作与范围分开存成可交叉组合的池 |
| 管理授权 / 委派 | 管理主体、可管理应用、可授模板 / 动作上限、目标人员边界、范围上限、期限、批准依据 | 与业务 Grant 分开；本人增权和越界审批拒绝；初始管理主体具名批准，不默认映射 Administrator |
| 授权变更事件 | actor、申请 / Grant 引用、事件、前后修订、原因、结果、时间、trace_id | 业务成功与授权变更一致留痕；不可由普通表单伪造审批或删除历史 |
| 主体授权修订 | subject_user、授权 revision、更新依据 | subject_user 唯一；用于请求一致性及撤权串行边界，不覆盖认证 security_version |

动作子行只能引用注册目录中的稳定 ID；范围子行由注册结构验证，保存类型、版本、维度及稳定对象引用。模板和 Grant 均不可放入通配符、自由 SQL、可执行表达式或任意处理函数路径。批准人与动作执行人来自服务端真实上下文。

建议索引围绕主体 / App / 有效状态、模板版本、批准申请修订及范围对象设计；截止时间参与请求时判定。申请修订的唯一生效约束必须由数据库和事务共同保证，不能只做“先查不存在再插入”。索引与约束为候选，不在本轮执行 DDL。

API 时间须明确时区，服务端规范化；数据库序列化遵循经验证的目标 Site 规则。有效期采用开始包含、结束不包含，不混用浏览器、本机和服务端时钟。未填写截止时间不能自动解释成已批准长期授权。

## 3. 接口与调用契约候选

名称是能力语义，不是本轮新增公开 API。现有 `ok / data / error.code / retryable / trace_id` 响应形状优先保持；新增错误必须做客户端兼容验证。无登录、业务拒绝和服务不可用分别处理，不能把权限拒绝当作会话失效。

| 能力 | 输入 / 输出要点 | 服务端控制 |
| --- | --- | --- |
| 读取可授目录与模板 | App 与版本 → 管理边界内目录 | 普通用户只能看到可申请的目录；不泄漏他人或未获准范围 |
| 读取本人授权 | 当前身份 → 本人有效与历史 Grant 摘要 | 主体由会话取得，不能用客户端 User 查询任意他人 |
| 提交 / 修改申请 | 目标、固定模板版本、范围、期限、理由、expected_revision | 代申请核对目标人员边界；服务端固定修订和内容摘要 |
| 审批申请 | request_ref、expected_revision、决定、理由 | 具名审批权限、自审批排除、范围和期限上限；不能自填批准人 |
| 生效已批准申请 | 已批准修订、幂等键、expected_revision | 原子生成一致 Grant；申请唯一生效；重试返回同一结果 |
| 撤销 Grant | grant_ref、expected_revision、原因 | 按管理边界更新撤销与主体修订，保留事件 |
| 管理范围内查询 / 审计 | 固定筛选与游标 → 获准的最小投影 | 先限制可管理人员及对象，再统计、分页；无任意全量 User 枚举 |

所有管理写命令须使用受 CSRF / 会话保护的 POST，GET 不产生授权变更。普通 DocType REST / Desk 编辑、客户端 Document.flags 或 ignore_permissions 参数不能直接批准、增权或改审计；内部受控调用上下文不得由请求字段伪造。原生 Administrator 特例与原始数据库写路径仍须单独纳入覆盖验收，不能只靠页面禁用。

内部判定契约包括 `compile_scope`、`require_record_action`、`allowed_actions` 与授权变更后的修订更新。它们接收可信身份上下文、后端固定的语义动作及资源引用；公开业务接口不能透传 User、范围或已允许动作列表充当许可。管理人员为他人查询也必须先验证其管理边界。

## 4. 查询、记录及业务事务判定

### 4.1 查询与记录共享语义

1. 验证当前身份、App / 动作可用状态、定义兼容性和资源类型。
2. 获取该主体、App、动作下已批准且当前有效的完整 Grant；模板停用、动作退役、过期或撤销均参与判定。
3. 对每条 Grant 将本条全部范围条件取 AND，完整 Grant 之间取 OR；不取“全部角色动作 × 全部范围”的组合。
4. 由 App 注册适配器解析真实关联并编译固定资源类型的参数化过滤；无匹配范围返回拒绝条件，不能返回无条件查询。
5. 在数据库分页、聚合前应用过滤，再提供获准字段及父 / 子记录最小投影；记录操作使用同一语义重验。
6. 执行业务状态、经办资格、职责分离及关联影响检查；允许范围不覆盖这些业务守卫。

新增动作属于兼容目录扩展时，旧模板仍只含原动作，不因整个 definition_revision 改变而无条件失效。动作语义扩大或范围结构不兼容必须使用新版本 / 明确迁移；未知结构拒绝相关授权，不回退为 ALL。已经禁用的动作不能因旧模板仍引用它而复活。

Frappe 的列表权限 Hook 不覆盖 get_all，get_all 本身也不应用用户权限；因此 Hook 只是接入点，相关查询仍须显式接入。[官方 Hooks](https://docs.frappe.io/framework/user/en/python-api/hooks)、[官方 Database API](https://docs.frappe.io/framework/user/en/api/database)。目标 Frappe v16 查询 API、共享回退和 Administrator 行为须以实际安装源码及隔离测试再次核对。

### 4.2 写入、撤权及审计

授权内核不自行 commit。LIMS 现有提交 / 复核等服务会调用 `_commit()`，检查必须放在其业务事务内，覆盖读归属、状态修改、关联同步直到最终提交，不能仅在 Portal 入口检查后释放授权上下文。

首批串行化候选：受管写入与同主体授权撤销使用同一主体授权修订行，按统一顺序获取事务锁并重读事实；归属变化再按固定顺序锁定受影响记录。写入先取得锁并提交时，撤权随后生效；撤权先提交时，后续写入拒绝。不承诺撤销已经提交的业务事实。锁 API、隔离级别、首次修订行创建和死锁重试仍须在目标 MariaDB / Frappe 版本验证，这不是已兑现的即时撤权保证。

普通授权审计与 Grant 修改在同一事务提交。拒绝时业务事务必须先回滚；LIMS 既有 `audit_violation` 是单连接上先回滚、再干净提交拒绝审计，不是第二条连接。后续授权拒绝采用经验证的同等语义，不能写拒绝日志时顺带提交业务半成品。审计写入失败不得把拒绝变为允许。

首批以数据库事实为准，不提前引入跨请求的“允许”缓存。以后加缓存时同时约束主体修订、模板 / 动作状态、范围归属和最近到期点，事实不可核验时不使用旧许可；可用动作列表始终仅供界面展示。后台任务执行与结果取回重验授权，不能因排队时允许或技术服务身份而忽略实际主体。

## 5. 首批源码接入点与边界

| 路径 | 当前源码事实 | 后续设计要求 |
| --- | --- | --- |
| Portal Registry / Dispatcher | 已有 Hook、Manifest、传输能力白名单与 App 入口检查 | 单独注册业务授权定义及绑定；不删除白名单改成任意调用 |
| Portal access.py | 部分 LIMS 语义映射集中维护 | 后续由 App 定义语义绑定；通用入口仍执行统一检查 |
| LIMS results.py | 调 get_result_ledger 后在 Python 过滤与分页 | 不能只在 `_matches` 或 DTO 上过滤权限；范围先下推到数据来源 |
| LIMS get_result_ledger | 角色检查后使用 get_all 聚合样品、结果及关联资料 | 从获准任务 / 结果集合出发，限制样品、修订与关联投影，分页和总数一致 |
| LIMS tasks / summary / search / ledger | 多个读取面及汇总 / 待办 | 同一范围语义覆盖记录、计数、联想和入口，不能只修 results |
| LIMS submit_result / review_result | 已有原生动作、业务状态、操作签署、SoD、关联同步和显式提交 | 同事务加入授权必要条件，保留现有业务守卫与审计 |
| 原生详情 / REST / Report / 共享 / File | 不经过 Portal Dispatcher 的入口 | 必须证明同域资源不可绕过；单个文档 Hook 拒绝不作为闭环证据 |
| User / 原生 Role / 账号交接 | 已有账号安全版本、角色移交与审计 | 授权修订独立；受管投影与 Grant 变更一致，不改写合法历史或新建身份 |

首批受管读取的实际切换必须覆盖该主体和资源的全部读取入口，也识别能返回相关数据的旧写入口。不能仅让 Portal 使用 enforced，却让原生 / 旧接口继续绕过同一边界；不能证明闭环时保持 shadow，不以页面局部隔离标 PASS。

任务分配、开始检验、结果批准、代提交、带稳定性关联记录、跨组父单完整导出及 COA / QA / QP / 留样 / 配置等后续域，按已有映射记录逐项明确影响后扩充。它们不在首批新模板中自动授予，本轮也不关闭或删除其现有功能。
