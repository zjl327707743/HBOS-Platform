## 2. 接入契约的职责

| 组件 | 负责的内容 | 扩展方式 |
| --- | --- | --- |
| Frappe 身份与组织主数据 | 登录身份、账号状态、人员和组织关联 | 复用既有对象及账号生命周期 |
| App 权限定义 | 已实现动作、资源类型、范围适配、业务约束 | 由已安装 App 的受信任后端声明 |
| 角色模板 | 可授予的动作组合和适用范围类型 | 经批准创建新模板版本 |
| 人员授权 | User、应用、角色版本、范围条件、期限与批准依据 | 通过同一后端服务申请、审批和撤销 |
| 统一判定服务 | 授权匹配、有效期、版本及范围条件计算 | 稳定的通用契约，不集中枚举未来业务模块 |
| App 业务服务 | 记录归属、状态、签署、职责分离及关联影响 | 在业务操作中调用统一判定，保留领域守卫 |
| Portal / Desk | 展示及发起操作 | 根据后端结果展示，提交时重新检查 |

权限定义描述系统能够做什么，人员授权记录谁获准做什么，两者职责不同。App 不能另维护一份可独立编辑的人员授权真相。授权注册不能依赖 Portal 页面已经存在；后台接口和任务同样需要授权边界。

## 3. App 权限定义

| 字段 | 含义与要求 |
| --- | --- |
| app_id | 稳定、唯一的应用标识，与已安装 App 的注册来源绑定 |
| contract_version | 注册契约版本；不支持的版本拒绝接入对应应用 |
| definition_revision | 本次动作及范围定义修订，用于兼容检查与审计 |
| resource_types | 本 App 的资源类型，以及服务器端可信归属解析器 |
| actions | 动作 ID、中文名称、资源类型、支持的范围类型及风险类别 |
| scope_types | 范围 ID、结构版本、参数约束、查询过滤和记录匹配适配 |
| bindings | Provider 能力、业务 API、原生操作与语义动作的明确映射 |
| availability | 已实现、可用和启用状态；实现及验收证据不能由普通配置操作伪造 |
| native_projection | 受管原生角色、单据权限及页面映射；不代表可以忽略范围检查 |

动作 ID 使用应用命名空间，例如 lims.results.review。中文标签可以调整，稳定 ID 不因显示名称改变而重建。不同 App 不得覆盖彼此的命名空间；重复 ID、未知动作、未注册范围类型、绑定遗漏及版本不兼容应拒绝对应能力，不向其他 App 扩散故障。

声明可以随 App 发布同步为只读目录，目录不提供编辑后端处理函数或任意查询脚本的入口。角色配置只能选择 App 已声明且允许授予的动作。新增功能仍须开发、登记、接入后端检查和验收，不能仅增加目录名称就获得可执行功能。

现有 summary / tasks / results 等 Provider 协议可继续保留。业务动作目录另行声明，避免每增加业务动作都扩展中央枚举；也不能通过删除现有方法白名单，让客户端任意指定 Python 方法。Portal 的接口契约版本和权限定义版本分别治理。

## 4. 角色模板及版本

| 字段 | 含义与要求 |
| --- | --- |
| role_template_id / app_id | 稳定模板 ID 与所属应用 |
| version | 角色模板版本，已批准版本的内容不可原地改写 |
| title | 面向人员管理的中文名称 |
| action_ids | 本版本明确包含的动作，不能用通配符包含未来动作 |
| scope_constraints | 可用范围类型及必要条件，不替代 App 业务约束 |
| approval / status | 申请、批准、停用状态及依据 |

App 可以提供初始模板，受权管理员可以在已注册动作内调整组合。模板增权须形成新版本及影响人员清单；既有授权引用旧版本，不能因同名角色增加动作而自动增权。授权升级本身是一次审批和审计操作，不能修改旧版本冒充历史已批准内容。

禁止使用“本模块全部功能”或 lims.* 作为包含未来动作的动态授权。对于应用级只读等模板，也必须展开为本版本已登记动作。必要时的应急运维能力单独管理，不能推导为质量签署权。

权限退役须在服务端明确禁用，对引用它的授权记录保留历史。角色版本固定不能阻止安全撤权；已经停用的动作不因旧版本仍包含它而继续放行。权限 ID 不复用于不同含义，重命名兼容必须证明语义没有扩大。

跨 App 岗位模板只能生成多条完整的人员授权，不能把不同应用的角色及范围合并成可任意组合的列表。2026-10-08 补充[岗位任职关系契约](权限管理_岗位任职与角色关联后端契约.md)：页面角色通过固定版本引用各 App 模板，具体岗位关联逐组件范围，人员任职按固定批准内容派生完整 Grant；新增版本不自动升级既有人员。

## 5. 人员授权及范围结构

| 字段 | 含义与要求 |
| --- | --- |
| grant_id / revision | 稳定授权 ID 与修订，支持并发及审计关联 |
| subject_user | 引用 Frappe User，不另建 Portal 人员身份 |
| app_id | 指向已注册应用 |
| role_template_id / role_version | 指向确定的已批准角色版本 |
| scope_terms | 经 App 校验的范围条件，绑定在本条授权内 |
| valid_from / valid_until | 服务器时间判断；到期边界采用开始包含、结束不包含 |
| status | 待审批、生效、撤销；过期按时间计算，定时任务只负责治理和记录 |
| requester / approver / basis | 申请人、批准人、授权依据和变更原因 |
| delegation_ref | 如为委派授权，关联批准的委派边界及期限 |
| source_refs | 岗位派生授权补充任职修订、关联版本及失效 generation、角色组件和固定批准依据；请求时校验当前来源有效性 |

范围结构至少表达类型、结构版本、维度、稳定对象 ID 及明确的是否包含下级选项。相同维度中明确列出的对象通常表示任选其一，不同维度同时满足；若 App 有其他关系语义，必须在范围契约中声明并验证，不能由客户端提供任意表达式。

完整授权之间取并集：先检查某条授权是否含当前动作，再应用这条授权的全部范围条件。不能把所有授权的动作并成一份、范围并成另一份，再计算任意组合。空范围、无法解析的对象、缺失归属或不支持的结构版本均不能回退为全量访问。全公司等范围须显式声明和批准。

员工业务按有效 Employee 关联判断身份；本人考勤不能使用记录 owner 代替员工归属。关联缺失或有歧义时拒绝依赖该关联的业务，保留资料维护及待关联体验。技术账号、外部协作账号和服务账号需明确身份类别及批准用途，不能靠“没有被排除”自动认定为内部员工。

委派权是独立授权，拥有业务动作不等于可以授权他人。被委派管理员只能授予批准的动作、对象范围、目标人员和期限；不能给自己提权，不能通过更宽模板版本、包含下级或延长有效期突破边界。审批状态及受管字段不得通过普通 DocType 写入绕过。

## 6. 后端判定与查询契约

建议先固定以下能力语义；函数名和文件位置在 IAM-0 对齐后再确定：

| 能力 | 输入及输出 | 服务端要求 |
| --- | --- | --- |
| 注册目录 | 已安装 App 定义 → 经校验的目录 | 仅信任后端注册来源，检查唯一性与版本 |
| 查询范围编译 | 当前身份、固定动作、资源类型 → 查询条件 | 在数据库分页、聚合前过滤；无有效范围时返回拒绝条件 |
| 记录动作判定 | 当前身份、固定动作、资源引用 → 允许或拒绝 | 从真实记录解析归属，保留全部业务约束 |
| 记录可用动作 | 获准查看的记录 → 当前 allowed_actions | 供界面展示，不成为之后提交的授权凭据 |
| 权限解释 | 授权范围内的人员与记录 → 授权依据 | 普通用户查本人，管理员受委派范围限制，不泄露无权记录 |
| 授权变更 | 申请、审批、升级、撤销 → 新修订及审计 | 校验委派边界、并发版本及审批状态 |

调用方身份来自 Frappe 会话或受控服务身份。动作与处理函数的绑定来自后端；客户端提供的 User、scope、allowed_actions 或版本字段不能决定权限。每次操作都判断功能是否可用、身份是否有效、授权及角色版本是否有效、范围是否匹配、业务条件是否满足。

列表、详情、搜索、统计、下拉联想、打印、导出、附件和后台任务使用一致的动作及范围依据。不能先取得全量结果再在浏览器过滤，也不能在全量分页后才删除无权项。直接 API、原生单据及子表读取须一并验证。

原生 Role / DocPerm / User Permission 继续提供通用保护；可表达的受管部分作为授权的受控投影。独立编辑、直接角色赋予及模板展开导致的漂移必须可检测，不能成为受管业务的备用放行依据。353 条 Custom DocPerm 等 Site 配置须逐项纳入迁移核对，不能批量覆盖。

get_all、原始 SQL、ignore_permissions 及直接数据库写入不会因建立目录而自动安全，相关服务必须显式执行检查。权限 Hook 只是接入点：第一步与第二步已核对的 Frappe 16.26.3 共享回退说明，不能只靠一个返回拒绝的文档 Hook 就宣布范围隔离完成。受管业务的原生共享不得扩大范围，既有共享与新增共享路径均需检查。

父单包含多个范围的任务或子记录时，受控投影只返回明确获准的字段和子记录。原生完整详情、报表及附件如果尚不能保证隔离，不能因其中一个子项可见就返回整份内容。内建 Administrator 的原生权限特例须作为应急边界记录；应用内质量守卫继续执行，不用它代替普通角色验收。

## 7. 入口、缓存与关联操作

Portal、Desk、人员授权管理分别授权。当前有 Desk Access 的角色会影响普通用户的 System User 类型；迁移不批量清空角色或修改全局 Desk Access。服务端入口规则及专用入口接口须检查资格，共用业务 API 按动作和资源判断。无 Desk Access 角色映射需隔离验收后确定，不能只改前端按钮。

Bootstrap 的应用、能力及范围摘要用于展示。完整角色与范围关系留在后端；能力并集不能与范围并集相乘。若增加前端摘要字段，按契约版本兼容发布，记录级操作仍重新判定。

授权、模板、动作启停和相关归属改变后，更新可核验的权限修订并失效相关缓存。到期由请求时检查，缓存不得超过下一到期点，缓存或版本检查失败不能继续使用旧许可。Desk 资格变化还须验证已有会话中的用户类型信息。后台任务执行、导出结果取回、知识引用和缓存读取时再次检查。

敏感写操作在业务事务内复核权限、归属和状态，并与授权撤销形成明确的串行边界；写前检查不能替代对并发撤权的验证。记录归属从 A 改到 B、库存调拨等操作须检查所有受影响端点。批准结果联动稳定性记录等操作须检查授权影响图，不能只检查主记录。

## 8. LIMS 首批试点规格

首批围绕普通检验任务和结果，用隔离测试人员及 A / B 检验组验证完整授权。以下是拟定语义动作，不表示新增接口已实现或开放；现有 Portal 同名能力仅说明已有表达，不表示新范围授权已经生效。

| 拟定动作 | 现有入口或服务 | 范围及必须保留的约束 |
| --- | --- | --- |
| lims.tasks.read | tasks Provider | 任务 lab_department；仅查询获准任务 |
| lims.tasks.assign | assign_task | 当前和目标检验组、任务归属及已有状态规则；目标人员关系需业务确认 |
| lims.tasks.execute | start_task | 任务检验组及已有经办人 / 管理人员规则 |
| lims.results.read | results / ledger 投影 | result.task → task.lab_department；隔离列表、统计和详情 |
| lims.results.submit | submit_result | 同上；保留检验人及受控代填条件 |
| lims.results.review | review_result | 同上；已提交且复核人不等于检验人 |
| lims.results.approve | approve_result | 同上；已复核、非 OOS 候选且批准人区别于检验人和复核人 |

HBOS Lab Department 是检验组主数据，不能用 Employee.department 或组长身份直接替代授权。当前该对象没有 Company 关联字段，试点不能假称已有公司维度隔离。Test Result 的检验组由真实 task 关联解析，不信任请求携带的组编号。

拟定模板可包含“检验员 v1”“结果复核人 v1”“结果批准人 v1”，分别列出动作。它们不自动替换、重命名或削减现有 LIMS Analyst / Reviewer / Manager 等原生 Role；兼容映射必须逐项验证。既有 Reviewer 可执行批准的事实不等于新“复核人”模板自动包含批准动作。QA、QP、稳定性、留样、配置管理等目录随后由对应服务声明，本轮不推定其完整动作。

generate_tasks 要选择检验组。未分组样品的登记 / 接收授权、跨组样品共享字段和任务分配资格需先明确，不能由部门匹配临时兜底。涉及稳定性、留样或跨记录自动同步的写动作，在关联影响未验证前不得进入首批 enforced。

首批混合任职样例：同一 User 获得“结果复核人 v1 + A 组”和“检验员 v1 + B 组”。可复核 A 组他人结果，可提交 B 组符合经办规则的结果；不能复核 B 组，也不能复核本人 A 组结果。

## 9. 新模块与功能的演进流程

1. App 实现后端功能、可信归属解析和业务守卫，声明动作、范围类型及版本；没有 Portal 页面也需要登记。
2. 平台校验并呈现目录。尚未实现、未启用或绑定不完整的动作不可实际放行；新增动作默认没有普通人员授权。
3. 如需要，建立新角色模板版本，展示增减动作、范围及受影响授权；不能自动更新所有同名角色。
4. 对批准的人员执行显式授权升级，并处理范围结构的兼容或受控迁移。
5. 完成普通身份的正向、负向、直接接口、原生入口和撤权验收，再启用对应能力。
6. 动作退役、App 停用或版本回退时保留授权与审计历史。不支持的定义拒绝相关能力；已撤销和过期的授权不得复活。

例：增加 lims.results.bulk_export 时，新动作独立登记、实现并验收；检验员 v1 不自动获得它。只有新模板版本包含该动作且人员升级获批后，才能在批准范围导出。该动作在本文仅为未来示例，不表示已经实现批量导出。

## 10. 迁移方式与实施边界

| 阶段 | 行为 | 放行条件 |
| --- | --- | --- |
| legacy | 现有已登记基线仍走原检查 | 仅用于迁移中的明确既有动作，新增及未知动作不得借此放行 |
| shadow | 比较新旧判定，仍保留原业务行为 | 明确记录差异及预期收窄；不是范围隔离验收 PASS |
| enforced | 统一授权成为受管动作的必要条件，并保留业务守卫 | 目标 Site、人员、原生路径及关联影响已验证，Owner 批准切换 |

迁移按应用、动作和明确资源类型逐步启用。先在隔离环境核对合法旧权限的来源，将范围不明的权限列为待治理，不自动转成全公司权限。不得把任意失败降级成 legacy；回退不恢复已撤销的授权。首次启用前校验原生 Role / Role Profile / User Permission / Custom DocPerm / DocShare 的实际差异。

本轮只交付设计规格。后续实施先对齐 IAM-0 和目标 Site，再选择首批资源与字段，形成逐项实施差异。Portal 管理中心及员工自助页面属于后续步骤，仍遵守原型设计和 Owner 审查要求。

| A12 | 归属从 A 改 B、分配任务或关联稳定性同步 | 检查全部受影响范围；影响图未覆盖则不切换该写动作 |
| A13 | 操作和撤权并发、提交重试 | 授权与业务事务边界可证明；不因重试绕过撤权或重复签署 |
| A14 | 代码回退、App 停用再启用、动作退役 | 不复活撤销 / 过期授权，不复用权限 ID 扩大语义 |
| A15 | 定义与查询编译对同一资源分别判定 | 范围语义一致，分页和聚合前已过滤 |
| A16 | 修改受管原生 Role / 模板投影 | 可发现漂移，不能因此获得额外受管业务权限 |
