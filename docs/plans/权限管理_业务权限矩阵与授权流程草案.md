## 1. 统一管理的业务对象

人员仍引用现有 Frappe User；员工和组织资格复用 Employee / Department。一次授权完整包含“人员 + 应用 + 已批准模板版本 + 数据范围 + 生效期限 + 批准依据”。每条授权独立匹配动作和范围，不把一个检验组的复核资格与另一个检验组的检验资格拼接。

下表是职责分工候选，中文称呼不是本轮新增的 Frappe Role，具名人员均待确认。

| 职责 | 可以负责的事 | 不自动取得的权限 |
| --- | --- | --- |
| 普通成员 | 申请本人岗位权限、查看本人授权及申请状态 | 审批或直接修改自己的授权 |
| 检验组业务负责人 | 确认人员业务资格、目标组及岗位需求，提出变更或撤权 | 仅因 head_user 字段成为授权管理员或质量批准人 |
| 授权审批人 | 在其已批准管理边界内批准、拒绝或退回具体申请 | 越范围审批、给自己提权、以审批身份执行检验签署 |
| 权限管理员 | 受控登记模板、核对审批版本、执行与批准内容一致的授权和撤权 | 选择更宽模板、扩大范围、延长期限或凭 System Manager 直接增权 |
| 技术运维 | 维护已批准的运行环境和故障处置 | 自动取得检验、复核或批准业务资格 |
| 业务审查人 | 按另行批准的审计范围复查申请、授权和变更历史 | 因可以查看审计就能修改结果或人员授权 |

开发期由谁实际审批见 Q1。即使审批与执行岗位由同一人员兼任，后端也必须分别验证其管理边界；不能通过普通 User / Role / Grant 单据写入绕过受控流程。普通管理人员本人受益的增权申请应由另一名有权人员审批；若没有独立审批人，记录为治理缺口，不自动生效。

实施顺序沿用“登记与模板版本 → 读取隔离 → 提交 / 复核及撤权”。任务分配、开始检验、结果批准及其他业务域在归属、影响和验收补齐后扩充。表中后续动作仍保留其当前业务事实，不表示现有功能已被关闭。

## 5. 授权申请、审批与撤权

拟定流程：**申请 → 资格及范围核对 → 审批 → 按批准版本生效 → 到期或撤销留痕**。批准流程见 Q1，以下规则不因审批岗位选择改变。

1. 申请填写既有 User、具体 App、模板及固定版本、稳定范围对象、起止时间和业务理由；本人申请或有权人员代申请都留真实发起人。
2. 核对人员资格、组归属、模板可授予状态及批准人的委派边界。未实现的动作、空范围、未知版本或超界内容不能批准为生效授权。
3. 审批对象是上述内容的固定修订。退回后修改范围、期限或模板必须重新提交，不能在已批准申请上悄悄换版本。
4. 受控执行只创建与批准内容一致的完整 Grant。业务岗位、审批权和执行管理权分别验证；生效结果可回溯到批准依据。
5. 临时授权必须填写明确截止时间；长期授权也须明确批准，不以留空冒充已批准长期。延期、跨组和模板增权按新申请 / 修订审批；不能自动扩大旧授权。
6. 停用、离职、调岗、资格失效、授权到期或违规撤权分别记录来源与原因。网络失败或未确认的同步缺失不能批量当离职；但不能以验证失败扩大权限。
7. 撤销由有权主体按边界执行并留历史，后续受保护请求按当前事实判定；已完成业务记录不改写，不承诺回滚已完成在途操作。任务执行及结果取回同样重验。

状态候选：申请为草稿 / 待审批 / 退回 / 拒绝 / 已批准 / 已取消；Grant 的有效性同时检查批准、生效时间、截止时间及撤销事实。“已批准”不等于尚未到开始时间的授权已经可用，定时任务也不能成为到期判断的唯一依据。这些状态是流程草案，不是新增 Select 枚举或现有对象状态改动。

模板增加功能形成新版本，人员只有明确升级获批后才取得新增动作。跨 App 岗位将生成各 App 内的完整授权，不能拼成跨应用的角色范围池。
